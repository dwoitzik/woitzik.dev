CNPG needs WAL archiving to object storage. Gitea needs artifact storage. The options: AWS S3 (recurring cost), Backblaze B2 (egress fees), or MinIO (self-hosted, no recurring cost). MinIO on k3s runs as a single pod with a local PersistentVolume and exposes an S3 API on port 9000. It isn't distributed, redundant, or production-grade. For a homelab, that's an acceptable trade.

Its role is deliberately different from [Garage](/blog/velero-garage-k3s-backup/), the other S3-compatible store in this cluster: Garage backs Velero, and MinIO backs everything else. Splitting them means a Garage incident (like [the SQLite corruption that hit its metadata volume](/blog/nfs-vs-local-path-sqlite-trap/)) doesn't also take out CNPG's WAL archiving.

**[View the complete homelab infrastructure source on GitHub](https://github.com/dwoitzik/homelab-infrastructure)**

## Why MinIO

AWS S3 costs money. Backblaze B2 is cheap for storage but charges for egress. In a homelab where backups go to local disk and the only S3 consumers besides Velero are CNPG and Gitea, MinIO removes the external dependency entirely.

The downside: MinIO on a single node with a single drive has no redundancy. If the PVC is lost (disk failure, Proxmox host crash), all S3 data is gone.

## Deployment

MinIO runs as a StatefulSet with a single PersistentVolume:

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: minio
  namespace: minio
spec:
  replicas: 1
  serviceName: minio
  selector:
    matchLabels:
      app: minio
  template:
    metadata:
      labels:
        app: minio
    spec:
      containers:
        - name: minio
          image: minio/minio
          command: ["minio", "server", "/data"]
          ports:
            - containerPort: 9000
            - containerPort: 9001
          env:
            - name: MINIO_ROOT_USER
              valueFrom:
                secretKeyRef:
                  name: minio-credentials
                  key: root-user
            - name: MINIO_ROOT_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: minio-credentials
                  key: root-password
          volumeMounts:
            - name: data
              mountPath: /data
  volumeClaimTemplates:
    - metadata:
        name: data
      spec:
        accessModes: ["ReadWriteOnce"]
        resources:
          requests:
            storage: 100Gi
```

The 100Gi PVC is backed by local-path storage, with no Longhorn replication underneath. A single-drive MinIO deployment has no erasure coding either, so nothing in this stack provides durability for the data on that volume.

## The Console

MinIO's web console runs on port 9001. Access it via Traefik:

```yaml
apiVersion: traefik.io/v1alpha1
kind: IngressRoute
metadata:
  name: minio-console
  namespace: minio
spec:
  entryPoints:
    - websecure
  routes:
    - match: Host(`minio.lab.woitzik.dev`)
      kind: Rule
      services:
        - name: minio
          port: 9001
  tls:
    secretName: lab-wildcard-tls
```

Since mid-2025 the community edition console is reduced to an object browser. Bucket, user, and policy management happen through the `mc` CLI.

## Bucket Configuration

Two buckets for two consumers:

```bash
# CNPG WAL archives
mc mb minio/cnpg-wal

# Gitea artifacts
mc mb minio/gitea-artifacts
```

Each consumer gets its own access key:

```bash
# Create CNPG user with read/write on cnpg-wal only
mc admin user add minio cnpg-user cnpg-password
mc admin policy attach minio readwrite cnpg-wal --user cnpg-user
```

MinIO's built-in `readwrite` policy covers every bucket, though. Restricting a user to `cnpg-wal` alone takes a custom policy scoped to `arn:aws:s3:::cnpg-wal` and `arn:aws:s3:::cnpg-wal/*`, created with `mc admin policy create` and attached with `mc admin policy attach minio <policy> --user cnpg-user`.

## Integrating With CNPG

CNPG's Barman backup target points at MinIO for continuous WAL archiving:

```yaml
apiVersion: postgresql.cnpg.io/v1
kind: Cluster
metadata:
  name: nextcloud-db
  namespace: nextcloud
spec:
  backup:
    barmanObjectStore:
      destinationPath: "s3://cnpg-wal/nextcloud-db"
      endpointURL: "http://minio.minio.svc:9000"
      s3Credentials:
        accessKeyId:
          name: minio-credentials
          key: ACCESS_KEY_ID
        secretAccessKey:
          name: minio-credentials
          key: SECRET_ACCESS_KEY
```

CNPG archives each WAL segment to MinIO as it completes, not on a schedule. If the database PVC is lost, CNPG can restore from the last base backup and replay every archived WAL segment. See [the CNPG write-up](/blog/cnpg-postgresql-operator-k3s/) for the full failover story; this MinIO bucket is the backup half of that setup.

## The Storage Reality

MinIO on a single node with local-path storage is not HA. If the disk dies, the data is gone.

The other cost is space. On a [BMAX Mini PC\*](/go/4bv3yF1) with a 512GB NVMe, a 100Gi PVC is 20% of the disk. That's acceptable for a homelab where the alternative is paying for S3.

## Monitoring

MinIO exposes Prometheus metrics:

```
minio_cluster_disk_free_bytes 42949672960
minio_cluster_disk_total_bytes 107374182400
minio_s3_requests_total{bucket="cnpg-wal"} 1250
```

Alert when `disk_free_bytes` drops below 10GB: something is filling a bucket, usually WAL archives that aren't being cleaned up after a base backup.
