Rebuilding [Vault with External Secrets Operator](/blog/external-secrets-operator-vault-kubernetes/) from scratch is one thing when you're setting it up for the first time. It's a different problem when Vault held real secrets for 25+ services and the cluster that created it is gone. A fresh Vault install gives you a fresh, empty secret store, which is the wrong outcome when the goal is disaster recovery, not a clean slate.

**[View the complete homelab infrastructure source on GitHub](https://github.com/dwoitzik/homelab-infrastructure)**

## The Circular Dependency

The old Vault's unseal keys lived in a Kubernetes Secret in the old cluster. That's a reasonable choice for a homelab, and the [polling-sidecar auto-unseal pattern](/blog/vault-auto-unseal-polling-sidecar/) I use depends on that Secret existing. But reading a Kubernetes Secret needs a running API server, and a running API server for the *old* cluster needs its datastore. Booting the old cluster's full control plane, the thing that had just gone through a disaster, is the kind of unnecessary risk a careful recovery avoids.

The chain: **old k3s datastore → unseal keys → new Vault.** Breaking it meant getting exactly one object out of the old datastore without standing up everything that depended on it.

## Breaking the Cycle With a Disposable, Isolated Node

The datastore itself was a single SQLite file, already extracted during the read-only Tier-1 verification pass and dated to before any later incident touched the VM it came from. Reading it doesn't need a full multi-node cluster. It needs one k3s server process willing to open it and answer API requests.

```bash
# On a throwaway VM, with no role in the real cluster:
# 1. Copy the extracted (clean, pre-incident) datastore and the original join token
scp pve:/mnt/extracted/vm-k3s-server/k3s-db/state.db  ./state.db
scp pve:/mnt/extracted/vm-k3s-server/token             ./token

# 2. Install k3s pointed at that datastore, fully isolated
INSTALL_K3S_EXEC="server --disable-agent --bind-address=127.0.0.1 \
  --disable=coredns,servicelb,traefik,metrics-server,local-storage" \
  ./install.sh
```

One snag: the fresh install's auto-generated TLS and credential files were newer than the copied datastore, and k3s refused to start rather than risk a cluster outage. "Files newer than datastore" is the kind of self-check you want a system to have, even when it's inconvenient. Deleting the fresh install's generated cert and credential files, so k3s recreated them from the copied datastore, fixed it.

With that single-node, network-isolated instance running, the target object came out with one command:

```bash
kubectl get secret vault-unseal-keys -n vault -o yaml > unseal-keys.yaml
```

Never echoed, never printed to a terminal, redirected straight to a file. A small script stripped the stale metadata (`resourceVersion`, `uid`, `managedFields`), matching by field *name* only so the key material was never read, and the result was applied into the new cluster's `vault` namespace. The throwaway VM was discarded afterward. It never touched anything except a copy of already-extracted data.

## Verifying It's Actually the Old Vault, Not a Coincidence

The Vault Helm chart deploys with a fresh, empty PVC; Helm has no way to know old data belongs there. Getting the real raft data into that PVC meant scaling Vault to zero, moving the empty PVC contents aside (kept, not deleted, in case of rollback), and copying in the preserved raft directory from the extraction.

Scaling back to one replica and checking `vault status` is the proof, not a subjective "looks right" (Version and Build Date lines trimmed):

```
Key                Value
---                -----
Seal Type          shamir
Initialized        true
Sealed             true
Total Shares       3
Threshold          2
Unseal Progress    0/2
Unseal Nonce       n/a
Storage Type       raft
HA Enabled         true
```

A Vault on an empty PVC reports `Initialized: false`. This one reported `true`, with the same 3-share, threshold-2 seal configuration as the old cluster, which can only come from the transplanted raft data. A sealed Vault doesn't show its Cluster ID or Raft index; those appear once it is unsealed. Applying the transplanted unseal-keys Secret and letting the [polling sidecar](/blog/vault-auto-unseal-polling-sidecar/) do its normal job unsealed it on the first attempt, and only then did `vault status` show the Cluster ID matching the pre-incident cluster. That's the same Vault continuing from where its data left off, not just "a Vault came up."

## The Root Token Was a Different Problem

Unlike the unseal keys, the original root token had never been written to a Kubernetes Secret. That's by design: a root token is meant for initial setup and should then be revoked or stored outside the cluster. Correct practice, and it also meant there was no copy to recover.

Vault has a documented procedure for this: `generate-root`. With a quorum of unseal key shares available (2 of the 3 restored above meet the threshold), Vault mints a new root token without needing the old one:

```bash
vault operator generate-root -init
# Vault returns a nonce and an OTP

vault operator generate-root -nonce=<nonce>
# Provide unseal key shares, one at a time, until threshold is met

# Final output includes an encoded token - decode with the OTP from step 1
vault operator generate-root -decode=<encoded-token> -otp=<otp>
```

This is Vault's supported recovery path for a lost root token, gated by the same unseal-key quorum that protects everything else, not a workaround. The new token went straight to a file and was never displayed in a terminal, same discipline as the unseal keys. It was then applied into the `ClusterSecretStore`'s token Secret so External Secrets Operator could resume syncing.

## What Made This Recoverable at All

Two unglamorous decisions. The datastore extraction happened read-only, before any later incident could touch it, so there was a known-clean copy to work from. And the unseal keys had been stored as a Kubernetes object in the first place, not only on paper or in someone's head. A Secret object is recoverable through a path like this one; a value that only ever existed in one person's memory is not.

---

Azure has its own version of this circular dependency. If the identities and role assignments that grant access to a Key Vault break along with the rest of a subscription, getting back in can require the very access the vault is supposed to grant. The answer has the same shape as Vault's: a break-glass path, such as an emergency access account that doesn't depend on the normal RBAC chain, so a circular dependency can't become a permanent lockout.

[Zero Trust Networks\*](/go/zero-trust-networks-book) is the book I'd point at for the underlying principle: a break-glass recovery path only works if it was designed in before you needed it, not improvised during the incident.
