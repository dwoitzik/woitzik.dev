[Velero's BackupStorageLocation](/blog/velero-garage-k3s-backup/) came up `Unavailable` the first time it synced against a freshly restored Garage instance:

```
403 AccessDenied: No such key: GKf5de79528ade5ffced70bd20
```

That error string is worth quoting exactly, because it's misleading on first read. It looks like a permissions problem, but it's an identity problem: Garage isn't saying the key lacks access, it's saying the key doesn't exist at all.

**[View the complete homelab infrastructure source on GitHub](https://github.com/dwoitzik/homelab-infrastructure)**

## The Credential Didn't Match Anything

[Vault stores Velero's Garage credentials](/blog/external-secrets-operator-vault-kubernetes/) at `secret/garage`, synced into the cluster as a normal Kubernetes Secret via ExternalSecrets. The access key ID Vault had on file for `velero-access-key-id` wasn't present in Garage's key store at all: not expired, not access-restricted, absent. Garage's key list confirmed it. A different key, `velero-s3`, existed with the right RW grant on the `velero` bucket, under an ID Vault had never been told about.

Nothing done during this fix caused it. It was pre-existing drift between two systems that are supposed to agree: Vault's stored value and Garage's key store had already diverged, either from a rotation that only touched one side or from a key regenerated without the matching Vault write-back. Either way, the lesson is the one that shows up anywhere secrets are synced in one direction: **the store of record and the system it authenticates against can silently disagree, and nothing surfaces that until something tries to actually use the stale value.**

## The Mistake, and Why It Mattered

Retrieving the valid key's secret value should have been routine:

```bash
garage key info velero-s3 --show-secret
```

It was run directly in an interactive shell instead of being redirected to a file. The secret key appeared in plain view in the output. It wasn't leaked externally or committed anywhere, but it was displayed where it shouldn't have been, which broke the file-redirect-only discipline kept for every other credential handled up to that point (unseal keys, root tokens, storage keys). It's the exact class of mistake [the gitleaks sweep of this same repo](/blog/gitleaks-secret-scanning-homelab-remediation/) exists to catch after the fact. The difference is that this one was caught immediately instead of months later in a full-history scan.

The exposed key was treated as compromised regardless of how short the exposure window was. No "it was only visible for a second, probably fine." A new Garage access key (`velero-s3-rotated`) was created with the same RW grant on the `velero` bucket, and the exposed key was deleted from Garage outright:

```bash
garage key create velero-s3-rotated
garage bucket allow --read --write velero --key velero-s3-rotated
garage key delete --yes <exposed-key-id>
```

Once deleted, the old key can't authenticate at all, wherever the exposed value might have ended up. The new credentials went into `velero-s3-credentials` via file redirect only, Velero and its node-agent were restarted, and the BackupStorageLocation came back `Available`.

## What Didn't Get Fixed, and Why I Stopped There

Vault's `secret/garage` entry is still out of sync, now in a second way: it points at neither the original stale key nor the new rotated one. At the time, no credential narrower than the root token could write to `secret/garage`, and generating a root token outside Vault's documented recovery flow wasn't something to improvise just to close the loop faster. The live fix (new key, wired directly into the Kubernetes Secret) works on its own. The Vault write-back is tracked as a follow-up, not silently skipped and not rushed through a shortcut that would have been worse than leaving it inconsistent for a day. The structural fix came later: a Vault AppRole bound to a policy with `create`, `read`, `update`, and `list` on exactly `secret/data/garage` and `secret/data/homepage`, so Garage key write-backs no longer need the root token at all.

That's a deliberate pattern: fix what's safe to fix with the access already in hand, document exactly what's still inconsistent and why, and don't reach for elevated credentials just to make a ledger entry tidier. [Recovering a lost Vault root token the right way](/blog/vault-raft-recovery-disposable-k3s-lost-root-token/), through Vault's own `generate-root` quorum flow, not a shortcut, is the same instinct applied to a much bigger version of this problem.

A backup target coming back "Available" also isn't proof the backups are trustworthy: [a scheduled Velero backup can report success and still not be restorable](/blog/vault-backup-crash-consistency-restore-proof/), for reasons that have nothing to do with credentials at all. Fixing the connection is necessary. It isn't sufficient.

---

The Azure analogue is a service principal secret rotated in Key Vault but never re-synced to whatever consumes it. The calling service keeps authenticating with a value Key Vault no longer considers current, and nothing fails loudly until the old secret expires. Automating that sync (Secrets Store CSI Driver auto-rotation, or an equivalent poll-and-refresh pattern) closes the same gap this Vault/Garage drift exposed.

[The Linux Command Line\*](/go/4gEAhv9) is the book I'd point people at for the habit that prevents mistakes like the one above. Redirecting output instead of trusting yourself never to look at the wrong thing at the wrong moment is a shell fundamental, not a security-specific skill.
