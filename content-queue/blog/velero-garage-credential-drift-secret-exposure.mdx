[Velero's BackupStorageLocation](/blog/velero-garage-k3s-backup/) came up `Unavailable` the first time it synced against a freshly restored Garage instance:

```
403 AccessDenied: No such key: GKf5de79528ade5ffced70bd20
```

That error string is worth quoting exactly, because it's misleading on first read — it looks like a permissions problem, not an identity problem. It isn't. Garage isn't saying the key lacks access; it's saying the key doesn't exist at all.

**[View the complete homelab infrastructure source on GitHub 🐙](https://github.com/dwoitzik/homelab-infrastructure)**

## The Credential Didn't Match Anything

[Vault stores Velero's Garage credentials](/blog/external-secrets-operator-vault-kubernetes/) at `secret/garage`, synced into the cluster as a normal Kubernetes Secret via ExternalSecrets. The access key ID Vault had on file for `velero-access-key-id` simply wasn't present in Garage's own key store — not expired, not access-restricted, genuinely absent. Checking Garage's actual key list directly confirmed it: a different key, `velero-s3`, existed with the right RW grant on the `velero` bucket, just under an ID Vault had never been told about.

This wasn't caused by anything in this session — it's pre-existing drift between two systems that are supposed to agree: Vault's stored value and Garage's own key store had already diverged, either from a rotation that only touched one side or a key regenerated without the corresponding Vault write-back. Either way, the takeaway is the same one that shows up anywhere secrets are synced one-directionally: **the store of record and the system it authenticates against can silently disagree, and nothing surfaces that until something tries to actually use the stale value.**

## The Mistake, and Why It Mattered

Retrieving the valid key's secret value should have been routine:

```bash
garage key info velero-s3 --show-secret
```

It was run directly, in an interactive shell, instead of redirected to a file first. The secret key value appeared in plain view in that output — not leaked externally, not committed anywhere, but displayed somewhere it shouldn't have been, breaking the same file-redirect-only discipline that had been maintained for every other credential handled up to that point (unseal keys, root tokens, storage keys). It's the exact class of mistake [the gitleaks sweep of this same repo](/blog/gitleaks-secret-scanning-homelab-remediation/) exists to catch after the fact — the difference here is it was caught immediately, in the moment, instead of months later in a full-history scan.

The response treated the exposed key as compromised regardless of how realistic the actual exposure window was — no "it was only visible for a second, probably fine." A brand-new Garage access key (`velero-s3-rotated`) was created with the same RW grant on the `velero` bucket, and the exposed key was deleted from Garage outright:

```bash
garage key new --name velero-s3-rotated
garage bucket allow --read --write velero --key velero-s3-rotated
garage key delete <exposed-key-id>
```

Deleting the old key means it can no longer authenticate at all, even if the exposed value somehow ended up somewhere it shouldn't. The new credentials went into `velero-s3-credentials` via file-redirect only, restarted Velero and its node-agent, and the BackupStorageLocation came back `Available`.

## What Didn't Get Fixed, and Why That's the Correct Stopping Point

Vault's `secret/garage` entry is now out of sync a *second* way — it points at neither the original stale key nor the new rotated one. Writing the corrected value back into Vault needs a root token, and generating or extracting one outside of Vault's own documented recovery flow wasn't something to improvise around just to close this loop faster. The live fix (new key, wired directly into the Kubernetes Secret) is fully functional on its own; the Vault write-back is tracked as a follow-up, not silently skipped and not rushed through with a shortcut that would have been a worse trade than leaving it inconsistent for a day.

That's a deliberate pattern, not a one-off: fix what's safe to fix with the access already in hand, document precisely what's still inconsistent and why, and don't reach for elevated credentials just to make a ledger entry tidier. [Recovering a lost Vault root token the right way](/blog/vault-raft-recovery-disposable-k3s-lost-root-token/) — through Vault's own `generate-root` quorum flow, not a shortcut — is the same instinct applied to a much bigger version of this exact problem.

It's also a reminder that a backup target coming back "Available" isn't proof the backup itself is trustworthy — [a scheduled Velero backup can report success and still not be restorable](/blog/vault-backup-crash-consistency-restore-proof/), for reasons that have nothing to do with credentials at all. Fixing the connection is necessary. It isn't sufficient.

---

The Azure analogue is a service principal or managed identity whose secret was rotated in Key Vault but never re-synced to whatever's actually consuming it — the calling service keeps authenticating with a value Key Vault no longer considers current, and nothing fails loudly until the old secret's expiry actually hits. Automating that sync (via CSI Secret Store driver auto-rotation, or an equivalent poll-and-refresh pattern) closes the same gap this Vault/Garage drift exposed manually.

[The Linux Command Line\*](/go/4gEAhv9) is the book I'd point people at for the underlying habit that catches mistakes like the one above before they matter — redirecting output rather than trusting yourself to never look at the wrong thing at the wrong moment is a shell-scripting fundamental, not a security-specific skill.
