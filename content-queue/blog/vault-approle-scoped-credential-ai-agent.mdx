I use an AI coding agent (Claude Code, given real but constrained access to one of my own LXCs) for a chunk of the disaster-recovery and hardening work on this homelab — the kind of long, tedious, multi-step infrastructure archaeology that benefits from something that doesn't get bored halfway through. It's genuinely useful. It's also, over one long recovery mission, put my [Vault](/blog/vault-zero-networkpolicy-argocd-tracking-gap/) root token into its own tool output four separate times, each one a real, if contained, exposure. The pattern was always the same: some task needed to write or read a Garage-related secret, no narrower credential existed, so whoever set the agent up for that task reached for the root token — again.

**[View the complete homelab infrastructure source on GitHub 🐙](https://github.com/dwoitzik/homelab-infrastructure)**

## The Task That Made This Non-Optional

I needed to write four fresh Garage API key pairs into Vault after Garage's metadata store was [wiped and re-provisioned following a corruption incident](/blog/garage-lmdb-metadata-dedicated-disk/). That meant touching Vault again. Doing it with the root token a fifth time, even carefully, wasn't going to fix anything — the fix had to be a narrower credential, not more discipline applied to the same one. Four incidents across one mission means "be more careful" has already been tried, and it's already failed four times.

## A Narrow AppRole, Scoped to Exactly What's Needed

I created a Vault AppRole bound to a policy scoped to exactly two KV v2 paths:

```hcl
path "secret/data/garage" {
  capabilities = ["create", "read", "update", "list"]
}
path "secret/metadata/garage" {
  capabilities = ["read", "list"]
}
path "secret/data/homepage" {
  capabilities = ["create", "read", "update", "list"]
}
path "secret/metadata/homepage" {
  capabilities = ["read", "list"]
}
```

Role settings matter as much as the path scoping: `token_ttl=1h`, `token_max_ttl=4h` — any token minted from this role is short-lived by design, not a standing credential — and `secret_id_ttl=24h`, meaning the credential used to *obtain* a token also expires. `role_id` (not sensitive, functions like a username) and `secret_id` (sensitive, generated once) live on the agent's own LXC, mode 600, root-only. When the `secret_id` expires, generating a fresh one needs a human with real Vault access — the AppRole's own token can't mint new `secret_id`s for itself, deliberately.

`secret/homepage` is in the same policy even though nothing wrote to it in that pass — my homepage dashboard already expects several properties there (a Proxmox token, an ArgoCD token, CrowdSec credentials) that aren't populated yet. Generating those requires touching their respective source systems first, a separate task I didn't have the inputs for right then — but the AppRole is ready for it without needing a second bootstrap later.

## The Chicken-and-Egg, and the Mistake I'm Disclosing Rather Than Hiding

Setting up an AppRole in the first place needs privileged Vault access — a genuine chicken-and-egg with "get the root token out of the working path." I bootstrapped it with a one-time root token I generated fresh via `vault operator generate-root`, using my own Shamir unseal key shares, specifically for this purpose, with an explicit note to myself to revoke it immediately once the AppRole existed and worked.

A real mistake happened during that bootstrap, and I'm writing it down rather than smoothing it over: the first authentication attempt used `vault login -` (token piped via stdin) to establish a session for the setup commands. `vault login`'s own confirmation output prints the token it just authenticated with — which put the root token value into the agent's tool output, exactly the exposure pattern this whole project existed to stop, on the very first step of fixing it. I caught it immediately, not later. Every subsequent credential-handling step — the AppRole's `secret_id`, the four Garage secrets — used `VAULT_TOKEN=$(cat /path/to/token)` per-command instead of `vault login`, specifically to not repeat it.

**If you're scripting anything against Vault: `vault login`'s stdout echoes the token back at you. Never use it for a credential that has to stay out of your own logs or tool output — use `VAULT_TOKEN=$(cat ...)` per command instead.**

## Revocation That Didn't Quite Close the Loop

Per my own instruction to revoke the bootstrap root token immediately, I ran `vault token revoke -self` against it twice, from two independently fresh extractions of the token value. Both attempts failed identically: `403, invalid token`. I checked this wasn't a wider Vault problem before assuming anything — a fresh AppRole login succeeded immediately after, using the exact same execution path, confirming Vault's auth system itself was healthy and the problem was specific to that one token. Most likely explanation: the token had already expired or been invalidated by some other mechanism before the second revoke attempt — not fully understood, and I stopped chasing it after two clean attempts with two independently fresh extractions, per my own "max 3 attempts, different hypotheses, then park" rule.

Practically, this is very likely a non-issue — a token Vault itself already rejects as invalid is already inert. But I can't verify that with certainty from the AppRole's own narrow access, and deliberately isn't re-escalating past it to check, which would undermine the entire point of building it. If you have real Vault access and want to confirm a bootstrap token is genuinely dead, `vault token lookup -accessor <accessor>` against the original `generate-root` output settles it without needing the token itself.

## Why This Is the Actual Fix

I could have written a rule — "always use the AppRole, never the root token" — and called it done. That's precisely what had already failed four times: a rule an agent (or a human) has to remember under exactly the conditions that produced all four incidents — fast-moving debugging, an unfamiliar error, a session that's already run long — is a rule that gets forgotten. The AppRole works because it doesn't require anyone to remember anything: when a task needs a Garage or homepage secret, the only credential that's actually *available* for that task is the narrow one. There's no root token sitting in reach to reach for instead.

---

The Azure-shaped equivalent is scoping a Managed Identity's role assignments to exactly the Key Vault secrets a specific pipeline needs, instead of handing it Contributor on the whole subscription because it's faster to set up once. It's slower to configure the first time and it's the only version of the setup that survives someone being in a hurry six months later.

[The Phoenix Project\*](/go/4f4RHQf) has a line I think about a lot for exactly this kind of fix: the goal isn't to make people more careful, it's to change the system so carefulness stops being the thing standing between a mistake and a real incident.
