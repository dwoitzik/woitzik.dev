I use an AI coding agent (Claude Code, with real but constrained access to one of my own LXCs) for a chunk of the disaster-recovery and hardening work on this homelab: long, tedious, multi-step infrastructure archaeology that benefits from something that doesn't get bored halfway through. It is useful. Over one long recovery mission, it also put my [Vault](/blog/vault-zero-networkpolicy-argocd-tracking-gap/) root token into its own tool output four separate times, each one a real, if contained, exposure. The pattern was always the same: a task needed to read or write a Garage-related secret, no narrower credential existed, so the root token got used again.

**[View the complete homelab infrastructure source on GitHub 🐙](https://github.com/dwoitzik/homelab-infrastructure)**

## The Task That Made This Non-Optional

I needed to write four fresh Garage API key pairs into Vault after Garage's metadata store was [wiped and re-provisioned following a corruption incident](/blog/garage-lmdb-metadata-dedicated-disk/). That meant touching Vault again. Using the root token a fifth time, however carefully, would not have fixed anything. Four incidents in one mission means "be more careful" had already been tried and had failed four times. The fix had to be a narrower credential.

## A Narrow AppRole, Scoped to Exactly What's Needed

I created a Vault AppRole bound to a policy that covers exactly two KV v2 secrets, `garage` and `homepage`, through their data and metadata paths:

```hcl
path "secret/data/garage" {
  capabilities = ["create", "read", "update", "list"]
}
path "secret/metadata/garage" {
  capabilities = ["read", "list"]
}
path "secret/data/homepage" {
  capabilities = ["create", "read", "update", "list"]
}
path "secret/metadata/homepage" {
  capabilities = ["read", "list"]
}
```

The role settings matter as much as the path scoping. With `token_ttl=1h` and `token_max_ttl=4h`, any token minted from this role is short-lived by design rather than a standing credential. With `secret_id_ttl=24h`, the credential used to *obtain* a token expires too. The `role_id` (not sensitive, it works like a username) and the `secret_id` (sensitive, generated once) live on the agent's own LXC, mode 600, root-only. When the `secret_id` expires, generating a fresh one takes a human with real Vault access. The AppRole's own token deliberately cannot mint new `secret_id`s for itself.

`secret/homepage` is in the policy even though nothing wrote to it in that pass. My homepage dashboard already expects several properties there (a Proxmox token, an ArgoCD token, CrowdSec credentials) that aren't populated yet. Generating them means touching each source system first, a separate task I didn't have the inputs for at the time. The AppRole is ready for it without a second bootstrap.

## The Chicken-and-Egg, and the Mistake I'm Disclosing Rather Than Hiding

Setting up an AppRole requires privileged Vault access in the first place, which is a real chicken-and-egg problem when the goal is to get the root token out of the working path. I bootstrapped it with a one-time root token generated fresh via `vault operator generate-root` from my own Shamir unseal key shares, for this purpose only, with a note to myself to revoke it as soon as the AppRole existed and worked.

A real mistake happened during that bootstrap, and I'm writing it down rather than smoothing it over. The first authentication attempt used `vault login -` (token piped via stdin) to open a session for the setup commands. `vault login` prints the token it just authenticated with as part of its confirmation output, so the root token value landed in the agent's tool output. That was exactly the exposure this whole project existed to stop, on the very first step of fixing it. I caught it immediately. Every later credential-handling step (the AppRole's `secret_id`, the four Garage secrets) used `VAULT_TOKEN=$(cat /path/to/token)` per command instead of `vault login`, so it could not happen again.

**If you're scripting anything against Vault: `vault login` echoes the token to stdout. `-no-print` suppresses that, but the token still gets written to the token helper (`~/.vault-token` by default). For a credential that has to stay out of your logs and tool output, use `VAULT_TOKEN=$(cat ...)` per command instead.**

## Revocation That Didn't Quite Close the Loop

Following my own instruction to revoke the bootstrap root token immediately, I ran `vault token revoke -self` against it twice, from two independent fresh extractions of the token value. Both attempts failed identically: `403, invalid token`. Before assuming anything, I checked that this wasn't a wider Vault problem. A fresh AppRole login succeeded right after, through the exact same execution path, so Vault's auth system was healthy and the problem was specific to that one token. Root tokens from `generate-root` have no TTL, so simple expiry doesn't explain it. Something else had invalidated the token before the revoke attempts, and I don't fully understand what. I stopped after two clean attempts, per my own "max 3 attempts, different hypotheses, then park" rule.

In practice this is very likely a non-issue: a token Vault already rejects as invalid is inert. But I can't verify that with certainty from the AppRole's narrow access, and I am deliberately not re-escalating to check, because that would undermine the point of building it. If you have real Vault access and want to confirm a bootstrap token is dead, `vault token lookup -accessor <accessor>` settles it without needing the token itself. That only works if you noted the accessor while the token was still valid (`vault token lookup` shows it); the audit log HMACs accessors by default.

## Why This Is the Actual Fix

I could have written a rule ("always use the AppRole, never the root token") and called it done. That is what had already failed four times. A rule that an agent or a human has to remember under the exact conditions that produced all four incidents (fast-moving debugging, an unfamiliar error, a session that has already run long) is a rule that gets forgotten. The AppRole works because nobody has to remember anything: when a task needs a Garage or homepage secret, the narrow credential is the only one *available* for it. There is no root token within reach.

---

The Azure equivalent is scoping a Managed Identity's role assignments to exactly the Key Vault secrets a specific pipeline needs, instead of granting it Contributor on the whole subscription because that is faster to set up once. The scoped version takes longer to configure the first time, and it is the only version that survives someone being in a hurry six months later.

[The Phoenix Project\*](/go/4f4RHQf) keeps coming back to the same idea that applies here: change the system so that carefulness is no longer the only thing standing between a mistake and a real incident.
