Die übliche Antwort auf „Wie komme ich von außen an meinen Dienst?“ lautet: Port auf, DNS auf einen Reverse Proxy, fertig. Das funktioniert, bis jemand dein Admin-Panel scannt, deinen Router ins DDoS-Botnetz zieht oder der Provider deinen Host wegen Missbrauchs abschaltet.

Drei Dienste in meinem Homelab sind heute über Cloudflare Tunnel aus dem Internet erreichbar: Immich für das Foto-Backup der Familie, Jellyfin für Medien und der Analytics-Endpunkt dieser Website. Keiner davon braucht eine eingehende Firewall-Regel. Die MikroTik-Firewall [bleibt default-deny](/blog/mikrotik-zero-trust-firewall-terraform/), und `cloudflared` transportiert ihren Traffic über eine ausgehende Verbindung, die mein Cluster selbst aufbaut. Die eine Ausnahme auf dem Router ist Headscale, das sich nicht hinter den Tunnel legen lässt (siehe Nachtrag).

> **Nachtrag (November 2026):** Zwei Aussagen aus der ersten Fassung stimmen nicht mehr. Erstens ist das Netz nicht mehr frei von eingehenden Ports. Das TS2021-Registrierungsprotokoll von Headscale baut die Verbindung mit `Upgrade: tailscale-control-protocol` um, und diesen Header leiten weder `cloudflared` noch Traefik weiter. Die Headscale-Doku sagt selbst, dass Headscale hinter einem Cloudflare Tunnel oder Proxy nicht unterstützt wird. Seit dem 2026-08-28 ist `headscale.woitzik.dev` deshalb ein DNS-only-Record, der auf die WAN-IP auflöst, und eine einzige Portweiterleitung für TCP/443 (Fritz!Box auf den MikroTik, dort ein per Terraform verwaltetes dst-nat plus Forward-Accept auf den Reverse Proxy mit nginx und CrowdSec in der DMZ, 10.0.30.2) bedient genau diesen Hostnamen. Zweitens hat sich die Liste der getunnelten Dienste geändert. Atlantis ist im August 2026 aus dem Tunnel geflogen (ein selbst gehosteter GitHub-Actions-Runner ersetzt den eingehenden Webhook), `analytics.woitzik.dev` für Rybbit kam am 2026-08-29 dazu, und Jellyfin ist seit dem 2026-10-19 wieder öffentlich. Der Tunnel bedient heute `photos`, `analytics` und `media`, alles andere bekommt am Tunnel eine 404. Den Abschnitt zu Atlantis und Traefik lasse ich wegen der Technik stehen, als historisch markiert.

## Die Architektur

Ein klassisches Setup ist eine Kette, in der drei Dinge gleichzeitig stimmen müssen: offene Ports im Router, DNS auf eine öffentliche IP und ein Reverse Proxy mit der richtigen TLS-Konfiguration. Jedes Glied ist eine eigene Fehlerquelle und eine eigene Angriffsfläche.

Der Tunnel dreht die Kette um. Ein `cloudflared`-Daemon im Cluster baut eine dauerhafte ausgehende Verbindung zu den Edge-Servern von Cloudflare auf. Anfragen für die konfigurierten Hostnamen kommen über genau diese Verbindung herein, eingehend ist für diese Hostnamen kein Port offen:

```
Internet → Cloudflare Edge → (bestehende ausgehende Verbindung) → cloudflared im Cluster → dein Dienst
```

Neben der Sicherheit fällt eine ganze Klasse von Konfiguration weg: Es gibt keine öffentliche IP, die auf etwas zeigt, keine NAT-Regel, die ich beim Provider-Wechsel mitnehmen muss, und keinen offenen Port 80 für eine Let's-Encrypt-Challenge.

Die Ingress-Regeln liegen in Terraform (Cloudflare-Provider v5, dort sind `config` und `ingress` Attribute, keine Blöcke):

```hcl
# terraform/stacks/cloudflare/main.tf (gekürzt)
resource "cloudflare_zero_trust_tunnel_cloudflared_config" "homelab" {
  account_id = var.account_id
  tunnel_id  = var.tunnel_id

  config = {
    ingress = [
      {
        hostname = "photos.woitzik.dev"
        service  = "http://immich-server.apps.svc.cluster.local:2283"
        origin_request = {
          no_tls_verify            = false
          connect_timeout          = 10
          tcp_keep_alive           = 30
          keep_alive_connections   = 10
          http_host_header         = "photos.woitzik.dev"
          disable_chunked_encoding = false
        }
      },
      {
        hostname = "analytics.woitzik.dev"
        service  = "http://10.0.20.205:80"
        origin_request = {
          no_tls_verify    = false
          http_host_header = "analytics.woitzik.dev"
        }
      },
      {
        hostname = "media.woitzik.dev"
        service  = "http://10.0.20.254:8096"
        origin_request = {
          no_tls_verify    = false
          http_host_header = "media.woitzik.dev"
        }
      },
      { service = "http_status:404" }
    ]
  }
}
```

Die Catch-all-Regel `http_status:404` ist **Pflicht**: `cloudflared` akzeptiert keine Ingress-Konfiguration, deren letzte Regel nicht jede Anfrage abfängt. Sie ist zugleich die Zugriffsregel. Jeder Hostname ohne eigene Regel bekommt am Tunnel eine 404 und erreicht den Cluster nie. So bleiben die gut 40 übrigen internen Hostnamen auf LAN und VPN beschränkt.

## Split-DNS auf AdGuard

Der Tunnel erzeugt ein Split-Brain-Problem im DNS. Öffentliches DNS zeigt die getunnelten Hostnamen auf die Anycast-IPs von Cloudflare. LAN-Clients sollen interne Dienste dagegen direkt über die Traefik-VIP erreichen, ohne Umweg über Cloudflare. Dieselben `woitzik.dev`-Namen müssen also je nach Resolver unterschiedlich aufgelöst werden.

AdGuard Home löst das mit einem Wildcard-Rewrite:

```yaml
# ansible/roles/adguard/templates/AdGuardHome.yaml.j2 (Auszug)
rewrites:
  - domain: "*.woitzik.dev"
    answer: "10.0.20.200"   # Traefik LoadBalancer IP
    enabled: true
  - domain: headscale.woitzik.dev
    answer: "10.0.20.200"
    enabled: true
```

Die Wildcard `*.woitzik.dev` deckt alle internen Dienste ab, auch die getunnelten. Ein Smartphone im heimischen WLAN löst `photos.woitzik.dev` auf Traefik auf und lädt direkt in den Cluster hoch. Dasselbe Smartphone im Mobilfunknetz fragt AdGuard gar nicht und nimmt öffentliches DNS und den Tunnel. Eine Zeit lang hatte ich einen spezifischeren Rewrite, der `photos` auf die Anycast-IPs von Cloudflare festnagelte, damit auch LAN-Clients durch den Tunnel gehen. Den habe ich wieder entfernt: Der Umweg über Cloudflare bringt aus dem LAN nichts außer dem 100-MB-Limit pro Request, um das es weiter unten geht. Hostnamen, die intern eine andere Antwort brauchen (etwa die Minecraft-Server mit reinem TCP), bekommen einen eigenen, spezifischeren Rewrite, den AdGuard der Wildcard vorzieht.

Die Falle dabei: **Die Wildcard gilt auch für die Search-Domain.** Steht die Search-Domain eines Proxmox-Hosts auf `woitzik.dev`, wird jeder kurze interne Hostname in die Wildcard erweitert, auch `pve.woitzik.dev` und `pbs.woitzik.dev`, die nie auf Traefik auflösen dürfen. Ein verwandtes Leck mit anderer Ursache fiel mir beim Setup auf: PTR-Queries für k3s-Pod-IPs (10.42.0.0/16) gingen an die FritzBox. Bei leerem `private_networks` behandelt AdGuard alle RFC-1918-Bereiche als privat und schickt solche Reverse-Lookups an den privaten PTR-Resolver, hier die Fritz!Box. Die konnte sie nicht beantworten, und jede Query kostete einen Timeout von 2 Sekunden. Seit `private_networks` auf das Fritz!Box-LAN (192.168.178.0/24) beschränkt ist, ist Ruhe.

## Große Uploads und Chunked Encoding

Nach dem Umbau funktionierte Immich bis zum ersten großen Upload. Fotos und Videos brachen reproduzierbar bei 60 bis 80 % mit `ECONNRESET` ab, kleine Dateien gingen problemlos durch.

Mein erster Fix, festgehalten in CHANGELOG v0.8.0, setzte `chunked_encoding = true`, `write_timeout = 600` und `read_timeout = 120` im Origin-Request des Tunnels. Keine dieser Optionen gibt es in `cloudflared`. Der tatsächliche Schalter heißt `disableChunkedEncoding` (im Terraform-Provider `disable_chunked_encoding`), und Chunked Transfer zum Origin ist ohnehin standardmäßig aktiv. Die aktuelle Konfiguration setzt diesen Default explizit:

```hcl
origin_request = {
  no_tls_verify            = false
  connect_timeout          = 10
  tcp_keep_alive           = 30
  keep_alive_connections   = 10
  http_host_header         = "photos.woitzik.dev"
  disable_chunked_encoding = false
}
```

Mit `disable_chunked_encoding = false` streamt `cloudflared` den Request-Body in Chunks zum Origin, statt die gesamte Payload zu puffern. Einen Write-Timeout pro Origin, den man hochsetzen könnte, gibt es nicht.

Die andere Grenze, die du kennen solltest: Der Cloudflare-Proxy begrenzt die Größe eines Request-Bodys je nach Plan (100 MB bei Free und Pro). Ein einzelner Upload-Request darüber wird schon an der Edge abgewiesen, egal was in der Tunnel-Konfiguration steht. Das betrifft **jeden** Dienst hinter einem Cloudflare Tunnel, der große Dateien in einem Request annimmt, also auch Nextcloud und Paperless. Prüf also zuerst, wie der Client Uploads aufteilt, bevor du den Tunnel verdächtigst. Die Fehlermeldung (`ECONNRESET`) zeigt nämlich auf ein Netzwerkproblem und nicht auf ein Limit. Bei mir greift das Limit nur unterwegs: Im LAN schickt der Wildcard-Rewrite `photos.woitzik.dev` direkt an Traefik, große Uploads berühren Cloudflare dort gar nicht.

## Atlantis durch Traefik (historisch)

Dieser Abschnitt beschreibt, wie Atlantis bis August 2026 erreichbar war. Heute hat Atlantis weder einen Tunnel-Eintrag noch einen öffentlichen DNS-Record. Ein selbst gehosteter GitHub-Actions-Runner fragt GitHub ausgehend ab, von außen muss niemand mehr an Atlantis heran. Das Muster passt trotzdem für jeden Dienst, der öffentlich sein muss und keinen eigenen Login hat.

Atlantis braucht GitHub-Webhooks für Terraform-PR-Events. Der Reflex ist, Atlantis direkt über den Tunnel freizugeben. Das Problem: **Die Web-UI von Atlantis hat ohne explizit aktivierte Basic Auth keine Authentifizierung.** Wer die URL findet, kann Plan-Ausgaben lesen und Locks freigeben. Ein Tunnel löst das nicht, er macht die ungeschützte Oberfläche nur leichter erreichbar.

Die Lösung ist, Atlantis zuerst durch Traefik zu leiten, damit die [Authelia](/blog/k3s-authelia-proxmox-homelab/) ForwardAuth-Middleware greift, bevor der Request Atlantis erreicht:

```hcl
{
  hostname = "atlantis.woitzik.dev"
  service  = "https://traefik.kube-system.svc.cluster.local:443"
  origin_request = {
    no_tls_verify      = false
    http_host_header   = "atlantis.woitzik.dev"
    origin_server_name = "atlantis.woitzik.dev"
  }
}
```

Der Tunnel zeigt also auf den HTTPS-Entrypoint von Traefik, nicht auf Atlantis. `origin_server_name` ist nötig, weil `cloudflared` das Zertifikat von Traefik sonst gegen den Service-Namen (`traefik.kube-system.svc.cluster.local`) prüft und mit 502 abbricht. Der Plain-HTTP-Port von Traefik funktioniert auch nicht: Traefik leitet ihn auf HTTPS um, und der Tunnel reicht die Umleitung in einer Schleife an den Client zurück.

Atlantis läuft auf einem eigenen LXC (10.0.20.250). Traefik erreicht es über einen Service ohne Selector mit manuellem Endpoints-Objekt. Die IngressRoute hat zwei Routen:

```yaml
apiVersion: traefik.io/v1alpha1
kind: IngressRoute
metadata:
  name: atlantis-final
  namespace: apps
spec:
  entryPoints: [websecure]
  routes:
  # GitHub webhook path: no Authelia, the webhook's HMAC secret is the auth
  - match: Host(`atlantis.woitzik.dev`) && PathPrefix(`/events`)
    kind: Rule
    priority: 10
    services: [{name: external-atlantis, port: 4141}]
  - match: Host(`atlantis.woitzik.dev`)
    kind: Rule
    priority: 1
    middlewares:
      - name: crowdsec-bouncer
      - name: authelia
      - name: websockets
    services: [{name: external-atlantis, port: 4141}]
```

Die GitHub-Webhooks gehen an `/events` und umgehen Authelia, weil ein Forward-Auth-Redirect die Zustellung kaputt machen würde. Ungeschützt ist dieser Pfad trotzdem nicht: Atlantis prüft die HMAC-Signatur jedes Webhooks gegen das gemeinsame Secret. Alles andere, auch die **Web-UI** mit Plan-Ausgaben und Lock-Verwaltung, erfordert die Anmeldung über Authelia.

Dieses Muster (Cloudflare Tunnel → Traefik → Authelia → Dienst) passt für jeden externen Dienst ohne eigene Authentifizierung. Der Tunnel übernimmt den Ingress, Traefik Routing und TLS, Authelia die Authentifizierung.

## DNS-Records verwalten

Die DNS-Records für die Tunnel-CNAMEs sind Terraform-verwaltet:

```hcl
resource "cloudflare_dns_record" "tunnel_photos" {
  zone_id = var.zone_id
  name    = "photos"
  type    = "CNAME"
  content = "abc123.cfargotunnel.com"
  proxied = true
  ttl     = 1
}
```

`proxied = true` heißt, dass der Traffic durch den Cloudflare-Proxy läuft. Das bringt DDoS-Schutz, Rate Limiting und WAF-Regeln mit. `ttl = 1` bedeutet „automatisch“, was Cloudflare für geproxte Records ohnehin vorschreibt.

In der echten Datei steht bei `content` `"${var.tunnel_id}.cfargotunnel.com"`; `media` und `analytics` sehen genauso aus.

Zwei Records sind `proxied = false`. `headscale.woitzik.dev` ist ein DNS-only-Record auf die WAN-IP, den ein DDNS-CronJob im Cluster aktuell hält (Terraform ignoriert Änderungen an `content`), weil das Headscale-Protokoll nicht durch den Cloudflare-Proxy kommt. Der Minecraft-Record ist ein CNAME auf einen `playit.gg`-Hostnamen, denn reiner TCP-Spieletraffic geht ebenfalls nicht durch den HTTP-Proxy von Cloudflare. Die alten Records `atlantis`, `auth` und `home` sowie die öffentliche Wildcard `*.woitzik.dev` sind seit August 2026 gelöscht. Diese Namen lösen nur noch im LAN und im Tailnet auf.

---

Das Modell ohne eingehende Ports entspricht Azure Front Door mit Private-Link-Origins: Externer Traffic läuft durch einen verwalteten Proxy, berührt die eigene Firewall nie, und der Origin braucht keinen öffentlichen Endpunkt. Das Split-DNS-Problem entspricht den Azure Private DNS Zones, bei denen interne Clients auf Private Endpoints auflösen und externe über öffentliches DNS. Andere Werkzeuge, dieselbe Architektur.
