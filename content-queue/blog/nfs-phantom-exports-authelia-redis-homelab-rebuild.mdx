The same bug hit twice in one rebuild, in two different applications, weeks apart. Both times the root cause was an `/etc/exports` file that had once been correct and had quietly stopped matching the filesystem. Nothing complained until something tried to use the paths it described.

## First Occurrence: A Gitea PVC That Looked Permanently Empty

While [verifying restored Tier-1 data](/blog/proxmox-pbs-restore-tier1-data-verification/), Gitea's local-path PVC turned up as a 44KB skeleton: a config template, no real data, weeks older than the incident that supposedly caused the loss. One of three independent checks I ran to confirm it wasn't recoverable was the NFS export layer. The Ansible-managed `/etc/exports` listed an export path for this exact application among roughly eighteen entries, several of them for apps that had since moved from NFS-backed storage to `local-path`.

None of those eighteen directories existed on the NFS server's filesystem. Some entries had been made obsolete by the local-path migration and never removed, and nobody had checked that the directories behind the rest existed at all. That ruled out "the current data lives on the NFS path instead" (there was nothing there to find). It also surfaced a separate problem nobody had noticed: eighteen phantom exports in a config file that had never once been exercised.

## Second Occurrence: A Redis Deployment That Wouldn't Mount

Weeks later, Redis for Authelia's session storage needed a PVC on the `nfs-client` storage class. That provisioner mounts one base export, `/nfs-data/k8s-general`, and creates a subdirectory per PVC under it, and that base export was one of the eighteen phantom paths from the first time around. The gap had been logged, not fixed, because it wasn't blocking anything yet.

This time it did block something. The provisioner tried to mount an export path that did not exist on the NFS server and failed outright. Not "data missing," but "there is nowhere to write at all."

```bash
# What the export config declared:
cat /etc/exports
# /nfs-data/redis  10.0.20.0/24(rw,sync,no_subtree_check)
# ...seventeen more identical-looking lines

# What actually existed on disk:
ls /nfs-data/
# (nothing - the parent directory itself had never been created)
```

The fix was additive and mechanical once identified: create every declared export directory that was missing, then re-export.

```bash
mkdir -p /nfs-data/redis
exportfs -ra
```

All eighteen got fixed in one pass, instead of waiting for each to block whatever app needed it next.

## The Second, Unrelated Bug in the Same Deployment

Getting Redis's PVC to mount uncovered a second, separate gap: `nfs-common`, the client-side NFS tooling, was missing from the k3s node base image. The minimal Debian cloud template these nodes were cloned from never had it, so any `nfs-client` PVC on a freshly provisioned node would fail to mount no matter how correct the export was. I installed it by hand on both current nodes to unblock; the durable fix is baking `nfs-common` into the base template (or an Ansible task that runs before anything needs NFS), so it stops being a surprise on every future node join.

One more gotcha from the same pass, because it looks like a bug the first time you see it: an `ExternalSecret` with `creationPolicy: Merge` (used here for Authelia's secrets, which combine values from Vault with values already in the Secret) requires the target Kubernetes Secret to exist already. External Secrets Operator won't create one from scratch under `Merge`. The fix is to bootstrap an empty seed Secret first, every time this policy is used. It's documented behavior, not a bug, but the failure only shows up in the ExternalSecret's status, which is easy to miss on first encounter.

## Why the Same Root Cause Hid for So Long

Drift between a declared state (the Ansible-managed `/etc/exports`) and the filesystem (whether the directories exist) produces almost no visible errors until something tries to use a stale entry. `exportfs` does notice a missing path: it logs `Failed to stat <path>: No such file or directory` and skips that entry. But that line lands in an Ansible handler's output or the `nfs-server` journal, where nobody reads it, and the rest of the file exports fine. A client mounting the skipped path gets a generic mount failure that looks like a dozen other causes. The gap survived every Ansible run that re-applied the same `/etc/exports`, because re-applying a correct-looking config doesn't check whether the filesystem underneath still matches.

The practical lesson: a storage migration (NFS-backed to `local-path`, in this case) needs a matching cleanup pass on the *old* storage's export and config layer, not just a cutover of the apps that used it. Leaving the old declarations in place "just in case" doesn't keep a safety net. It leaves confident-looking exports with nothing behind them, waiting to fail the next time something uses one. It's the same kind of problem as [an NFS-backed PVC turning out to double as a backup target](/blog/velero-nfs-provisioner-root-mount-redundant-backup/): invisible until someone traces what's mounted where.

The closest Azure analogue is an Azure Files share name or storage endpoint passed into a Bicep template as a plain string parameter long after the storage account behind it was decommissioned. The template deploys "successfully" because a string is just a string; nothing checks that it still points at something real. The failure only surfaces when a workload tries to mount or connect.
