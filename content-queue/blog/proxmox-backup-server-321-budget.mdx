The 3-2-1 rule asks for 3 copies of your data, on 2 different media, with 1 offsite. Proxmox Backup Server (PBS) covers the "2 media" part cheaply: on my homelab it runs directly on the Proxmox VE host, a [BMAX Mini PC*](/go/4bv3yF1), and writes deduplicated snapshots of every VM and LXC to a [2TB Seagate External HDD*](/go/4vxwLpY). That part works and is checked after every run. The "1 offsite" part for PBS does not exist right now. My only active offsite copy is Velero's, and it covers a handful of Kubernetes namespaces, not the VM images. This post describes the setup as it actually runs, including the gap.

## PBS on the Proxmox Host

PBS used to live in its own LXC (`ct-mgmt-pbs-01`). That container is gone. PBS now runs host-native on `pve-mgmt-01`, installed from the `pbs-no-subscription` repository next to PVE. Ansible manages the install (`ansible/roles/pbs/`): it removes the enterprise repo files, adds the PBS repo as a deb822 source, and installs `proxmox-backup-server`.

The datastore sits on the ZFS pool `archive`, a single-vdev pool on the USB HDD, mounted at `/mnt/pbs-storage`. In PVE it shows up as the storage `local-pbs`.

Co-locating PBS with PVE saves the RAM and disk of a dedicated guest. The cost is that a dead host takes PBS with it. Restoring after host loss starts with reinstalling PVE and PBS and re-importing the `archive` pool from the HDD, which is the main reason the HDD is external and not inside the box.

One hardware detail is load-bearing: the HDD must sit on a USB 3 port. On USB 3 it reads around 60 MB/s. When it ended up on a USB 2 port, throughput dropped to 3 to 13 MB/s, which turns a backup window into a backup night.

## The Backup Job

PBS doesn't pull backups. PVE pushes them through a regular vzdump job that targets the PBS storage. Mine lives in `/etc/pve/jobs.cfg`, and `pvescheduler` logs it like this when it starts:

```text
INFO: starting new backup job: vzdump
  --mailnotification failure --node pve-mgmt-01 --quiet 1 --storage local-pbs
  --compress zstd --exclude 9000 --all 1
  --prune-backups 'keep-daily=7,keep-weekly=4' --mode snapshot
```

The schedule is `*-*-01/2 03:00`, so every other night at 03:00, not daily. Every guest is included except VM `9000`, the cloud-init template, which holds no unique state. Retention is 7 daily and 4 weekly snapshots. A full run takes roughly 76 minutes.

That run is not free on a single-disk host. All VM and LXC disks live on one DRAM-less NVMe, and a snapshot-mode backup reads every guest disk while the guests keep writing. vzdump's global throttle in `/etc/vzdump.conf` (Ansible-managed, see ADR-023) keeps it from starving everything else:

```text
bwlimit: 51200
ionice: 7
```

`bwlimit` is in KiB/s, so 50 MiB/s. Even throttled, the job pushes host load well past what normal daytime work does. My host watchdog alerts on load, and it now raises its threshold only while a `vzdump` process is actually running (ADR-053), so the backup window stops paging me every night.

## Checking That Backups Are Real

A green vzdump exit status is not proof of a usable backup. Two guests once produced 1-byte "successful" backups for two nights in a row before failing outright. Since then a vzdump hook script (the `script:` directive in `/etc/vzdump.conf`) runs at `job-end`. It reads what was actually committed to `local-pbs` via `pvesm list`, flags any guest whose newest backup is missing, too old, or smaller than 100 MiB, sends an ntfy alert, and writes a `pve_pbs_backup_healthy` metric for Prometheus.

Restores also run from the PVE side, either in the web UI (select `local-pbs`, open Backups, pick the snapshot, Restore) or on the CLI:

```bash
# List available backups on the PBS storage
pvesm list local-pbs --content backup

# Restore a container or a VM from a specific snapshot
pct restore <vmid> local-pbs:backup/ct/<vmid>/<timestamp> --storage local-lvm
qmrestore local-pbs:backup/vm/<vmid>/<timestamp> <vmid>
```

The hook proves a backup landed with a plausible size. It does not prove the guest boots or the data inside is intact. That takes a real restore to a scratch target, which is on my quarterly DR checklist but not automated yet.

## Pruning Has a Blind Spot

The `--prune-backups` option only reaches guests that still exist in the Proxmox config. Snapshots of deleted guests, and of guests added to the job's `exclude` list later, are never pruned. On my datastore that left 29 orphaned snapshots: 15 from the retired PBS LXC, 12 from the template VM excluded after the fact, and 2 from abandoned recovery clones. Their logical size adds up to roughly 300 GB, but because PBS deduplicates, they account for far less of the 212 GB the datastore actually references. Cleaning them up is hygiene, not a space win. The inventory comes from:

```bash
pvesm list local-pbs --content backup | awk '{print $5}' | sort -n | uniq -c
```

## The Missing Offsite Leg

This is where my setup does not meet 3-2-1.

The original plan synced the PBS datastore to Google Drive with rclone (`gdrive:Backup-Homelab/PBS`). The config and script are still deployed by the `pbs` role, but the cron job is deliberately `state: absent`. Two reasons. First, the Drive account doesn't have the free space for the datastore. Second, even before the quota ran out, the sync almost never finished: a PBS datastore is tens of thousands of small chunk files, and Google Drive's API throttles that pattern hard. A manual test sync ran at about 1.6 KiB/s with an ETA of roughly 12 weeks for the first full copy. I wrote that one up separately in [Google Drive API throttling vs. PBS chunk storage](/blog/google-drive-api-throttling-backup-chunk-storage/).

Cloudflare R2 is offsite and active, but it holds Velero backups only: the `apps`, `vault`, `database`, and `argocd` namespaces, with large volumes excluded, kept for 3 days. A guard pauses that schedule before usage hits R2's 10GB free tier. 212 GB of PBS data doesn't fit that budget. At R2's list price of $0.015/GB-month it would come to roughly $3 a month for storage, plus operation charges for the chunk uploads, so it is affordable but not free, and it is a decision I haven't made yet. Unlike [Garage](/blog/velero-garage-k3s-backup/), which runs inside the cluster it backs up, R2 sits outside the host entirely, and that independence is the whole point of [an offsite target](/blog/velero-backup-circularity-garage-r2-offsite/).

So the honest count today: the live guests on the NVMe plus the PBS copy on the HDD give two copies on two media, both in the same room. Velero adds a third copy of the critical Kubernetes data in Garage and an offsite one in R2. The VM and LXC images have no offsite copy. The realistic options are a long unattended initial sync to a better-suited target, bundling chunks before upload, or paying for object storage sized to the datastore. Until one of those is in place, a fire or theft takes the PBS backups along with the host.
