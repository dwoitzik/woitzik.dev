## A.8.22 - Segregation of Networks

This is the control the Hub & Spoke pattern is named after. ISO 27001:2022 explicitly calls for network segregation based on criticality and trust level - a flat network fails this control by definition, regardless of how strong the firewall rules on top of it are.

```hcl
resource "azurerm_virtual_network_peering" "hub_to_spoke1" {
  name                      = "peer-hub-to-spoke1"
  virtual_network_name      = azurerm_virtual_network.hub.name
  remote_virtual_network_id = azurerm_virtual_network.spoke1.id
  allow_forwarded_traffic   = true
}

resource "azurerm_virtual_network_peering" "hub_to_spoke2" {
  name                      = "peer-hub-to-spoke2"
  virtual_network_name      = azurerm_virtual_network.hub.name
  remote_virtual_network_id = azurerm_virtual_network.spoke2.id
  allow_forwarded_traffic   = true
}
```

No peering resource connects Spoke 1 directly to Spoke 2. That absence is the control - Spoke-to-Spoke traffic has no path that doesn't go through the Hub, where the Firewall can inspect it. An auditor testing this control isn't looking for a rule that blocks Spoke-to-Spoke traffic; they're looking for the fact that no route exists for such traffic to take in the first place.

## A.8.20 - Networks Security (Default-Deny)

Segregation without enforcement at the subnet boundary is incomplete - A.8.20 expects networks to be actively managed and controlled, not just topologically separated:

```hcl
resource "azurerm_network_security_group" "zero_trust" {
  name                = "nsg-zero-trust-${var.environment}"
  security_rule {
    name                       = "Allow-VNet-Inbound"
    priority                   = 100
    direction                  = "Inbound"
    access                     = "Allow"
    protocol                   = "*"
    source_address_prefix      = "VirtualNetwork"
    destination_address_prefix = "VirtualNetwork"
    source_port_range          = "*"
    destination_port_range     = "*"
  }
  security_rule {
    name                       = "Deny-Internet-Inbound"
    priority                   = 4096
    direction                  = "Inbound"
    access                     = "Deny"
    protocol                   = "*"
    source_address_prefix      = "Internet"
    destination_address_prefix = "*"
    source_port_range          = "*"
    destination_port_range     = "*"
  }
}

resource "azurerm_subnet_network_security_group_association" "spoke1_nsg" {
  subnet_id                 = azurerm_subnet.spoke1_default.id
  network_security_group_id = azurerm_network_security_group.zero_trust.id
}
```

The association resource matters as much as the NSG itself for this control - an unbound NSG satisfies nothing. Auditors checking A.8.20 compliance in an Azure environment specifically look for orphaned NSGs (defined but never associated), which is a common finding in hand-built environments and structurally impossible to miss in Terraform, since the association is right there in the same module.

## A.8.21 - Security of Network Services

Network services (DNS, in this context) need documented security and management arrangements - which for Private Link-based architectures means centralized DNS, not ad-hoc zones scattered per workload:

```hcl
resource "azurerm_private_dns_zone" "enterprise_zones" {
  for_each            = toset(var.private_dns_zones)
  name                = each.key
  resource_group_name = azurerm_resource_group.rg.name
}

resource "azurerm_private_dns_zone_virtual_network_link" "hub_links" {
  for_each              = azurerm_private_dns_zone.enterprise_zones
  name                  = "link-to-hub-${each.value.name}"
  private_dns_zone_name = each.value.name
  virtual_network_id    = azurerm_virtual_network.hub.id
}
```

Centralizing every Private Link DNS zone in the Hub, linked out to Spokes via peering, is what makes this control auditable at all - a reviewer can enumerate every DNS zone the environment depends on from one resource group, instead of discovering a rogue zone in Spoke 3 that nobody documented.

## A.8.9 - Configuration Management

This control expects configurations (including security configurations) to be established, documented, and maintained - a requirement Terraform satisfies structurally, but the module's DINE lifecycle blocks are the part worth calling out specifically, because they're the mechanism that keeps the *documented* configuration from silently drifting under externally-imposed changes:

```hcl
resource "azurerm_private_dns_zone" "enterprise_zones" {
  for_each = toset(var.private_dns_zones)
  name     = each.key

  lifecycle {
    ignore_changes = [
      tags["hidden-title"],
      tags["CreatedByPolicy"]
    ]
  }
}
```

Without this, Azure Policy's `DeployIfNotExists` tagging and Terraform's own idea of desired state fight each other indefinitely - which in an audited environment shows up as a resource whose actual configuration no longer matches what's declared in code. The `lifecycle` block is a narrow, deliberate exception that keeps the rest of the configuration under Terraform's control.

## A.5.15 - Access Control

A.5.15 asks for access rules based on business and security requirements - implemented here through Managed Identity and scoped role assignments rather than shared credentials:

```hcl
resource "azurerm_role_assignment" "spoke_app_kv_secrets" {
  scope                = azurerm_key_vault.kv.id
  role_definition_name = "Key Vault Secrets User"
  principal_id         = azurerm_linux_web_app.spoke_app.identity[0].principal_id
}
```

The audit trail for this control is the role assignment's scope and role definition, both visible directly in the Terraform plan - which role, on which resource, granted to which specific identity, is answered by the code rather than by asking whoever configured it and hoping they remember.

## A.8.16 - Monitoring Activities

The final piece: A.8.16 expects networks, systems, and applications to be monitored for anomalous behavior, with alerts investigated. Diagnostic Settings wired to a central Log Analytics workspace is the baseline that makes this possible:

```hcl
resource "azurerm_monitor_diagnostic_setting" "hub_nsg_diagnostics" {
  name                       = "diag-nsg-${var.environment}"
  target_resource_id         = azurerm_network_security_group.zero_trust.id
  log_analytics_workspace_id = azurerm_log_analytics_workspace.central.id

  enabled_log {
    category = "NetworkSecurityGroupEvent"
  }
}
```

## What This Covers - and What It Doesn't

This walkthrough covers the technological (A.8) and one organizational (A.5.15) control most directly implemented by the network module itself. Full ISO 27001 certification requires the entire management system: risk assessment methodology, the Statement of Applicability across all 93 Annex A controls, internal audits, management review, and the organizational controls (A.5) this module doesn't touch - HR security, supplier relationships, incident management processes.
