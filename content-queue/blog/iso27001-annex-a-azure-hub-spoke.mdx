## A.8.22: Segregation of Networks

This is the control the Hub & Spoke pattern most directly implements. A.8.22 requires groups of information services, users, and information systems to be segregated in the organization's networks. A flat network fails it, however strong the firewall rules on top of it are.

```hcl
resource "azurerm_virtual_network_peering" "hub_to_spoke1" {
  name                      = "peer-hub-to-spoke1"
  virtual_network_name      = azurerm_virtual_network.hub.name
  remote_virtual_network_id = azurerm_virtual_network.spoke1.id
  allow_forwarded_traffic   = true
}

resource "azurerm_virtual_network_peering" "hub_to_spoke2" {
  name                      = "peer-hub-to-spoke2"
  virtual_network_name      = azurerm_virtual_network.hub.name
  remote_virtual_network_id = azurerm_virtual_network.spoke2.id
  allow_forwarded_traffic   = true
}
```

No peering resource connects Spoke 1 directly to Spoke 2. That absence is the control. VNet peering is not transitive, so without a direct peering the only possible path between Spokes runs through the Hub, and only if a route table on each Spoke subnet sends that traffic to the Firewall as next hop. An auditor testing this control isn't looking for a rule that blocks Spoke-to-Spoke traffic. They're looking for the fact that no route exists for it except the one the Firewall inspects. (The excerpt shows the Hub-to-Spoke side; each peering also needs its Spoke-to-Hub counterpart.)

## A.8.20: Networks Security (Default-Deny)

Segregation without enforcement at the subnet boundary is incomplete. A.8.20 expects networks and network devices to be secured, managed, and controlled, not just topologically separated:

```hcl
resource "azurerm_network_security_group" "zero_trust" {
  name                = "nsg-zero-trust-${var.environment}"
  security_rule {
    name                       = "Allow-VNet-Inbound"
    priority                   = 100
    direction                  = "Inbound"
    access                     = "Allow"
    protocol                   = "*"
    source_address_prefix      = "VirtualNetwork"
    destination_address_prefix = "VirtualNetwork"
    source_port_range          = "*"
    destination_port_range     = "*"
  }
  security_rule {
    name                       = "Deny-Internet-Inbound"
    priority                   = 4096
    direction                  = "Inbound"
    access                     = "Deny"
    protocol                   = "*"
    source_address_prefix      = "Internet"
    destination_address_prefix = "*"
    source_port_range          = "*"
    destination_port_range     = "*"
  }
}

resource "azurerm_subnet_network_security_group_association" "spoke1_nsg" {
  subnet_id                 = azurerm_subnet.spoke1_default.id
  network_security_group_id = azurerm_network_security_group.zero_trust.id
}
```

The association resource matters as much as the NSG itself, because an unbound NSG satisfies nothing. Orphaned NSGs (defined but never associated) are a common finding in hand-built Azure environments. In Terraform the association sits in the same module as the NSG, so a missing one is visible in code review.

Two details an auditor may raise. Azure already ends every NSG with a built-in `DenyAllInBound` rule at priority 65500, so the explicit `Deny-Internet-Inbound` rule mostly documents intent in code. And the `VirtualNetwork` service tag includes peered address spaces, so `Allow-VNet-Inbound` does not restrict east-west traffic on its own. That job falls to the Hub Firewall and the routing described under A.8.22.

## A.8.21: Security of Network Services

A.8.21 asks for the security mechanisms, service levels, and requirements of network services to be identified, implemented, and monitored. For a Private Link-based architecture, the network service that matters most is DNS, and that means centralized zones, not ad-hoc ones scattered per workload:

```hcl
resource "azurerm_private_dns_zone" "enterprise_zones" {
  for_each            = toset(var.private_dns_zones)
  name                = each.key
  resource_group_name = azurerm_resource_group.rg.name
}

resource "azurerm_private_dns_zone_virtual_network_link" "hub_links" {
  for_each              = azurerm_private_dns_zone.enterprise_zones
  name                  = "link-to-hub-${each.value.name}"
  private_dns_zone_name = each.value.name
  virtual_network_id    = azurerm_virtual_network.hub.id
}
```

Centralizing every Private Link DNS zone in the Hub is what makes this control auditable. A reviewer can enumerate every DNS zone the environment depends on from one resource group, instead of discovering an undocumented zone in Spoke 3. Note that a zone linked only to the Hub VNet is not visible to peered Spokes by itself: the Spokes need to send DNS queries to a forwarder in the Hub (Azure Firewall DNS proxy or Azure DNS Private Resolver).

## A.8.9: Configuration Management

A.8.9 expects configurations, including security configurations, to be established, documented, implemented, monitored, and reviewed. Terraform covers most of that by design. The module's DINE lifecycle blocks deserve a closer look, because they keep the *documented* configuration from drifting under externally imposed changes:

```hcl
resource "azurerm_private_dns_zone" "enterprise_zones" {
  for_each = toset(var.private_dns_zones)
  name     = each.key

  lifecycle {
    ignore_changes = [
      tags["hidden-title"],
      tags["CreatedByPolicy"]
    ]
  }
}
```

Without this, tags written by Azure Policy remediation and Terraform's own idea of desired state fight each other on every apply. In an audited environment, that shows up as a resource whose actual configuration no longer matches what's declared in code. The `lifecycle` block is a narrow, deliberate exception that keeps the rest of the configuration under Terraform's control.

## A.5.15: Access Control

A.5.15 asks for rules controlling access based on business and information security requirements. Here that means Managed Identity and scoped role assignments rather than shared credentials:

```hcl
resource "azurerm_role_assignment" "spoke_app_kv_secrets" {
  scope                = azurerm_key_vault.kv.id
  role_definition_name = "Key Vault Secrets User"
  principal_id         = azurerm_linux_web_app.spoke_app.identity[0].principal_id
}
```

The audit trail for this control is the role assignment's scope and role definition, both visible in the Terraform plan. Which role, on which resource, granted to which identity: the code answers that, not whoever configured it from memory. The same evidence also supports A.5.18 (access rights).

## A.8.16: Monitoring Activities

A.8.16 expects networks, systems, and applications to be monitored for anomalous behavior, with appropriate action taken on potential incidents. Diagnostic Settings wired to a central Log Analytics workspace are the baseline for that, and they double as the log source for A.8.15 (logging):

```hcl
resource "azurerm_monitor_diagnostic_setting" "hub_nsg_diagnostics" {
  name                       = "diag-nsg-${var.environment}"
  target_resource_id         = azurerm_network_security_group.zero_trust.id
  log_analytics_workspace_id = azurerm_log_analytics_workspace.central.id

  enabled_log {
    category = "NetworkSecurityGroupEvent"
  }
}
```

For flow-level visibility, add VNet flow logs with Traffic Analytics on the same workspace. NSG flow logs can no longer be created since June 30, 2025, and Azure retires them on September 30, 2027. Diagnostic data on its own isn't monitoring either: A.8.16 also needs alert rules and someone who acts on them.

## What This Covers and What It Doesn't

This walkthrough covers the technological controls (A.8) and the one organizational control (A.5.15) most directly implemented by the network module itself. Full ISO 27001 certification requires the entire management system: risk assessment methodology, the Statement of Applicability across all 93 Annex A controls, internal audits, management review, and the organizational (A.5), people (A.6), and physical (A.7) controls this module doesn't touch, such as supplier relationships, incident management processes, and HR security.
