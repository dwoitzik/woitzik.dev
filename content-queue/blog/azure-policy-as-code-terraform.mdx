## Why Policy-as-Code on Top of Terraform Modules

A well-built Terraform module gets a resource configured correctly the first time it's deployed. It says nothing about what happens the next time someone runs `terraform apply` with a slightly different variable, or when a different team member deploys a resource by hand outside the module entirely. Azure Policy closes that gap. It evaluates continuously, not just at deploy time, and can deny a non-compliant resource creation outright instead of flagging it after the fact.

The two mechanisms complement each other. Terraform modules make the correct configuration the path of least resistance; Policy makes the incorrect configuration impossible (or at least loudly flagged) even when someone bypasses the module.

## Custom Policy Definitions

Azure ships hundreds of built-in policy definitions. The ones worth authoring yourself encode your own architecture decisions. Built-ins exist for public network access on storage, but usually with defaults and parameters that don't match your design, and a custom definition lets you state exactly what your Hub & Spoke requires, for example that every Storage Account disables public network access:

```hcl
resource "azurerm_policy_definition" "deny_public_storage" {
  name         = "deny-public-storage-access"
  policy_type  = "Custom"
  mode         = "All"
  display_name = "Deny Storage Accounts with public network access enabled"

  policy_rule = jsonencode({
    if = {
      allOf = [
        {
          field  = "type"
          equals = "Microsoft.Storage/storageAccounts"
        },
        {
          field    = "Microsoft.Storage/storageAccounts/publicNetworkAccess"
          notEquals = "Disabled"
        }
      ]
    }
    then = {
      effect = "deny"
    }
  })
}
```

`mode = "All"` evaluates resource groups, subscriptions, and all resource types, while `"Indexed"` only evaluates resource types that support tags and location. Storage accounts support both, so either mode would catch them here. Microsoft recommends `"All"` for most definitions and reserves `"Indexed"` for policies that enforce tags or locations. Using `"Indexed"` out of habit silently narrows what a policy catches as soon as it targets a resource type without tag support.

## Grouping Related Controls into an Initiative

A single deny policy is easy to reason about. A real compliance posture is a dozen or more related controls. Policy initiatives (policy set definitions) bundle related definitions so they can be assigned and tracked as one unit instead of a dozen separate assignments:

```hcl
resource "azurerm_policy_set_definition" "zero_trust_initiative" {
  name         = "zero-trust-baseline"
  policy_type  = "Custom"
  display_name = "Zero-Trust Network Baseline"

  policy_definition_reference {
    policy_definition_id = azurerm_policy_definition.deny_public_storage.id
  }

  policy_definition_reference {
    policy_definition_id = azurerm_policy_definition.require_nsg_association.id
  }

  policy_definition_reference {
    policy_definition_id = azurerm_policy_definition.require_private_endpoints.id
  }
}
```

Grouping these into `zero-trust-baseline` is what turns the individual controls from this blog's [NIS2](/blog/nis2-article-21-azure-terraform/) and [ISO 27001 Annex A](/blog/iso27001-annex-a-azure-hub-spoke/) mappings into one assignable, trackable unit. The Azure Policy compliance dashboard reports against the initiative as a whole, which is a far more useful audit artifact than a dozen unrelated assignment IDs.

## Assigning the Initiative

```hcl
resource "azurerm_subscription_policy_assignment" "zero_trust" {
  name                 = "zero-trust-baseline-assignment"
  policy_definition_id = azurerm_policy_set_definition.zero_trust_initiative.id
  subscription_id      = data.azurerm_subscription.current.id
  display_name         = "Zero-Trust Baseline - All Resources"
  location             = var.location # required when an identity is set

  identity {
    type = "SystemAssigned"
  }
}
```

The `identity` block matters as soon as a policy needs to *do* something rather than just evaluate. `deployIfNotExists` and `modify` effects both need a managed identity to carry out remediation, and Azure rejects an assignment of such a policy without one. A `deny` effect doesn't need it.

The quieter trap is RBAC. When you assign a policy in the portal, Azure grants the identity the roles listed in the definition's `roleDefinitionIds`. Terraform doesn't. Without a matching `azurerm_role_assignment` for `identity[0].principal_id`, the assignment looks fine and every remediation task fails on authorization.

## The Trap: Your Own Policy Fighting Your Own Terraform

The Hub & Spoke article's DINE section warned about this from the receiving end, and it's just as real when the policy and the Terraform deploying the guarded resource are both yours. A `modify` policy that tags resources for compliance tracking creates the same drift loop against your own pipeline as an externally imposed enterprise policy: Terraform removes the tags on every apply, and the policy puts them back.

```hcl
resource "azurerm_storage_account" "app_storage" {
  # ...

  lifecycle {
    ignore_changes = [
      tags["PolicyAssignedBy"],
      tags["ComplianceScanDate"]
    ]
  }
}
```

The fix is identical to the enterprise scenario: a narrow, deliberate `ignore_changes` on exactly the tags your own policy injects, nothing broader. Writing your own policies doesn't exempt you from this failure mode. If anything, it's easier to miss, because you assume a policy you wrote yourself won't surprise you.

## Testing Policy Changes Before They Deny Production

Any definition can run with `"effect": "Audit"`, which evaluates and reports non-compliance without blocking anything. Treat that as mandatory for every new policy:

```hcl
resource "azurerm_policy_definition" "deny_public_storage" {
  # ...
  policy_rule = jsonencode({
    if   = { /* ... */ }
    then = { effect = "[parameters('effectType')]" }
  })

  parameters = jsonencode({
    effectType = {
      type = "String"
      metadata = {
        displayName = "Effect"
      }
      allowedValues = ["Audit", "Deny"]
      defaultValue  = "Audit"
    }
  })
}
```

Parameterizing the effect means the same definition ships to production in `Audit` mode first, giving you a compliance report of what *would* have been denied. Once you've confirmed nothing legitimate breaks, flip the assignment's parameter to `Deny`. (An assignment's `enforce = false`, which maps to `DoNotEnforce`, is a second way to dry-run a policy without touching the definition.) Deploying straight to `Deny` is how a well-intentioned policy takes down an unrelated team's deployment on a Tuesday afternoon.

## What This Covers and What It Doesn't

This covers the mechanics of authoring, grouping, and assigning custom policy as Terraform code. A complete governance program also needs:

- **A documented exemption process** for the legitimate cases a blanket policy can't anticipate (the `azurerm_*_policy_exemption` resources, such as `azurerm_resource_policy_exemption`, exist for exactly this; use them sparingly and with an `expires_on` date)
- **A policy scope strategy:** subscription-level, management-group-level, or resource-group-level assignment, which depends on organizational structure this article doesn't cover
- **The organizational review process** around what gets promoted from `Audit` to `Deny`, which is a governance decision, not a Terraform one

## The Result

Custom Azure Policy definitions, grouped into initiatives and assigned as Terraform code, turn every compliance mapping on this blog from documentation into an enforced control:

- Custom definitions catch architecture-specific violations built-ins don't know about
- Initiatives group related controls into one auditable, trackable assignment
- `Audit`-first parameterization catches false positives before they become production outages
- The same `lifecycle { ignore_changes }` pattern from the receiving end of DINE policies applies equally when the policy is your own

This is the natural next layer on top of the [Hub & Spoke module](https://github.com/dwoitzik/terraform-azurerm-hub-spoke) already covered on this blog. The network architecture makes the right configuration easy; the policy layer denies the wrong one.
