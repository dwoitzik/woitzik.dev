I've [written before about zero-inbound-port Cloudflare Tunnel access](/blog/cloudflare-tunnel-zero-inbound-ports/) for Immich, Atlantis, and Jellyfin. Since then I've cut the public surface down to two hostnames. The wildcard ingress rule that made those three services reachable in the first place turned out to be the wrong default, and my criteria for what stays public have only gotten stricter.

**[View the complete homelab infrastructure source on GitHub](https://github.com/dwoitzik/homelab-infrastructure)**

## The Wildcard Was an Opt-Out Model

A single wildcard tunnel ingress rule plus a wildcard DNS record meant any hostname declared in an IngressRoute anywhere in this repo became internet-reachable automatically, gated only by whatever Traefik middleware that route happened to declare. That is opt-out: public by default, private only if something explicitly narrows it. It fixed a real problem fast (several services weren't reachable at all), but it traded that problem for a worse one.

An exposure audit of all ~46 hostnames declared at the time, cross-referenced against their Traefik middleware, confirmed the concern. Several hostnames had no Authelia gate and relied on their own app-level auth. At least one, a media-request UI, had no auth of any kind and not even basic rate limiting. Under an opt-out model, every new app and every IngressRoute added without thinking hard about exposure is public until someone notices and narrows it. Three real gaps had accumulated in less than a day of the wildcard existing.

## The Allowlist: Two Hostnames, Everything Else LAN/VPN-Only

The Cloudflare Tunnel's ingress config is now an explicit allowlist of exactly two hostnames:

- **`photos.woitzik.dev`** (Immich): family access to the photo library from outside the LAN or VPN is a real, named use case.
- **`headscale.woitzik.dev`**: structurally required. A device re-authenticating or joining the Tailscale mesh has to reach the control plane *before* any VPN path to it exists. This is the one hostname on the list that can't be VPN-only.

Every other hostname in the repo (Atlantis, Jellyfin, Vaultwarden, Nextcloud, Grafana, Vault, Authelia itself) has no Cloudflare DNS record and no tunnel ingress rule. They are reachable via LAN or the Tailscale/Headscale VPN only, through the same AdGuard split-horizon rewrite to Traefik's internal LoadBalancer that every internal client already uses. That path never touches Cloudflare or the public internet.

I checked Authelia specifically before dropping it instead of assuming. With only these two hostnames public, and neither the Headscale nor the Immich Traefik route using the Authelia forward-auth middleware, nothing publicly reachable depends on Authelia's login flow completing against a publicly resolvable hostname. Internal Authelia login is unaffected, since that path never touches Cloudflare either.

## Why Atlantis Dropped Off

In [the original tunnel article](/blog/cloudflare-tunnel-zero-inbound-ports/), Atlantis was one of the three hostnames routed through Traefik with Authelia in front. It isn't anymore. The reasoning is the same default-deny instinct applied one layer further: **only one hostname on this network is structurally required to be public.**

Atlantis never had a user-facing reason to be public. The requirement existed only because GitHub's webhook delivery is inbound push. [I've since removed that requirement by moving to a self-hosted GitHub Actions runner](/blog/atlantis-self-hosted-github-actions-runner/), which connects outbound instead of needing GitHub to reach in. With the runner in place, there is no argument left for Atlantis having a public hostname of any kind, allowlisted or otherwise. Vaultwarden, Nextcloud, and Grafana were never hard requirements either. All of them work through the Tailscale app from anywhere the client is installed, which is the operator experience I want.

## The Related Decision I Almost Got Wrong: My Agent's Terminal

Before settling on the allowlist, I'd made a narrower call about giving my AI coding agent's web terminal a public hostname. It returned 502 because a firewall rule blocks cross-VLAN traffic. The naive fix would have been a hole from my general-purpose application VLAN into the trusted-admin VLAN that host lives on. Any of the ~45 apps on the lower-trust side could then use that hole as a path toward the network segment holding the agent's SSH key, GitHub token, and Tailscale identity. Instead I gave the hostname its own Cloudflare Tunnel running directly on the agent's host. That way the admin VLAN never accepts an inbound connection from anywhere lower-trust; it only originates outbound connections, the same as it already does for GitHub and Cloudflare API calls.

That held for about two weeks. Then I removed it entirely. A dedicated tunnel avoids the cross-VLAN firewall problem, but it doesn't answer the more basic question: should a control-plane web terminal, something that can run arbitrary commands against my infrastructure, be publicly routable at all, whatever sits in front of it? The host already has its own Tailscale identity, so that is the remote-access path now. The tunnel and its DNS record are gone. Sometimes the right answer to "how do I expose this more carefully" is "don't expose it."

## The Trade-off

Away from home, everything except photos and the Tailscale control plane now requires the VPN client. That is a real convenience cost compared to "just open the URL," and it is the intended outcome. Every new service needs a deliberate decision to join the allowlist, not just an IngressRoute. That is a little extra process in exchange for a default that can't silently accumulate gaps the way the wildcard did.

The Azure equivalent is an explicit hostname allowlist on your Application Gateway or Front Door listeners instead of a wildcard rule that exposes anything with a matching custom domain. Same principle, one layer above network security groups: default-deny at the DNS and ingress layer, not only at the firewall underneath it.
