So verwalte ich meinen kompletten Homelab-Stack (MetalLB, Traefik, Longhorn, cert-manager, Authelia und Vaultwarden) als ein einziges Git-Repository mit ArgoCD.

## Die Repository-Struktur für GitOps

Alles liegt in einem Repository unter dem Verzeichnis `kubernetes/`:

```
homelab-infrastructure/
└── kubernetes/
    ├── apps/                    # User-facing applications
    │   ├── authelia/
    │   │   ├── authelia.yml     # Deployment + Service
    │   │   ├── configmap.yml    # ConfigMap
    │   │   ├── ingress.yml
    │   │   └── users_database_secret.yml
    │   └── vaultwarden/
    │       ├── ingress.yml
    │       └── pvc.yml
    ├── system/                  # Cluster infrastructure
    │   ├── argocd/              # ApplicationSet + ArgoCD config
    │   ├── argocd-config/       # ArgoCD's own ingress
    │   ├── cert-manager/        # Helm chart Application
    │   ├── cert-manager-config/ # ClusterIssuer
    │   ├── longhorn/            # Helm chart Application
    │   ├── metallb/             # Helm chart Application
    │   ├── metallb-config/      # IPAddressPool + L2Advertisement
    │   └── traefik/             # Helm chart Application
    └── test-app/                # nginx for smoke testing
```

Die Trennung zwischen `apps/` und `system/` ist Absicht. Systemkomponenten sind Cluster-Infrastruktur und müssen existieren, bevor Anwendungen laufen können. Anwendungen sind Workloads, die davon abhängen. Wenn beides getrennt liegt, ist diese Abhängigkeit schon am Repo-Aufbau zu sehen.

## Zwei Wege, wie Applications entstehen

Eine einzelne Root-Application gibt es in diesem Repo nicht. Applications kommen aus zwei Quellen.

**Alles unter `kubernetes/apps/`** greift ein einziges ApplicationSet ab, `kubernetes/system/argocd/apps-applicationset.yaml`. Sein Git-Directory-Generator macht aus jedem Unterverzeichnis eine eigene Application, benannt nach dem Verzeichnis:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: homelab-apps
  namespace: argocd
spec:
  generators:
    - git:
        repoURL: 'https://github.com/dwoitzik/homelab-infrastructure.git'
        revision: main
        directories:
          - path: kubernetes/apps/*
  template:
    metadata:
      name: '{{path.basename}}'
    spec:
      project: default
      source:
        repoURL: 'https://github.com/dwoitzik/homelab-infrastructure.git'
        targetRevision: main
        path: '{{path}}'
      destination:
        server: 'https://kubernetes.default.svc'
        namespace: apps
      syncPolicy:
        automated:
          prune: true
          selfHeal: true
        syncOptions:
          - CreateNamespace=true
```

Eine neue App ist ein neues Verzeichnis und ein Push. Ein Application-Manifest musst du dafür nicht schreiben.

**Alles unter `kubernetes/system/`** hat pro Komponente eine eigene `application.yml` (`cert-manager/application.yml`, `metallb/application.yml` und so weiter). Nichts hat diese Dateien erzeugt oder verfolgt: Jede musste einmal per `kubectl apply` angelegt werden. Genau das war die Schwachstelle dieses Setups, mehr dazu im Bootstrap-Abschnitt unten.

## Wie die Applications aufgebaut sind

Jede Komponente folgt einem von zwei Mustern, je nachdem, ob sie ein Helm-Chart oder rohe Manifeste ist.

**Muster 1: Helm-Chart aus einer externen Registry**

Für Upstream-Charts (MetalLB, Traefik, Longhorn, cert-manager) zeigt die Application direkt auf das Helm-Repository:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: cert-manager
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://charts.jetstack.io
    targetRevision: v1.14.4
    chart: cert-manager
    helm:
      values: |
        installCRDs: true
        extraArgs:
          - --dns01-recursive-nameservers=1.1.1.1:53,8.8.8.8:53
          - --dns01-recursive-nameservers-only
  destination:
    server: https://kubernetes.default.svc
    namespace: cert-manager
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true
```

Die Chart-Version ist fest gepinnt (`v1.14.4`). Nimm für Systemkomponenten nie `latest`. Du willst selbst bestimmen, wann Upgrades passieren, statt dich von ArgoCD bei irgendeinem Sync überraschen zu lassen.

**Muster 2: Rohe Manifeste aus Git**

Für CRD-Konfigurationen und Custom Resources, die ein Helm-Chart ergänzen, zeigt eine eigene Application auf einen Pfad im Git-Repository:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: cert-manager-config
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/dwoitzik/homelab-infrastructure.git
    targetRevision: main
    path: kubernetes/system/cert-manager-config
  destination:
    server: https://kubernetes.default.svc
    namespace: cert-manager
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
```

Dieses Muster (Helm-Chart-Application plus eigene Config-Application) gibt es für MetalLB und cert-manager. Die Trennung existiert, weil die CRDs aus dem Helm-Chart da sein müssen, bevor die Konfigurationsressourcen angewendet werden können. Sync Waves nutzt dieses Repo dafür nicht. Liegt die Konfiguration in einer eigenen Application, scheitert ein Sync mit fehlenden CRDs nur dort, ohne das Chart zu blockieren, und die Konfiguration zieht nach, sobald die CRDs da sind. Das ist einfacher, als die Reihenfolge innerhalb einer einzigen Application zu steuern.

## Der Deployment-Ablauf mit GitOps

Sobald der Cluster läuft, sieht der gesamte Deployment-Ablauf so aus:

```
1. Edit a file in the repository
2. git commit -m "describe the change"
3. git push
```

ArgoCD fragt das Repository standardmäßig alle 3 Minuten ab. Wenige Minuten nach einem Push erkennt es den Unterschied zwischen Sollzustand (Git) und Istzustand (Cluster) und gleicht ihn automatisch ab.

Kein `kubectl apply`. Kein `helm upgrade`. Kein SSH auf die Nodes. Die Git-History ist das Deployment-Log.

## ArgoCD-Bootstrap: das Henne-Ei-Problem

Ein Henne-Ei-Problem bleibt: ArgoCD muss existieren, bevor es irgendetwas verwalten kann. Die Bootstrap-Reihenfolge:

```bash
# 1. Install ArgoCD itself (one-time manual step)
kubectl create namespace argocd
kubectl apply -n argocd -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml

# 2. Create the ApplicationSet for kubernetes/apps/*
kubectl apply -f kubernetes/system/argocd/apps-applicationset.yaml

# 3. Create each system Application once
kubectl apply -f kubernetes/system/metallb/application.yml
kubectl apply -f kubernetes/system/cert-manager/application.yml
# ...one per component under kubernetes/system/
```

Nach Schritt 2 bauen sich die Apps aus Git selbst zusammen. Der Haken ist Schritt 3: Jede System-Application ist ein einmaliges `kubectl apply`, und sobald sie existiert, beobachtet nichts in ArgoCD die Datei, die sie definiert. Änderst du diese `application.yml` in Git, bleibt die laufende Application, wie sie war. Eine Prüfung im Juli 2026 fand 18 von 41 laufenden Applications in genau diesem Zustand. Die Lösung war eine weitere Application, `system-app-bootstrap`, die auf `kubernetes/system/` zeigt und jede `*/application.yml` einschließt. Damit werden auch die Definitionen selbst aus Git synchronisiert.

## Automatischer oder manueller Sync

Alle Applications in diesem Setup nutzen `automated` Sync mit `selfHeal: true`. Das heißt:

- ArgoCD wendet Änderungen automatisch an, sobald es eine Abweichung von Git erkennt
- Ändert jemand im Cluster etwas von Hand (`kubectl edit`, ein Klick in einem Dashboard), setzt ArgoCD das innerhalb von Minuten zurück
- `prune: true` bedeutet, dass Ressourcen, die aus Git gelöscht werden, auch aus dem Cluster verschwinden

Das ist bewusst streng. Der Cluster setzt Git als Quelle der Wahrheit durch, manuelle Änderungen überleben keinen Sync-Zyklus.

Für Produktiv-Workloads, bei denen du Änderungen vor dem Anwenden prüfen willst, stellst du auf manuellen Sync um und gibst Deployments über die UI oder die CLI von ArgoCD frei.

## Das Ergebnis

Mit ArgoCD als Verwalter des gesamten Stacks:

- **Reproduzierbarkeit:** Der Sollzustand des Clusters liegt komplett in Git, und ein Neuaufbau ist eine kurze, bekannte Liste von `kubectl apply`-Befehlen
- **Nachvollziehbarkeit:** Jede Änderung ist ein Git-Commit mit Autor, Zeitstempel und Diff
- **Schutz vor Drift:** `selfHeal: true` setzt manuelle Änderungen automatisch zurück
- **Klare Abhängigkeiten:** Systemkomponenten und ihre Konfiguration liegen in eigenen Applications, getrennt von den Workloads, die sie brauchen

Das gesamte Homelab, vom Bare Metal bis zu laufendem Authelia und Vaultwarden, ist ein Git-Repository. Brennt der Cluster ab: ArgoCD installieren, das ApplicationSet und die System-Applications anlegen, warten.

Eine Einschränkung habe ich erst später gelernt: Ein `Synced`-Badge beweist nicht, dass eine gemergte Änderung auch live ist. Über [drei gemergte Fixes, die nie wirksam wurden](/blog/gitops-merged-not-applied-argocd-drift/) (englischer Artikel), und wie man das prüft, habe ich separat geschrieben.
