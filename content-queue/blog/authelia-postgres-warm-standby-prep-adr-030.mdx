Authelia is the single sign-on gate in front of every service on my [BMAX Mini PC\*](/go/4bv3yF1)-based k3s cluster. If its Postgres backend is down, nothing behind it is reachable either, credentials or not. I already built a warm standby for the SQLite-backed side of this homelab (Headscale, Vaultwarden) and flagged Authelia's Postgres backend at the time as a heavier, architecturally different job that didn't belong in the same pass. ADR-030 is that follow-up: the groundwork for a Postgres warm standby, done properly rather than bolted on. It is prep work, not a tested failover yet, and one constraint it ran into deserves its own writeup.

## A Different Secrets Convention for This One Component

Most of this cluster's secrets flow through [HashiCorp Vault and External Secrets Operator](/blog/external-secrets-operator-vault-kubernetes/): store the value in Vault, let ESO sync a real Kubernetes `Secret` into the cluster, and nothing sensitive touches Git. The standby's replication password doesn't follow that path. This role generates and stores its password through the repo's **Ansible Vault** convention instead, encrypted in the Ansible variable tree and decrypted at playbook run time. The CNPG/Authelia role was built around that pattern before ESO existed in this cluster, and nothing forced a migration just for this change.

That is a real inconsistency: two different things called "vault," two secrets-management conventions, both live in the same repo depending on which component you're touching. The practical lesson is narrower than "pick one": **check which convention applies to the role you're editing before assuming it's the ESO path.** Guess wrong and you get a manifest that looks correct but references a `Secret` ESO never created.

## The IP You Can't Put in the Config Yet

The standby on `rpi-srv-02` replicates from the CNPG primary through a dedicated `LoadBalancer` Service, `postgres-authelia-standby-replication`, same [MetalLB L2 pattern](/blog/metallb-traefik-k3s-argocd/) as everything else on this cluster. The problem: MetalLB assigns that IP from its pool only once the Service object exists. You could pin an address up front with the `metallb.universe.tf/loadBalancerIPs` annotation, but this setup takes whatever the pool hands out, so the address the standby has to connect to isn't known when the Ansible role is written. The IP is a result of applying the config, not an input to writing it.

The role's default handles this by not guessing:

```yaml
# ansible/roles/postgres_authelia_standby/defaults/main.yml
# MetalLB-assigned once standby-replication-service.yml is applied, not
# knowable ahead of time. Set for real via `kubectl get svc
# postgres-authelia-standby-replication -n database`; a placeholder just fails fast.
postgres_authelia_standby_primary_host: "REPLACE-ME-with-the-real-LoadBalancer-IP"
```

Running the role with that default fails at the seeding step, because `pg_basebackup -h` can't resolve the placeholder, instead of producing a silent misconfiguration that shows up later as a connection that mysteriously doesn't work. The sequence has to be: apply the Service first, read back the IP MetalLB handed it, and set that value before the role seeds the standby and writes its `primary_conninfo`. The allowlists on the other side don't need it: they all name the standby's own LAN address, `10.0.20.3`, which is known. A placeholder that fails loudly beats a default plausible enough that nobody questions it. On a replication credential path, that kind of default stays silent until the day you need the failover and it doesn't work.

## Three Layers, One Trusted Host, Never the Tailnet

Because the standby's Postgres port has to be reachable at all (streaming replication needs a real network path, unlike the SQLite-over-SFTP design used for Headscale and Vaultwarden), the exposure is contained three independent ways instead of trusting any single control:

1. **`loadBalancerSourceRanges` on the Service itself.** MetalLB only announces the IP via ARP; the source filtering is enforced by kube-proxy, and the Service spec restricts allowed sources to exactly one already-trusted LAN host's `/32`.
2. **A NetworkPolicy `ipBlock` rule.** The same single-host restriction, enforced again inside the cluster's own network layer instead of relying on the Service's source-range filtering alone.
3. **A `pg_hba.conf` entry.** Postgres's own connection-level access control, scoped to that same host and the replication user, so a connection that somehow cleared the first two layers still has to authenticate as a role with only replication privileges.

One caveat the repo doesn't handle yet: layers 2 and 3 only work if the standby's source IP survives the trip to the pod. The Service doesn't set `externalTrafficPolicy`, so it runs with the default `Cluster`, and kube-proxy masquerades external traffic to a node address before forwarding it. The NetworkPolicy `ipBlock` and the `pg_hba` line would then see a node IP instead of `10.0.20.3` and reject the connection. That fails closed, not open, but it means replication can't connect as committed. `loadBalancerSourceRanges` is evaluated by kube-proxy before that rewrite, so layer 1 is unaffected. The fix is `externalTrafficPolicy: Local` on the Service, which preserves the client IP and makes MetalLB L2 announce the address only from the node running the primary pod.

No single layer would justify calling this "contained." A `loadBalancerSourceRanges` bypass, a NetworkPolicy misconfiguration or an overly permissive `pg_hba` line would each leave a real gap on its own. Together, a failure in any one layer still leaves two independent controls standing. All three point at the same already-trusted LAN address. This never crosses the Tailscale tailnet or the public internet, on purpose: reachability beyond one specific host wasn't a requirement, so it isn't in the design.

## What This Is (and Isn't) Yet

This is groundwork, not a drilled failover path. The password convention is decided, the fail-fast placeholder is in place and works as designed, and the three-layer containment model is defined. Not in this pass: a tested failover runbook, and proof that streaming replication holds up under a real primary-down drill the way the SQLite/Litestream standby did. That is the harder half of calling something a warm standby, and it is still ahead.

Streaming replication is a different reliability model from the WAL-shipping-to-files approach on the SQLite side of this homelab: a continuous replication connection instead of periodic segment shipping, with failure modes around connection stability and replication lag instead of file-sync timing. [Designing Data-Intensive Applications\*](/go/4aUtkCs) is still the clearest treatment I know of why those two models fail differently under the same network interruption, and it shaped how cautiously this pass treated "the IP isn't known yet" instead of working around it with a guess.
