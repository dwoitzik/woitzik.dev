I already wrote about [moving Garage's SQLite metadata off NFS after it corrupted from lock-delegation failures](/blog/nfs-vs-local-path-sqlite-trap/). That fix (`local-path` instead of `nfs-client`) was correct as far as it went. It ended *that specific* problem, not Garage's metadata problems in general. Garage runs my self-hosted S3-compatible store, which backs [Terraform's remote state](https://github.com/dwoitzik/homelab-infrastructure), [Velero's backup index](/blog/velero-garage-k3s-backup/), and the CNPG Postgres WAL archives. A corrupted or unavailable metadata store here doesn't just lose object listings; it stalls every Atlantis plan and apply (no state, no plan) and backup verification at the same time.

The second time it corrupted, the fix took two changes together: LMDB instead of SQLite, and a dedicated disk instead of `local-path`'s shared directory tree.

## Two Separate Problems

**Problem one: it corrupted again.** This time I traced it to fallout from an earlier `.recover` repair: the same SQLite recovery tool that saved the database once ended up contributing to a second crash-loop. Garage sat crash-looping for 14+ hours before I gave up on an in-place repair and did a full wipe and re-provision instead.

**Problem two, found while investigating the first: `garage-meta`'s `local-path` PVC had no explicit node pinning anywhere in the Deployment.** It lived wherever the pod happened to first schedule, sharing that node's local-lvm-backed storage directory with every other `local-path` consumer there, with no capacity accounting or discard behavior of its own. And it had drifted in practice: an earlier design doc recorded it on one k3s worker, but by the time I looked again it sat on a different node, the **control-plane** node, with nothing in git driving that placement either way. `local-path`'s PV affinity simply follows wherever the pod first landed.

Garage's metadata is on the hot path for every S3 request my backups and Terraform state depend on. Sharing a directory tree with whatever else lands on the same node, with no discard behavior and no capacity ceiling of its own, was never a deliberate choice. It was just the `local-path` default.

## The Fix: Two Changes, Done Together

**1. `db_engine`: `sqlite` → `lmdb`.** LMDB has been Garage's documented default since v0.9.0. SQLite was this cluster's historical choice, not a deliberate pick against LMDB. I migrated the live metadata (4 buckets, 4 keys, existing objects) with Garage's `garage convert-db` command instead of reinitializing an empty store. `-a`/`-i` name the input engine and path, `-b`/`-o` the output:

```bash
garage convert-db -a sqlite -i /path/to/db.sqlite -b lmdb -o /path/to/db.lmdb
```

Garage's own documentation is upfront that LMDB is "prone to database corruption after an unclean shutdown," so I added its documented mitigation on top:

```toml
metadata_auto_snapshot_interval = "6h"
```

The other documented mitigation, `replication_factor >= 2`, isn't available on single-node hardware, so the snapshots do the whole job here. Garage keeps the two most recent ones.

**2. Storage: `local-path` PVC → dedicated hostPath.** A new 8G virtio-scsi disk (`discard=on`), attached directly to the node running Garage, formatted ext4 with `noatime` and `discard`, mounted at `/mnt/garage-meta-dedicated`. The Deployment now carries an explicit `nodeSelector` pinning it to that node (previously the placement was only incidental, via `local-path`'s PV affinity) and mounts the new path via `hostPath` instead of a PVC:

```yaml
spec:
  template:
    spec:
      nodeSelector:
        kubernetes.io/hostname: vm-srv-k3s-11
      volumes:
        - name: meta
          hostPath:
            path: /mnt/garage-meta-dedicated
            type: Directory
```

## What This Isn't

This is **not** a relocation off my one fast NVMe onto something slower. I still have exactly one fast disk in this host, and Garage's metadata store is exactly the kind of low-latency, corruption-sensitive workload that belongs on it. What changed is *isolation*: a dedicated volume instead of sharing `local-path`'s common directory tree with whatever else lands on the node.

I looked at two other options for "off local-path" and rejected both. Moving to my only other StorageClass, NFS, was a non-starter. I'd already seen first-hand that NFS locking breaks embedded databases, and LMDB's memory-mapped file access is at least as exposed to network-filesystem coherency problems as SQLite's WAL; LMDB's own documentation warns against using it on remote filesystems. Moving to my USB-attached archive HDD was ruled out by my own standing rule: never place stateful PVs or databases on USB-attached storage or SD cards. Garage's actual object blobs already live there deliberately (large sequential writes, slow-is-fine); metadata is the opposite access pattern.

## The Honest Trade-off

I applied the disk change live via `qm set` rather than through Terraform. Atlantis's Garage API key was invalidated by the same wipe-and-reprovision, so nothing could plan or apply against any stack. The new disk attach isn't in Terraform yet. That gap is known and tracked, following the same "apply now, codify in IaC once the credential gap closes" pattern I've used for a few other emergency fixes on this host. It needs a follow-up PR before this counts as fully drift-free.

The Deployment is now hard-pinned to one specific node. If that VM is ever rebuilt, the disk attach and mount have to be recreated first, or the pod won't start: `hostPath` with `type: Directory` refuses to mount a path that doesn't exist instead of silently creating an empty directory on the root disk. I'd rather have that fail loudly than run without the isolation I just built.

---

The Azure-shaped version of "an embedded database that's corruption-sensitive to shared storage" is giving a self-managed database VM a dedicated Premium SSD v2 disk instead of putting its files on Azure Files. Same principle, different cloud: file-level locking and low-latency writes want dedicated block storage, not a shared network filesystem, however convenient the shared option looks on day one.

[Designing Data-Intensive Applications\*](/go/4aUtkCs) has the clearest explanation I've read of why a storage engine's on-disk design (B-tree vs. log-structured, copy-on-write pages like LMDB vs. a write-ahead log like SQLite's) matters as much for crash safety as for performance. Read it before you pick a `db_engine` value and move on.
