BSI C5 (Cloud Computing Compliance Criteria Catalogue) is the standard the German public sector and regulated industries ask cloud providers to meet, and increasingly expect of the cloud services their suppliers build on Azure. It is more specific than ISO 27001, more Germany-focused than NIS2, and rarely covered from the engineer's side instead of the auditor's.

Azure holds a C5 attestation for its platform. That covers Microsoft's side of the shared-responsibility model: the physical datacenters, the hypervisor, the platform controls. It says nothing about how you configured the resources inside your subscription. This article maps the C5 areas that land on your side of that line to the Terraform-managed Azure architecture already covered on this blog. It uses the C5:2020 area codes and criteria IDs. BSI has since published C5:2026 as the successor, so check which version your auditor attests against.

> **Disclaimer:** C5 attestation is a formal audit performed by a qualified auditor (typically a Wirtschaftsprüfer) against the full catalogue. This article is not that audit. It covers a subset of technical criteria most relevant to network and identity architecture, as a starting point for engineering the controls, not a substitute for attestation.

## The Criteria Areas That Map to Infrastructure Code

C5:2020 organizes its criteria into 17 areas, from personnel (HR) to procurement and development (DEV). Four areas map directly onto Terraform-managed Azure architecture:

**COS: Communication Security** (KOS in the German edition)
Technical safeguards, cross-network access, segregation of traffic, and documentation of the network topology (COS-01 to COS-08). This is the area a Hub & Spoke topology exists to satisfy.

**IDM: Identity and Access Management**
Granting, reviewing, and withdrawing access rights, privileged access, and authentication mechanisms (IDM-01 to IDM-09). The principle is that access rights match documented roles, not ad-hoc portal permissions granted during an incident and never revoked.

**CRY: Cryptography and Key Management**
Transport encryption (CRY-02), encryption of sensitive data at rest (CRY-03), and secure key management (CRY-04). This is Key Vault's reason for existing in a compliance-driven architecture.

**OPS: Operations**
Among much else, logging and monitoring (OPS-10 to OPS-17). It is one of the most concretely testable parts of the catalogue: an auditor can ask "show me the last 90 days" and either the logs exist or they don't.

## COS: Network Segmentation and Boundary Protection

C5's COS area asks, in substance, the same question NIS2 and KRITIS do: is the network segmented by function and criticality, and is there a documented, enforced boundary between zones? The Hub & Spoke topology with default-deny NSGs answers this directly. Azure's built-in `DenyAllInBound` rule already blocks unsolicited inbound traffic; an explicit rule in code makes the boundary visible in the Terraform an auditor reads:

```hcl
resource "azurerm_network_security_group" "c5_boundary" {
  name                = "nsg-c5-boundary-${var.environment}"
  location            = var.location
  resource_group_name = var.resource_group_name

  security_rule {
    name                       = "Deny-Internet-Inbound"
    priority                   = 4096
    direction                  = "Inbound"
    access                     = "Deny"
    protocol                   = "*"
    source_address_prefix      = "Internet"
    destination_address_prefix = "*"
    source_port_range          = "*"
    destination_port_range     = "*"
  }
}
```

C5 also requires transport encryption (CRY-02), and that applies to internal PaaS connections as much as to the public-facing edge. Enforce a minimum TLS version on every service:

```hcl
resource "azurerm_storage_account" "c5_storage" {
  name                     = "stc5${var.environment}"
  min_tls_version          = "TLS1_2"
  public_network_access_enabled = false
}
```

## IDM: Access Rights That Match Documented Roles

C5's identity criteria are less about *having* RBAC than about *provable, minimal* RBAC. Every principal's access should be traceable to a documented reason (IDM-02) and reviewed regularly (IDM-05), not accumulated permissions nobody remembers granting. Managed Identity plus scoped role assignments in Terraform gives you that traceability almost for free, because the assignment is its own record:

```hcl
resource "azurerm_role_assignment" "function_kv_reader" {
  scope                = azurerm_key_vault.kv.id
  role_definition_name = "Key Vault Secrets User"
  principal_id         = azurerm_linux_function_app.app.identity[0].principal_id

  description = "Function app reads TLS cert secrets - see ADR-014"
}
```

The `description` field is easy to skip, and it is what turns a role assignment into an auditable artifact instead of a bare permission grant. When an auditor asks "why does this identity have this access," a Terraform diff plus a linked architecture decision record answers the question; "someone needed it at the time" does not.

## CRY: Keys That Live in Key Vault, Not in App Settings

C5's cryptography criteria (CRY-01, CRY-04) expect keys and secrets to be centrally managed with a documented lifecycle. The failure mode this eliminates is a connection string in an App Service configuration blade, never rotated, known to everyone who ever had Contributor access:

```hcl
resource "azurerm_key_vault" "kv" {
  name                          = "kv-${var.environment}-${random_string.suffix.result}"
  public_network_access_enabled = false
  enable_rbac_authorization     = true

  network_acls {
    default_action = "Deny"
    bypass         = "AzureServices"
  }
}

resource "azurerm_key_vault_key" "cmk" {
  name         = "cmk-storage-${var.environment}"
  key_vault_id = azurerm_key_vault.kv.id
  key_type     = "RSA"
  key_size     = 2048

  rotation_policy {
    automatic {
      time_before_expiry = "P30D"
    }
    expire_after = "P1Y"
  }
}
```

`rotation_policy` with an explicit `expire_after` turns key rotation from a calendar reminder into infrastructure that enforces itself. That is closer to what "documented key management" means to a C5 auditor than a runbook nobody has followed since it was written.

## OPS: Logging as a Testable Control

The logging criteria (OPS-10 to OPS-17) are where the gap between "we have a monitoring strategy" and "show me the logs" is most visible. The easy mistake is wiring up Diagnostic Settings only for the resources that seemed important during the initial deployment:

```hcl
resource "azurerm_monitor_diagnostic_setting" "kv_diagnostics" {
  name                       = "diag-kv-${var.environment}"
  target_resource_id         = azurerm_key_vault.kv.id
  log_analytics_workspace_id = azurerm_log_analytics_workspace.central.id

  enabled_log {
    category = "AuditEvent"
  }
}
```

Apply Diagnostic Settings via `for_each` over every resource in a module that supports them, not as a one-off whenever someone remembers. Azure Policy with a DeployIfNotExists assignment catches the resources created outside your modules. An auditor sampling logging coverage across the estate will find the resource you forgot faster than the ones you configured correctly.

## What This Covers, and What It Doesn't

This covers a subset of C5's technical criteria relevant to network and identity architecture. Full C5 attestation also requires:

- **Organization and policies (OIS, SP):** information security organization, policies, and governance processes
- **Personnel (HR):** background checks, confidentiality agreements, security awareness training
- **Physical security (PS):** largely inherited from Microsoft's attestation when you run on Azure
- **Business continuity management (BCM):** documented and tested, not just implied by the infrastructure
- **Incident management, suppliers, and compliance (SIM, SSO, COM)**, among the remaining areas
- **The formal attestation itself**, performed by a qualified independent auditor against the complete catalogue
