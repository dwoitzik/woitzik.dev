[Headscale](/blog/headscale-oidc-k3s-authelia/) crash-looped with a startup fetch failure. On boot it makes a one-time OIDC discovery request to Authelia's issuer URL, `auth.woitzik.dev`. Inside the cluster, that hostname resolves to its public A record: Traefik's external LoadBalancer VIP, the same address my [split-DNS setup](/blog/cloudflare-tunnel-zero-inbound-ports/) hands to external clients. The request hairpins out to the VIP and back in, and that path turned out to be intermittently unreliable. Repeated probes from an in-cluster pod showed the first request succeeding and the next several failing instantly with connection refused. That was enough to fire both an availability alert and a probe-failure alert for Headscale.

## The Fix: A CoreDNS Override Instead of a One-Pod Workaround

Traefik's ClusterIP never touches the VIP or the hairpin path. It is plain in-cluster Service routing via kube-proxy, which doesn't share the VIP's failure mode. Traefik routes by Host header and SNI, not by which of its own IPs the request arrived on, so reaching it via ClusterIP instead of the external VIP changes nothing about which backend serves the request.

Once the routing was clear, the fix was simple. Any hostname called service-to-service from inside the cluster gets a CoreDNS override pointing it at Traefik's ClusterIP. k3s provides the `coredns-custom` ConfigMap as its extension point: keys ending in `.override` are imported into CoreDNS's main server block, so no image fork or Corefile rewrite is needed.

I kept the scope narrow and additive on purpose. Only hostnames with a confirmed in-cluster caller get an entry, which at the time meant just `auth.woitzik.dev` for Headscale's OIDC check. External clients still resolve the same names publicly and still hit the real external VIP. The override only changes what pods *inside* the cluster resolve.

I considered two alternatives and rejected both. Pointing Headscale's OIDC issuer straight at Authelia's ClusterIP would mean plain HTTP internally, because Authelia doesn't terminate TLS (Traefik does), and OIDC discovery requires HTTPS with a certificate matching the issuer URL. Downgrading that for reliability would have been a security regression dressed up as a fix. A second Traefik replica would reduce single-point-of-failure risk in general, which is worth doing separately, but it doesn't fix the hairpin path. The flakiness reproduced against a single healthy replica in testing, so a second one wouldn't have prevented this incident.

## The Same Question, Twice More That Week

Once "a hostname can mean something different depending on who resolves it" had sunk in, two more decisions from the same investigation turned out to be the same question in different form.

**Rybbit's tracker API has to bypass Authelia.** Rybbit, my self-hosted analytics for this site, needs its tracker script and event-ingest endpoint reachable by anonymous browsers. Every client-side analytics tool has this requirement, since a visitor's browser has no Authelia session and can't complete an SSO redirect. I bypassed Authelia's forward-auth for the tracker's API paths on the LAN/Tailscale side. The public Cloudflare Tunnel path already skips Traefik and Authelia by design, [per the same allowlist model everything else public follows](/blog/public-exposure-allowlist-two-hostnames/).

This is safe because Rybbit's backend gates dashboard reads on its own. I checked that directly instead of assuming it: an unauthenticated request to the dashboard API returns a hard `403` with no Authelia involved. Authelia was only ever a redundant outer layer for the dashboard *UI*, never the authorization boundary for the API, so bypassing it exposes nothing Rybbit doesn't already protect. The residual risk is that anyone can POST junk events to the ingest endpoint. That comes with this whole class of tool rather than with my setup, and Rybbit's bot detection sorts non-browser traffic into a separate table instead of mixing it into real analytics.

**Jellyfin's and Nextcloud's OIDC integrations both ship SSRF guards that block requests to private IP ranges.** That is correct behavior and exactly the kind of guard you want on by default. But Authelia's issuer resolves to an internal address, so OIDC discovery and token exchange can't complete with the guard on. For Jellyfin I relaxed it narrowly, scoped to the single Authelia provider config. Nextcloud has no per-provider equivalent. Its guard is global, so disabling it affects every remote-URL feature in the app, not only OIDC.

Both settings are admin-configured and not reachable through any anonymous or user-input path, so they add no attack surface for an external actor. They are still a deliberate reduction in defense-in-depth. Before adding a third OIDC provider on another internal hostname, re-check whether the same trade-off still makes sense.

## The Common Pattern

All three share one shape: a hostname or auth boundary that means one thing from outside the network and something structurally different from inside it, plus a piece of software that assumed both views would always agree. Headscale assumed `auth.woitzik.dev` would resolve to something it could reach twice in a row. Jellyfin's and Nextcloud's SSRF guards assumed "private IP" always means "untrusted." Authelia in front of Rybbit assumed every caller could hold an SSO session. None of those assumptions is wrong in general. They are wrong for a homelab that deliberately serves the same hostnames publicly and internally, for the reasons in the allowlist post above.

Every new service that calls another `*.woitzik.dev` hostname from inside the cluster has to be checked against this failure mode. Nothing catches it automatically; here it took Headscale's crash loop to surface it.

The Azure version of the CoreDNS fix is a Private DNS zone that resolves a service's custom domain to its Private Endpoint IP for in-VNet callers, while the public zone still resolves it to the public Front Door or Application Gateway address. It is split-horizon DNS under another name, solving the same problem: don't hairpin through the public edge for calls that never needed to leave the network.
