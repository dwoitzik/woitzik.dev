I'd already [restored three VMs read-only to inspect their disks](/blog/proxmox-pbs-restore-tier1-data-verification/), extracted what I needed, and never issued a single `qm start` against any of them. So when the newly-provisioned production VMs started failing SSH in a way that made no sense, the last place I looked was the VMs I was certain I'd never turned on.

## The Symptoms Didn't Point at the Real Cause

Two freshly cloned VMs, on the IP range production always used, started misbehaving right after joining the network. One timed out at the TCP/banner-exchange stage from every source I tried, including the Proxmox host itself. The other connected fine but rejected the correct SSH key. Both threw `REMOTE HOST IDENTIFICATION HAS CHANGED` warnings on repeated connections. That's normally the sign of a regenerated host key, and cloud-init does regenerate host keys whenever it sees a new instance ID, so that's where I spent the first hour: chasing a cloud-init instance-ID bug that was real, but not the cause of the outage.

A hard reset of each VM (`qm reset`) "fixed" the SSH issue, and both came back clean immediately. That should have been the first clue. A reset doesn't fix a cloud-init configuration bug. It only changed which of two machines currently held the connection.

## The Actual Number That Cracked It

`ping -c10` to one of the VMs returned round-trip times of 7–10 **seconds**. Not milliseconds. No SSH setting explains that; it's a host starved of resources, not a slow network path.

```bash
cat /proc/pressure/io
# some avg10=30.40 total=...
# full avg10=25.24 total=...
```

The `full` line means that for a quarter of the last ten seconds, every non-idle task on the host was stalled on I/O at the same time. `ps aux --sort=-%cpu` named the cause immediately: the three read-only forensic VMs from the earlier extraction were running as live, full QEMU processes. One was in D-state consuming 156% CPU. Another sat at 131% CPU, also in D-state. All three had started at the exact moment the host came back up from an unrelated reboot roughly an hour earlier.

## Root Cause: A Config Field That Survives a Restore Verbatim

`qm config` on all three showed `onboot: 1`, plus `ipconfig0` set to the same production IP addresses I had just assigned to the two new VMs. `qmrestore` restores the guest config from the PBS backup as it was, and the original pre-disaster VMs had `onboot: 1` because that's the correct setting for production VMs. Nothing in the read-only inspection work started them; every action against them had been a `qemu-nbd` mount, never a `qm start`. The *host reboot* did it, through Proxmox's normal autostart, because a config field meant for production guests came along with a restore meant only for forensic inspection.

That single inherited flag explained every symptom that had eaten the previous hour:

- **Two machines answering on the same IP** produce exactly this pattern: the SSH host key flapping depending on whose packets won a given exchange, pubkey rejections when the *other* machine's `authorized_keys` answered, and banner-exchange timeouts because I/O starvation delayed every response past the client timeout.
- **The `qm reset` "fixes"** worked by coincidence. They shifted which machine briefly won the IP race without touching the conflict.
- **Two separate Ansible runs** against the new VMs failed the same way, timing out mid-play with the same auth-flapping signature.

## The Fix, and the Actual Process Gap

```bash
qm stop 911 912 913        # graceful shutdown timed out first - host too I/O-starved
                            # for QMP to answer; hard stop succeeded
qm set 911 --onboot 0      # repeat for 912, 913
```

`/proc/pressure/io` began decaying immediately after the stop. Connectivity to the real production VMs returned to sub-millisecond pings within seconds.

The process fix matters more than the incident: **any PBS restore to a scratch or inspection-only VMID gets `onboot` disabled immediately after the restore completes, before anything else happens**, whatever the backed-up config says. That config is correct for the machine it originally described. It is not correct for a disposable copy of that machine at a different VMID. This is now a permanent pre-reboot checklist item: before any host reboot, every scratch or temporary VMID gets a `qm config` sweep for stray `onboot: 1` flags.

None of the Tier-1 data was at risk. Nothing these three VMs did while they were up touched the extraction location, and the extraction had been completed and verified well before the reboot. This was an availability incident, not a data-integrity one, and it cost about ninety minutes of host contention. It's still a sharp reminder that a restore procedure has to account for every field in the config, not just the disk contents.

This is the same class of failure as [the IP/MAC conflict I found while testing a disaster-recovery runbook for the first time](/blog/backup-restore-test-never-verified-network-conflict/): a restore that faithfully duplicates a source's network identity and lands on a network where that identity is already in use. That one turned up in a deliberate, controlled test. This one turned up as a real incident, the more expensive way to learn the same lesson.

Azure mostly prevents this one at the platform level. The platform owns private IP assignment, and a NIC can't be given a static private IP that another NIC in the subnet already holds, so a restored VM can't take over a live address. A Proxmox host has no such guardrail, which is why "disable autostart on every restored scratch VM, immediately, no exceptions" has to be a habit rather than an assumption.

[Designing Data-Intensive Applications\*](/go/4aUtkCs) has a useful chapter on this class of failure: two systems disagreeing about which one owns a piece of shared state. It's framed around distributed databases, not IP addresses, but the failure mode has the same shape.
