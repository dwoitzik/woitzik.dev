CNPG needs WAL archiving to object storage. Gitea needs artifact storage. The options: AWS S3 (recurring cost), Backblaze B2 (egress fees), or MinIO (self-hosted, no recurring cost). MinIO on k3s runs as a single pod with a local PersistentVolume, exposing an S3 API on port 9000. It's not distributed, not redundant, and not production-grade. For a homelab, it's exactly right.

This is a deliberately different role than [Garage](/blog/velero-garage-k3s-backup/), the other S3-compatible store in this cluster — Garage backs Velero specifically, and MinIO backs everything else. Splitting them means a Garage incident (like [the SQLite corruption that hit its metadata volume](/blog/nfs-vs-local-path-sqlite-trap/)) doesn't also take out CNPG's WAL archiving.

**[View the complete homelab infrastructure source on GitHub 🐙](https://github.com/dwoitzik/homelab-infrastructure)**

## Why MinIO

AWS S3 costs money. Backblaze B2 is cheap for storage but charges for egress. For a homelab where backups go to local disk and the only S3 consumers are Velero, CNPG, and Gitea, MinIO eliminates the external dependency entirely.

The downside: MinIO on a single node has no redundancy. If the PVC is lost (disk failure, Proxmox host crash), all S3 data is gone. Velero handles this by keeping a local copy of the last backup. CNPG handles it by keeping WAL archives on local disk as a fallback.

## Deployment

MinIO runs as a StatefulSet with a single PersistentVolume:

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: minio
  namespace: minio
spec:
  replicas: 1
  serviceName: minio
  selector:
    matchLabels:
      app: minio
  template:
    metadata:
      labels:
        app: minio
    spec:
      containers:
        - name: minio
          image: minio/minio
          command: ["minio", "server", "/data"]
          ports:
            - containerPort: 9000
            - containerPort: 9001
          env:
            - name: MINIO_ROOT_USER
              valueFrom:
                secretKeyRef:
                  name: minio-credentials
                  key: root-user
            - name: MINIO_ROOT_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: minio-credentials
                  key: root-password
          volumeMounts:
            - name: data
              mountPath: /data
  volumeClaimTemplates:
    - metadata:
        name: data
      spec:
        accessModes: ["ReadWriteOnce"]
        resources:
          requests:
            storage: 100Gi
```

The 100Gi PVC is backed by local-path storage (no Longhorn replication — MinIO handles its own data durability).

## The Console

MinIO's web console runs on port 9001. Access it via Traefik:

```yaml
apiVersion: traefik.io/v1alpha1
kind: IngressRoute
metadata:
  name: minio-console
  namespace: minio
spec:
  entryPoints:
    - websecure
  routes:
    - match: Host(`minio.lab.woitzik.dev`)
      kind: Rule
      services:
        - name: minio
          port: 9001
  tls:
    secretName: lab-wildcard-tls
```

The console lets you create buckets, upload files, and manage access policies.

## Bucket Configuration

Two buckets for two consumers:

```bash
# CNPG WAL archives
mc mb minio/cnpg-wal

# Gitea artifacts
mc mb minio/gitea-artifacts
```

Each consumer gets its own access key with limited permissions:

```bash
# Create CNPG user with read/write on cnpg-wal only
mc admin user add minio cnpg-user cnpg-password
mc admin policy attach minio readwrite cnpg-wal --user cnpg-user
```

## Integrating with CNPG

CNPG's Barman backup target points at MinIO for continuous WAL archiving:

```yaml
apiVersion: postgresql.cnpg.io/v1
kind: Cluster
metadata:
  name: nextcloud-db
  namespace: nextcloud
spec:
  backup:
    barmanObjectStore:
      destinationPath: "s3://cnpg-wal/nextcloud-db"
      endpointURL: "http://minio.minio.svc:9000"
      s3Credentials:
        accessKeyId:
          name: minio-credentials
          key: ACCESS_KEY_ID
        secretAccessKey:
          name: minio-credentials
          key: SECRET_ACCESS_KEY
```

CNPG streams WAL segments to MinIO continuously, not just on a schedule. When the PVC is lost, CNPG can replay from the last base backup plus every archived WAL segment. See [the CNPG deep dive](/blog/cnpg-postgresql-operator-k3s/) for the full failover story — this MinIO bucket is the backup half of that setup.

## The Storage Reality

MinIO on a single node with local-path storage is not HA. If the disk dies, the data is gone. The mitigation: CNPG's WAL archiving writes to MinIO and to local disk simultaneously, and Gitea's artifacts are reconstructible from Git — neither consumer treats this MinIO bucket as its only copy.

The real risk is the 100Gi PVC. On a [BMAX Mini PC*](https://amzn.to/4bv3yF1) with a 512GB NVMe, 100Gi is 20% of the disk. That's acceptable for a homelab where the alternative is paying for S3.

## Monitoring

MinIO exposes Prometheus metrics:

```
minio_cluster_disk_free_bytes 42949672960
minio_cluster_disk_total_bytes 107374182400
minio_s3_requests_total{bucket="cnpg-wal"} 1250
```

Alert: if `disk_free_bytes` drops below 10GB, something is filling up the bucket. Usually a WAL archive that isn't getting cleaned up after a base backup.
