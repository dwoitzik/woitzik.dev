Architecture documentation drifts from reality. I've already hit this at the Terraform level with [firewall rules Terraform didn't know about](/blog/mikrotik-firewall-rule-drift-orphaned-rules/), and network topology diagrams have the same problem, just less visibly, until someone needs the diagram to be right. [Scanopy](https://scanopy.net) (AGPL-3.0, self-hosted) automates the diagram: per-VLAN daemons do ARP discovery and TCP service fingerprinting, and a central server builds a self-updating topology map instead of a Visio file nobody has touched in six months.

**[View the complete homelab infrastructure source on GitHub 🐙](https://github.com/dwoitzik/homelab-infrastructure)**

## Two VLANs I Deliberately Didn't Scan

I deployed daemons on my management, general-application, and DMZ VLANs. I left my IoT and admin-workstation VLANs out entirely, on purpose. Neither has any persistent self-hosted compute today: IoT is untrusted consumer devices, and admin is just my own workstation. A scanner's value is proportional to how much self-hosted infrastructure a segment has. Standing up new, dedicated scanning infrastructure for two segments with nothing worth documenting isn't worth the added attack surface.

I also considered scanning those two remotely, with a Layer-3-only scan from an existing VLAN's daemon instead of new daemons on them. I rejected that too. It would need a new firewall hole into segments that currently have none, for subnets with nothing in them worth the hole.

## DaemonPoll, Not ServerPoll

Scanopy offers two connection modes: DaemonPoll, where the daemon connects outbound to the server and nothing ever reaches in to it, and ServerPoll, where the server connects inbound to the daemon on a fixed port. Upstream's docs suggest ServerPoll for DMZ deployments "where the daemon cannot make outbound connections." That doesn't describe my DMZ: the box already makes narrow, deliberate outbound connections (to CrowdSec's central API, for one). And DaemonPoll is the safer direction regardless, because nothing ever initiates a connection *into* the DMZ daemon from anywhere else on the network. I run DaemonPoll everywhere, including the two internal VLANs, where DaemonPoll is upstream's default anyway.

## No `privileged: true`, No Docker-Socket Mount

Upstream's `docker-compose.yml` runs the daemon with `privileged: true` and a read-only Docker-socket bind mount. The socket is there so the daemon can tag which container sits behind a discovered open port. Neither is required for the scanning itself: ARP discovery and raw TCP port scanning need the `NET_RAW` and `NET_ADMIN` capabilities, not full privileged mode.

```yaml
# what I run instead of upstream's default
cap_add:
  - NET_RAW
  - NET_ADMIN
# no privileged: true
# no /var/run/docker.sock mount
```

A read-only Docker-socket bind mount is still full Docker API access. The `:ro` flag only stops the container from modifying the socket file; it doesn't limit which API calls go over it. So "read-only mount" is misleading shorthand for "effectively root on whatever host it's mounted on." Granting that to a network scanner sitting next to my DMZ's CrowdSec stack would defeat the point of running a scanner carefully. I accepted the trade-off instead: no automatic correlation between an open port and the container that owns it. Checking that by hand is slower, but it's a contained cost, not a standing root-equivalent credential on a DMZ host.

## The Narrowest Firewall Rule Per Daemon, No WAN Exposure at All

The management and DMZ daemons reach the central server through a dedicated LoadBalancer Service whose `loadBalancerSourceRanges` allow only those two hosts' addresses, matched by equally narrow MikroTik forward rules: one source host, one destination, one port. Unlike Headscale's deliberate public exposure, [one of exactly two hostnames on my public allowlist](/blog/public-exposure-allowlist-two-hostnames/), this has no public or WAN-facing component. It's internal by design and should stay that way. A topology scanner reachable from the internet would hand an attacker a map of everything else worth attacking.

## Consequences Worth Knowing If You Copy This

The general-application-VLAN daemon runs with host networking, so the NetworkPolicy egress rules that cover everything else on that node don't apply to it. Its egress is governed only by the node's OS and the MikroTik firewall, and anyone editing that NetworkPolicy file later shouldn't assume it touches this daemon. I also stood up one new, minimal, single-purpose host purely to run the management-VLAN daemon, since that's the one segment with no existing host to piggyback on.

The Azure equivalent of self-updating topology mapping is Network Watcher's topology view plus VNet flow logs (the successor to NSG flow logs, which Microsoft is retiring). The instinct is the same whether the network underneath is a homelab VLAN trunk or a set of peered VNets: stop trusting a hand-maintained diagram and generate the picture from what's actually observed.
