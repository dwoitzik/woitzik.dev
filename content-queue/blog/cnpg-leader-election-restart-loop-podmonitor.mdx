The CloudNativePG operator had restarted 310 times in 21 days. Every restart followed the same pattern: the operator lost its leader-election lease, controller-runtime terminated the process instantly, and Kubernetes restarted it. With a single replica, there was nothing to take over — a brief apiserver latency blip just killed the only operator pod.

The fix was loosening leader-election timeouts. The investigation also uncovered a PodMonitor that was never actually scraped by Prometheus despite showing as Synced and Healthy in ArgoCD.

## The Symptom

```
kubectl get pods -n cnpg-system
# NAME                                    READY   STATUS             RESTARTS
# cnpg-cloudnative-pg-5f8b9c4d6-xk2p4   1/1     Running            310
```

310 restarts. Not gradual — bursty. The operator would survive for hours, then restart 5 times in 10 minutes, then stabilize again. The pattern correlated with I/O spikes on the host — a [BMAX Ryzen 7 8745HS Mini PC&#42;](https://amzn.to/4bv3yF1) running K3s, PostgreSQL, and local LLM inference simultaneously. The I/O fragility is a known pattern on these mini PCs when multiple workloads compete for NVMe bandwidth.

## The Root Cause: Leader-Election Timeout

Every restart's previous-container log ended the same way:

```
Leader election retry deadline exceeded
context deadline exceeded
```

The operator's leader-election lease renewal was timing out against the apiserver. When the renewal fails, controller-runtime terminates the entire process — by design, so a healthy replica can take over. With a single replica (no HA), there's nothing to take over. The only operator pod dies, Kubernetes restarts it, and the cycle repeats.

The defaults are aggressive:

| Flag | Default | What it means |
|---|---|---|
| `--leader-lease-duration` | 15s | How long the lease is valid |
| `--leader-renew-deadline` | 10s | How long to retry renewal before giving up |

On a host with known I/O fragility, a 10-second renewal window is too tight. A brief apiserver latency spike exceeds the deadline, and the operator kills itself.

## The Fix

```yaml
# kubernetes/system/cloudnative-pg/application.yml
additionalArgs:
  - --leader-lease-duration=60
  - --leader-renew-deadline=50
```

Scaled 5x, same ratio already applied to etcd's own heartbeat/election timeouts in the Ansible inventory for the identical underlying cause. Confirmed these flags exist on the live v1.25.0 binary via `--help` before deploying — not guessed.

After the change: **0 restarts in 7 days**.

## The Second Problem: PodMonitor Never Scraped

While investigating the restarts, I checked the CNPG metrics pipeline. The operator's `enablePodMonitor: true` was set, and ArgoCD showed the PodMonitor as Synced/Healthy. But Prometheus had no CNPG metrics.

The operator-generated PodMonitor only carries `cnpg.io/cluster` as a label. This cluster's Prometheus requires `release: kube-prometheus-stack` on every PodMonitor via its `podMonitorSelector`:

```bash
kubectl get prometheus -o jsonpath='{.spec.podMonitorSelector}'
# → {"matchLabels":{"release":"kube-prometheus-stack"}}
```

The operator-generated PodMonitor didn't have `release: kube-prometheus-stack`. Prometheus never selected it. ArgoCD showed it as healthy because the object existed and matched its own sync criteria — not because Prometheus was scraping it.

### The Trap

CNPG's CRD has no field to add metadata labels to the auto-generated PodMonitor. `podMonitorRelabelings` only rewrites already-scraped samples — it can't make Prometheus notice the object in the first place. There's no way to make the operator-generated PodMonitor work with this Prometheus setup.

### The Fix: Git-Managed PodMonitor

```yaml
# kubernetes/system/postgres/postgres-monitoring.yml
apiVersion: monitoring.coreos.com/v1
kind: PodMonitor
metadata:
  name: postgres-authelia
  namespace: database
  labels:
    cnpg.io/cluster: postgres-authelia
    release: kube-prometheus-stack  # the missing label
spec:
  namespaceSelector:
    matchNames:
      - database
  selector:
    matchLabels:
      cnpg.io/cluster: postgres-authelia
  podMetricsEndpoints:
    - port: metrics
```

Disabled the operator's own (`enablePodMonitor: false`) and replaced it with a git-managed PodMonitor carrying both labels. Metrics started appearing immediately.

## Lessons

**1. Leader-election timeouts are I/O-dependent.** If your host has I/O fragility, the defaults (15s/10s) may be too tight. Scale them up and verify the flags exist on your version's binary first.

**2. "Synced/Healthy" in ArgoCD ≠ "working."** The PodMonitor object existed and was correctly applied. But Prometheus never selected it because of a missing label. ArgoCD's health check doesn't verify that Prometheus is actually scraping the target.

**3. Operator-generated resources may not match your Prometheus setup.** CNPG, like many operators, generates monitoring resources with its own label scheme. If your Prometheus uses a `podMonitorSelector`, the generated resources may silently fail.

**4. Single-replica leader-election is a design decision, not a bug.** CNPG terminates on lease loss by design — it assumes another replica will take over. In a single-replica setup, this becomes a death loop. The fix is loosening timeouts, not changing the operator's behavior.
