On 2026-10-15 nobody could join my Paper Minecraft server, including players sitting on the same home network as the server. It turned out to be two unrelated breakages at once. The external path through playit.gg was down because `playit-agent` 1.0.10 was handed an IPv6 relay address and never fell back to IPv4, on a DMZ with no IPv6 uplink. The internal path had simply never existed: no firewall rule let LAN clients into the DMZ, and the reverse proxy in front of the game server had never published its stream ports. I fixed the internal path with two published ports and two forward rules, so LAN players no longer depend on a third-party tunnel at all.

**[View the complete homelab infrastructure source on GitHub](https://github.com/dwoitzik/homelab-infrastructure)**

## The setup

The game server runs in `ct-dmz-games-01` at `10.0.30.3`, in the DMZ VLAN (`10.0.30.0/24`). The DMZ is isolated on purpose: the MikroTik forward chain ends in a drop, and every hole into the DMZ is an explicit Terraform resource, the model from [my zero-trust MikroTik firewall](/blog/mikrotik-zero-trust-firewall-terraform/).

There are two ways in:

- **External:** `mc.woitzik.dev` is a Cloudflare CNAME to a playit.gg tunnel hostname. The playit agent opens an outbound tunnel to playit's relays, so no WAN port forward is needed and the home IP never appears in the path.
- **Internal:** AdGuard rewrites `mc.woitzik.dev` to `10.0.30.3` for LAN clients. A second name points at the Nginx Proxy Manager stream proxy at `10.0.30.2`, which forwards raw TCP to the game server with CrowdSec in front.

On paper, internal players never touch playit. In practice, the internal path had never been tested end to end.

## Breakage 1: the agent dials an IPv6 relay and gives up

The agent log showed a reconnect loop. playit's control API handed the agent an IPv6 relay address:

```text
[2602:fbaf:840::1]:5525
```

The DMZ has no IPv6 uplink, so the connect failed with `AddrNotAvailable`, the control session never came up, and the agent looped on `SessionNotSetup`. It never tried an IPv4 relay.

This is a known upstream bug, [playit-agent issue #194](https://github.com/playit-cloud/playit-agent/issues/194): "Latest Agent - Container: Fails ipv6 and doesn't fall back to ipv4". It was opened on 2026-07-15 against version 1.0.10, the same version I was running, and is still open as I write this. The log in the issue shows the same pattern with a different relay address: an IPv6 tunnel server on port 5525, `Network unreachable`, and `control session expired; reconnecting` with `reason=SessionNotSetup`. There is no maintainer reply on it. One user linked from the issue pinned the agent back to 1.0.8 because "1.0.10 is broken on IPv4-only hosts".

The detail that saved me time: disabling IPv6 locally does not help. The relay address comes from playit's API, not from local DNS resolution, so no amount of `sysctl` or resolver tweaking on the LXC changes which address the agent dials. The fix has to happen on playit's side. The workaround recorded in my ADR is an account setting: under `playit.gg/account/settings`, set the IPv6 option to IPv4 only.

That fixes remote players. It does nothing for the more embarrassing half.

## Breakage 2: the LAN path was never opened

That left the internal path, and it failed for two separate reasons.

**The firewall dropped them.** The MikroTik forward chain had no accept rule into `10.0.30.0/24` from the internal VLANs or from the FritzBox LAN (`192.168.178.0/24`). The only allow from the FritzBox side went to `10.0.20.200` on ports 80 and 443. So a player on the FritzBox LAN, or on any internal VLAN except Admin, had the connection dropped, whether they used the proxy IP or the game server IP.

**The proxy wasn't listening.** Even a connection the firewall allowed would have failed. NPM's stream configs (`1.conf` and `2.conf`) existed and pointed at `10.0.30.3`, but the `npm` container had never published ports 25565 and 25566. The stream blocks listened inside the container with no host port bound, and clients got `Connection refused`.

Both gaps had been there all along. Nobody noticed while the tunnel worked.

## Fix part 1: publish the stream ports (#903)

The ports went into the DMZ proxy group vars:

```yaml
# ansible/group_vars/dmz_proxies.yml
npm_stream_ports:
  - "25565:25565"
  - "25566:25566"
```

and the compose template loops over them next to the existing HTTP ports:

```jinja
      - '80:80'
      - '81:81'
      - '443:443'
{% for p in npm_stream_ports | default([]) %}
      - '{{ p }}'
{% endfor %}
```

After the Ansible run, `10.0.30.2:25565` proxied to the Paper server, verified live.

## Fix part 2: two forward rules and a masquerade (#904)

Two accept rules, scoped to the two Minecraft ports and the DMZ subnet, placed before the final drop:

```hcl
resource "routeros_ip_firewall_filter" "fwd_internal_to_dmz_minecraft" {
  action       = "accept"
  chain        = "forward"
  protocol     = "tcp"
  src_address  = "10.0.0.0/8"
  dst_address  = "10.0.30.0/24"
  dst_port     = "25565,25566"
  place_before = routeros_ip_firewall_filter.fwd_99_drop_all.id
  comment      = "20: Internal - Minecraft to DMZ (game LXC + NPM stream proxy)"

  lifecycle {
    ignore_changes = [place_before]
  }
}

resource "routeros_ip_firewall_filter" "fwd_heimnetz_to_dmz_minecraft" {
  action       = "accept"
  chain        = "forward"
  protocol     = "tcp"
  src_address  = "192.168.178.0/24"
  dst_address  = "10.0.30.0/24"
  dst_port     = "25565,25566"
  place_before = routeros_ip_firewall_filter.fwd_99_drop_all.id
  comment      = "21: Heimnetz - Minecraft to DMZ (NPM stream proxy)"

  lifecycle {
    ignore_changes = [place_before]
  }
}
```

The FritzBox LAN is a foreign subnet from the DMZ's point of view, so its return traffic needs NAT back out, the same way the existing FritzBox-to-server-VLAN rule works:

```hcl
resource "routeros_ip_firewall_nat" "srcnat_masquerade_heimnetz_to_dmz" {
  chain       = "srcnat"
  action      = "masquerade"
  src_address = "192.168.178.0/24"
  dst_address = "10.0.30.0/24"
  comment     = "NAT: Masquerade Heimnetz to DMZ (Minecraft) for return traffic"
}
```

The consequence is that the proxy sees FritzBox-LAN players as the router's IP, not their own. That was already true for every other FritzBox-to-internal service, and LAN players are trusted, so I accepted it.

The resulting path for every LAN player is `client -> 10.0.30.2 (NPM stream proxy) -> 10.0.30.3:25565`. Direct connections to the game server are allowed too, only because AdGuard already resolves `mc.woitzik.dev` to `10.0.30.3` for internal clients.

Blast radius: two TCP ports into one subnet. No other DMZ service became reachable from the LAN. Like every rule in this stack, it went through a PR and the GitHub Actions apply workflow behind the `terraform-apply` gate, not through Winbox.

## Cleaning up the DNS half (#920)

While going through the public side, I found that the `_minecraft._tcp.mc` SRV record existed in Cloudflare but had been created in the dashboard and never tracked. The CNAME was in Terraform and the SRV was not. #920 adopted it with an import block, and its target reuses `var.mc_playit_hostname`, the same variable the CNAME uses, so a playit reassignment keeps both records pointing at the same relay. The plan against the live zone was a pure adoption:

```text
1 to import, 0 to add, 0 to change, 0 to destroy
```

## What is still open

ADR-055 does not fix playit. It removes the dependency for LAN players. The account-side IPv4-only setting is the documented path for remote players, and the ADR names the fallback if playit does not recover: drop the tunnel in favour of a port forward on the FritzBox, written up as its own ADR.

The pattern stuck. When I added an Enshrouded server to the same LXC four days later, it got the same LAN-to-DMZ treatment from the start: a scoped forward rule for its UDP ports, with playit only for remote players.

## Checklist

- **When a tunnel agent loops, check which address family it dials.** An IPv6 relay on an IPv4-only network fails with errors like `AddrNotAvailable` or `Network unreachable`, and the session never sets up.
- **Know where the relay address comes from.** If the control API hands it out, local IPv6 settings won't change it. Look for an account or server-side setting, or pin a known-good agent version.
- **Test the LAN path on purpose.** If every player uses the tunnel, the internal path is untested, and you will find its gaps on the day the tunnel breaks.
- **A proxy config is not a listener.** For NPM streams, check that the container actually publishes the port: `docker ps` should list it.
- **Open the DMZ by port and subnet, before the final drop.** Two ports, one destination subnet, named rules with comments.
- **Masquerade traffic from foreign subnets** like an ISP router's LAN, or the replies leave by the wrong path.
- **Track every DNS record the service depends on.** A dashboard-created SRV next to a Terraform CNAME is drift waiting for the next relay change.
