## Gitea Actions: The GitHub Actions Clone

Gitea 1.22 introduced Actions, a CI system that reads `.gitea/workflows/*.yml` files — the same YAML format as GitHub Actions. The key differences:

- Workflows live in `.gitea/workflows/` instead of `.github/workflows/`
- The runner is a separate binary (`act_runner`) that polls Gitea for jobs
- Artifacts and logs are stored in Gitea's database, not S3
- Secrets are managed in the Gitea UI

The YAML syntax is identical. Most GitHub Actions workflows work in Gitea with minimal changes.

## Deploying Gitea on k3s

Gitea runs as a StatefulSet with PostgreSQL:

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: gitea
  namespace: gitea
spec:
  replicas: 1
  serviceName: gitea
  selector:
    matchLabels:
      app: gitea
  template:
    metadata:
      labels:
        app: gitea
    spec:
      containers:
        - name: gitea
          image: gitea/gitea:1.22
          ports:
            - containerPort: 3000
            - containerPort: 22
          env:
            - name: GITEA__DATABASE__DB_TYPE
              value: "postgres"
            - name: GITEA__DATABASE__HOST
              value: "gitea-db.gitea.svc:5432"
            - name: GITEA__DATABASE__NAME
              value: "gitea"
          volumeMounts:
            - name: data
              mountPath: /data
  volumeClaimTemplates:
    - metadata:
        name: data
      spec:
        accessModes: ["ReadWriteOnce"]
        resources:
          requests:
            storage: 10Gi
```

## The Action Runner

The `act_runner` binary runs as a Deployment, polling Gitea for jobs:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: gitea-runner
  namespace: gitea
spec:
  replicas: 2
  selector:
    matchLabels:
      app: gitea-runner
  template:
    metadata:
      labels:
        app: gitea-runner
    spec:
      containers:
        - name: runner
          image: gitea/act_runner:latest
          env:
            - name: GITEA_INSTANCE_URL
              value: "http://gitea.gitea.svc:3000"
            - name: GITEA_RUNNER_REGISTRATION_TOKEN
              valueFrom:
                secretKeyRef:
                  name: gitea-runner-token
                  key: token
            - name: GITEA_RUNNER_NAME
              value: "k3s-runner"
            - name: GITEA_RUNNER_LABELS
              value: "ubuntu-latest:docker://node:20-bookworm"
```

The runner registration token is generated in the Gitea UI under Site Administration → Runners → Create New Runner.

## Workflow Migration

A GitHub Actions workflow migrates to Gitea by moving the file:

```
.github/workflows/ci.yml  →  .gitea/workflows/ci.yml
```

The YAML content stays the same. The only change: if the workflow references `github.event_name` or `github.repository`, those context variables are `gitea.event_name` and `gitea.repository` in Gitea. Most workflows don't reference these directly.

## Docker-in-Docker

Many CI workflows need Docker (building images, running containers). The Gitea runner supports Docker-in-Docker via the `--privileged` flag or by mounting the Docker socket:

```yaml
# .gitea/workflows/docker-build.yml
name: Build and Push
on: [push]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Build
        run: docker build -t myapp:${{ github.sha }} .
      - name: Push
        run: |
          echo ${{ secrets.DOCKER_PASSWORD }} | docker login -u ${{ secrets.DOCKER_USERNAME }} --password-stdin
          docker push myapp:${{ github.sha }}
```

The runner label `ubuntu-latest:docker://node:20-bookworm` tells the runner to execute jobs inside a Docker container. For Docker-in-Docker, change the runner label to include `--privileged`:

```yaml
GITEA_RUNNER_LABELS: "ubuntu-latest:docker://ghcr.io/catthehacker/ubuntu:act-latest"
```

## Resource Limits

On a homelab [BMAX Mini PC*](/go/4bv3yF1), the Gitea runner shouldn't consume all resources. Set resource limits on the runner Deployment:

```yaml
resources:
  requests:
    cpu: "500m"
    memory: "512Mi"
  limits:
    cpu: "2"
    memory: "2Gi"
```

Two runners with 2GB each = 4GB. On a 64GB machine, that's negligible. The runners share the CPU with k3s workloads, so `cpu: "2"` is a request, not a reservation.

## The Trade-off

Gitea Actions is not as mature as GitHub Actions. Missing features: matrix builds, reusable workflows, and the marketplace of pre-built actions. For a homelab infrastructure repo that runs Terraform, Ansible, and container builds, these missing features don't matter — Terraform changes still go through [Atlantis](/blog/mikrotik-terraform-gitops-firewall-management/) for the actual apply, so Gitea Actions only needs to handle lint and plan. The YAML syntax is the same, the runner runs on your hardware, and there's no minute limit.
