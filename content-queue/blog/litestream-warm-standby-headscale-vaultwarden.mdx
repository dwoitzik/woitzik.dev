My entire k3s cluster runs on one Proxmox host. That's a documented, accepted constraint, not an oversight: zero-downtime HA is not achievable on this hardware. But "no zero-downtime HA" doesn't have to mean "everything critical goes down together with no plan." A NetworkPolicy drift once took my Tailscale subnet router and Cloudflare tunnel down for days, and every incident like that means noticing and diagnosing it by hand while the whole cluster is unreachable. I wanted [Headscale](/blog/headscale-oidc-k3s-authelia/) and Vaultwarden to survive that.

**[View the complete homelab infrastructure source on GitHub](https://github.com/dwoitzik/homelab-infrastructure)**

## Warm Standby, Manual Failover

Zero-downtime HA was never the goal, and a single-operator homelab doesn't need it. It needs short outages and near-zero data loss, not automatic failover with its own false-positive and split-brain risk on a stack this small. So continuous replication keeps a standby current, and a documented, **human-triggered** failover avoids split-brain by construction. Only one copy ever accepts writes, because starting the standby containers is itself the first deliberate step of failover. There is no always-on second replica waiting to race the primary.

**Replication: Litestream, SQLite WAL streaming, primary → standby**, for Headscale and Vaultwarden specifically. Both are single SQLite-backed processes with tiny resource footprints, which is exactly what Litestream is built for. I chose it over periodic backup-and-restore because it gets the recovery point objective down to seconds instead of "however old the last backup is," and over Postgres-style replication because neither app uses Postgres.

**Replica destination: [`rpi-srv-02`](/blog/raspberry-pi-dns-edge-not-k3s-worker/), plain LAN SFTP, not through the tailnet.** Making Headscale's own control plane a dependency for replicating Headscale's data would be circular: a degraded tailnet is exactly when this replication matters most. The SFTP user is chrooted, key-auth-only, and has no shell, so the plain LAN path doesn't widen the attack surface much compared to tunneling over Tailscale.

**Standby runtime: Docker on `rpi-srv-02`, containers present but stopped.** That Pi isn't a k3s node and doesn't need to become one for two containers; Docker is already there for DNS. Standby containers are deployed and configured but never auto-started; starting them is the first step of the failover runbook, on purpose, so there's never a moment with two writers live at once.

## What I Investigated and Explicitly Didn't Build

I considered Authelia too and checked rather than assumed: its storage config points at CNPG-managed Postgres, not SQLite. Litestream is SQLite-specific, so it doesn't apply. A Postgres warm standby (native streaming replication or WAL shipping to an ARM Postgres instance) is a heavier and architecturally different job on a Raspberry Pi 4B than the SQLite sidecar pattern, with a different resource footprint and different failure modes. I left it as a separate item instead of forcing the SQLite pattern onto it or rushing a Postgres replication design into the same pass. Traefik, Garage, and the whole CNPG cluster fall in the same category: bigger jobs, not natural extensions of this design, and not built here.

## What's Actually Live

The replica target on `rpi-srv-02`: a dedicated system user, chrooted via an sshd `Match` block with `ForceCommand internal-sftp`, with replica directories on the Pi's SSD. Litestream sidecars on both the Headscale and Vaultwarden Deployments ship WAL segments continuously. I verified that live: both sidecars log replica-sync activity, an SFTP check confirmed the files landed, and both apps kept serving traffic throughout.

Host-key pinning, which Litestream's docs strongly recommend, is not enabled. I tried it and reverted it after hitting a confirmed host-key-type incompatibility in the Go SSH client. I accepted that for a LAN-only hop that NetworkPolicy already restricts to this one destination, backed by a key-auth-only, chrooted account with no shell.

The Docker Compose standby definitions are deployed, and the failover runbook is written: confirm the primary is down, reach the Pi, `litestream restore`, start the standby, flip AdGuard's DNS rewrites and the Cloudflare Tunnel target, verify against a real client, plus the mirror-image failback.

## The Gap I Found While Building the Standby, Not Before

Headscale's private key and noise private key, and Vaultwarden's RSA key, are static identity and signing material that live on the same volume as the SQLite database but *outside* it. Litestream only replicates the SQLite database, so these three files are out of its scope. Without them, a standby restored from the SQLite replica alone would generate fresh keys on first start, which breaks every existing device's trust relationship with Headscale (a full tailnet re-registration) and invalidates every existing Vaultwarden auth token.

I had a Claude Code session try to extract these files to seed the standby, and my credential-safety tooling ([the PreToolUse hook system I built after a string of secret-exposure incidents](/blog/claude-code-pretooluse-hook-credential-safety/)) correctly blocked it. Pulling a key-shaped file out of a running pod is exactly the read it exists to prevent, and I didn't route around it. **These three files still need to be copied to the standby by hand, once, before it's usable.** They practically never rotate, so it's a one-time bootstrap step, but until it's done the gap is real.

## Status: Not Yet Rehearsed Against Live Traffic

Everything above is deployed. What I haven't done is the induced-failure test: stop a primary, confirm the standby serves real traffic, confirm failback is clean, with a real DNS and tunnel flip against production routing. I deliberately didn't run that in the same pass as building it. It's the riskiest part of the design because it touches live routing, and it belongs in a scheduled game-day exercise or a real incident, not an unattended test. Two one-time manual prerequisites are also still outstanding: the three static identity files above, and Headscale's OIDC client secret. Both need me with real access, not an agent session.

Failover, when it happens, takes minutes, not milliseconds. That's by design: automatic failover was the wrong goal for a single-operator setup.

---

The Azure version of this pattern is a warm-standby VM in a paired region with continuous log shipping and a documented, human-approved failover runbook. It's cheaper and simpler than active-active multi-region, and the right trade when an outage of minutes, orchestrated by a human, is acceptable and fully automatic failover isn't worth the added failure surface.
