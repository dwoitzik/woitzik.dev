Both of my <AffiliateLink href="/go/4wNS0oI">Raspberry Pi 4Bs</AffiliateLink>, the pair running [AdGuard Home and Unbound in an active/passive Keepalived setup](/blog/unbound-adguard-keepalived-homelab/), have had `k3s-agent` installed for months. Disabled, never joined, just sitting there. Nobody had made an actual decision about it; it was left over from an earlier "maybe the Pis should do double duty" attempt that never got finished one way or the other. During a recovery pass I finally had to answer the question directly: should these boxes be k3s workers, or not?

**[View the complete homelab infrastructure source on GitHub](https://github.com/dwoitzik/homelab-infrastructure)**

## The Question Wasn't New, Just Never Fully Closed

An earlier decision had already ruled out putting the Pis into etcd for two reasons: SD-card write fragility against etcd's fsync-heavy raft log, and mixing a critical-path responsibility (DNS) with Kubernetes blast radius on the same small boxes. Separately, etcd got pulled out of this cluster entirely in favor of k3s's embedded SQLite datastore. That settles the first objection structurally: there is no etcd role left to put on the Pis at all.

But that earlier ruling was scoped to etcd *membership*. It never addressed the option that was still live on disk: the Pis as plain k3s **agents**, meaning workers with no control-plane role. Being agent-only instead of server-only doesn't change the blast-radius argument, but the original decision never said so, and a disabled-but-installed agent binary is exactly the kind of half-finished state that invites a future me (or a future automated recovery pass) to assume it was meant to be finished.

## Why Agent-Only Doesn't Dodge the Real Problem

DNS is the single most critical shared dependency on this network. Every other host, including the k3s VMs themselves and my own SSH access to anything, resolves through these two Pis. A k3s agent problem on one of them (an OOM, a bad pod, a kubelet bug) risks degrading DNS network-wide, and that risk doesn't scale down just because the Pi is a worker instead of a control-plane member. It's the same shared-blast-radius argument as the etcd case, only weaker in degree.

SD-card write pressure is smaller here too, but not zero: a k3s agent still writes kubelet state, container logs, and image layers locally. Less write pressure than etcd, meaningfully more than "run AdGuard and nothing else." I already treat these SD cards as disposable, write-fragile hardware as a hard rule, not a soft preference, and adding *any* new source of sustained writes cuts against that rule for a benefit I don't actually need.

And I don't need the compute. My two k3s VM workers already provide plenty of worker capacity on the host's own fast local NVMe storage. Adding two low-powered, high-latency, write-fragile ARM boxes to the scheduler's pool doesn't relieve any resource pressure that actually exists. It adds two more places for something to go wrong, in exchange for scheduling headroom I'm not using.

## Decision: DNS/Edge Only, Uninstall Instead of Disable

Both Pis stay out of k3s entirely: no control-plane role, no agent role. Their job stays DNS (AdGuard + Unbound) plus light, non-critical Docker workloads, same as documented in [the DNS hardening writeup](/blog/raspberry-pi-edge-hardening-watchdog-fail2ban-nftables/). The dormant `k3s-agent` install gets **uninstalled**, not left disabled. An unused install is attack surface and confusion for no benefit, and "disabled" isn't the same thing as "gone."

```bash
# rpi1, rpi2 - remove the dormant install, don't just leave it disabled
/usr/local/bin/k3s-agent-uninstall.sh
```

If Pi compute is ever needed for cluster workloads, the prerequisite is USB-SSD boot on both Pis first. That is a real hardware migration, not a config flag, followed by a multi-night stable baseline before trusting anything critical to it, and then joining as workers only, never control-plane. Given the two k3s VM workers' current utilization, I'm not close to needing that.

## The Part That Looks Like a Contradiction (But Isn't)

Around the same time I was ruling the Pis *out* of the cluster, I also decided to give one of them (`rpi-srv-02`, which now has a USB-SATA SSD attached) an important job: hosting [Headscale](/blog/headscale-oidc-k3s-authelia/), the Tailscale control plane that gates remote access to this whole network, as a standalone Docker Compose service.

That is consistent with "keep the Pis out of k3s." Joining a k3s cluster means sharing a scheduler, a control plane, and a blast radius with every other pod on that cluster. Running one well-understood, low-resource service in its own container is the opposite: an isolated, single-purpose workload with none of that coupling, the same operating model DNS already uses on these boxes.

The reasoning for moving Headscale specifically: my whole homelab runs on a single physical Proxmox host, and there's no getting around that being a single point of failure for everything k3s-hosted, Headscale included. Of the two candidates worth moving off that host, Headscale and Vaultwarden, I picked Headscale. Vaultwarden holds Tier-1 password data and already has a proven Velero backup and restore path; a botched live migration of real vault data costs far more than moving it off the host would gain. Headscale's dataset is small, SQLite-backed, and cheap to verify via backup and restore. Losing it temporarily means new device registrations and network map updates pause; existing Tailscale peers keep their connections to each other. Lower blast radius if the migration goes wrong, and more value from being reachable independently of the one host most likely to need a reboot, including when I need remote access to fix that host.

**Status: decided, not yet executed.** This is the plan, not a completed migration. I haven't partitioned the SSD, migrated the SQLite database, or cut DNS over yet, and I'm not going to claim otherwise. Headscale gates remote access to this entire network; that's Tier-1-adjacent enough to deserve its own careful, verified pass, not something to rush into the same session as the decision.

---

The Azure-shaped version of this same argument is deciding what belongs on an AKS cluster's system node pool versus a dedicated Azure Container Instance or a small VM outside the cluster entirely: shared scheduler membership isn't free just because the hardware has spare capacity. A service the rest of your infrastructure depends on for basic reachability (DNS here, a DNS-based service discovery layer there) is exactly what you don't want sharing a blast radius with everything else you run.

[The Linux Command Line\*](/go/4gEAhv9) is still the book I hand people who ask why I bother hand-rolling systemd units and uninstall scripts on "just two Raspberry Pis" instead of treating them as disposable cattle. On hardware this constrained, understanding exactly what's running and why is cheaper than automating around a mystery.
