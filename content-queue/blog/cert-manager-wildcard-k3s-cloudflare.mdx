Let's Encrypt's HTTP-01 challenge requires port 80 to be reachable from the internet. Behind a [MikroTik RB5009*](https://amzn.to/4w08b21) with default-deny firewall rules and no public IP on the k3s nodes, that's a non-starter. DNS-01 validation solves this: the cert-manager solver proves domain ownership by creating a TXT record in Cloudflare, and Let's Encrypt verifies the record exists. No port forwarding, no inbound traffic.

## The Problem with HTTP-01

The standard cert-manager setup uses an HTTP-01 ACME solver. A Challenge resource is created, Traefik routes `/.well-known/acme-challenge/` to a temporary pod, Let's Encrypt hits that pod, and the certificate is issued. It works — unless:

- The router blocks inbound port 80 (default-deny)
- The cluster runs behind CGN (no public IPv4)
- You want a wildcard certificate (`*.lab.woitzik.dev`)

HTTP-01 cannot issue wildcard certificates. Period. DNS-01 is the only option for wildcards.

## Switching to DNS-01

The cert-manager ClusterIssuer changes from HTTP-01 to DNS-01 with a Cloudflare API token:

```yaml
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: letsencrypt-prod
spec:
  acme:
    server: https://acme-v02.api.letsencrypt.org/directory
    email: david@woitzik.dev
    privateKeySecretRef:
      name: letsencrypt-prod-account-key
    solvers:
      - dns01:
          cloudflare:
            apiTokenSecretRef:
              name: cloudflare-api-token
              key: api-token
        selector:
          dnsZones:
            - "lab.woitzik.dev"
```

The Cloudflare API token needs `Zone:DNS:Edit` permission for the `lab.woitzik.dev` zone. Create it in the Cloudflare dashboard under My Profile → API Tokens → Create Token → Edit zone DNS.

## The Secret

The API token lives in a Kubernetes Secret in the `cert-manager` namespace:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: cloudflare-api-token
  namespace: cert-manager
type: Opaque
stringData:
  api-token: "your-cloudflare-api-token-here"
```

In production, this should come from Vault via ExternalSecrets, not from a YAML file applied with `kubectl apply`.

## The Certificate

Once the ClusterIssuer is ready, requesting a wildcard certificate is straightforward:

```yaml
apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: lab-wildcard
  namespace: traefik
spec:
  secretName: lab-wildcard-tls
  issuerRef:
    name: letsencrypt-prod
    kind: ClusterIssuer
  dnsNames:
    - "lab.woitzik.dev"
    - "*.lab.woitzik.dev"
```

cert-manager creates the Certificate resource, creates an Order, creates a Challenge, adds the TXT record to Cloudflare via the API, waits for Let's Encrypt to verify, and stores the certificate in the `lab-wildcard-tls` Secret.

## Traefik Integration

The wildcard certificate Secret is referenced in the Traefik Helm values:

```yaml
# traefik values
additionalVolumeMounts:
  - name: wildcard-tls
    mountPath: /certs
    readOnly: true

volumes:
  - name: wildcard-tls
    secret:
      secretName: lab-wildcard-tls
```

Or, more commonly, reference the Secret directly in an IngressRoute TLS config:

```yaml
apiVersion: traefik.io/v1alpha1
kind: IngressRoute
metadata:
  name: grafana
  namespace: monitoring
spec:
  entryPoints:
    - websecure
  routes:
    - match: Host(`grafana.lab.woitzik.dev`)
      kind: Rule
      services:
        - name: grafana
          port: 3000
  tls:
    secretName: lab-wildcard-tls
```

Every service that uses `*.lab.woitzik.dev` gets TLS automatically. No per-service certificates, no HTTP-01 challenges, no port 80.

## The Timing Problem

DNS-01 challenges take longer than HTTP-01. The TXT record propagation can take 30-60 seconds, Let's Encrypt verification adds another lookup, and the whole process typically takes 2-5 minutes. If you're used to HTTP-01 taking 30 seconds, this feels slow. It's normal.

The cert-manager logs show the challenge flow:

```
Waiting for DNS01 challenge propagation...
Successfully created record "_acme-challenge.lab.woitzik.dev"
Verifying the DNS01 challenge...
Challenge verified - DNS01 record found
```

The certificate renews automatically 30 days before expiry, which means the DNS-01 dance happens about once every 60 days. You won't notice it unless you're watching the cert-manager logs.

## Gotcha: Cloudflare Proxy Mode

If the Cloudflare proxy (orange cloud) is enabled for the `lab.woitzik.dev` zone, DNS-01 still works — the proxy only affects HTTP traffic, not DNS TXT records. But if you're using Cloudflare for your public domain and a separate zone for the lab, make sure the lab zone has the API token scoped to it. A token scoped to the wrong zone returns a silent 403 from the Cloudflare API, and cert-manager logs a cryptic `urn:ietf:params:acme:error:unauthorized` error that takes an hour to debug.

The fix: scope the API token to the exact zone where the TXT records will be created.
