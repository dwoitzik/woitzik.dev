I already wrote about [scoping my AI agent's Vault access down to a narrow AppRole](/blog/vault-approle-scoped-credential-ai-agent/) after the root token leaked into its tool output. That fixed Vault specifically. It didn't fix the shape of the problem, which showed up again almost immediately in a completely different file: debugging why `gh auth status` reported logged-out, I had the agent `cat` its GitHub CLI config to see what was in it — and printed three live personal access tokens straight into the transcript.

Six real secret-exposure incidents across one recovery mission, all the same shape. Every one was a legitimate debugging step — "let me see what's in this file," "let me check if this changed" — landing on a path that happened to hold a live credential.

## The Rule Was Not the Fix

Six incidents in one mission means "be more careful" had already been tried, repeatedly, and had already failed six times. A rule an agent has to remember is a rule that gets forgotten under exactly the conditions — fast-moving debugging, an unfamiliar error, a session that's already run long — that produced all six incidents in the first place. If the fix is going to actually hold, it has to be structural: something that doesn't depend on anyone, human or model, remembering not to do the obvious debugging thing in the moment.

## Step One: Kill the Multi-Purpose Credential File

The `gh auth status` incident happened because GitHub's own CLI writes every configured account's token into one general-purpose state file in plaintext. That file *inviting* a "let me just look at this" debugging reflex is the real bug — a single-purpose file with one job has nothing else in it worth opening.

I replaced `gh auth login`'s state file entirely with a token sourced from a dedicated, single-purpose, `0600` file, read via command substitution at the point of use and never written to disk as an environment variable or session state:

```bash
GH_TOKEN=$(cat /root/.secrets/gh_token) gh api ...
```

The old multi-account config file is gone; the unused accounts it held were logged out first. This isn't just "a narrower file" — it changes the shape of the risk. Nothing about a single-purpose credential file invites inspection, because there's nothing else in it to look at.

## Step Two: Sweep for What Else Was Lying Around

Once I started actually looking, I found more than the one file. A 191MB leftover workspace from the original disaster-recovery session held two unseal-key files in plain, world-readable permissions, plus close to 200MB of database dump tarballs that could contain application-level credentials inside the dumps themselves. I verified these were safe to delete without ever printing their contents: hash-compared the unseal-key files against their known-good encrypted values elsewhere — exact match, meaning these were pure redundant plaintext copies of values already safely stored — confirmed zero references anywhere in the repo, confirmed the live databases the dumps came from were independently backed up, and deleted the whole thing.

Three more loose plaintext credential files turned up — a Proxmox token, a GitHub PAT, a Vault session token, apparent leftovers from earlier sessions' handoffs. I couldn't safely confirm whether each was still live or already stale without decrypting or printing content this whole project exists to stop doing, so I moved them into a mechanically-protected quarantine location instead of either deleting unverified material or leaving it loose, and flagged them for a human to confirm disposal.

**Disclosed honestly rather than smoothed over:** I never did the equivalent sweep across my k3s guest VMs, because the agent has no SSH access there — its key was only ever deployed to a specific subset of hosts. The standard k3s credential paths are covered generically in the deny-list below on the chance access ever changes, but that's not the same as an actual sweep having happened.

## Step Three: A Hook That Makes the Read Mechanically Impossible

`~/.claude/settings.json` now runs a `PreToolUse` hook before every Bash tool call the agent makes — enforced by the harness itself, not by the agent remembering a rule. Two tiers:

**Tier 1 — never legitimately read for their content, no exception.** SSH private keys, the kubeconfig, the Ansible Vault password file, the AppRole `secret_id`, the old GitHub CLI config path, standard k3s server token and TLS paths. Every tool that needs these takes them as a *path argument* and reads them internally — `kubectl`, `ssh`, `ansible-vault` — never by having their bytes printed into a terminal. The hook denies `cat`, `less`, `head`, `tail`, a Python one-liner that opens the file, anything, against any of these paths, unconditionally.

**Tier 2 — the opposite design, for `/root/.secrets/*`.** These files exist specifically to be sourced via `$(cat <path>)` into an environment variable at the point of use — the `GH_TOKEN` pattern above. That one substitution form is allowed; any bare read, pipe, or redirect of the same path is denied. It's a text-matching heuristic, not a real shell parser, so it can't perfectly distinguish "inside `$()` feeding a variable" from "displayed" in every possible construction — but the common, accidental case (someone just `cat`s the file to see what's in it) is exactly what it catches, and that's the actual threat model here.

Two real bugs surfaced while building this, worth leaving visible as a caution against trusting a first-draft regex: home-directory shorthand (`~/`, `$HOME/`) wasn't normalized in the first version — the exact command that caused the `gh` incident would have slipped past an absolute-path-only pattern entirely. And matching the read-verb `od` (octal dump) without a word-boundary anchor matched as a substring inside `chmod`, blocking an unrelated permission-fixing command — caught live while moving the flagged credential files above.

## Proof

Re-running the exact command that caused the original incident:

```console
$ cat ~/.config/gh/hosts.yml
Blocked by deny-credential-read hook: this command would print the raw
content of a Tier-1 credential path...
```

The underlying file doesn't even exist anymore given the design change above, but this proves the hook would have caught it independently of that. Legitimate operations continue working unimpeded — `kubectl --kubeconfig ~/.kube/config get nodes`, `ssh -i ~/.ssh/agent_key`, and `GH_TOKEN=$(cat /root/.secrets/gh_token) gh api user` all succeed normally, because none of them ever put the credential's bytes into visible output.

## What This Doesn't Cover, Said Plainly

**Text matching, not a real shell parser.** A sufficiently adversarial command — a path built via string concatenation, base64-encoded and decoded inline — could evade this. That's not the threat model I'm defending against: every real incident here was an accidental, plainly-written command, not an attempt to route around a safeguard. This is accident prevention for a tool operating in good faith, not a security boundary against a hostile actor who already has shell access.

**New credential files can appear that aren't yet on the deny-list.** This hook closes the *known* shape of the problem. It doesn't prevent a genuinely new credential-holding file from being created somewhere it doesn't know to look. A general-purpose pattern-redaction wrapper for files that aren't hard-denied but could incidentally contain something credential-shaped covers some of that gap — advisory, not enforced — but the real mitigation is the same habit that fixed the `gh` file in the first place: route every new credential through `/root/.secrets/` or Vault, never a loose file somewhere general-purpose.

---

If you're giving any AI coding agent real shell access to infrastructure with live credentials on it — and I think that's an increasingly normal thing to do, not a fringe case — the lesson generalizes past Vault or GitHub tokens specifically: don't rely on the agent (or yourself) remembering which files are dangerous to open. Make the dangerous read structurally unavailable instead, and keep the resulting deny-list as a living document, not a one-time setup step.

[The Linux Command Line\*](/go/4gEAhv9) is where I'd point anyone building their own version of this hook — understanding exactly how shell word-splitting, substitution, and redirection actually work is the difference between a deny-list that holds and one that has a `chmod`-shaped hole in it on day one.
