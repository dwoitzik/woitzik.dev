I already wrote about [scoping my AI agent's Vault access down to a narrow AppRole](/blog/vault-approle-scoped-credential-ai-agent/) after the root token leaked into its tool output. That fixed Vault. It didn't fix the shape of the problem, which showed up again almost immediately in a different file. Debugging why `gh auth status` reported logged-out, I had the agent `cat` its GitHub CLI config to see what was in it, and it printed three live personal access tokens straight into the transcript.

That made six secret-exposure incidents across one recovery mission, all the same shape. Every one was a legitimate debugging step ("let me see what's in this file," "let me check if this changed") landing on a path that happened to hold a live credential.

## The Rule Was Not the Fix

Six incidents in one mission means "be more careful" had already been tried and had failed six times. A rule an agent has to remember gets forgotten under exactly the conditions that produced all six incidents: fast-moving debugging, an unfamiliar error, a session that has already run long. A fix that holds has to be structural. It can't depend on anyone, human or model, remembering not to do the obvious debugging thing in the moment.

## Step One: Kill the Multi-Purpose Credential File

The `gh auth status` incident happened because on a headless host with no system keyring, the GitHub CLI falls back to storing every logged-in account's token in plaintext in one general-purpose state file, `~/.config/gh/hosts.yml`. A file like that invites the "let me just look at this" reflex, and that is the real bug. A single-purpose file has nothing else in it worth opening.

I replaced the `gh auth login` state with a token in a dedicated `0600` file, read via command substitution at the point of use. It is set only for that one command, never exported into the session or saved in gh's config:

```bash
GH_TOKEN=$(cat /root/.secrets/gh_token) gh api ...
```

The old multi-account config file is gone; I logged out the unused accounts it held first. This changes the shape of the risk, not just the size of the file: nothing about a single-purpose credential file invites inspection, because there's nothing else in it to look at.

## Step Two: Sweep for What Else Was Lying Around

Once I started looking, I found more than the one file. A 191MB leftover workspace from the original disaster-recovery session held two world-readable unseal-key files, plus database dump tarballs (most of that 191MB) that could contain application-level credentials. I verified all of it was safe to delete without ever printing the contents. The unseal-key files hash-matched the known-good copies already stored safely elsewhere, so they were redundant plaintext duplicates. Nothing in the repo referenced any of it, and the live databases behind the dumps were independently backed up. Then I deleted the whole workspace.

Three more loose plaintext credential files turned up: a Proxmox token, a GitHub PAT, and a Vault session token, apparently left over from earlier sessions' handoffs. I couldn't confirm whether each was still live without printing content this whole project exists to stop printing. So instead of deleting unverified material or leaving it loose, I moved them into a quarantine location the hook protects and flagged them for a human to confirm disposal.

**Not covered:** I never did the same sweep across my k3s guest VMs, because the agent has no SSH access there. Its key was only ever deployed to a specific subset of hosts. The standard k3s credential paths are in the deny-list below in case that access ever changes, but that's not the same as a sweep having happened.

## Step Three: A Hook That Makes the Read Mechanically Impossible

`~/.claude/settings.json` now runs a `PreToolUse` hook before every Bash tool call the agent makes. The harness enforces it; the agent doesn't have to remember anything. There are two tiers.

**Tier 1: never legitimately read for their content, no exceptions.** SSH private keys, the kubeconfig, the Ansible Vault password file, the AppRole `secret_id`, the old GitHub CLI config path, and the standard k3s server token and TLS paths. Every tool that needs these (`kubectl`, `ssh`, `ansible-vault`) takes them as a *path argument* and reads them internally, never by printing their bytes into a terminal. The hook unconditionally denies `cat`, `less`, `head`, `tail`, a Python one-liner that opens the file, or anything else that reads one of these paths.

**Tier 2: the opposite design, for `/root/.secrets/*`.** These files exist to be read via `$(cat <path>)` into an environment variable at the point of use, the `GH_TOKEN` pattern above. That one substitution form is allowed; any bare read, pipe, or redirect of the same path is denied. It's a text-matching heuristic, not a shell parser, so it can't distinguish "inside `$()` feeding a variable" from "displayed" in every possible construction. It does catch the common accidental case, someone running `cat` on the file to see what's in it, and that's the threat model here.

Two bugs surfaced while building this, and I'm leaving them visible as a caution against trusting a first-draft regex. First, the initial version didn't normalize home-directory shorthand (`~/`, `$HOME/`), so the exact command that caused the `gh` incident would have slipped past an absolute-path-only pattern. Second, matching the read verb `od` (octal dump) without a word-boundary anchor matched the substring inside `chmod` and blocked an unrelated permission fix. I caught that live while moving the quarantined credential files above.

## Proof

Re-running the exact command that caused the original incident:

```console
$ cat ~/.config/gh/hosts.yml
Blocked by deny-credential-read hook: this command would print the raw
content of a Tier-1 credential path...
```

The file doesn't exist anymore after the change above, but this shows the hook would have caught the read on its own. Legitimate operations still work: `kubectl --kubeconfig ~/.kube/config get nodes`, `ssh -i ~/.ssh/agent_key`, and `GH_TOKEN=$(cat /root/.secrets/gh_token) gh api user` all succeed, because none of them put the credential's bytes into visible output.

## What This Doesn't Cover

**Text matching, not a shell parser.** A deliberately evasive command (a path built by string concatenation, or base64-encoded and decoded inline) could get past this. That's not the threat model. Every real incident here was an accidental, plainly written command, not an attempt to route around a safeguard. This is accident prevention for a tool operating in good faith, not a security boundary against a hostile actor who already has shell access.

**New credential files can appear that aren't on the deny-list yet.** The hook closes the *known* shape of the problem. It can't stop a new credential-holding file from showing up somewhere it doesn't know to look. A pattern-redaction wrapper for files that aren't hard-denied but might contain something credential-shaped covers part of that gap, but it's advisory, not enforced. The real mitigation is the habit that fixed the `gh` file in the first place: route every new credential through `/root/.secrets/` or Vault, never a loose file somewhere general-purpose.

---

If you give an AI coding agent shell access to infrastructure with live credentials on it (an increasingly normal setup, not a fringe case), the lesson goes beyond Vault or GitHub tokens. Don't rely on the agent, or yourself, remembering which files are dangerous to open. Make the dangerous read structurally unavailable, and keep the deny-list as a living document instead of a one-time setup step.

[The Linux Command Line\*](/go/4gEAhv9) is where I'd point anyone building their own version of this hook. Knowing exactly how shell word-splitting, substitution, and redirection work is the difference between a deny-list that holds and one that has a `chmod`-shaped hole in it on day one.
