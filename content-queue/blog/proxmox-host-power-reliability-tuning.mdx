## CPU Governor: `powersave`, Not a Compromise

In active mode (`amd_pstate=active`), AMD's P-State driver replaces `acpi-cpufreq` and hands frequency selection to the CPU firmware. It only offers the `performance` and `powersave` governors; `schedutil`, the usual default people reach for, isn't available. The Energy Performance Preference (EPP) hint does the fine-grained power/performance balancing on top of the governor, so `powersave` with `EPP=balance_power` is the right choice here, not a downgrade:

```bash
echo powersave > /sys/devices/system/cpu/cpu*/cpufreq/scaling_governor
echo balance_power > /sys/devices/system/cpu/cpu*/cpufreq/energy_performance_preference
```

## The `vzdump` Global Throttle

Backup I/O on a single shared NVMe competes directly with every live workload during the backup window unless something tells it not to. `vzdump`'s config supports a bandwidth cap (`bwlimit`, in KiB/s, so `100000` is roughly 100 MB/s) and an I/O priority (`ionice`, where `8` selects the idle class). Together they make backups yield to everything else on the disk instead of racing it at full speed:

```
# /etc/vzdump.conf
bwlimit: 100000
ionice: 8
```

One caveat from the Proxmox docs: `ionice` only takes effect with the BFQ I/O scheduler, and for snapshot-mode VM backups it only affects the compressor. NVMe devices default to the `none` scheduler, so on this disk the bandwidth cap does the real work unless BFQ is enabled.

## An LVM Autoextend Threshold That Could Never Succeed

My single physical volume has zero free space at the volume-group level, so there is nowhere for LVM's thin-pool autoextend to extend *into*. Once pool usage crossed the 80% threshold, LVM refused to create new thin LVs, which includes the snapshots `vzdump` takes. That bought zero protection, because there was never free space to grow into. I raised the threshold to 92% rather than disabling the check outright, to keep a margin before the unrecoverable failure mode: a thin pool that's actually full risks I/O errors across every guest on it, which is far worse than a single failed backup.

## A Backup Health Check That Doesn't Trust `vzdump`'s Own Exit Code

`vzdump` reporting success tells you the command ran without error. It doesn't tell you the archive it wrote is a complete backup rather than a near-empty stub. I have seen a job exit `0` after writing almost nothing useful. I added a hook script, registered as `vzdump`'s job-end script, that checks each backup's datastore manifest size and age per VM ID, independent of the exit status:

```bash
# job-end hook, simplified
manifest_size=$(stat -c %s "$backup_manifest")
if [ "$manifest_size" -lt "$MIN_EXPECTED_SIZE" ]; then
  notify "Backup for VMID $VMID reported success but wrote a near-empty archive"
fi
```

## Watchdog Alerts That Stop Repeating Themselves

A flat rate-limited watchdog re-alerts on every check cycle for a single ongoing condition, which trains you to ignore it. I switched to escalating backoff: 15, 30, 60, 120, then 240 minutes between repeat alerts for the same condition, resetting to 15 the moment it clears. A new problem still alerts promptly; a known, unresolved one stops spamming without going silent.

## World-Readable Power Counters

The kernel's RAPL power-capping interface (`/sys/class/powercap/intel-rapl:0/energy_uj`; AMD CPUs use the same `intel-rapl` path) is root-only by default. That breaks any unprivileged metrics exporter trying to read power draw, and it fails quietly: no error, the value never populates. A udev rule makes the counters world-readable and survives reboots and device re-enumeration, unlike a one-off `chmod`:

```
# udev rule
SUBSYSTEM=="powercap", ACTION=="add", RUN+="/bin/chmod -R a+r /sys%p"
```

This is a real security trade-off, and the root-only default exists for a reason. The kernel locked these counters down in 2020 after the PLATYPUS research (CVE-2020-8694) showed unprivileged energy readings can leak data through a power side channel. On a single-admin Proxmox host with no untrusted local users, and guests that can't see the host's sysfs, I accept that. On a shared machine I wouldn't; run the exporter as root or with a dedicated group instead.

## `vm.swappiness`: Reduced, Not Disabled

This host showed sustained swap I/O under memory pressure, and every swapped page is a write to the same NVMe every decision above is trying to spare. I reduced `vm.swappiness` to 5, not to zero. The host has real memory-pressure problems under load ([the same pressure the overcommit guard exists to catch before it becomes an ARC deadlock](/blog/overcommit-guard-python-host-freeze/)), and going further trades "less swap I/O" for "more OOM-kill risk." That is a bad trade when memory pressure is a known constraint rather than a hypothetical one.

## None of This Was One Plan

Every one of these landed incident by incident over about a week, not as a designed tuning pass. The common thread is real (one host, one disk, no headroom to hide mistakes in), but I'd rather say plainly that the timing wasn't planned than present seven separate fixes as one deliberate architecture. The LVM and `vzdump` tuning are mitigations for a hardware constraint. The actual fix would be a second disk or a second host, and I have neither.
