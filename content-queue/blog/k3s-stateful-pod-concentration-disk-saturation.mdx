One of [my three k3s VMs](/blog/k3s-three-vm-topology-overhead-measured/) hung completely. SSH, the guest agent and QEMU's own block-device query all timed out, while `info status` still answered: the QEMU process was alive, and the guest OS underneath it was wedged, not the hypervisor. A force stop and restart brought the API server and all three nodes back `Ready`. That fixed the symptom. It didn't explain the cause, and the cause turned out to be bigger than one node: nothing in the cluster had ever enforced pod spread, so most of the stateful workload sat on that VM.

## Storage Was Still Saturated After the Restart

I didn't assume the restart had fixed the underlying problem; I checked. `iostat -x` on the Proxmox host showed the LVM-thin data and metadata devices at 97–99.9% utilization, with discard latency spiking to 734ms on the physical NVMe. Whatever caused the hang was still happening.

## My First Theory Was Only Partly Right

My working assumption was that PVCs from `local-path` (the one node-affine StorageClass in this cluster) had pinned nearly the entire stateful workload onto this node over time. I checked instead of trusting it: the `local-path` PVCs were **already reasonably distributed**, six on the hung node and four on each of the other two. A real but modest 6-of-14 share, not "essentially everything."

I'd also assumed Garage's and Immich's library volumes were node-pinned, since they're statically provisioned rather than created through a StorageClass. Wrong again. Both are **NFS-backed**, confirmed via each PV's mount options, and follow the pod wherever it's scheduled like any other NFS PVC. (Garage does have a second, pinned volume for its metadata store, covered in [the dedicated-disk migration I wrote about separately](/blog/garage-lmdb-metadata-dedicated-disk/). That one is a deliberate, documented exception and not part of this finding.)

Cross-referencing live pod placement told the real story. The workloads concentrated on the hung node were Garage, two Postgres instances, every ArgoCD component, Alertmanager, Grafana, all five Loki pods, several exporters and Tempo. They were overwhelmingly backed by NFS or by no persistent storage at all. Storage type wasn't what kept them there.

## The Real Cause: Nothing Had Ever Enforced Spread

A grep across every Helm values block and every plain manifest in the cluster returned zero matches for `topologySpreadConstraints` or `podAntiAffinity`. These workloads weren't held by a storage constraint. They had never moved since they first landed, most plausibly because this node was the original control-plane node and existed before the two workers carried much load. The default scheduler only places new pods; it never rebalances running pods off a node. That is scheduling inertia rather than a hard constraint, which is good news: most of it can be fixed by rescheduling instead of migrating data.

## A Routine Backup Tipped Two Nodes NotReady

While investigating, I triggered a one-off manual backup to verify the onsite path end to end. Partway through, **the hung node and one other went briefly `NotReady`**. A single routine operation, the same kind that runs on schedule every night, was enough to destabilize a cluster this concentrated. I deleted the backup immediately, both nodes recovered within seconds, and nothing else was damaged. On its own that isn't proof of causation, but the correlation was strong enough that I didn't retry it outside a watched window. It is very likely the same mechanism behind disk-contention symptoms from earlier incidents, and it matches the restart counts I found: one Postgres pod alone had 121 restarts.

## The Fix: Reschedule the Safe Ones, Add a Soft Preference, Leave the Rest

Three parts, in order of risk:

**1. Reschedule the NFS-backed and storage-less pods one at a time, verifying each is healthy before moving to the next.** No PV-level data migration needed: deleting the pod (or a rollout restart for a Deployment) is enough, since NFS-backed data follows the pod. Many of the affected workloads are core cluster infrastructure (ArgoCD, the entire monitoring stack, Velero itself), so I ran this as its own watched session. Not folded into an unrelated change, and not unattended, given what the backup test had just shown.

**2. Add a soft node-affinity preference away from the hot node so it doesn't re-accumulate.** I reached for `topologySpreadConstraints` first, and it doesn't fit. It spreads pods matching a label selector across topology domains, which in practice means replicas of one workload. Every pod on my list was a single-replica, unrelated workload, so there was nothing for a spread constraint to balance against. Instead: `nodeAffinity` with `preferredDuringSchedulingIgnoredDuringExecution`, weight 100, excluding the hot node by hostname. Soft on purpose. This is a three-node cluster with one control-plane node and two workers of different sizes, and a hard requirement risks pods going `Pending` when an uneven placement is justified. That failure mode is worse than an imperfect spread.

**3. Leave the `local-path`-pinned pods where they are, for now.** They're a smaller share of the imbalance and already not badly skewed. Migrating them needs a real data-copy procedure through a throwaway pod, and with no CSI snapshot support on this cluster there's no cheap rollback if it goes wrong. Doing the lower-risk fix first and revisiting this only if the node stays hot was the right order, even though two of the pinned pods are arguably more valuable to rebalance than some I did move.

**One deliberate gap:** ArgoCD's core components (server, repo-server, redis, dex, the controllers) aren't sourced from this repo's manifests at all; only their ConfigMaps, RBAC and networking are. There's no GitOps-tracked manifest to add `affinity:` to. Fixing that properly means either vendoring ArgoCD's install manifest into the repo or an untracked imperative patch, and the latter defeats the point of managing the cluster as code. I logged it as a separate gap instead of patching around it.

## The Follow-Up That Almost Repeated the Same Mistake

A few days after the fix, my smallest worker node hit 100% memory utilization, causing containerd kill timeouts and cascading restarts of unrelated pods on it. The cause: my soft preference only excluded the *original* hot node and treated the two workers as interchangeable landing spots. They aren't. Prometheus alone, with no resource requests or limits ever set, was using over a third of that node's allocatable memory, on top of everything I'd just steered onto it. [I'd already done a separate pass on Prometheus's memory growth](/blog/prometheus-sizing-homelab-ram/) for a different reason. This was a fresh instance of the same lesson: an unbounded resource footprint eventually becomes someone else's outage.

Fix: Prometheus's affinity now also excludes the smaller worker, forcing it onto the larger one, and it has explicit memory requests and limits so the scheduler accounts for its real footprint instead of treating it as free. An unrelated app was adding to the same pressure. It had been pinned to the smallest node *because* it's memory-heavy, which is backwards. I moved it to the original hot node, which after the reschedule finally had headroom.

---

The Azure equivalent is an AKS cluster where every workload lands on the system node pool because nobody set up a user node pool and tainted the system pool to force separation. The failure mode isn't unique to bare-metal k3s. It's the default whenever a scheduler is never told to prefer spreading.

[Designing Data-Intensive Applications\*](/go/4aUtkCs) covers this class of problem from the database side: a system with no active rebalancing simply accretes load wherever it first landed. The parallel to Kubernetes scheduling inertia is closer than the book's own framing suggests.
