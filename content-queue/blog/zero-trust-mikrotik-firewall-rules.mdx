"Zero trust" is the kind of term that sounds like marketing until you implement it. The principle is simple: never trust, always verify. Every connection is authenticated and authorized, regardless of where it originates. On a MikroTik RB5009*, this means default-deny firewall chains, explicit allow rules per service, and VLAN-based microsegmentation. The same architecture that protects enterprise networks, running on a router that costs less than a single Azure VM.

**[View the complete homelab infrastructure source on GitHub 🐙](https://github.com/dwoitzik/homelab-infrastructure)**

## The Starting Point

Most home networks have a single firewall rule: allow everything outbound. The MikroTik default configuration is similar — the `forward` chain accepts all traffic that's part of an established connection. New connections from the DMZ to the server VLAN? Accepted. From IOT to the internet? Accepted. From anywhere to the Kubernetes API? Accepted.

Zero-trust inverts this: the default is deny. Every allowed connection is an explicit rule.

## The VLAN Layout

| VLAN | Zone | CIDR | Purpose |
|---|---|---|---|
| 10 | Management | 10.0.10.0/24 | Router, switches, PBS |
| 20 | Server | 10.0.20.0/24 | Proxmox, k3s nodes |
| 30 | DMZ | 10.0.30.0/24 | Reverse proxy, DNS |
| 40 | IOT | 10.0.40.0/24 | Smart home devices |
| 100 | Admin | 10.0.100.0/24 | Management workstation |

Every device is on a VLAN. The firewall rules control which VLANs can talk to which.

## The Default-Deny Chain

The first rule in the `forward` chain:

```routeros
/ip/firewall/filter
add chain=forward action=drop \
  comment="Default deny all forwarded traffic"
```

Everything that isn't explicitly allowed is dropped. This breaks everything — immediately. The next step is adding allow rules.

## The Allow Rules

Allow established connections (stateful firewall):

```routeros
add chain=forward connection-state=established,related \
  action=accept comment="Allow established connections"
```

Allow DNS from any VLAN to the DNS servers:

```routeros
add chain=forward src-address=10.0.0.0/8 \
  dst-address=10.0.30.2,10.0.30.3 dst-port=53 \
  protocol=udp action=accept comment="Allow DNS to AdGuard"
```

Allow HTTP/HTTPS from DMZ to server VLAN (reverse proxy to backends):

```routeros
add chain=forward src-address=10.0.30.0/24 \
  dst-address=10.0.20.0/24 dst-port=80,443,3000,8080 \
  protocol=tcp action=accept comment="DMZ to server HTTP"
```

Allow Kubernetes API from admin VLAN:

```routeros
add chain=forward src-address=10.0.100.0/24 \
  dst-address=10.0.20.0/24 dst-port=6443 \
  protocol=tcp action=accept comment="Admin to k8s API"
```

Allow WireGuard from internet:

```routeros
add chain=forward src-address=0.0.0.0/0 \
  dst-address=10.0.20.0/24 dst-port=13231 \
  protocol=udp action=accept comment="WireGuard VPN"
```

Every other connection is dropped by the default-deny rule.

## The Input Chain

The `input` chain controls traffic to the router itself:

```routeros
/ip/firewall/filter
add chain=input connection-state=established,related \
  action=accept comment="Allow established to router"
add chain=input src-address=10.0.0.0/8 dst-port=8291 \
  protocol=tcp action=accept comment="WinBox from LAN"
add chain=input src-address=10.0.0.0/8 dst-port=22 \
  protocol=tcp action=accept comment="SSH from LAN"
add chain=input action=drop comment="Drop all other input"
```

WinBox and SSH are only accessible from the LAN. No management access from the internet.

## Terraform Management

The firewall rules are managed via Terraform, not WinBox:

```hcl
resource "routeros_ip_firewall_rule" "default_deny" {
  chain    = "forward"
  action   = "drop"
  comment  = "Default deny all forwarded traffic"
}

resource "routeros_ip_firewall_rule" "allow_established" {
  chain            = "forward"
  connection_state = ["established", "related"]
  action           = "accept"
  comment          = "Allow established connections"
  place_before     = routeros_ip_firewall_rule.default_deny.id
}
```

Every rule change goes through a PR, `terraform plan` shows the diff, and `terraform apply` pushes to the router. No manual WinBox changes. No configuration drift.

## Testing the Rules

After applying the rules, test from each VLAN:

```bash
# From DMZ (10.0.30.2) — should succeed
curl http://10.0.20.252:3000  # Grafana
# Result: 200 OK

# From IOT (10.0.40.x) — should fail
curl http://10.0.20.252:3000
# Result: Connection refused (dropped by firewall)

# From Admin (10.0.100.x) — should succeed
ssh root@10.0.20.251
# Result: Connection established
```

The IOT VLAN can't reach the server VLAN. That's the point — smart home devices don't need access to the Kubernetes cluster.

## The Monitoring Gap

Firewall logs are critical for zero-trust. Without logging, you don't know what's being dropped:

```routeros
add chain=forward action=log \
  log-prefix="DROP-FWD: " \
  comment="Log dropped forward traffic"
```

The log prefix `DROP-FWD:` makes it easy to grep in the system log. For Prometheus integration, use the `mikrotik_exporter` community project to expose firewall counters as metrics.
