I run [Homepage](https://gethomepage.dev/) as the landing page for my homelab: one dashboard with live widgets instead of a bookmarks folder. Two widgets showed an API error for weeks: Proxmox VE and CrowdSec, both on the same [BMAX Mini PC\*](/go/4bv3yF1)-based k3s cluster, both blocked on the same root cause: no scoped credential existed for either service yet. Wiring both up looked like a ten-minute config task. Between mid-August and early September 2026 it turned into two separate credential-model lessons, two NetworkPolicy gaps neither widget's docs mention, and a self-inflicted overwrite I caught before it broke anything.

## Two Widgets, Two Completely Different Credential Types

"Give the dashboard read access to service X" looks like one generic problem. It isn't. Proxmox VE authenticates API clients with **API tokens** scoped through its own user/role/ACL system. CrowdSec authenticates two different classes of caller through separate credential types that aren't interchangeable: **bouncers**, which *enforce* decisions (like a Traefik plugin), and **machines**, which *feed detections into or read alerts from* the Local API (LAPI), like a dashboard widget. Getting either widget live meant learning that service's actual auth model, not pasting a token into a YAML field.

## Proxmox: The Privilege-Separation Gotcha

Creating a least-privilege Proxmox API token looks straightforward:

```bash
pveum user add homepage@pve --comment "Read-only dashboard widget"
pveum acl modify / -user homepage@pve -role PVEAuditor
pveum user token add homepage@pve homepage --privsep 1
```

`PVEAuditor` is Proxmox's built-in read-only role, so there is no custom role to maintain.

That last flag is the part that isn't obvious until it bites you. Proxmox API tokens default to **privilege separation on** (`--privsep 1`), which means the token does not automatically inherit its owning user's ACL grants. The user has the role. The token does not, until you grant the ACL **again, separately, on the token itself**:

```bash
pveum acl modify / -token 'homepage@pve!homepage' -role PVEAuditor
```

Skip that second grant and the token has no permissions of its own, so the widget gets nothing useful back, even though `pveum user permissions homepage@pve` shows the role sitting right there on the user. A privilege-separated token gets the intersection of the user's and the token's own permissions, so both grants have to exist. Privsep is there so a leaked token can't act with the full authority of the user that issued it. That's the right default, but it means "give the user a role" is only half the job.

In Homepage the widget's `username` is the full token ID, `homepage@pve!homepage`, and the `password` is the token secret. The realm in that ID is whatever realm the user lives in: the example in Homepage's docs uses `@pam`, my token user lives in `@pve`. The widget also talks to the host directly on port 8006, not to the Authelia-protected hostname, because a server-side request to that would just get redirected to the login page.

## CrowdSec: A Machine Credential, Not a Bouncer Key

The Traefik CrowdSec bouncer plugin already had its own API key, issued with `cscli bouncers add`. That key authenticates a bouncer, a component asking "should I block this?" A dashboard widget asking "what's your current decision count and top blocked IPs?" is a different kind of caller: a **machine**, registered with `cscli machines add`, which authenticates against the Local API (LAPI) the way an agent or another CrowdSec instance would, not the way an enforcement plugin does. Reusing the bouncer key for the widget can't work: Homepage's CrowdSec widget source logs in by posting a username and password to `/v1/watchers/login`, which is the machine login. A bouncer key, sent as an `X-Api-Key` header, has no place in that request.

The second, less obvious part: CrowdSec here runs as a **DaemonSet, one pod per node (three at the time), each with its own local LAPI and its own machine database on an `emptyDir`, not a shared, centralized instance.** A machine registered with `cscli machines add` inside one pod exists only in that pod's database, and only until that pod restarts, because the `emptyDir` goes with it. The widget's queries land on whichever pod the Service routes to, so a one-off registration works on one pod and fails on the others, and then disappears. The fix in the repo is a small sidecar in every CrowdSec pod that waits for its local LAPI's `/health` endpoint and then runs `cscli machines add` with a fixed username and password from the same Vault-backed Secret the widget reads, on every boot. That sidecar had two bugs of its own (a readiness check that could never pass and a missing `profiles.yaml` mount) and silently did nothing for about three weeks, until I checked it live in September. Coming from Vault-backed ExternalSecrets, where [one secret in Vault syncs uniformly to every consumer](/blog/external-secrets-operator-vault-kubernetes/), the CrowdSec case is different: the Secret syncs fine, but the registration it feeds is per pod and has to be redone on every start.

## The NetworkPolicy Gap Neither Widget Mentioned

The CrowdSec widget was also blocked at the network layer, twice over, by default-deny [NetworkPolicies](/blog/kubernetes-database-namespace-network-policies/) that predated it.

The first gap was on the receiving side. The `security` namespace's default-deny ingress only allowed port 8080 from Traefik's pods in `kube-system`, for the bouncer. A test from inside the Homepage pod got `connection refused` against both the CrowdSec Service and a CrowdSec pod IP directly, regardless of credentials, while Traefik's bouncer traffic worked fine. The fix was an ingress rule in `security`, scoped to the Homepage pod:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-from-homepage
  namespace: security
spec:
  podSelector:
    matchLabels:
      app.kubernetes.io/name: crowdsec
  policyTypes:
    - Ingress
  ingress:
    - from:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: apps
          podSelector:
            matchLabels:
              app: homepage
      ports:
        - port: 8080
          protocol: TCP
```

The second gap was on the sending side and only showed up once the credentials existed. Homepage's existing egress rule allowed `10.0.0.0/8` for LAN hosts, and the CrowdSec Service's ClusterIP sits outside that range. Adding a dashboard widget doesn't touch egress rules, so nothing surfaced the gap until the widget needed a connection nobody had explicitly allowed:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-egress-homepage-crowdsec
  namespace: apps
spec:
  podSelector:
    matchLabels:
      app: homepage
  policyTypes:
    - Egress
  egress:
    - to:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: security
          podSelector:
            matchLabels:
              app.kubernetes.io/name: crowdsec
      ports:
        - protocol: TCP
          port: 8080
```

Under a default-deny NetworkPolicy model, *every* new integration needs its own explicit rules on both ends, not only the ones that touch something sensitive.

## The Collateral Damage I Caught Before It Shipped

Registering the CrowdSec machine by hand had one more side effect that wasn't in any widget setup guide. Unless you point `-f` at another path, `cscli machines add` writes the new credentials to `/etc/crowdsec/local_api_credentials.yaml` on that pod. That's the file the pod's own agent uses to authenticate to its local LAPI. My first live fix, a `cscli machines add ... --force` for the dashboard machine, had overwritten the pod's own default registration with the dashboard's.

Nothing broke immediately. That file lives on the container's ephemeral root filesystem, so a restart resets it, but the same restart also wipes the dashboard machine from the `emptyDir` database, and the widget would have quietly broken again. That is why the sidecar registers a separately named machine and passes `-f /tmp/unused-credentials.yaml`: it never touches the pod's own credentials file, and the two identities survive independently.

## What Actually Fixed It, Summarized

| Symptom | Root Cause | Fix |
|---|---|---|
| Proxmox widget: no data despite correct user role | Privilege separation: token doesn't inherit the user's ACL grant | Grant the role to the token explicitly (`-token 'user@pve!id'`), not just the user |
| CrowdSec widget: no usable credential | Only a bouncer key existed; the widget logs in as a machine | Register a machine via `cscli machines add`, on every pod, on every boot (sidecar) |
| CrowdSec widget: `connection refused` | Default-deny ingress in `security` only allowed Traefik | `allow-from-homepage` ingress rule, scoped to the Homepage pod |
| CrowdSec widget: still blocked once credentials existed | Homepage's egress allowed `10.0.0.0/8`, not the Service ClusterIP | `allow-egress-homepage-crowdsec` egress rule |
| CrowdSec pod: own credentials overwritten | Manual `cscli machines add` without `-f` writes `local_api_credentials.yaml` | Sidecar registers a separate machine and writes its file elsewhere |

These were separate gotchas, not one bug with several symptoms, and they surfaced over about three weeks of dashboard config. When a widget "just needs a token," check whether the service has more than one credential model, whether privilege separation applies, whether NetworkPolicy already default-denies the path, and, if the registration step writes anything to disk, what else reads that file.
