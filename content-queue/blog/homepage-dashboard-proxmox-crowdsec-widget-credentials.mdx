Two widgets sat greyed out for weeks: Proxmox VE and CrowdSec, both on the same [BMAX Mini PC\*](/go/4bv3yF1)-based k3s cluster, both blocked on the same root cause: no scoped credential existed for either service yet. ## Two Widgets, Two Completely Different Credential Types

"Give the dashboard read access to service X" looks like one generic problem. It isn't. Proxmox VE authenticates API clients with **API tokens** scoped through its own user/role/ACL system. CrowdSec authenticates two different classes of caller through separate credential types that aren't interchangeable: **bouncers**, which *enforce* decisions (like a Traefik plugin), and **machines**, which *feed detections into or read alerts from* the Local API (LAPI), like a dashboard widget. Getting either widget live meant learning that service's actual auth model, not pasting a token into a YAML field.

## Proxmox: the Privilege-Separation Gotcha

Creating a least-privilege Proxmox API token looks straightforward:

```bash
pveum user add homepage-widget@pve --comment "Read-only dashboard widget"
pveum role add HomepageReadOnly -privs "VM.Audit,Sys.Audit,Datastore.Audit"
pveum acl modify / -user homepage-widget@pve -role HomepageReadOnly
pveum user token add homepage-widget@pve dashboard --privsep 1
```

That last flag is the part that isn't obvious until it bites you. Proxmox API tokens default to **privilege separation on** (`--privsep 1`), which means the token does not automatically inherit its owning user's ACL grants. The user has the role. The token does not, until you grant the ACL **again, separately, on the token itself**:

```bash
pveum acl modify / -token 'homepage-widget@pve!dashboard' -role HomepageReadOnly
```

Skip that second grant and the widget's API calls come back empty or `403`, even though `pveum user permissions homepage-widget@pve` shows the role sitting right there on the user. A privilege-separated token gets the intersection of the user's and the token's own permissions, so both grants have to exist. Privsep is there so a leaked token can't act with the full authority of the user that issued it. That's the right default, but it means "give the user a role" is only half the job.

## CrowdSec: a Machine Credential, Not a Bouncer Key

The Traefik CrowdSec bouncer plugin already had its own API key, issued with `cscli bouncers add`. That key authenticates a bouncer, a component asking "should I block this?" A dashboard widget asking "what's your current decision count and top blocked IPs?" is a different kind of caller: a **machine**, registered with `cscli machines add`, which authenticates against the Local API (LAPI) the way an agent or another CrowdSec instance would, not the way an enforcement plugin does. Reusing the bouncer key for the widget doesn't work. It's the wrong credential type for the endpoint the widget queries, and CrowdSec's auth middleware rejects it outright rather than degrading silently.

The second, less obvious part: this CrowdSec deployment runs **three pod replicas, each with its own local LAPI and its own local SQLite database, not a shared, centralized instance.** That's a deliberate lightweight-agent design, but it means a machine credential registered against one replica's LAPI is only valid for that replica. The widget's queries land on whichever pod the Service happens to route to at that moment, so the machine registration has to be understood (and, if you want consistent widget data regardless of which replica answers, replicated) per-instance rather than once, cluster-wide. Coming from Vault-backed ExternalSecrets, where [one secret in Vault syncs uniformly to every consumer](/blog/external-secrets-operator-vault-kubernetes/), the CrowdSec case is different, and treating it like another synced secret is the mistake to avoid.

## The NetworkPolicy Gap Neither Widget Mentioned

With both credentials correctly scoped, the CrowdSec widget still came back empty. No auth error this time, just a timeout. The Homepage pod's outbound traffic to the CrowdSec LAPI Service was silently dropped by a default-deny [NetworkPolicy](/blog/kubernetes-database-namespace-network-policies/) that predated this widget. Adding a dashboard widget doesn't touch egress rules, so nothing surfaced the gap until the widget needed a connection nobody had explicitly allowed:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: homepage-egress-crowdsec
  namespace: homepage
spec:
  podSelector:
    matchLabels:
      app: homepage
  policyTypes:
    - Egress
  egress:
    - to:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: crowdsec
      ports:
        - protocol: TCP
          port: 8080
```

Same shape as the Proxmox VE widget's egress rule to the host outside the cluster. Under a default-deny NetworkPolicy model, *every* new integration needs its own explicit egress rule, not only the ones that touch something sensitive.

## The Collateral Damage I Caught Before It Shipped

Registering the CrowdSec machine had one more side effect that wasn't in any widget setup guide. Unless you pass `-f`, `cscli machines add` writes the new credentials to `/etc/crowdsec/local_api_credentials.yaml` on that pod. That's the file each replica's local agent uses to re-authenticate to its own LAPI after a restart. Adding the dashboard's machine credential had silently overwritten it.

Nothing broke immediately, because the running agent process still held its old, already-authenticated connection in memory. It would have broken on the next pod restart or rollout, when the agent tried to reconnect using a credentials file that no longer matched what its local LAPI expected. A delayed failure like that would have looked, days later, completely unrelated to a dashboard widget change. Catching it meant deliberately testing a restart rather than trusting that "the widget works now" was the end of the story, then regenerating each replica's local-agent credentials back to a working state before moving on.

## What Actually Fixed It, Summarized

| Symptom | Root Cause | Fix |
|---|---|---|
| Proxmox widget: empty data / `403` despite correct user role | Privilege separation: token doesn't inherit the user's ACL grant | Grant the role to the token explicitly (`-token 'user@pve!id'`), not just the user |
| CrowdSec widget: auth rejected outright | Reused the bouncer API key instead of a machine credential | Register a real machine via `cscli machines add`, per replica |
| CrowdSec widget: auth correct, still times out | Default-deny NetworkPolicy blocking egress to the LAPI Service | Explicit egress `NetworkPolicy` from the widget's namespace to CrowdSec's |
| CrowdSec local agents: silent, delayed restart failure risk | `cscli machines add` overwrote each replica's own local-agent credentials file | Caught by deliberately testing a restart; regenerated local-agent credentials per replica |

These were four separate gotchas, not one bug with four symptoms, and they all surfaced in the same afternoon of dashboard config. When a widget "just needs a token," check whether the service has more than one credential model, whether privilege separation applies, whether NetworkPolicy already default-denies the path, and, if the registration step writes anything to disk, what else reads that file.
