The EU AI Act's obligations for high-risk AI systems read like a checklist written by people who have never deployed a RAG pipeline: risk management, data governance, record-keeping, transparency, human oversight, accuracy and cybersecurity. None of it says "Terraform" or "Private Endpoint." A large part of it is still implementable in infrastructure code if you already have a properly network-isolated Azure OpenAI deployment.

This article maps the technical obligations most relevant to a Retrieval-Augmented Generation system to the [Zero-Trust Azure OpenAI RAG architecture](/blog/azure-rag-shared-private-link-automation/) already covered on this blog: concrete resource blocks, not legal summary.

A customer-support RAG bot and one used for credit decisions are treated very differently. ## The Obligations That Actually Touch Infrastructure

Of the AI Act's requirements for high-risk systems (Articles 8–15), four map directly onto how the system is built and deployed rather than onto model choice or documentation:

**Article 12: Record-keeping**
High-risk AI systems must "technically allow for the automatic recording of events (logs) over the lifetime of the system", enough to identify risk situations, support post-market monitoring, and let deployers monitor operation. Deployers must keep those logs for at least six months (Article 26(6)). This is a logging requirement on the system itself, not a paperwork one.

**Article 10: Data governance**
Training, validation, and testing data must be subject to appropriate data governance: relevant, sufficiently representative, and "to the best extent possible, free of errors and complete", with documented origin and collection processes. The Article doesn't mention retrieval corpora. For RAG, applying the same discipline to the sources the retrieval layer may pull from is my reading of its intent, and the defensible one, since that corpus shapes outputs as directly as training data does.

**Article 15: Accuracy, robustness and cybersecurity**
High-risk systems must achieve "an appropriate level of accuracy, robustness, and cybersecurity" and be resilient against attempts by unauthorized third parties to alter their use, outputs, or performance. Article 15(5) names data poisoning explicitly, along with inputs designed to make the model err. For an LLM-backed system, prompt injection via retrieved content falls squarely into that second category.

**Article 14: Human oversight**
Systems must be designed so a human can effectively oversee them, including the ability to intervene or halt operation (the Act's "stop button" in Article 14(4)(e)).

## Control 1: Automatic Record-Keeping via Diagnostic Settings

Article 12 requires logging sufficient to reconstruct what the system did. For a RAG pipeline that means both the OpenAI inference calls and the AI Search retrieval queries, not just one half of the pipeline:

```hcl
resource "azurerm_monitor_diagnostic_setting" "openai_logs" {
  name                       = "diag-openai-${var.environment}"
  target_resource_id         = azurerm_cognitive_account.openai.id
  log_analytics_workspace_id = azurerm_log_analytics_workspace.ai_governance.id

  enabled_log {
    category = "RequestResponse"
  }
  enabled_log {
    category = "Audit"
  }
}

resource "azurerm_monitor_diagnostic_setting" "search_logs" {
  name                       = "diag-search-${var.environment}"
  target_resource_id         = azurerm_search_service.search.id
  log_analytics_workspace_id = azurerm_log_analytics_workspace.ai_governance.id

  enabled_log {
    category = "OperationLogs"
  }
}
```

These diagnostic logs record metadata: which operation ran, when, for which deployment, with what status and latency. The `RequestResponse` category does not contain prompt or completion text. If your risk assessment says you need the actual prompt/completion pairs to reconstruct a decision, log them yourself, either in the application or at an API Management gateway in front of the endpoint, into the same workspace.

Set retention deliberately: at least the six months Article 26(6) requires of deployers, long enough for post-market monitoring, and paired with a documented data-minimization policy for anything containing personal data. The AI Act's logging obligations don't override GDPR.

## Control 2: Data Governance at the Retrieval Boundary

For a standard ML system, Article 10 is about training data curation. For RAG, the equivalent surface is the retrieval corpus: the documents AI Search is allowed to pull into context. An unrestricted ingestion pipeline where any service principal can write to the search index is exactly the kind of governance gap Article 10 is meant to close.

```hcl
resource "azurerm_role_assignment" "ingestion_writer_only" {
  scope                = azurerm_search_service.search.id
  role_definition_name = "Search Index Data Contributor"
  principal_id          = azurerm_user_assigned_identity.ingestion_pipeline.principal_id
}

resource "azurerm_role_assignment" "app_reader_only" {
  scope                = azurerm_search_service.search.id
  role_definition_name = "Search Index Data Reader"
  principal_id          = azurerm_linux_web_app.rag_frontend.identity[0].principal_id
}
```

Only the ingestion pipeline's identity can write to the index; the application serving end-user queries can only read. This is the same least-privilege RBAC pattern from the base module's Identity Chaining, applied to the data-governance boundary Article 10 asks for: a documented, enforced answer to "what can add data this system will treat as ground truth."

## Control 3: Network Isolation as a Cybersecurity Control

Article 15 explicitly calls out resilience against attempts to manipulate a system's behavior. For an LLM pipeline, that includes indirect prompt injection via retrieved documents and outright data poisoning of the search index. Better prompts don't solve either. Limiting who can reach the model and the index does, which is the network isolation this blog has covered as a security default, now doing double duty as a compliance control:

```hcl
resource "azurerm_cognitive_account" "openai" {
  name                           = "oai-${var.environment}"
  kind                           = "OpenAI"
  public_network_access_enabled  = false
  local_auth_enabled             = false

  network_acls {
    default_action = "Deny"
  }
}
```

Combine this with Azure OpenAI's built-in content filtering (on by default; don't turn it off for latency on a high-risk system) and the attack surface for prompt injection and for data exfiltration through the model's outputs shrinks to what's reachable inside the VNet. That's the same [Private Endpoint and Identity Chaining setup](/blog/azure-rag-shared-private-link-automation/) already documented for this module.

## Control 4: Human Oversight Without a Human in the Loop for Every Call

Article 14 does not require a human to approve every inference, which wouldn't be viable for most RAG use cases. It does require the ability to detect abnormal behavior and intervene. An Azure Monitor alert on unusual request volume, wired to actually page someone, is the infrastructure-level answer:

```hcl
resource "azurerm_monitor_metric_alert" "anomalous_request_volume" {
  name                = "alert-openai-anomaly-${var.environment}"
  resource_group_name = var.resource_group_name
  scopes              = [azurerm_cognitive_account.openai.id]
  severity            = 2

  criteria {
    metric_namespace = "Microsoft.CognitiveServices/accounts"
    metric_name      = "TotalCalls"
    aggregation      = "Total"
    operator         = "GreaterThan"
    threshold        = var.expected_max_hourly_calls
  }

  action {
    action_group_id = azurerm_monitor_action_group.oncall.id
  }
}
```

This is a static threshold, and `azurerm_monitor_metric_alert` evaluates over a 5-minute window unless you set `window_size`. For a threshold named in calls per hour, add `window_size = "PT1H"`, or use `dynamic_criteria` if you want Azure to learn the baseline instead.

Paired with a feature flag or App Configuration setting that can disable the inference endpoint without a redeploy, this gives a human the actual ability the Act asks for: to notice something is wrong and stop it, on a timescale that matters.

## What This Covers and What It Doesn't

This covers the technical logging, data-governance, and cybersecurity infrastructure behind a compliant RAG deployment. Full AI Act compliance for a system that is actually high-risk also requires:

- **Conformity assessment (Article 43) and CE marking (Article 48)**: an organizational and legal process, not an infrastructure one
- **The risk management system itself (Article 9)**: documented, iterative risk assessment, which infrastructure supports but does not replace
- **Technical documentation (Article 11)** describing the system's purpose, architecture, and limitations
- **Instructions for use for deployers (Article 13)**, and transparency toward people who interact with the system directly (Article 50)
