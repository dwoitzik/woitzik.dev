I've [already written about the drift class where ArgoCD says `Synced` but the live cluster is stale or running an inert config](/blog/gitops-merged-not-applied-argocd-drift/): a stuck sync timestamp, a Helm values typo that silently no-ops. This is the mirror image, and it's worse in one way: ArgoCD can't see it *by construction*, not because of a bug. A raw manifest that was never wrapped in an ArgoCD `Application` has no sync status to be wrong about. Nothing reconciles it. A `kubectl apply` that never happened (a forgotten step after a merge, an agent session that ran out of context mid-task) looks correct in git and does nothing on the cluster until something downstream breaks and someone goes looking.

## Four Incidents, Same Root Cause

This bit me four separate times, across four different resource kinds: a `pve-exporter` ExternalSecret, a Kyverno ClusterPolicy, a NetworkPolicy on my database namespace, and, worst of all, a dead man's switch CronJob that was merged through a reviewed PR and then never `kubectl apply`'d. I found it only through a manual live-vs-git sweep during an unrelated repo audit. A dead man's switch exists to catch the cluster going silent, and a manifest sitting in git gives zero protection until it's running.

All four share the same root cause: they're standalone raw manifests, not wrapped in an ArgoCD `Application`. ArgoCD's `selfHeal` keeps everything it manages in sync with git, but nothing reconciles files nobody wrapped in an `Application` in the first place.

One boundary case turned up while building this. My `postgres` system directory *is* ArgoCD-managed, and its sync was stuck in a loop on one resource that still wasn't live after nine auto-heal attempts. That's a separate bug. This checker reports ground truth, declared versus live; it doesn't diagnose why an ArgoCD-managed resource fails to self-heal. I tracked that one separately.

## What I Built

A scheduled check, running every 30 minutes plus manual dispatch, that walks every YAML file under my raw-manifest directory, extracts every declared object that isn't an ArgoCD `Application`/`AppProject`/`ApplicationSet` (already self-healed, out of scope) or a `Secret` (see below), and confirms each one actually exists live via `kubectl get`. Any gap fails the job and pushes an alert.

I considered the more thorough-sounding fix, bringing every standalone CronJob, PrometheusRule and ExternalSecret under ArgoCD, and rejected it. Some of these files are direct-`kubectl`-apply on purpose: Kyverno's own policy file needs to be hand-editable live during an incident without fighting `selfHeal`. Re-architecting how many already-working files are managed was the wrong scope. The failure mode is "nobody ever ran the first apply", not "these files drift from git". A diff-based guard catches that regardless of *why* a file is standalone, and it covers any new standalone file automatically, with no design decision about how to bring it into ArgoCD.

### Why a Scheduled GitHub Actions Job, Not an In-Cluster CronJob

The [self-hosted runner I'm already building for Atlantis](/blog/atlantis-self-hosted-github-actions-runner/) already has network access to the apiserver, so this piggybacks on it rather than adding a new piece of infrastructure. Running the check from outside the cluster is also closer to what it verifies: "is this really live", not "does a pod inside the cluster agree it's live". That distinction matters when the apiserver itself, or the cluster's own alerting path, is what's broken.

### Credential Scoping

The checker uses a dedicated ServiceAccount bound to the built-in `view` ClusterRole, plus an explicit read-only rule for every CRD group `view` doesn't aggregate: Kyverno, CNPG, Traefik, MetalLB, cert-manager, Velero, the Prometheus Operator, and RBAC resources themselves, since `view` deliberately excludes reading Roles and ClusterRoles. I found this gap the hard way. The first properly configured run reported 69 of 211 objects "missing", all false positives from missing RBAC.

`Secret` is excluded on purpose. Checking whether a Secret exists needs `get`/`list` on secrets, which also lets the credential read secret *values*. That's not a trade worth making for a credential that lives on a CI runner's disk. A missing Secret is also the least silent of the four incident classes: its consumer pod fails visibly, which is less dangerous than the other three.

## Proof It Actually Catches the Gap

I tested it by deleting an applied, non-ArgoCD-managed CronJob and re-running the checker. It reported the missing CronJob immediately with exit code 1. I re-applied it right after; the real dead man's switch was never down for the test. Separately, the first run with correct RBAC found three real, pre-existing gaps: a PodMonitor and two chaos-mesh Schedules, all declared in git and never applied. That's the exact failure class this guard targets, caught on day one without an incident.

## What This Guard Still Can't See

The same night, while resolving an unrelated PR to migrate a service off the cluster, I found a running native Docker container on one of my Raspberry Pis, entirely outside git. It came from an apparently abandoned earlier attempt at the same migration that PR proposed. Two stale registrations, both confirmed offline before I decommissioned them.

That's the mirror image of everything above: **undeclared and manually run**, rather than **declared and never applied**. This guard only looks at what's declared in the manifest directory and asks "is this live". It can't notice something running that was never declared, on a host it doesn't look at. That's a separate gap. Closing it needs a different mechanism, an inventory sweep of every host's running containers against what Ansible and Kubernetes declare, which is a much bigger job than this guard and not something I've built.

---

The Azure DevOps equivalent is a scheduled pipeline that diffs `az resource list` against what your Bicep or Terraform templates declare, independent of the pipeline's own deployment history. A green "deployment succeeded" run proves the command executed, not that the resource still exists afterward. Same gap, same fix.
