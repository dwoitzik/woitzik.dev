Migrating a Proxmox VE host's root filesystem from a thick LVM volume to a thin-provisioned pool, live, is a well-understood procedure: sync the running root to a new logical volume, verify, swap, reboot. I'd already fixed the groundwork for it. `proxmox-boot-tool` was failing silently because `/etc/kernel/proxmox-boot-uuids` didn't exist, and `/etc/kernel/cmdline` was missing entirely, so the bootloader was quietly falling back to whatever the running kernel's command line happened to be. That included two boot parameters (`processor.max_cstate=1 idle=nomwait`) that a previous investigation had tested and explicitly reverted for making idle temperatures worse, yet they were still active. Both got cleaned up before the migration reboot.

All of this ran on the same single physical [mini PC host\*](/go/4bv3yF1) that later needed a full [Tier-1 data verification pass](/blog/proxmox-pbs-restore-tier1-data-verification/). One host, no IPMI, no out-of-band console: if SSH broke during any of this, physical access was the only way back in.

## The Mistake: rsync Doesn't Know What a FUSE Mount Is

The final sync step before the LVM swap was a recursive copy of the live root to the new logical volume. `rsync -a /` treats every path under `/` as ordinary files to copy. It has no idea that `/etc/pve` isn't a real directory on disk. It's `pmxcfs`, Proxmox's cluster filesystem, a FUSE mount over a directory that should be empty on the underlying root; the real data lives in `/var/lib/pve-cluster/config.db` and gets rendered into `/etc/pve` at runtime.

The rsync copied `/etc/pve`'s live, FUSE-rendered contents as real, static files onto the new root. On the next boot, `pve-cluster.service` tried to mount its FUSE filesystem over a directory that was no longer empty, and crash-looped.

## The Lockout, and the Wrong First Hypothesis

With `pve-cluster` down, root SSH access to the host broke entirely. Every key was rejected, from every source tried, including a fresh jump-host hop with its own identity. The first hypothesis was `fail2ban`. The second was `authorized_keys` corruption from the rsync. Neither was right, and chasing both cost real time during an active lockout with no console access.

Getting the host back required a physical power-cycle, the only recovery path on hardware with no IPMI. That power-cycle happened to resolve both problems at once: `pve-cluster` came up clean with an empty `/etc/pve` to mount into (a follow-up session had emptied the stray file copy in the meantime), and SSH worked immediately, with the exact same keys that had just been rejected.

## Root-Causing It Properly, After the Fact

"It started working again" is not a root cause, and stopping there would mean the same lockout could recur for the same reason with no faster way to diagnose it next time. The actual chain:

`/root/.ssh/authorized_keys` on a Proxmox host is a symlink to `/etc/pve/priv/authorized_keys`. That is standard `pmxcfs` behavior, so root's authorized keys are consistent across every node in a cluster. `/etc/pve` is a FUSE mount. While `pve-cluster.service` was crash-looping, `/etc/pve` was unavailable, so the symlink pointed at nothing. `sshd` had no authorized key to check root's logins against, regardless of whether the actual key material was intact. This fully explains the "broke, then started working with the same keys for no clear reason" observation: it tracks `pve-cluster`'s health, not key corruption, and the timing lines up exactly with when that service was down.

## The Structural Fix

```bash
# Root's authorized_keys is normally a symlink into pmxcfs:
# /root/.ssh/authorized_keys -> /etc/pve/priv/authorized_keys

# Add a plain, non-symlinked fallback with the same keys:
cp /etc/pve/priv/authorized_keys /root/.ssh/authorized_keys2
chmod 600 /root/.ssh/authorized_keys2
```

OpenSSH's compiled-in default for `AuthorizedKeysFile` is `.ssh/authorized_keys .ssh/authorized_keys2`, so the second file is already a fallback path. I confirmed it in `sshd_config`, where the directive was present but commented out, which means the built-in default was in effect. No `sshd_config` edit was needed, and that matters: `sshd_config` is exactly the file you don't want to touch as part of a larger batch of changes, since a mistake there can lock you out in a way that's much harder to diagnose than a stale symlink. I validated with `sshd -t` and then authenticated from a brand-new SSH session, not the one already connected, before calling it done.

Root SSH access on this host now survives a `pve-cluster.service` outage. A healthy cluster filesystem is no longer a precondition for logging in at all.

One maintenance cost comes with it: `authorized_keys2` is a copy, so a key added or revoked through `/etc/pve/priv/authorized_keys` has to be mirrored there by hand.

## The Smaller Regression That Came Along for the Ride

Post-reboot verification of the LVM-thin migration turned up one more thing: the root entry in `/etc/fstab` had lost its `noatime` flag somewhere in the same incident window, most likely overwritten when the stray `/etc/pve` copy was cleaned up, since that work touched files in the same area. Re-adding it and running a live `mount -o remount,noatime /` closed it without another reboot. Small on its own, but it is a reason to check explicitly instead of assuming that a file nobody meant to edit is unchanged, especially right after an incident where multiple sessions edited overlapping parts of the filesystem.

## The Actual Lesson

`rsync` skips nothing by convention. `rsync -a /` (or any bare `/` source) copies every mounted filesystem underneath it unless you pass `-x` (`--one-file-system`) or explicit excludes for every FUSE and virtual mountpoint on the host: `/etc/pve`, `/proc`, `/sys`, `/dev`, `/run`. On a host without IPMI, that exclusion list is the difference between a routine live migration and an SSH lockout with physical access as the only way out. It is the same host-level fragility that turned [a restored scratch VM's inherited config flag](/blog/onboot-scratch-vm-io-storm-network-conflict/) into a full network conflict a few weeks later.

---

The Azure parallel is any migration tool that treats a mounted network share, a Key Vault-backed volume, or an Azure Files mount as an ordinary directory during a lift-and-shift, copying its rendered contents as static files instead of preserving the mount. The fix pattern is identical: know which paths on a system are real files and which are a live projection of something else, and never let a generic recursive copy treat the two the same way.
