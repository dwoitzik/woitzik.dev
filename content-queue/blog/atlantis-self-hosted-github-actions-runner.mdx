Every other public hostname in my homelab exists because a human wants to reach something from outside the LAN. Atlantis was the exception, for a boring structural reason: GitHub delivers webhooks by pushing them inbound. When a PR opens or someone comments `atlantis plan`, GitHub has to reach Atlantis to tell it. Atlantis is built around those webhooks and has no mode where it polls GitHub for the event instead. That's a machine-to-machine direction problem, not a "someone needs this from their phone" need, and it's the only reason `atlantis.woitzik.dev` ever had a public Cloudflare Tunnel entry.

**[View the complete homelab infrastructure source on GitHub](https://github.com/dwoitzik/homelab-infrastructure)**

## The Exposure Audit Already Pulled the Rug Out

I'd [already migrated Atlantis to its own LXC once and accidentally made it fully public](/blog/infra-migration-silently-removed-auth-atlantis/), which I fixed by routing it back through Traefik with Authelia in front. A later exposure audit went further. I moved my public surface from an opt-out wildcard tunnel to an explicit two-hostname allowlist, and Atlantis doesn't need to be on that list the way, say, a device-registration endpoint does. Its DNS record and tunnel ingress rule were dropped.

That created a self-inflicted chicken-and-egg problem: the change that closed Atlantis's public exposure also removed the path GitHub's webhook needs to say "a PR was opened, go plan." Not dangerous, since the risky state was already closed, but it left Atlantis stuck. `atlantis plan`/`apply` PR comments had nowhere to land until I fixed the direction problem properly, instead of reopening the hole every time a webhook needed to get through.

## Two Options, and Why the Obvious One Loses

**Option B: keep Atlantis public, narrow the door.** Cloudflare Access in front of the hostname, a WAF rule restricting source IPs to GitHub's published webhook ranges, and HMAC signature verification on the payload (Atlantis already does this with its webhook secret). It's a legitimate, standard pattern; GitHub documents both signature validation and its webhook IP ranges for exactly this purpose. I took it seriously. But every piece of it is configuration that has to stay correct indefinitely: the allowlist has to track GitHub's ranges as they change, Access has to stay configured, and the secret has to stay in place on both ends. Each of those can regress to "open" without anyone noticing, which is how the wildcard-tunnel mistake happened in the first place: one bad day, one skipped review, and the door is open again.

**Option A: self-hosted GitHub Actions runner.** A runner inside my network polls GitHub outbound for jobs; GitHub never opens a connection inward. The `atlantis.woitzik.dev` tunnel entry goes away entirely instead of being narrowed. A GitHub Actions workflow running the equivalent `terraform plan`/`apply`-on-PR-comment flow runs on that runner.

I picked Option A. There's nothing to regress because nothing listens on the public internet, as opposed to "nothing listening as long as five separate things stay correctly configured."

One caveat for anyone copying this: the homelab repo is public, and GitHub advises against self-hosted runners on public repositories because a workflow triggered from a fork can run arbitrary code on the runner. The workflows have to be written so untrusted PRs never reach it, for example by gating runs on the commenter's permissions and on a protected Environment.

## The Side Benefit I Didn't Expect

Atlantis's current deployment holds the Proxmox API token, the Cloudflare API token and RouterOS credentials in its running container. Anything that can reach Atlantis's API is one bug away from them, and while the tunnel entry existed that meant the public internet. A runner with no inbound path removes the whole "what if Atlantis's own auth has a bug" class of risk for the most sensitive credentials in the stack. That follows from not being reachable at all, and it shrinks the same credential-exposure risk that [a separate pass through this homelab's Vault access tackled from the other direction](/blog/vault-terraform-config-staged-migration/).

GitHub Actions can reproduce the Atlantis workflow: `issue_comment`-triggered workflows (plus `workflow_dispatch` for manual runs) cover the PR-comment-driven `plan`/`apply` flow, `gh pr comment` posts plan output back to the PR like Atlantis does, and GitHub Environments with required reviewers replace Atlantis's apply gate. Day to day, nothing gets worse. What I lose is Atlantis's web UI showing all locks and plans across the repo, which for a homelab repo with a handful of concurrent PRs is an easy trade.

## Honest Status: Decided, Not Yet Migrated

This is a decision, not a finished migration. Until the workflows exist and the runner is registered, `atlantis plan`/`apply` PR comments have nowhere to go. That's a known, tracked gap. The now-unused webhook secret stays in Vault until the migration lands and I can retire it; removing it before anything replaces it would be housekeeping for its own sake.

The migration is sequenced work: one workflow per Terraform stack (or one parameterized workflow), a runner to register and patch like any other host in the inventory, and decommissioning Atlantis's webhook listener once the workflows are proven. It's its own project, not something to rush through in the session where I decided on it. [The last time I rushed an Atlantis change](/blog/atlantis-terraform-destroyed-itself-mid-apply/), it went badly.

In Azure the same trade-off shows up as a self-hosted Azure DevOps or GitHub Actions agent inside a private VNet versus a build-service webhook endpoint exposed through an Application Gateway with IP restrictions. Same two options, same asymmetry: the agent that polls outbound has no listener to misconfigure, and the exposed endpoint works fine until someone forgets to update an IP range when the provider rotates addresses.

[The Phoenix Project\*](/go/4f4RHQf) is the book I keep coming back to for this kind of decision. It isn't about Terraform or Kubernetes, but it's the sharpest account I know of choosing the boring, structurally sound fix over the clever one.
