[Velero was already backing up the cluster nightly](/blog/velero-backup-false-positive-no-data/), and after fixing the earlier false-positive bug, `velero backup describe --details` showed real `Pod Volume Backups: Completed` counts for every namespace, Vault included. That looked like proof the backup worked. It wasn't. A scheduled backup that reports success is a weaker claim than a backup you can restore from, and the only way to tell them apart is to restore it.

**[View the complete homelab infrastructure source on GitHub 🐙](https://github.com/dwoitzik/homelab-infrastructure)**

## The Restore Drill

The plan was simple: pick a namespace, restore its latest backup into a scratch namespace via `namespaceMapping`, and check the data is usable, not just present.

```bash
velero restore create vault-restore-proof \
  --from-backup daily-backup-20270301050012 \
  --namespace-mappings vault:vault-restore-proof
```

The PVC bound. The pod came up `Running`. On paper, that's a green check. Then:

```
$ kubectl exec -n vault-restore-proof vault-0 -- vault status
Initialized     false
Sealed          true
```

`Initialized: false` on a namespace restored from a Vault that had been initialized, unsealed, and in daily use for months. The files were there (correct size, correct ownership, nothing obviously missing), but Vault didn't recognize its own data.

## Why: Filesystem Snapshots Aren't Crash-Consistent

Velero's file system backup (Kopia, run by the node-agent DaemonSet) walks the PVC's files and copies them live while the pod that owns them keeps running. For config or plain files, that's fine. For a database engine's on-disk files it's a real problem, and Vault's integrated raft storage is exactly that: BoltDB files for the raft log and for the data itself. The copy can land mid-write, capturing some pages from before a transaction and some from after, with no guarantee the result is a state the engine ever had on disk at any single point in time.

This class of bug is easy to miss because most of what you back up in a homelab doesn't care. Postgres, Vaultwarden's SQLite file, and Paperless's document store all restored cleanly through the same path, either because their write patterns and Velero's timing happened not to collide badly enough to matter, or because their engines tolerate a torn file better than raft/bolt does. Vault's `Initialized: false` wasn't a Vault-specific fluke. It was the one place in this cluster where a timing problem that is *always* possible surfaced as a visible failure.

[Designing Data-Intensive Applications\*](/go/4aUtkCs) makes the same distinction when it discusses consistent snapshots for seeding new replicas: a copy of on-disk state taken without coordinating with the system's write path is not a consistent snapshot, however correct the copy tool is. Kopia did its job. It copied the file as it existed at the moment it read each part. That file just wasn't a state Vault ever considered final.

## The Fix: Stop Using the Path That Doesn't Work, Then Build the One That Does

The immediate fix was the same annotation I use elsewhere in this cluster for a different reason, [excluding a redundant NFS root-mount volume](/blog/velero-nfs-provisioner-root-mount-redundant-backup/). There the reason was "this data is redundant." Here it's "this data cannot be safely captured this way."

```yaml
# Vault StatefulSet pod template
metadata:
  annotations:
    backup.velero.io/backup-volumes-excludes: data
```

This stops the daily schedule from producing a Vault backup that looks successful in `velero backup describe` but can't be restored. False coverage is worse than none, because a visible gap at least prompts you to build something.

**What this doesn't do:** give Vault a working backup. Vault's raft data is fine on the live cluster; the unseal-key-recoverable transplant approach [used to recover a lost root token after a full rebuild](/blog/vault-raft-recovery-disposable-k3s-lost-root-token/) shows the live data is sound. What's missing is an *ongoing, verified* backup path for it. The right tool is Vault's own `vault operator raft snapshot save`: a consistent, application-level snapshot taken through Vault's API instead of a raw file copy underneath it, written somewhere Velero or Garage can pick up on a schedule. That part isn't built yet. The exclusion stops a broken backup from lying about its health; it doesn't replace the backup Vault still needs.

## What This Proves About the Rest of the Cluster

The restore drill wasn't limited to Vault. It also targeted a normal `apps` namespace (vaultwarden, garage, cloudflared, headscale, authelia, tailscale-subnet-router) and came back clean: PVC bound, pod running, and vaultwarden's `db.sqlite3` restored at exactly the same byte count as the live database. That's the bar a backup claim needs to clear: not "the schedule ran" or "the API returned success," but matching data after a real restore into a namespace with nothing else to fall back on. A byte count is a good first check; a checksum or opening the restored database is the stronger one.

The lesson generalizes past Vault: any process with its own consistency model for its files is a candidate for the same failure mode, not only key-value databases. A generic filesystem backup tool has no way to know which of your PVCs fall into that category. You have to know your own stack well enough to ask the question per-service, then prove the answer with an actual restore instead of trusting a green backup status.

---

Azure Backup draws the same line with its own terms: application-consistent, file-system-consistent, and crash-consistent recovery points. On a running Windows VM, Azure VM backup takes application-consistent snapshots through VSS. On Linux you get file-system-consistent snapshots unless you add pre- and post-scripts that quiesce the database, and when the backup extension can't coordinate with the guest at all, the recovery point is only crash-consistent, which is the file-copy problem above. The failure mode is identical: the dashboard shows green either way, and only a real restore test tells you which kind you have.
