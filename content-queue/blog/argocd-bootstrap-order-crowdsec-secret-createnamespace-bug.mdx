A [GitOps repository](/blog/argocd-gitops-k3s-homelab/) that's been running for months accumulates a false sense of confidence: every manifest in it is, by definition, one that's already working. That confidence evaporates the moment you have to bootstrap the same repository against a brand-new cluster - which is exactly when two real, previously-invisible bugs in the manifests themselves showed up, neither of which had anything to do with the rebuild itself.

**[View the complete homelab infrastructure source on GitHub 🐙](https://github.com/dwoitzik/homelab-infrastructure)**

## Bug One: A Secret Reference With No Secret Behind It

Traefik's Application manifest referenced a CrowdSec bouncer API key two ways: as a plaintext environment variable value committed directly in the YAML, and as a Kubernetes Secret (`crowdsec-bouncer-key`) the pod also expected to mount. The plaintext value in Git is its own separate problem - flagged directly rather than silently rewritten, since scrubbing git history is a call for whoever owns the repository, not something to do unilaterally mid-recovery. But the Secret itself simply didn't exist anywhere in the new cluster, because nothing in the GitOps repository actually creates it - it had clearly been created manually, once, on the original cluster, and never captured as code.

The pod sat in `FailedMount` for about eight minutes before this was diagnosed. The unblock was a manual `kubectl create secret` using the already-exposed plaintext value, purely to get Traefik running - specifically using `--from-file` rather than `--from-literal`, so the value wouldn't also land in shell history or a process list. That's a workaround, not a fix: the real fix is rotating the key and moving it into Vault behind an ExternalSecret like every other credential in the cluster, which needs Vault itself to exist first - a dependency this rebuild hadn't reached yet at the point this bug surfaced.

## Bug Two: A Sync Option Present on Every Sibling, Missing on One

cert-manager's Application manifest was missing `syncOptions: [CreateNamespace=true]` - present on the sibling Applications for MetalLB and Traefik, absent on this one alone, and present in the [correctly-written version of this exact Application](/blog/cert-manager-wildcard-k3s-cloudflare/) documented elsewhere on this site. The first sync attempt failed outright:

```
namespaces "cert-manager" not found
```

ArgoCD retried five times and gave up rather than retry indefinitely. The unblock here was a manual `kubectl create namespace cert-manager` plus a manual sync trigger, since ArgoCD's own automated retry window had already elapsed by the time this was diagnosed. Compare the working pattern from a sibling Application, which is the actual permanent fix:

```yaml
# What MetalLB and Traefik already had - and cert-manager needed too
syncPolicy:
  automated:
    prune: true
    selfHeal: true
  syncOptions:
    - CreateNamespace=true
```

One missing line in one file, invisible for months because the namespace already existed on the running cluster from whenever it was originally created by hand - the exact same root cause as Bug One: a piece of manually-created state that the GitOps repository quietly depended on without ever declaring.

## Both Bugs Have the Same Shape

A GitOps repository that's been running continuously never has to re-create its own prerequisites - namespaces, one-off Secrets, anything set up by hand once, early on. It works every day without those pieces being declared anywhere, because they already exist and nothing ever deletes them. The only thing that exposes the gap is bootstrapping the exact same repository against a cluster that has none of that implicit state - which is precisely what a real disaster recovery does, and precisely why "the manifests have been running fine for months" is not the same claim as "the manifests are complete."

A separate, smaller version of the same class of problem: applying the ApplicationSet CRD via plain `kubectl apply` failed on an oversized `last-applied-configuration` annotation - a known `kubectl` limitation, not an ArgoCD bug - and needed `--server-side` instead. Three different failure modes, one underlying cause: manifests that were correct for the specific way they'd always been applied before, and incorrect the moment that context changed.

## Why Not Just Apply Everything at Once

The repository has an ApplicationSet that auto-generates one Application per directory under `kubernetes/apps/` - at the time, more than thirty of them, including Vaultwarden, Gitea, Immich, and Nextcloud - plus a second bulk file tracking roughly fifteen more system-level components (Vault, cloudnative-pg, the full monitoring stack). Both are real, tested, and ready to use. Neither got applied during this bootstrap.

The reasoning: none of those thirty-plus apps' actual data existed in the new cluster yet. Vault, ExternalSecrets, and the NFS storage provisioner - dependencies nearly every one of those apps needs just to start - weren't live yet either. Applying the ApplicationSet at that point wouldn't have restored thirty real applications; it would have spun up thirty *empty* ones, each claiming a fresh PVC, which then need to be found and manually overwritten with restored data after the fact - a strictly worse and riskier ordering than restoring each app's data before its first sync ever happens. A fresh, empty Immich or a brand-new Gitea repository is not a smaller version of a successful recovery. It's a different failure, wearing a green checkmark.

Instead, each `kubernetes/system/*/application.yml` got applied individually, in dependency order, verified healthy before moving to the next - the same deliberate, one-thing-at-a-time approach that caught both bugs above in the first place. Bulk-applying thirty-plus manifests simultaneously would have produced thirty-plus simultaneous failure signals to untangle instead of two clear ones. The ApplicationSet and the bulk system-bootstrap file both stay staged, ready to take over once every component they'd cover has already been verified working the careful way - the "let GitOps own everything" step comes last, not first, in a from-scratch rebuild.

---

The Azure Bicep/Terraform equivalent is a `az deployment` that's been running as an incremental update against the same resource group for a year - it will happily skip re-declaring a resource group, a role assignment, or a diagnostic setting that already exists, right up until you deploy the identical template into a fresh subscription and discover which pieces were never actually captured as code. The fix discipline is identical: periodically deploy the full template into a genuinely empty environment, not just incrementally onto one that's already correct.
