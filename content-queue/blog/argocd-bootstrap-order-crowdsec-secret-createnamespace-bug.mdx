A [GitOps repository](/blog/argocd-gitops-k3s-homelab/) that has been running for months builds false confidence: every manifest in it is, by definition, one that already works. That confidence lasts until you bootstrap the same repository against a brand-new cluster. That's when two bugs in the manifests themselves showed up, both invisible until then and neither caused by the rebuild.

**[View the complete homelab infrastructure source on GitHub 🐙](https://github.com/dwoitzik/homelab-infrastructure)**

## Bug One: A Secret Reference With No Secret Behind It

Traefik's Application manifest referenced a CrowdSec bouncer API key two ways: as a plaintext environment variable value committed directly in the YAML, and as a Kubernetes Secret (`crowdsec-bouncer-key`) the pod also expected to mount. The plaintext value in Git is a separate problem. I flagged it instead of rewriting it on the spot, because scrubbing git history is not something to do in the middle of a recovery. The Secret, meanwhile, didn't exist anywhere in the new cluster, because nothing in the GitOps repository creates it. It had been created by hand, once, on the original cluster, and never captured as code.

The pod sat in `FailedMount` for about eight minutes before I diagnosed it. The unblock was a manual `kubectl create secret` with the already-exposed plaintext value, purely to get Traefik running. I used `--from-file` rather than `--from-literal` so the value wouldn't also land in shell history or a process list. That's a workaround. The real fix is rotating the key and moving it into Vault behind an ExternalSecret like every other credential in the cluster, and that needs Vault to exist first, which the rebuild hadn't reached yet when this bug surfaced.

## Bug Two: A Sync Option Present on Every Sibling, Missing on One

cert-manager's Application manifest was missing `syncOptions: [CreateNamespace=true]`. The sibling Applications for MetalLB and Traefik had it, and so does the [correct version of this exact Application](/blog/cert-manager-wildcard-k3s-cloudflare/) documented elsewhere on this site. Only this one file lacked it. The first sync failed outright:

```
namespaces "cert-manager" not found
```

ArgoCD retried five times and gave up. The unblock was a manual `kubectl create namespace cert-manager` plus a manual sync, since the automated retries were already exhausted by the time I diagnosed it. The permanent fix is the pattern the sibling Applications already use:

```yaml
# What MetalLB and Traefik already had - and cert-manager needed too
syncPolicy:
  automated:
    prune: true
    selfHeal: true
  syncOptions:
    - CreateNamespace=true
```

One missing line in one file, invisible for months because the namespace already existed on the running cluster, created by hand at some point. Same root cause as Bug One: manually created state that the GitOps repository depended on without ever declaring it.

## Both Bugs Have the Same Shape

A GitOps repository that runs continuously never has to re-create its own prerequisites: namespaces, one-off Secrets, anything set up by hand once, early on. It works every day without those pieces being declared anywhere, because they already exist and nothing deletes them. Only bootstrapping the same repository against a cluster with none of that implicit state exposes the gap. That's exactly what a real disaster recovery does, and it's why "the manifests have been running fine for months" is a different claim from "the manifests are complete."

A smaller case of the same class: applying the ApplicationSet CRD with plain `kubectl apply` failed because the `last-applied-configuration` annotation exceeded the 256 KiB annotation size limit. That's a known client-side apply limitation, not an ArgoCD bug, and `--server-side` avoids it. Three failure modes, one cause: manifests that were correct for the way they had always been applied, and wrong the moment that context changed.

## Why Not Just Apply Everything at Once

The repository has an ApplicationSet that generates one Application per directory under `kubernetes/apps/` (at the time more than thirty, including Vaultwarden, Gitea, Immich, and Nextcloud), plus a second bulk file tracking roughly fifteen more system-level components (Vault, cloudnative-pg, the full monitoring stack). Both are real, tested, and ready to use. Neither got applied during this bootstrap.

None of those thirty-plus apps' data existed in the new cluster yet. Vault, ExternalSecrets, and the NFS storage provisioner, which nearly every one of those apps needs just to start, weren't live either. Applying the ApplicationSet at that point wouldn't have restored thirty applications. It would have spun up thirty *empty* ones, each claiming a fresh PVC that then has to be found and overwritten with restored data after the fact. That ordering is strictly worse and riskier than restoring each app's data before its first sync. A fresh, empty Immich or a brand-new Gitea is not a partial recovery. It's a different failure with a green checkmark on it.

Instead, I applied each `kubernetes/system/*/application.yml` individually, in dependency order, and verified it healthy before moving on. That one-at-a-time approach is what caught both bugs above. Bulk-applying thirty-plus manifests at once would have produced thirty-plus simultaneous failure signals to untangle instead of two clear ones. The ApplicationSet and the bulk system-bootstrap file stay staged until every component they cover has been verified the slow way. In a from-scratch rebuild, "let GitOps own everything" is the last step, not the first.

The Azure equivalent is a Bicep template deployed with `az deployment group create` in incremental mode against the same resource group for a year. Incremental mode leaves alone anything in the resource group that the template doesn't declare, so a hand-made role assignment or diagnostic setting keeps working right up until you deploy the identical template into a fresh subscription and find out which pieces were never captured as code. Terraform has the same blind spot for anything outside its state. The discipline is the same too: periodically deploy the full template into an empty environment, not just incrementally onto one that's already correct.
