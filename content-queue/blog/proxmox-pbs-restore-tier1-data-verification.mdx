When my single [mini PC Proxmox host\*](/go/4bv3yF1) needed a full foundation rebuild (boot disk migration, kernel cleanup, the works), the first rule wasn't "start rebuilding." It was "prove nothing is lost before you touch anything." A rebuild you can't verify is a slower way to lose data. A consumer mini PC like this one has no IPMI or out-of-band console (see the [full hardware tour](/blog/homelab-hardware-tour-physical-rack/)), so every recovery step here had to work over SSH or not at all.

The three VMs at risk were the entire k3s control plane and worker set. Every stateful PVC for Vaultwarden, Headscale, Vault, Authelia's Postgres and more lived on their local-path storage. Before any host-level change, all three needed their data extracted and independently verified. Below is the method, including the one dataset that looked lost and turned out never to have held data.

## Rule One: Restore to Scratch VMIDs, Never Boot Them

Proxmox VE's `qmrestore` will happily overwrite the original VMID with `--force`, or restore under a new one and boot it straight away with `--start`. Neither is what you want when the goal is *inspection*, not *recovery in place*. The restores from Proxmox Backup Server targeted scratch VMIDs (911/912/913, deliberately outside the original 211/212/213 range) on HDD-backed storage instead of the host's NVMe, so the restore itself wouldn't add wear to the drive whose failure mode you might be trying to diagnose.

```bash
# Restore to a scratch VMID, on HDD storage, never the production range
qmrestore <backup-id> 911 --storage media
```

None of the three VMs was ever started. A restored VM that boots starts writing to its disk immediately (new logs, DHCP renewals, cron jobs), which is the opposite of what you want when the point is a byte-for-byte read of what was there at backup time.

## Rule Two: Mount Read-Only, Extract, Then Verify Against a Copy

To look inside a restored disk without booting it, `qemu-nbd` maps the qcow2/raw image as a block device, which you then mount read-only:

```bash
qemu-nbd -r -c /dev/nbd0 /path/to/vm-911-disk-0.raw
mount -o ro,noload /dev/nbd0p3 /mnt/inspect
```

`noload` matters here. It skips ext4 journal replay, which would otherwise write to the "read-only" mount to bring the filesystem to a consistent state. `ro` alone doesn't guarantee zero writes.

Once mounted, the local-path PVC directories are plain filesystem paths (`/var/lib/rancher/k3s/storage/`). A straight `rsync -a` from the read-only mount to a separate HDD-backed extraction directory gets everything off the restored disk without writing to it.

One finding this surfaced immediately: a worker node's local-path directory had three PVC directories that were duplicates of what the control-plane node already had, identical in bytes and file count: stale, orphaned copies from before those pods were rescheduled. Comparing mtimes settled which copy was current: the control-plane copies were dated to the actual backup window, the worker's were three weeks stale. Preserve both if you're not sure, but only trust the one whose timestamp matches reality.

The one class of failure read-only mounts can't help with: databases that need to run their own recovery logic to be queryable. SQLite files opened directly on a `ro,noload` mount failed with locking-protocol errors. The same files opened fine once copied to a writable location, where SQLite could create its shared-memory file and process the WAL normally. If you need to query a database from an extracted PVC, copy first, query second.

## Rule Three: One Missing Dataset, Three Independent Ways to Check

Not every dataset came back clean. One service's PVC turned up as an empty 44KB skeleton (a config template, no database, no repository data) with a modification time weeks older than the incident that supposedly caused the loss. That detail mattered: if the PVC was already empty before anything went wrong, it was a pre-existing condition and not a casualty of the rebuild.

Proving that took three independent checks:

1. **Every VM disk in the backup set:** I checked whether a current copy existed anywhere else in the restored disk set. It didn't; the only copy anywhere was the same stale skeleton.
2. **The live NFS export layer:** a completely different storage path, unrelated to the k3s VM disks. The Ansible-managed `/etc/exports` listed a path for this exact service, but the directory didn't exist on disk at all. A phantom export, not a live copy.
3. **The application-level backup layer** (a separate Velero/kopia S3 backup, independent of the Proxmox VM backups): I stood up a temporary, single-node, read-only-backed instance of the backup target just to query it directly. It held exactly two snapshots of the matching PVC, both with identical content hashes, both matching the same empty skeleton already found on disk.

Three unrelated recovery paths, three confirmations of the same state. That is what "verified lost" requires: enough independent checks that a blind spot in any one of them can't produce the wrong answer, not a single check that comes back empty. Afterward it was confirmed that this service had never held data worth preserving, so it closed out as expected rather than as a loss.

## The General Pattern

Everything else (Vault's Raft data, Vaultwarden's SQLite database and RSA signing key, Authelia's Postgres cluster) followed the same rules: scratch VMID, read-only mount, extract to a separate location, verify against a second copy of the tool or method wherever one exists. None of it required booting a single VM, and none of it put a byte of write load on the disk whose health was already in question.

A disaster recovery process that requires booting the thing you're trying to verify is backwards. Prove the data survived first, with tools that only read. Only then rebuild the system that will run it. Catching gaps before they turn into a real incident is what a [tested restore runbook](/blog/backup-restore-test-never-verified-network-conflict/) is for, and a working [Velero + Garage backup layer](/blog/velero-garage-k3s-backup/) makes this routine instead of a one-time forensic exercise.

---

Enterprise disaster recovery follows the same rule with different tools. Azure Backup's File Recovery mounts a VM recovery point's disks over iSCSI so you can browse files without restoring the VM, and Azure Site Recovery's test failover is meant to run in an isolated network so you can verify a recovery point without touching production. Verify before you commit, and never let the verification step be the thing that puts data at risk.
