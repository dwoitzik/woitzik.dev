Discord voice was choppy, and in one direction only: I heard everyone fine, but others heard me as robotic, garbled audio that came and went. Over mobile data it was clean, which put the problem on my home network path, not Discord or the ISP.

The investigation led to a textbook bufferbloat setup on the [MikroTik RB5009\*](/go/4w08b21): no QoS or AQM on the WAN interface, a 50 Mbit upload ceiling that is easy to saturate, and RouterOS's default `pfifo` queue doing nothing to stop one bulk transfer from monopolizing the link against latency-sensitive UDP voice traffic.

**[View the complete homelab infrastructure source on GitHub](https://github.com/dwoitzik/homelab-infrastructure)**

## The Investigation

First step: check what was actually configured on the WAN. `/queue simple` and `/queue tree` were both empty, so `ether1` (WAN) was running on RouterOS's default `pfifo` (plain FIFO, no active queue management).

The ISP profile is asymmetric cable: 1000 Mbit down, 50 Mbit up. That is the value from repeated live speedtests, not MySpeed's configured target, which happened to match but wasn't the authoritative source. A 50 Mbit uplink is easy to fill, and without AQM nothing stops the send buffer from filling up and inflating latency for everything sharing the link.

The next question was what saturates the upload. I went through the WAN-upload consumers:

- **Garage/PBS backups**: LAN-local, don't cross the WAN. Ruled out.
- **PBS Google Drive offsite sync**: already disabled (REL-051). Ruled out.
- **Image pulls**: downloads, not uploads. Ruled out.
- **Cloudflare-tunneled remote Jellyfin/Immich streaming**: the realistic WAN-upload consumer.

So the traffic profile is mostly latency-insensitive bulk upload (media streaming through Cloudflare), with Discord's UDP voice flow competing for the same 50 Mbit.

## Why Simple Queues, Not Queue Trees

The usual RouterOS QoS design is mangle plus queue tree: mark packets by type in mangle, then shape the marks with queue-tree rules. The obstacle here is that **FastTrack is enabled globally** (see `firewall_deterministic.tf`). Once a connection is fasttracked, its packets skip the firewall, including mangle, so a mark-based queue tree would stop seeing most real traffic, which is exactly the traffic that needs shaping.

My reasoning at the time was that an address-based Simple Queue sidesteps this: its `target` is a plain IP-range match with no mangle dependency. That part is true, but it does not get around FastTrack. See the correction below.

## The Fix: PCQ Behind a Rate Cap

The change is 51 lines of Terraform, most of which is the comment block explaining the reasoning. The resource itself:

```hcl
# terraform/stacks/network/qos.tf

resource "routeros_queue_simple" "wan_egress_sqm" {
  name      = "wan-egress-sqm"
  target    = ["10.0.0.0/16"]
  max_limit = "45M/900M"
  queue     = "pcq-upload-default/pcq-download-default"
  comment   = "SQM: cap WAN link under real measured ISP ceiling (1000/50 Mbit) + PCQ per-flow fairness so one bulk transfer can't fill the buffer and starve latency-sensitive traffic (Discord voice bufferbloat fix)"
}
```

Three details matter.

**1. `max_limit = "45M/900M"`: 90% of the real ceiling, not 100%.** Capping below the ISP's ceiling makes this router's queue the bottleneck instead of the modem's. Without that margin, the bottleneck (and its buffer) stays inside the ISP modem, outside this queue's control, and the bufferbloat just happens there instead.

**2. `queue = "pcq-upload-default/pcq-download-default"`: fairness between hosts.** PCQ splits traffic into sub-queues and serves them in turn. The default PCQ types classify by address (`pcq-upload-default` by source address, `pcq-download-default` by destination address), so the fairness is per host rather than per 5-tuple flow. For this problem that is enough: the Cloudflare tunnel's bulk upload and the machine running Discord come from different LAN addresses, so each gets its own sub-queue instead of the bulk stream monopolizing the link.

**3. `target = ["10.0.0.0/16"]`: all VLANs in one queue.** Deliberately not split per VLAN yet. The goal is fixing the shared WAN bottleneck, not per-VLAN prioritization. All five VLANs (10.0.10.0/24 through 10.0.100.0/24) share this WAN link.

## Correction: FastTrack Bypasses Simple Queues Too

The original version of this post (and the comment in `qos.tf`) claimed a Simple Queue works independently of FastTrack. That is wrong. MikroTik's [Packet Flow in RouterOS](https://help.mikrotik.com/docs/spaces/ROS/pages/328227/Packet+Flow+in+RouterOS) documentation lists what fasttracked packets skip: the firewall, connection tracking, **simple queues**, queue trees with `parent=global`, traffic-flow, IP accounting, IPsec, and more. With the global `fasttrack-connection` rule for `established,related` in place, this queue only sees packets that are not fasttracked, which leaves out most of a long-lived bulk stream.

So the queue above is not enough on its own. Two ways to make shaping actually apply, both documented by MikroTik:

- **Exempt the shaped traffic from FastTrack**, for example by narrowing the fasttrack rule so WAN-bound traffic is accepted without being fasttracked. This costs router CPU, so measure the load at full line rate.
- **Shape on the interface queue instead.** Interface queues are not on the FastTrack bypass list. Set `ether1`'s queue to a rate-limited AQM type, or attach a queue tree to `ether1` (not `parent=global`).

A second claim from the original also needs correcting. I had concluded there was no CAKE because `/queue type print` listed only `pfifo`/`bfifo`/`red`/`sfq`/`pcq`/`mq-pfifo`. That command lists the queue types that are configured, not the kinds RouterOS supports. RouterOS 7, which the RB5009 runs, can create CAKE and fq_codel types with `/queue type add kind=cake` or `kind=fq-codel`. CAKE with a bandwidth limit on the WAN interface is the more direct fix for bufferbloat than PCQ.

## Validation

Terraform: `fmt -check`, `validate`, and `tflint` were all clean on the change.

It was not applied when I wrote this. It went up as a PR for `atlantis plan` review, because I want to see the plan before any apply on the network stack. This is the gateway router, and a misconfiguration here affects every device in the apartment. Given the correction above, the plan and the change itself need another pass before the bufferbloat can count as fixed.

---

The principle carries over to any shared link: keep the bottleneck in a queue you control, cap it just below the real line rate, and do not let one bulk sender own the buffer. And confirm your shaping is actually on the packet path you think it is.
