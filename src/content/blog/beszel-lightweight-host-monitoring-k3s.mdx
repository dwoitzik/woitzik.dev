I already run `kube-prometheus-stack` with Prometheus, Grafana, and Loki, which covers everything inside the cluster. Host-level metrics like CPU temperature, disk health, and per-node resource usage on the Proxmox VMs and bare-metal machines needed something separate. The node-exporter inside kube-prometheus handles the k3s nodes, but the non-Kubernetes hosts were a blind spot: the Raspberry Pi 4B edge nodes (today I'd buy the [Raspberry Pi 5\*](/go/4wETNfv) instead) and the [BMAX Mini PC\*](/go/4bv3yF1) running Proxmox itself.

The obvious answer was another exporter. But I didn't want to manage another exporter, another Prometheus scrape config, and another set of dashboards for something that only needs to answer "is this machine healthy right now?"

## What Beszel Is

Beszel is a lightweight host monitoring hub with per-host agents. One container runs the dashboard, and each machine you want to monitor runs a small agent. It collects the basics (CPU, memory, disk, network, temperatures) without a full metrics pipeline.

What sold me: the entire deployment is one YAML file, it runs comfortably on a 64Mi memory request, and it has a built-in API health endpoint that makes Kubernetes probes trivial.

It also has to stay internal-only. No public DNS record, no Cloudflare proxy: the Beszel dashboard has no reason to be reachable from the internet. It's an admin surface, not a user-facing service.

## The Deployment

The full manifest lives at `kubernetes/apps/beszel/beszel.yml` and follows the same pattern as every other app in this cluster: PVC first, Deployment second, Service third, IngressRoute last.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: beszel
  namespace: apps
spec:
  replicas: 1
  strategy:
    type: Recreate
  selector:
    matchLabels:
      app: beszel
  template:
    spec:
      dnsConfig:
        options:
          - name: ndots
            value: "1"
      containers:
        - name: beszel
          image: henrygd/beszel:0.18.7
          env:
            - name: APP_URL
              value: https://beszel.woitzik.dev
          securityContext:
            allowPrivilegeEscalation: false
            seccompProfile:
              type: RuntimeDefault
            capabilities:
              drop: ["ALL"]
          ports:
            - containerPort: 8090
          volumeMounts:
            - name: data
              mountPath: /beszel_data
          resources:
            requests:
              cpu: 25m
              memory: 64Mi
            limits:
              cpu: 200m
              memory: 128Mi
```

The `ndots: 1` DNS config is the same tweak I use on every deployment in this cluster. With the Kubernetes default of `ndots: 5`, any name with fewer than five dots, including external ones like `api.github.com`, is tried against every search domain (`apps.svc.cluster.local`, `svc.cluster.local`, `cluster.local`) before being resolved as-is. Each external lookup then costs several failed queries first. With `ndots: 1`, any name containing a dot is tried as an absolute name first, and single-label names like `beszel` still go through the search list.

The security context follows the same hardening pattern as everything else: no privilege escalation, seccomp `RuntimeDefault`, all capabilities dropped. The container doesn't need any of them.

The PVC is `nfs-client`, not `local-path`, for the same reason as every other app in this repo: local-path pins the PV to whichever node created it, and nfs-client doesn't. Velero's daily schedule already covers the `apps` namespace with `defaultVolumesToFsBackup`, so the PVC gets backed up without any extra configuration.

## Kyverno Caught the First Attempt

The image tag is pinned to `0.18.7`, not `:latest`. That wasn't my first instinct: I initially wrote `henrygd/beszel:latest` because it was quicker. Kyverno's `disallow-latest-tag` policy, by then enforced in the `apps` namespace, rejected it at the admission webhook before any pod was created. That's what the policy is for. With an unpinned tag, what you deploy depends on whatever the registry serves at apply time, not on what you tested.

If you run Kyverno and don't have this policy, add it. It catches exactly this kind of lazy shorthand before it turns into a "works on my machine" surprise.

## Internal-Only by Design

The IngressRoute makes this clear:

```yaml
apiVersion: traefik.io/v1alpha1
kind: IngressRoute
metadata:
  name: beszel-final
  namespace: apps
spec:
  entryPoints: [websecure]
  routes:
    - match: Host(`beszel.woitzik.dev`)
      kind: Rule
      middlewares: [{name: authelia}]
      services: [{name: beszel, port: 8090}]
  tls: {secretName: wildcard-woitzik-dev-tls}
```

There's no `cloudflare_dns_record` in Terraform for `beszel.woitzik.dev`. The hostname only resolves inside the LAN, through AdGuard's wildcard rewrite that points `*.woitzik.dev` at the Traefik VIP. The Authelia middleware gates access with the same SSO login as every other admin surface in the cluster.

I use the same pattern for ArgoCD, Gitea, and any other service that needs to be reachable from the LAN but has no business on the public internet. It costs nothing to maintain: no public DNS entry, no WAF rules, no extra certificate (the existing wildcard covers it), and no internet-facing attack surface. The DNS wildcard does all the work.

## Resource Usage

128Mi memory limit, 200m CPU limit. For context, Prometheus alone uses 2Gi on this cluster. Beszel's footprint is closer to a sidecar than to a standalone monitoring system.

Monitoring tools have a nasty habit of becoming the thing that needs monitoring. A tool capped at 128Mi that reports on 16Gi nodes isn't going to be what tips your resource budget.

## What It Covers vs. What It Doesn't

Beszel handles the basics: CPU, memory, disk, network, temperatures. It does not replace Prometheus for cluster-level metrics, alerting, or log aggregation. It answers "is this specific host healthy right now?", while Prometheus answers "is my infrastructure operating within its SLOs?"

In my setup, kube-prometheus-stack (Prometheus, Loki, Alertmanager, Grafana) owns cluster metrics, service-level alerting, and dashboards. Beszel owns host-level health for every machine in the rack, in one dashboard that never leaves the LAN.

If you're running a smaller homelab without a full Prometheus stack, Beszel might be enough on its own. If you already have Prometheus, it fills the gap for non-Kubernetes hosts without adding another exporter to manage.

---

The same principle holds from a 10-inch rack to a multi-subscription Azure landing zone: separate the monitoring layers, keep each one focused, and make sure the monitoring tool itself isn't the weakest link in resource consumption or attack surface.
