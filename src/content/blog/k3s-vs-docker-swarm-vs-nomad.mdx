Choosing between k3s, Docker Swarm, and Nomad stopped being a features question some time ago. It is now a question of **project trajectory**, and the three projects are heading in different directions. k3s tracks upstream Kubernetes within weeks and ships three supported release lines at once. Docker Swarm still works, but its vendor has redirected development toward Kubernetes, and Docker Engine v29 broke parts of it badly. Nomad is the technically lightest option and the only one of the three that is not open source.

## TL;DR: The Picks

| Orchestrator | Pick it if | Main risk in 2026 | License |
|---|---|---|---|
| **k3s** | You want Kubernetes, or your tooling already assumes it | You inherit the Kubernetes upgrade treadmill | Apache-2.0 |
| **Docker Swarm** | You already run it and need cluster mode with no extra daemon | Docker Engine v29 dropped client and plugin compatibility | Apache-2.0 |
| **Nomad** | You want one scheduler for mixed container and non-container workloads | BUSL source-available, not open source | BUSL → MPL-2.0 after 4 years |

If you are starting fresh in 2026, the default is k3s. Nomad is lighter and Docker Swarm is simpler to learn, but k3s is the only one of the three with a release cadence you can plan against, and the surrounding ecosystem has consolidated around Kubernetes.

## The three facts that decide it

Before features, three documented facts constrain the decision.

### 1. Docker Engine v29 broke Swarm compatibility

Docker Engine v29.0.0 raised the **minimum supported daemon API version to 1.44**, dropping compatibility with clients built against Docker Engine older than v25. Tooling compiled against an older API gets a hard `client version ... is too old` rejection. You can lower the floor again with `DOCKER_MIN_API_VERSION` or `min-api-version` in `daemon.json`, and v29.3.0 relaxed the default to API 1.40, but anyone who upgraded through v29.0 to v29.2 without knowing that hit the wall first.

The damage is not evenly distributed, and this is the part that matters if you run Swarm: **legacy (V1) Docker volume plugins are rejected by the v29 daemon.** Because Swarm requires cluster-scoped persistent storage, Swarm operators hit this disproportionately. The failure mode is nasty: Docker keeps the volume metadata but cannot reach the plugin needed to mount the volume, so **your data appears to be gone while it is still intact on the storage target**.

There is a second trap in the same release line. On v29.0.0 through v29.2.0, encrypted overlay networks **stop passing traffic to containers on v28 and older Engines**, with no error. That is exactly the state a staged rollout puts you in: some nodes on v29, the rest still on v28. Docker fixed it in v29.2.1. If you use encrypted overlay networks, skip v29.0.0 to v29.2.0 entirely and upgrade straight to v29.2.1 or later.

### 2. Docker has redirected Swarm development toward Kubernetes

Docker's own retired-products page is unusually direct about SwarmKit, the project that powers Swarm mode:

> While Swarm mode remains functional, development has slowed in favor of Kubernetes-based solutions.

That is the vendor stating the trajectory. Swarm is not scheduled for removal: `docker swarm init` still works, and the mode is still documented as built into the Engine. But this is maintenance, not investment. Portainer, the most visible Swarm management platform, published an advisory on 2026-03-10 recommending caution with continuing to run Swarm and planning a gradual move to Kubernetes.

### 3. Nomad is not open source

This one gets repeated wrong. Nomad Community Edition is licensed under the **Business Source License**. The change license is MPL 2.0, but it applies *four years after the version is published*. A Nomad release from today becomes MPL 2.0 in 2030. If you need an open source orchestrator in 2026, Nomad is not one.

The support situation is stable but newly complicated. Since April 2026, after the IBM acquisition, HashiCorp's self-managed products follow IBM's enterprise software lifecycle. Nomad's support windows:

| Version | Base support ends | Extended support ends | Ongoing extended ends |
|---|---|---|---|
| 1.8.x (LTS) | 2026-04-30 | 2026-04-30 | 2026-04-30 |
| 1.10.x (LTS) | 2027-04-30 | 2027-04-30 | 2027-04-30 |
| 1.11.x | 2026-10-31 | 2026-10-31 | 2026-10-31 |
| 2.0.x | 2028-04-30 | 2029-04-30 | 2032-04-30 |

1.8.x is already out of support as of this writing, and 1.11.x ends 2026-10-31, within weeks. **Nomad v1.10.x is the last LTS line.** From the 2.0.0 release onward, Nomad also drops semantic versioning for IBM's Version-Modification-Fix model, so tooling that parses Nomad version strings needs updating.

One operational warning before you plan a mixed estate: a Nomad Enterprise cluster **cannot be downgraded**, and servers running open-source Nomad will *panic* if joined to an Enterprise cluster, because the Raft entries for Enterprise features are not parseable by the open-source build. Test that boundary before you need it.

## k3s: the default for a reason

k3s is a conformant Kubernetes distribution packaged as a single binary. As of October 2026 it maintains **three release lines concurrently**: v1.36.4+k3s1 is current, with v1.35.8 and v1.34.11 still receiving backports. Each build pins its whole dependency set. For v1.34.11+k3s1 that is Kubernetes v1.34.11, Kine v0.16.4, SQLite 3.53.4, etcd v3.6.14-k3s1, containerd v2.2.7-k3s1, runc v1.4.2, Flannel v0.28.4, metrics-server v0.9.0, Traefik v3.7.13, CoreDNS v1.14.7, helm-controller v0.16.27 and local-path-provisioner v0.0.37.

That pinned list matters more than it looks. When something breaks at 02:00 you can read which exact version of which component is running instead of discovering it. My own homelab runs k3s across several nodes, and that pinned-component view is what makes problems like [ArgoCD cache staleness on a shared resource](/blog/argocd-cache-staleness-shared-resource-warning/) or [picking the wrong storage backend for cluster state](/blog/nfs-vs-local-path-sqlite-trap/) diagnosable at all.

The cost of k3s is that you inherit Kubernetes' upgrade treadmill. Upgrading across three minor versions is not a hobby, and every Helm chart in your stack is a chance for the chart to be behind the API version you just moved to. One concrete example from the 1.34 line: the bundled Traefik chart moved to v40.x, which renamed the ingress-nginx migration provider from `kubernetesIngressNginx` to `kubernetesIngressNGINX`. That is a breaking change arriving inside a k3s patch release.

I have written about the parts that bite in practice. The [Velero and Garage S3 backup chain](/blog/velero-garage-k3s-backup/) and [Unbound with AdGuard and keepalived](/blog/unbound-adguard-keepalived-homelab/) are both k3s deployments that took real iteration to get right.

## Docker Swarm: simpler, and now on borrowed time

Swarm's real advantage is that it is *already there*. No second daemon, no new control plane, no new YAML dialect. If your Docker workflow is a `compose` file and a handful of services, `docker stack deploy` is a very small step up, and the service model with rolling updates and health checks is more capable than plain Compose.

The case against it in 2026 is the two items above: the v29 compatibility break with its silent overlay-traffic failure mode, and a vendor that has said in writing that development has slowed. Neither makes Swarm unusable tomorrow. Both mean every future upgrade is a risk you cannot get support for.

If you are on Swarm, the sensible 2026 posture is: pin the Engine version deliberately, verify you are on v29.2.1 or later, audit for V1 volume plugins **before** you upgrade rather than after, and start introducing Kubernetes for new workloads so you are not migrating everything at once.

## Nomad: the best scheduler, the weakest license

Setting licensing aside, Nomad is well designed for its niche. It schedules containers, binaries, VMs and batch jobs through one job specification, it is built around a single deliberately small binary rather than a multi-component control plane, and its UI is easier to reason about than anything in the Kubernetes ecosystem. For a mixed estate (a few containers alongside a scheduled data job, an ETL step, a Windows task), that unification is the whole point, and Kubernetes does not do it without extra machinery.

Against that: BUSL rather than an OSI license, a support matrix reshuffled by the IBM acquisition, a semantic-versioning break at 2.0, and an ecosystem that assumes Kubernetes. If your team already lives in Kubernetes YAML, Nomad's job syntax is a second language to maintain for a saving you have to measure yourself.

## Head-to-Head

| Dimension | k3s | Docker Swarm | Nomad |
|---|---|---|---|
| Scheduling unit | Pod | Service (task) | Job (group, task, service) |
| Non-container workloads | No | No | Yes: binaries, VMs, batch |
| Control plane footprint | Single binary per node | Built into the Docker Engine, no extra daemon | Single binary |
| License | Apache-2.0 | Apache-2.0 | BUSL, becomes MPL-2.0 after 4 years |
| 2026 release cadence | Three concurrent K8s lines | Slowed, vendor-prioritised elsewhere | Spring/fall features, monthly as needed |
| Ecosystem direction | Consolidating around it | Maintenance | Stable, narrower |
| Upgrading is | Hard (K8s treadmill) | Easy | Moderate (mind the VMF versioning break) |

## Which one should you run?

**Run k3s** if your workloads are containers and you want the Kubernetes ecosystem: Helm, ArgoCD, Prometheus operators, the CNCF ecosystem at large. This is the default in 2026 and the choice I would make for anything new.

**Stay on Docker Swarm** only if you already run it in production and the migration cost is real. Treat it as a managed liability: pin versions, avoid the v29 trap, and plan the exit. Do not adopt it new in 2026.

**Run Nomad** if scheduling heterogeneous workload types on one control plane is worth more to you than an OSI license and a Kubernetes-shaped ecosystem. Make that trade knowingly: you are choosing source-available software with a four-year conversion clock, not open source.

If you cannot decide between two, run both on the same hardware for a month with one real workload. The theoretical comparison above is the least interesting part; how each behaves with your actual data on your actual disks is what decides it.

## Frequently Asked Questions

### Is Docker Swarm being deprecated?

Not formally. There is no scheduled removal, `docker swarm init` still works, and Swarm mode is still part of Docker Engine. But Docker's own documentation states that SwarmKit development "has slowed in favor of Kubernetes-based solutions," so treat it as maintenance-only. The practical risk arrived with Docker Engine v29, which broke client and plugin compatibility and hit Swarm operators hardest.

### Is Nomad open source?

No. Nomad Community Edition is licensed under the Business Source License. Versions become MPL 2.0 four years after publication, so a release from 2026 becomes open source in 2030. If you require an OSI-approved license today, that rules Nomad out. k3s and Docker Swarm are both Apache-2.0.

### Is k3s just "Kubernetes but worse"?

No. It is a conformant Kubernetes distribution (same API server, same controllers, same ecosystem) delivered as one binary with sensible defaults. The compromise is operational, not functional: you give up control over the component versions to get a maintainable install, which is why the pinned component list is worth reading before you debug anything.

### Can I run Docker Swarm and Kubernetes on the same host?

Technically, yes, but you should not. Both want to own the container runtime and the network stack, and the interaction between a Swarm overlay network and a CNI is a debugging experience you do not need to have. Run them on separate machines.

### What is the safest way to upgrade a Swarm cluster to Docker v29?

Go straight to v29.2.1 or later and skip v29.0.0 through v29.2.0, where encrypted overlay traffic to containers on older Engines silently stops during a staged rollout. Before you start, inventory your volume plugins: any V1 plugin will be rejected by the v29 daemon, and the resulting "missing" data is usually still on the storage target. Export your data first.

### Does Nomad support Kubernetes workloads?

Not natively. Nomad is not a Kubernetes scheduler and does not run Kubernetes manifests. There is no compatibility path if you need the Kubernetes API; pick k3s instead. Nomad's own strength, scheduling binaries and batch jobs alongside containers, is what Kubernetes does not offer natively.
