Three times in one week, my Proxmox host froze completely. No SSH, no web UI, no console. The only recovery was a hard power cycle. Each time, I lost every running VM and LXC at once: k3s control plane, workers, databases, all of it.

The first time, I blamed a kernel bug. The second time, I blamed ZFS. The third time, I found the actual chain: a marginal PSU causing CPU throttling under load, which pushed ZFS into a deadlock that locked the entire host.

## The Symptoms

The freezes weren't random. They correlated with sustained I/O load, specifically with several workloads competing for NVMe bandwidth at the same time:

- k3s datastore writes landing on the same NVMe as the ZFS pool
- Ollama LLM inference spinning up large model loads
- Paperless OCR bursts hitting the disk queue hard

Under moderate load, everything was fine. Under sustained high load across multiple subsystems, the host would lock up within minutes.

The first two freezes produced no useful logs. `journalctl` cut off mid-entry. No kernel panic, no oops, no MCE. Just silence.

## The PSU Theory

My [BMAX Mini PC\*](/go/4bv3yF1), an older B5A Pro (Ryzen 7 5825U), ships with an external power adapter that is undersized for what this chip can draw. (The linked current model has moved on to the newer 8745HS chip; the PSU and TDP details below are specific to my older unit.) The 5825U is a 15W-class mobile chip, but the BIOS on this board was set to a 54W TDP, and with all cores loaded (k3s workers, Ollama inference, OCR workers) the CPU boosts far past its nominal TDP.

The evidence for the PSU is circumstantial, not a measured overload: the freezes only happened when several heavy workloads ran at once, never at idle. An external adapter pushed past its rating lets its output voltage sag, and the board responds by throttling the CPU to cut power draw. That's where the real trouble started. (A plug-in meter like the [TP-Link Tapo P110\*](/go/3STKPwD) is the cheap way to check wall draw on your own box before assuming software.)

## The ZFS Deadlock

ZFS batches writes into transaction groups (txgs). Dirty data accumulates in memory and is written out by the `txg_sync` thread, by default at least every 5 seconds or sooner once enough dirty data piles up. While a txg sync is in progress, new writes that exceed the dirty-data limit are throttled and eventually wait for it to finish.

When the CPU throttles mid-sync and I/O latency spikes at the same time, the sync takes far longer than usual. Writers pile up behind it, memory pressure rises, and the ARC has to evict to make room.

My working theory for ZFS 2.4.1, the version running on this host, is that ARC eviction ended up blocked behind the stalled txg sync. That matches a deadlock class OpenZFS has documented before under memory pressure ([txg_sync hung task when shrinking ARC, openzfs/zfs#4319](https://github.com/openzfs/zfs/issues/4319), [ARC eviction thread blocking on allocations, openzfs/zfs#12985](https://github.com/openzfs/zfs/pull/12985)). The result is a circular wait: ARC eviction needs the txg to complete, the txg needs I/O bandwidth, I/O is delayed by CPU throttling, CPU throttling is caused by the PSU sag, and the PSU sags because everything is running at once.

The host doesn't panic. It just stops responding to anything that touches disk.

## The Fixes

### Fix 1: Disk I/O Isolation

The k3s VMs and the ZFS pool were sharing the same NVMe, and host-side page caching of VM disk I/O added to the contention. I moved the k3s VM disks to `cache=none` + `aio=native`:

```hcl
# terraform/stacks/proxmox/vm.tf
disks {
  scsi {
    scsi0 {
      disk {
        size    = "50G"
        cache   = "none"
        aio     = "native"
        storage = "local-lvm"
      }
    }
  }
}
```

`cache=none` opens the disk with `O_DIRECT`, bypassing the host page cache, so the guest handles its own caching. `aio=native` uses Linux native AIO instead of Proxmox VE's default `io_uring` (or the `threads` pool). It requires `O_DIRECT`, which is why it pairs with `cache=none`. This alone reduced I/O latency variance by 40% under load.

### Fix 2: ZFS ARC Limits

Without a cap, the ARC can grow to a large share of RAM and then has to shrink under memory pressure, which is exactly the eviction path implicated above. I capped it:

```bash
# /etc/modprobe.d/zfs.conf
# 4GB max ARC
options zfs zfs_arc_max=4294967296
```

On a 64GB host, 4GB is enough for read caching and leaves the rest to the VMs, so the ARC rarely has to evict under pressure. (Dirty data has its own limit, `zfs_dirty_data_max`, which defaults to 10% of RAM capped at 4GB.)

### Fix 3: txg Timeout Tuning

`zfs_txg_timeout` defaults to 5 seconds. On hardware with known I/O fragility, I shortened it:

```bash
# /etc/modprobe.d/zfs.conf
options zfs zfs_txg_timeout=2
```

The name is misleading: ZFS never aborts or retries a txg. `zfs_txg_timeout` is the maximum interval between txg syncs. Shortening it to 2 seconds means each txg carries less dirty data, so each sync finishes faster and a latency spike stalls less work behind it. It's a mitigation that shrinks the window for the deadlock, not a fix for it.

### Fix 4: Staggered Boot Order

The boot storm was a separate but related trigger. All VMs and LXCs starting at once drove the load average to 147 on the single NVMe. I added staggered boot ordering:

```hcl
# NFS boots first (no k3s dependency)
# k3s VMs boot 30s apart
# LXCs start last
```

This prevents the "everyone needs disk at once" pattern that was triggering the PSU sag in the first place.

## What It Taught Me

The root cause was hardware. But the software (ZFS 2.4.1) turned a power delivery problem into a host-level deadlock. My guess is that on ext4 or XFS the same PSU sag would have shown up as slow I/O or errors rather than a complete freeze.

First lesson: when debugging host-level freezes, check the physical layer (PSU capacity, thermal throttling, NVMe heat) before digging into kernel logs and ZFS tuning parameters. Second lesson: ZFS is excellent for data integrity, but its complexity leaves edge cases where a minor hardware issue becomes a major software deadlock.

After these four changes, plus dropping the BIOS TDP from 54W to 25W, the host has been stable through sustained load tests. (Weeks later, `ryzenadj -i` showed the BIOS slider isn't enforced on this board: with 25W set, the SMU still reported a 35W STAPM limit. Power limits are now applied at boot with `ryzenadj` instead.) The PSU is still marginal, and the proper fix is a higher-capacity unit. Until then, the software mitigations keep the hardware weakness from cascading into a deadlock.

The difference is that Azure hides the PSU behind an SLA: you get a throttled VM instead of a frozen host.
