Run `az aks create` with the defaults and you get a public API server FQDN, a Standard Load Balancer that gives every node a direct outbound path to the internet, and local accounts enabled, so an admin kubeconfig works from anywhere the API server is reachable. None of that is a bug. It's the fast path, and for a demo cluster it's fine.

For a cluster inside a governed Hub & Spoke, those are three separate audit findings. This is the Terraform that closes them: a private API server, forced-tunneled egress through a firewall you already control, and private-endpoint-only ACR and Key Vault.

## Target Architecture

```
                         ┌─────────────────────┐
                         │   Azure Firewall     │  ← you supply the IP
                         │  (existing / NVA)     │
                         └──────────┬───────────┘
                                    │ UDR: 0.0.0.0/0
                         ┌──────────┴───────────┐
                         │   vnet-aks            │
                         │                       │
              ┌──────────┴──────────┐  ┌─────────┴──────────┐
              │  snet-aks-nodes     │  │ snet-private-       │
              │  (default-deny NSG) │  │ endpoints            │
              │                     │  │  - ACR (Premium)     │
              │  Private AKS        │  │  - Key Vault         │
              │  (no public FQDN)   │  │                      │
              └─────────────────────┘  └─────────────────────┘
```

Three decisions drive the design, the same ones behind the [Hub & Spoke module](/blog/azure-terraform-hub-spoke-zero-trust/) this cluster is built to sit behind. The control plane has no public endpoint and is reachable only from inside the VNet, a peered network, or a VPN. Node egress is forced-tunneled instead of using default outbound, so every packet leaves through a firewall you control. And the dependencies, ACR and Key Vault, are reachable only through private endpoints.

## Step 1: The API Server Has No Public FQDN

```hcl
resource "azurerm_kubernetes_cluster" "this" {
  # ...
  private_cluster_enabled             = true
  private_dns_zone_id                 = azurerm_private_dns_zone.aks.id
  private_cluster_public_fqdn_enabled = false

  network_profile {
    network_plugin = "azure"
    network_policy = "azure"
    outbound_type  = "userDefinedRouting"
  }
}
```

`private_cluster_public_fqdn_enabled = false` is the setting people miss. With `private_cluster_enabled = true` alone, AKS still publishes a public DNS record for the API server that resolves to its private IP. Nobody outside can connect to it, but it advertises the cluster and leaks internal addressing for no benefit. With the public FQDN disabled, the only name left is the private one, resolvable only through the Private DNS Zone.

The cluster needs its own Private DNS Zone for the API server (`privatelink.<region>.azmk8s.io`), linked to the VNet. It uses the same DINE-policy-safe `lifecycle.ignore_changes` pattern as the [Hub & Spoke module's](/blog/azure-terraform-hub-spoke-zero-trust/) centralized zones, because Azure Policy tagging fights this resource too.

## Step 2: `userDefinedRouting`, the Setting That Matters Most

`network_plugin = "azure"` and `network_policy = "azure"` get most of the attention in AKS networking guides. The setting that decides whether egress is inspectable is `outbound_type`.

Left at its default (`loadBalancer`), AKS provisions its own Standard Load Balancer outbound rule and every node gets a direct, uninspected path to the internet. A private API server with fully public node egress is a common half-measure: it looks locked down in the portal and isn't.

```hcl
resource "azurerm_route_table" "aks_egress" {
  route {
    name                   = "default-via-firewall"
    address_prefix         = "0.0.0.0/0"
    next_hop_type          = "VirtualAppliance"
    next_hop_in_ip_address = var.firewall_private_ip
  }
}

resource "azurerm_subnet_route_table_association" "aks_nodes" {
  subnet_id      = azurerm_subnet.aks_nodes.id
  route_table_id = azurerm_route_table.aks_egress.id
}
```

`outbound_type = "userDefinedRouting"` tells AKS to use this route table instead of provisioning its own path. The Route Table has to exist and be associated with the node subnet *before* the cluster is created. `depends_on` enforces that ordering, because AKS checks at creation time that the subnet has a `0.0.0.0/0` route and fails otherwise. The firewall also has to allow AKS's required outbound FQDNs and ports (the `AzureKubernetesService` FQDN tag on Azure Firewall covers most of them), or node provisioning fails.

## Step 3: ACR and Key Vault Without a Public Endpoint

Nodes still need to pull images and often read secrets. The naive fix, `admin_enabled = true` on the registry plus a shared pull secret in a Kubernetes Secret, is a credential that outlives any single deployment and shows up in `kubectl get secret -o yaml` for anyone who can read Secrets in that namespace.

```hcl
resource "azurerm_container_registry" "this" {
  sku                            = "Premium" # required for Private Link
  admin_enabled                  = false
  public_network_access_enabled  = false
}

resource "azurerm_role_assignment" "aks_acr_pull" {
  scope                            = azurerm_container_registry.this[0].id
  role_definition_name             = "AcrPull"
  principal_id                     = azurerm_kubernetes_cluster.this.kubelet_identity[0].object_id
  skip_service_principal_aad_check = true
}
```

The kubelet identity, which is the identity that pulls images (not the cluster's control-plane identity), gets `AcrPull` directly. No credential to rotate, nothing in a Secret, nothing to leak outside Entra ID. Key Vault follows the same shape: RBAC authorization, `public_network_access_enabled = false`, and `Key Vault Secrets User` for the kubelet identity, so the CSI Secrets Store driver can mount secrets without a static key.

## What This Doesn't Do

It's a starting cluster, not a finished platform. There's no Entra ID integration for `kubectl` auth (add `azure_active_directory_role_based_access_control` yourself), no multi-pool topology, and no cluster autoscaler wiring. `sku_tier` defaults to `Free`, which has no uptime SLA; set `Standard` for production. It also assumes you already have a firewall whose private IP you can hand it. If you don't, pair it with the [Azure Firewall Forced Tunneling module](https://github.com/dwoitzik/terraform-azurerm-firewall-forced-tunneling).

For running production Kubernetes past the "it deployed" stage, with the workflows and failure modes a getting-started guide skips, [GitOps and Kubernetes\*](/go/gitops-kubernetes-book) is the reference I kept open while building this.
