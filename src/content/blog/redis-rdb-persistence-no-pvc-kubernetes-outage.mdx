The Nextcloud outage looked like a capabilities problem at first. The cluster had just received a `securityContext` hardening pass (`readOnlyRootFilesystem: true` and dropped capabilities across most containers), and the timing fit. Pods were up and passed readiness checks, but PHP requests hung and returned zero bytes. The capabilities hardening had broken things before, on the same [BMAX Mini PC\*](/go/4bv3yF1) k3s cluster where the [securityContext post-mortem](/blog/kubernetes-securitycontext-hardening-broke-9-containers/) happened. It was a reasonable assumption.

It was wrong. The capabilities issue was real, but it wasn't what took Nextcloud down. This is the Redis story.

**[View the complete homelab infrastructure source on GitHub 🐙](https://github.com/dwoitzik/homelab-infrastructure)**

## The Setup That Created the Problem

Nextcloud's session data and file lock cache both run through a Redis instance deployed as a sidecar-style container in the same manifest. That Redis container had no `PersistentVolumeClaim`. It was intentionally ephemeral and purely in-memory; sessions only had to survive as long as the pod.

The problem: Redis doesn't know it's running without a PVC. Its default configuration ships with persistence enabled:

```
save 3600 1   # write RDB snapshot if 1 key changed in the last hour
save 300 100  # write RDB snapshot if 100 keys changed in the last 5 minutes
save 60 10000 # write RDB snapshot if 10000 keys changed in the last minute
```

Nextcloud is a busy application. Normal use easily generates 100 session and lock writes within 300 seconds. When that threshold triggered, Redis tried to write a snapshot and hit a read-only filesystem:

```
Failed opening the temp RDB file temp-repl-16307.rdb (in server root dir /data)
for saving: Read-only file system
Background saving error
```

On its own, that error would be logged and Redis would retry on the next threshold. The problem is `stop-writes-on-bgsave-error`, which is `yes` by default and means what it says: as long as the last background save failed, **Redis refuses every write command**.

## Why the Logs Were Misleading

The Redis log showed the RDB error. But Redis was still running, still answering `PING`, still reachable over the network. It only refused writes. From Nextcloud's side, the PHP session handler called `SET` and got a `MISCONF` error back instead of `OK`. PHP's error handling in that path doesn't surface a visible 500. It hangs the request or returns an empty response, depending on the session lock timeout.

From outside, pages loaded up to the authentication stage, then returned nothing. No 500, no timeout message. That looks exactly like what `capabilities.drop: [ALL]` does when it breaks an entrypoint: the process starts, gets partway through initialization, then stops.

The actual diagnostic path that found it:

```bash
# Redis container never restarted (restart count 0), so there is no
# previous instance: read the current container's log, not --previous
kubectl logs nextcloud-<pod> -n apps -c redis-nextcloud

# Key lines:
# "Failed opening the temp RDB file ... for saving: Read-only file system"
# "Background saving error"

# Confirm Redis is refusing writes:
kubectl exec -it nextcloud-<pod> -n apps -c redis-nextcloud -- redis-cli SET test_key test_val
# → (error) MISCONF Redis is configured to save RDB snapshots...
```

Once the Redis error surfaced, the fix was obvious.

## The Fix: Invoke redis-server Directly with Persistence Off

The fix reused the pattern already in place for the cluster's other ephemeral Redis instances (immich-redis, valkey): invoke `redis-server` directly with explicit flags instead of relying on the image's default config.

```yaml
# Before: redis-nextcloud relied on image defaults (persistence on)
containers:
  - name: redis-nextcloud
    image: redis:8

# After: explicit command disabling both RDB and AOF
  - name: redis-nextcloud
    image: redis:8
    command:
      - redis-server
      - "--save"
      - ""          # empty string disables all save thresholds
      - "--appendonly"
      - "no"
```

The same change applied to paperless's Redis, which had the same no-PVC configuration. The Authelia Redis stayed as it was. It has a real PVC (`kubernetes/system/redis`), so its `--appendonly yes` configuration is intentional and works.

## The Asymmetry That Makes This Hard to Catch

Redis with persistence enabled and no PVC doesn't fail immediately. It runs, accepts connections, handles traffic, and looks healthy in every Kubernetes signal:

- Pod status: `Running`
- Readiness probe: passing (Redis responds to TCP or `PING` checks)
- ArgoCD application: `Synced/Healthy`
- Restart count: 0

The failure only appears once the first save threshold is hit. With the `300 100` rule (100 writes in 5 minutes) that can be minutes into normal operation, or an hour later via `3600 1` if traffic is light. Once the first RDB save fails and `stop-writes-on-bgsave-error` kicks in, the failure is silent at the Redis level and confusing at the application level.

The check that would have prevented the outage:

```bash
# Before deploying any Redis instance, check whether it has a PVC:
grep -A 20 "redis" kubernetes/apps/nextcloud/nextcloud.yml | grep -i "persistentVolumeClaim\|claimName"
# If nothing → persistence must be explicitly disabled
```

Or, more defensively, make it policy: any Redis container without a PVC in its volume list gets `--save "" --appendonly no`.

## Why This Shows Up in Hardened Clusters More Than Default Ones

The `readOnlyRootFilesystem: true` hardening is what surfaced this. Without it, Redis would have written its RDB snapshots to the container's writable filesystem: wasteful, potentially filling the node's ephemeral storage, but harmless in the short term. The write would succeed, `stop-writes-on-bgsave-error` would never trigger, and the outage would never happen.

The hardening exposed a misconfiguration that had only stayed dormant because the filesystem was writable. The hardening was correct. The Redis configuration was wrong, and the writable filesystem had been absorbing the mistake without anyone noticing.

---

The same applies to any Redis instance in Kubernetes whose sessions, cache, or other data don't need to survive a pod restart. If the Redis container has no PVC, give it `--save "" --appendonly no` as explicit arguments instead of inheriting defaults designed for a server with durable storage.
