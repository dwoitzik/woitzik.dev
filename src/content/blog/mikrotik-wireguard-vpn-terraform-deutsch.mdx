Remote-Zugriff läuft seitdem über [Headscale mit OIDC über Authelia](/blog/headscale-oidc-k3s-authelia/) (englischer Artikel). Die Terraform-Muster unten funktionieren auf RouterOS 7 weiterhin, laufen bei mir aber nicht mehr.

WireGuard ist inzwischen der Standard für Remote-Access-VPNs: schnell, einfach und mit moderner Kryptografie. Dieses Setup läuft auf einem MikroTik RB5009, auf dem RouterOS 7 WireGuard nativ beherrscht, ganz ohne zusätzlichen Container. Die einfache Einrichtung verleitet allerdings zu schlampiger Sicherheit, etwa jedem verbundenen Gerät vollen Zugriff aufs gesamte interne Netz zu geben.

In einer sicheren Umgebung, ob Unternehmensnetz oder Homelab, sollte ein Handy, das ein Dashboard abruft, nicht dieselben Netzwerkrechte haben wie ein Admin-Laptop, der Infrastruktur deployt.

Dieser Artikel automatisiert ein WireGuard-„Roadwarrior"-Setup auf MikroTik RouterOS mit Terraform und setzt rollenbasierten Zugriff über Firewall-Filter durch.

## 1. Die VPN-Topologie festlegen

> **🇬🇧 English:** Die englische Fassung dieses Artikels: [Automating MikroTik WireGuard VPN with Role-Based Access via Terraform →](/blog/mikrotik-wireguard-vpn-terraform/).

Am Anfang stehen das VPN-Subnetz, der Listen-Port und die festen IPs für jeden Peer (jedes Gerät). In Terraform-`locals` liegt das alles an einer Stelle, und IP-Konflikte fallen später gar nicht erst an.

```hcl
locals {
  vpn_config = {
    subnet = "10.6.0.0/24"
    port   = 51820
    name   = "wg-roadwarrior"
  }

  vpn_handy_ip  = "10.6.0.2/32"
  vpn_laptop_ip = "10.6.0.3/32"
}
```

## 2. Das WireGuard-Interface anlegen

Mit dem `terraform-routeros`-Provider brauchen WireGuard-Interface und Gateway-IP des Routers im VPN-Subnetz genau zwei Ressourcen.

```hcl
# Create the WireGuard Interface
resource "routeros_wireguard" "wg_vpn" {
  name        = local.vpn_config.name
  listen_port = local.vpn_config.port
  comment     = "Remote Access VPN"
}

# Assign the Gateway IP to the Router
resource "routeros_ip_address" "wg_ip" {
  interface = routeros_wireguard.wg_vpn.name
  # Uses cidrhost to automatically calculate the first IP (.1)
  address   = "${cidrhost(local.vpn_config.subnet, 1)}/24"
}
```

*`cidrhost()` berechnet die `.1`-Adresse aus dem Subnetz in den `locals`, es gibt also keine Adresse, bei der man sich vertippen kann. Wer den Bereich `10.6.0.0/24` von Hand wählt, prüft ihn vorher im [IPv4-Subnetzrechner](https://woitzik.dev/tools/subnet-calculator/) auf Überschneidungen. Ein VPN-Bereich, der sich mit einem LAN-Bereich überlappt, fällt oft erst Wochen später als kaputte Route auf.*

## 3. Die Peers (Geräte) anlegen

Als Nächstes kommen die Public Keys der Geräte auf den Router. WireGuard arbeitet mit Cryptokey Routing: Über das Feld `allowed_address` entscheidet der Router, zu welchem Peer eine IP gehört, und verwirft Pakete eines Peers, deren Quell-IP nicht in dessen Liste steht.

Weil jede `/32`-Adresse fest an einen Key gebunden ist, hat jedes Gerät eine feste Identität, auf die sich die Firewall-Regeln später verlassen können.

```hcl
resource "routeros_wireguard_peer" "handy_dw" {
  interface            = routeros_wireguard.wg_vpn.name
  comment              = "Smartphone DW - Limited Access"
  public_key           = "X9iI0RGNf7kTxdBOs4CsDcOQtKRFMYALY/ugHv67uAo="
  allowed_address      = [local.vpn_handy_ip]
  persistent_keepalive = "25s"
}

resource "routeros_wireguard_peer" "laptop_dw" {
  interface            = routeros_wireguard.wg_vpn.name
  comment              = "Laptop DW - Full Admin Access"
  public_key           = "zD+/yfLfjQ7N1H5NBIwa2zKNd/bLZ6VRdEbKBxCmOVA="
  allowed_address      = [local.vpn_laptop_ip]
  persistent_keepalive = "25s"
}
```

## 4. Rollenbasierten Zugriff durchsetzen (die Firewall)

Das VPN steht, aber ohne Firewall-Regeln kommt der Verkehr nirgendwo an, vorausgesetzt, es gibt eine strikte Default-Deny-Firewall wie in meinem [Artikel zur Zero-Trust-Firewall auf MikroTik](/blog/mikrotik-zero-trust-firewall-terraform/).

Die Forward-Chain legt fest, was jedes Gerät erreichen darf.

### Der Admin-Laptop (voller Zugriff)

Der Laptop ist ein vertrauenswürdiges Admin-Gerät. Er bekommt den gesamten Block `10.0.0.0/16`: Server, Management-Interfaces und die DMZ.

```hcl
resource "routeros_ip_firewall_filter" "fwd_06_vpn_laptop" {
  action       = "accept"
  chain        = "forward"
  src_address  = local.vpn_laptop_ip
  dst_address  = "10.0.0.0/16"
  place_before = routeros_ip_firewall_filter.fwd_99_drop_all.id
  comment      = "06: VPN - Laptop Full Access"
  
  lifecycle {
    ignore_changes = [src_address]
  }
}
```

### Das Handy (Split-Tunnel, eingeschränkter Zugriff)

Handys sind das größere Risiko. Sie hängen in öffentlichen WLANs und gehen verloren. Das Handy darf deshalb nur in bestimmte Service-Subnetze: das [Server-Netz `vlan20`](/blog/mikrotik-vlan-filtering-terraform-proxmox/) und den DMZ-Proxy. Auf das Proxmox-Management-VLAN und interne Infrastruktur-Backends hat es keinen Zugriff.

```hcl
resource "routeros_ip_firewall_filter" "fwd_07_vpn_handy_srv" {
  action       = "accept"
  chain        = "forward"
  src_address  = local.vpn_handy_ip
  dst_address  = "10.0.20.0/24"
  place_before = routeros_ip_firewall_filter.fwd_99_drop_all.id
  comment      = "07: VPN - Mobile limited to internal services"
}

resource "routeros_ip_firewall_filter" "fwd_08_vpn_handy_dmz" {
  action       = "accept"
  chain        = "forward"
  src_address  = local.vpn_handy_ip
  dst_address  = "10.0.30.0/24"
  place_before = routeros_ip_firewall_filter.fwd_99_drop_all.id
  comment      = "08: VPN - Mobile access to DMZ (External Proxy)"
}
```

*`place_before` setzt diese Regeln oberhalb der abschließenden „Drop All"-Regel ein, die die Chain verankert.*

## 5. Die Input-Chain nicht vergessen

Damit das VPN überhaupt eine Verbindung aufbauen kann, muss der Listen-Port auf dem WAN-Interface des Routers offen sein. Diese Regel gehört in die `input`-Chain, weil der Handshake am Router selbst endet.

```hcl
resource "routeros_ip_firewall_filter" "in_02_wg" {
  action       = "accept"
  chain        = "input"
  protocol     = "udp"
  dst_port     = local.vpn_config.port
  in_interface = "ether1"
  place_before = routeros_ip_firewall_filter.drop_all_input.id
  comment      = "IN-02: WireGuard handshake"
}
```

## Identität als Adresse

Das statische Cryptokey Routing von WireGuard bindet jeden Geräte-Key an eine feste IP-Adresse. Liegt diese Zuordnung in Terraform, stehen Identität und Firewall-Policy im selben geprüften Code, und die Zero-Trust-Regeln bleiben strikt, lesbar und in Git dokumentiert.

Kryptografische Identität an Netzwerkzugriff zu koppeln ist dasselbe Prinzip wie bei Azure Private Link und Managed Identity, nur eine Schicht höher.
