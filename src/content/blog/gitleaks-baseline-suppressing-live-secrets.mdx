A previous article covered [setting up gitleaks for homelab secret scanning](/blog/gitleaks-secret-scanning-homelab-remediation/): the setup, the pre-commit hook, and getting CI to fail on new commits that contain secrets. The setup was correct, the tool was running, and CI was green. It had also been suppressing a live production credential for weeks.

This follow-up is about what happens after gitleaks is running: the specific way a baseline file breaks the guarantees you think you have.

**[View the complete homelab infrastructure source on GitHub](https://github.com/dwoitzik/homelab-infrastructure)**

## What a Baseline File Does (and Is Supposed to Do)

When gitleaks first runs on an existing repo, it finds every secret-shaped string in the full git history, including secrets introduced years ago, rotated long since, and completely inert. Flagging those in CI creates noise that teaches developers to tune gitleaks out entirely, which is worse than not having it.

The baseline workflow is the standard answer: run gitleaks once (by default `gitleaks detect` scans the full commit history), export all findings to a JSON report, commit that file, and point later runs at it with `--baseline-path` so any finding already in the baseline is ignored. Commits that introduce *new* secrets still fail; old known-inert findings don't.

```bash
# Generate baseline from current HEAD
gitleaks detect --report-format json --report-path .gitleaks-baseline.json

# Tell gitleaks to use it
gitleaks detect --baseline-path .gitleaks-baseline.json
```

The assumption built into this workflow is that findings in the baseline are inert. They were there before the baseline was generated, they have been there since, and they are known.

## The Assumption That Broke It

The baseline was generated at a point when the repo contained Garage's `rpc_secret` and `admin_token` committed in a YAML file. Those were real production values (the cluster was live and using those exact secrets), but the baseline treated them as "known, reviewed, not a problem."

The commit that introduced them landed a few weeks before the baseline was generated, so the baseline capture included them. From then on, gitleaks treated them as baseline findings and never alerted on them.

```json
// .gitleaks-baseline.json - what it actually contained
{
  "Description": "Generic API Key",
  "StartLine": 8,
  "Match": "rpc_secret: \"REDACTED\"",
  "Secret": "REDACTED",
  "File": "kubernetes/system/garage/garage.yml",
  ...
}
```

gitleaks had identified the secret correctly. Nobody acted on it because the baseline said it was known.

## How the Finding Was Caught

The finding surfaced during a security audit pass. It came from a manual re-review of the baseline file itself, not from a gitleaks run. The review question was: "for each finding in this baseline, has the secret actually been rotated, or did we just suppress it?"

Garage's `rpc_secret` and `admin_token` had not been rotated. The values in the baseline were the values running in production. The baseline was suppressing a live credential committed to a public repository.

The audit entry:

```
SEC-013: Garage rpc_secret and admin_token committed to public repo
Status: CRITICAL - values unrotated since 2026-06-03 commit
Suppressed by: .gitleaks-baseline.json (line 47, line 89)
Action: rotate both via Vault, force ExternalSecret resync, restart Garage
```

## The Remediation

Rotation went through Vault, where the secrets were already supposed to live per the ExternalSecret setup:

```bash
# Write new secrets to Vault
vault kv patch secret/garage \
  rpc_secret="$(openssl rand -hex 32)" \
  admin_token="$(openssl rand -hex 32)"

# Force ExternalSecret to re-sync
kubectl annotate externalsecret garage-secret -n system \
  force-sync="$(date +%s)" --overwrite

# Verify new secret picked up
kubectl get secret garage-secret -n system -o jsonpath='{.data.rpc_secret}' | base64 -d

# Restart Garage to pick up new RPC secret
kubectl rollout restart deployment/garage -n system

# Verify RPC handshake succeeded on new secret
kubectl logs -l app=garage -n system | grep -i "rpc\|handshake\|connect" | tail -20
```

After rotation, the baseline was regenerated. It now contains only findings where the secret is confirmed rotated or confirmed not to be a real secret.

## The Structural Fix: Baseline Review as Part of the Rotation Workflow

Baseline files are useful. The problem is that "added to baseline" and "rotated and safe" are two different states that the workflow treats identically. Every finding in a baseline needs a documented reason for its suppression, and "it was already there when I set up gitleaks" is not one.

The updated workflow:

```bash
# Never auto-add to baseline without a verified status
# Each entry in .gitleaks-baseline.json now has a comment in the adjacent audit doc:
# - ROTATED: secret value changed, old value in history is inert
# - FALSE_POSITIVE: not actually a secret (test value, placeholder, etc.)
# - PENDING_ROTATION: known issue, rotation scheduled, date logged
```

PENDING_ROTATION is the honest version of what the original baseline was doing. It is explicit, it has a date, and it shows up in the audit document as an open finding instead of a silently closed one.

**The concrete check to run against any existing gitleaks baseline:**

```bash
# For each secret in the baseline, check if it's still in the live cluster:
# 1. Get the secret value from the baseline
# 2. Check Vault / ExternalSecret / live Secret for the current value
# 3. If they match → not rotated, baseline is suppressing a live credential
jq -r '.[].Secret' .gitleaks-baseline.json | while read secret; do
  echo "Checking: ${secret:0:8}..."
  # grep your Vault / k8s secrets for this value
done
```

This check doesn't fit into automated CI, because it needs access to the live secret values, not just the git history. It belongs in a periodic manual audit, not a commit hook. It is also the only check that answers the question that matters here: are the secrets gitleaks ignores actually safe to ignore?

The same class of problem shows up in Azure at scale. An Azure Policy exemption takes a resource out of the non-compliant count because someone exempted it when the policy was first assigned, not because the underlying condition was fixed. In a summary view, exempted and remediated both stop showing up as problems. Periodic review of exemptions, like periodic review of a gitleaks baseline, is the only way to tell the difference.
