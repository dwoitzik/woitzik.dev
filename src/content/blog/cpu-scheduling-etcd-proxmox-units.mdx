**Update:** this cluster has since moved off etcd entirely. A single-server k3s setup uses the
embedded SQLite datastore by default, and the multi-server HA path that would have used etcd
was never turned on here. The CPU-contention problem and the `cpu.units` fix below were real
while etcd was in play, and the underlying lesson (latency-sensitive, write-heavy workloads need
scheduling priority when they share a host with bursty ones like LLM inference or game servers)
still holds for anyone running multi-server etcd today. Read this as a general reference, not
a description of this cluster's current architecture.

etcd is the datastore behind the Kubernetes API. Every write (a ConfigMap update, a Lease renewal, a pod binding) is committed to etcd. When etcd is slow, everything is slow; when etcd times out, the API server stops answering.

On a single Proxmox host running k3s VMs alongside Ollama LLM inference, Minecraft game servers, and Docker media workloads, etcd shares CPU with everything else. Without scheduling priority, a Minecraft player join and an Ollama model load can delay etcd's writes enough to trigger leader-election timeouts.

The fix is `cpu.units = 2048` on the k3s VMs, while most other guests keep no explicit value and run at the cgroup v2 default of 100. These are the same VMs that get [staggered boot ordering](/blog/staggered-vm-boot-load-average-147/) to prevent I/O storms in the first place.

## How Proxmox CPU Scheduling Works

Proxmox relies on the kernel's fair scheduler (CFS, replaced by EEVDF from kernel 6.6) and cgroup CPU weights. Each guest gets a `cpu.units` value (`cpuunits` in Proxmox terms) that sets its share of CPU time when several guests compete for the same physical cores.

Only the ratio matters. When two guests with equal units compete for a single core, each gets 50% of the CPU time. When one has `units = 2048` and the other `units = 1024`, the first gets 2/3 and the second 1/3. Watch the baseline: Proxmox VE's default is 1024 only on cgroup v1. On cgroup v2 (every PVE 7 and 8 install) the default is 100, so a guest with no explicit value weighs about 1/20 of a 2048 guest, not 1/2. Set the value explicitly on every guest if you want a predictable ratio.

This is CPU weighting (priority when cores are shared), not CPU pinning (restricting a VM to specific cores). On a host with 16 threads and 12+ VMs/LXCs, most cores are shared between multiple workloads.

## The etcd Problem

etcd's performance depends on write latency. Every write (Lease renewal, ConfigMap update, Secret sync) requires an fdatasync to the WAL (write-ahead log) on disk before etcd acknowledges it. Controllers built on controller-runtime use those Lease objects for leader election, with defaults of a 15-second lease and a 10-second renew deadline. If the leader can't renew its Lease within the deadline, controller-runtime exits the process and the pod restarts.

On a single NVMe shared by all VMs, etcd's fdatasync competes with:
- Ollama reading model weights from disk (14GB qwen2.5 model)
- Minecraft world writes from the DMZ game server
- NFS serving PVC data to k3s pods
- ZFS txg commits flushing dirty data

Under normal load this is fine: NVMe IOPS are high enough to handle all of them. But when Ollama starts loading a 26B model (Gemma 4) and Minecraft generates terrain simultaneously, the NVMe queue depth spikes, fdatasync latency increases, and etcd's lease renewal window shrinks.

Without CPU priority, the etcd process also competes for CPU time with these workloads, so it can be slow to get scheduled even after its I/O completes. The scheduler doesn't know that etcd's commit is more important than Ollama's matrix multiplication. It sees runnable threads and, at equal weight, shares the CPU equally.

## The Fix

```hcl
# terraform/stacks/proxmox/vm.tf
# k3s VMs - explicit scheduling weight
resource "proxmox_virtual_environment_vm" "vm_srv_k3s_11_master" {
  cpu {
    cores = 6
    type  = "host"
    units = 2048
  }
}

# terraform/stacks/proxmox/lxc.tf
# Ollama LXC - units unset, so the cgroup v2 default of 100 applies
resource "proxmox_virtual_environment_container" "ct_srv_ai_01" {
  cpu {
    cores = 2
    limit = 2
  }
}
```

The k3s VMs get `units = 2048`. The Ollama LXC has no `units` set, so it runs at the cgroup v2 default of 100. When the k3s VM and Ollama compete for the same core, the k3s VM gets about 2048/2148, roughly 95% of the time. The one LXC that also runs at 2048 is the Minecraft server, because tick latency matters to players; it competes with the k3s VMs at equal weight.

This doesn't reduce Ollama's throughput under normal conditions. Without contention, Ollama still gets all the CPU it requests. The priority only kicks in when multiple workloads compete for the same cores simultaneously.

## The Evidence

Before `cpu.units = 2048`, the CNPG operator was restarting due to leader-election timeouts:

```
kubectl get pods -n cnpg-system
# NAME                                    RESTARTS
# cnpg-cloudnative-pg-5f8b9c4d6-xk2p4   310
```

310 restarts in 21 days. Each restart's log showed:

```
Leader election retry deadline exceeded
context deadline exceeded
```

After applying `cpu.units = 2048` and loosening the operator's leader-election timing (`--leader-lease-duration=60` and `--leader-renew-deadline=50`, both in seconds, up from the 15s/10s defaults), restarts dropped to zero.

The CPU priority alone didn't fix it; the leader-election timeout increase was also necessary. But the CPU priority reduced the frequency of fdatasync delays enough that the 50-second deadline is never challenged under normal load.

## The RAM Priority Interaction

CPU priority and memory priority are separate in Proxmox. `cpu.units` affects CPU scheduling; `memory.dedicated` and `memory.floating` affect RAM allocation.

On this host, both matter:
- etcd needs low-latency CPU for fdatasync (solved by `cpu.units`)
- k3s control-plane needs guaranteed RAM for API server and scheduler (solved by `memory.dedicated = 12284`, the same VM-vs-LXC memory model covered in [the overcommit guard writeup](/blog/overcommit-guard-python-host-freeze/))

The RAM allocation is a hard reservation: 12 GB is always available for the k3s-11 VM. The CPU priority is a soft weighting that only matters when cores are shared. Both are necessary: without RAM priority, the k3s VM could be ballooned down to 4 GB under pressure; without CPU priority, etcd could lose the fdatasync race to Ollama.

## What I'd Change

1. **Pin etcd to specific cores.** Proxmox's `affinity` setting only restricts where a VM may run. Guaranteeing etcd a core also means keeping every other guest off it, and that core then sits idle whenever etcd does. On a 16-thread host with 12+ workloads, the utilization loss isn't worth it.

2. **Monitor etcd fdatasync latency directly.** Prometheus can scrape etcd's `etcd_disk_wal_fsync_duration_seconds` metric. etcd's hardware guidance asks for a p99 under 10ms; an alert at p99 > 100ms would catch contention well before it triggers leader-election timeouts.

---

CPU scheduling priority is the same concept as Azure VM series selection: E-series VMs are memory-optimized, F-series are compute-optimized, and Dv5-series offer balanced resources. Choosing the wrong series for etcd (a latency-sensitive, write-heavy workload) produces the same performance degradation as running it without `cpu.units` on Proxmox. The difference is that changing it on Azure means resizing the VM, which reboots it, while Proxmox applies a new `cpuunits` value to a running guest.
