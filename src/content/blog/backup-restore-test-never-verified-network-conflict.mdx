`DISASTER-RECOVERY.md` had a Tier 1 procedure: restore the latest Proxmox Backup Server snapshot for a given container, boot it, confirm the application comes back up with real data. It was written carefully, reviewed, and had sat untested for months. Writing a recovery runbook and running a recovery are two different acts of verification, and only one of them had happened.

Running it for the first time found two problems: a network conflict nobody had documented, and a fallback tier that no longer existed.

## The Test, Designed to Be Safe

I picked `ct-srv-atlantis-01`. Not because it's low-stakes, but because its data (Terraform plan history, lock state) can be reconstructed if something goes wrong, unlike, say, Nextcloud's file storage. Backups go to a local [Seagate 2TB External HDD\*](/go/4vxwLpY), deliberately: a backup target that depends on the thing you're backing up *away from* defeats the purpose.

The test design: restore the latest PBS snapshot to a scratch VMID distinct from the running original, boot it there, verify that its Docker stack auto-starts and real data is present, then destroy the scratch instance. The live original was never touched or stopped, so the test couldn't take it down. That was the plan, anyway.

```bash
# Restore to a new, unused CTID -- not overwriting the original.
# ct-srv-atlantis-01 is an LXC, so this is pct restore (qmrestore for VMs);
# list snapshot volume IDs with: pvesm list <pbs-storage>
pct restore 9901 <pbs-storage>:backup/ct/<ctid>/<timestamp> --storage <target-storage>

# Original ct-srv-atlantis-01 keeps running the entire time
```

That's the right way to test a restore without creating the outage you're testing recovery from. It almost held up.

## The Gotcha the Documentation Never Mentioned

The restored container came up. Its Docker stack auto-started through the systemd unit already in place. Its data was intact: Terraform state, PR history, everything as expected.

Then it started fighting with the original over the network.

A restore from PBS brings back the source's container configuration as-is, including its static IP and MAC address. The scratch container 9901 booted with the same IP and MAC as the still-running `ct-srv-atlantis-01`. Two hosts claiming the same IP and MAC on the same VLAN produce exactly the failure you'd expect: ARP conflicts, the switch's MAC table flapping between two ports, traffic landing on whichever host answered last, and either host silently losing connectivity for a while.

```bash
# What actually needs to happen before booting a restored scratch instance:
# 1. Restore to new VMID (already being done)
# 2. Before first boot: change the network config to avoid IP/MAC collision
pct set 9901 -net0 name=eth0,bridge=vmbr0,ip=<scratch-ip>/24,hwaddr=<new-mac>
# 3. Only then start it
pct start 9901
```

Planning didn't catch this. Running the test did, when the original container's connectivity briefly degraded. It isn't a PBS bug. A restore is a duplicate of the source, network identity included. `pct restore` has a `--unique` flag that assigns a random MAC, but a static IP still has to be changed by hand before first boot, and the runbook mentioned neither.

## The Second Finding: A Runbook Step That Would Have Failed

While writing up this test, a second problem surfaced. It came not from testing but from cross-checking Tier 1's other listed recovery path against a separate finding from the same week: the Google Drive offsite sync had its own throttling and drift issues (REL-051), covered in a separate write-up. The runbook's fallback for "total PBS storage loss" pointed at that offsite sync as the recovery source.

That sync had been deliberately disabled months earlier. The destination Google Drive account didn't have enough free space for the datastore, so the sync was turned off instead of being left to fail daily. The runbook still described it as an active recovery tier. Following it during a real total-loss event would have sent someone down a dead end in the middle of an outage.

```markdown
<!-- DISASTER-RECOVERY.md, before -->
### Tier 1: Total PBS Storage Loss
Restore from the Google Drive offsite backup: [procedure]

<!-- After -->
### Tier 1: Total PBS Storage Loss
**No working recovery path currently exists for this scenario.**
Google Drive offsite sync is deliberately disabled (insufficient storage
quota for this datastore's chunk format - see docs/backup-strategy.md).
This is a known, deferred gap, not an oversight.
```

Documenting "this doesn't work" is strictly better than documenting a procedure that looks complete and fails at the one moment it matters. In an incident, a runbook that's honest about its gaps beats one that's optimistically wrong.

## Why "Documented" and "Tested" Are Different Claims

The instinct after writing a recovery procedure is to consider the job done: the steps are correct, they were reviewed, they match how the backup tool is supposed to work. But "the steps are correct on paper" and "these steps, run against a real host, produce a working restore" are different claims, and only the second one matters during an incident. The same applies to Kubernetes-level backups: a [Velero + Garage backup architecture](/blog/velero-garage-k3s-backup/) is only as trustworthy as its last verified restore.

The IP/MAC conflict only shows up when you run the restore on a network with other live devices on it, which is the situation a real recovery is in. A test in isolation (a lab VLAN with nothing else running) wouldn't have found it.

**The practice this argues for:** every documented recovery procedure gets a scheduled dry run, on a cadence that matches how often the underlying infrastructure changes (new network segments, new backup targets, new container images). Treat a runbook that hasn't been executed in the last few months as unverified, however carefully it reads.

---

The same gap shows up in Azure disaster recovery plans built on Azure Site Recovery (ASR) or storage account geo-redundancy: the failover procedure is documented, the RTO/RPO numbers are in the compliance doc, and nobody has triggered a failover drill against a network topology that matches production. The IP duplication here has a direct Azure analogue. ASR test failovers are meant to land in an isolated VNet for exactly this reason; run one into a network that can reach production, with the replica keeping the source's IP, and you recreate this conflict. Test the actual failover, not just the plan for one.
