[Garage S3](/blog/velero-garage-k3s-backup/), my self-hosted S3-compatible object store, ran with SQLite as its metadata database. In June 2026, while I was chasing memory pressure in Loki, I found Garage logging `database disk image is malformed` (SQLite's `SQLITE_CORRUPT`) and later `locking protocol` errors. Reads still worked, which is why nobody noticed sooner, but Velero backup writes and Loki chunk flushes were failing, and the `terraform-state` bucket lived in the same metadata store.

The root cause: Garage's metadata volume was an NFS-backed PersistentVolume, and SQLite's WAL (write-ahead logging) mode does not work over a network filesystem. The SQLite docs say so explicitly. The fix at the time was moving every embedded database to `local-path`.

**Update (November 2026):** The Garage part of that fix did not last. On 2026-08-21, before this post went up, Garage's metadata moved off `local-path` as well: the engine changed from SQLite to LMDB (Garage's own default since v0.9.0, converted with `garage convert-db`) and the metadata directory moved to a dedicated 8 GB disk attached to one k3s node, mounted as a `hostPath`. Since 2026-11-15 that same disk is mounted through a static local PersistentVolume instead of `hostPath`. NFS was ruled out again for LMDB for the same reason as below. The SQLite-on-NFS lesson and the `local-path` rule for Mealie and Home Assistant still stand.

## The Storage Classes

My k3s cluster has two StorageClasses:

```yaml
# NFS - for most workloads (rendered by the nfs-subdir-external-provisioner Helm chart)
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: nfs-client
provisioner: cluster.local/nfs-provisioner-nfs-subdir-external-provisioner
reclaimPolicy: Retain
volumeBindingMode: Immediate
parameters:
  archiveOnDelete: "true"
  pathPattern: "${.PVC.namespace}/${.PVC.name}"
  onDelete: "retain"
mountOptions:
  - nfsvers=4.1
  - hard
  - timeo=600
  - retrans=3
---
# Local-path - for embedded databases (k3s built-in)
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: local-path
provisioner: rancher.io/local-path
reclaimPolicy: Delete
volumeBindingMode: WaitForFirstConsumer
```

The NFS server address and export are not StorageClass parameters. nfs-subdir-external-provisioner takes them as Helm values (`nfs.server: 10.0.20.100`, `nfs.path: /nfs-data/k8s-general`), mounts that export into its own pod, and creates one subdirectory per PVC. The chart derives the provisioner name from the release (`cluster.local/<release>-nfs-subdir-external-provisioner`); the plain manifests from the project's `deploy/` directory use `k8s-sigs.io/nfs-subdir-external-provisioner` instead. Whatever `kubectl get storageclass` shows is the one that counts.

NFS (`nfs-client`) is the default. It's backed by a dedicated LXC (`ct-srv-nfs-01`) that exports a directory from the Proxmox host, so the storage survives pod rescheduling: a pod on k3s-12 can mount the same PVC as a pod on k3s-13 because the NFS server is independent of any cluster node.

Local-path (`local-path`) pins the PV to whichever node created it through node affinity. The pod can only be scheduled on that node; if the node is down, the pod stays `Pending` until it comes back. That's a real limitation, and for some workloads it's the right trade-off.

## Why SQLite and NFS Don't Work

SQLite coordinates concurrent access with POSIX advisory locks (`fcntl()` with `F_SETLK`/`F_SETLKW`). On a local filesystem the kernel enforces those locks. On NFS, the lock has to travel over the network, and how it does depends on the protocol version:

1. **NFSv3** has no locking in the protocol itself. Locks go through the separate Network Lock Manager (NLM) sideband protocol, served by `rpc.lockd` and `rpc.statd` on client and server. If those daemons aren't running or reachable, or a client mounts with `nolock`, `fcntl()` locks only apply on the local client. Two clients can then both hold an "exclusive" lock on the same file.

2. **NFSv4** builds locking into the protocol (`LOCK`/`LOCKU` operations with lease-based state), so there is no `lockd`. Locks are leases: if a client can't renew in time, the server can drop its state, and lock behavior depends on the server and client implementations getting lease expiry and recovery right.

3. **WAL mode adds a harder problem.** Even with correct locks, WAL keeps a wal-index in a `-shm` file that every connection memory-maps as shared memory. From [sqlite.org/wal.html](https://www.sqlite.org/wal.html): "All processes using a database must be on the same host computer; WAL does not work over a network filesystem." Memory-mapped pages of a file on NFS are not kept coherent between clients, and NFS client-side caching gives only close-to-open consistency.

SQLite's own [How To Corrupt An SQLite Database File](https://www.sqlite.org/howtocorrupt.html) lists broken or missing lock implementations on network filesystems, "and NFS in particular", as a known corruption cause. When the locking or the shared wal-index breaks down, two writers can believe they own the database at the same time, and pages get overwritten.

## The Garage Incident

In June 2026 Garage ran with two storage mounts:

```yaml
# kubernetes/apps/garage/garage.yml (June 2026)
volumes:
  - name: data
    persistentVolumeClaim:
      claimName: garage-data      # NFS - bucket objects
  - name: meta
    persistentVolumeClaim:
      claimName: garage-meta      # SQLite metadata, nfs-client at the time
```

The `data` volume (bucket objects) is on NFS. That's fine: Garage writes objects as plain files and doesn't rely on file locks for them. The `meta` volume (the SQLite database) was *also* on NFS: on 2026-06-17 every PVC in the cluster moved from Longhorn to `nfs-client`, `garage-meta` included.

Six days later the metadata database was corrupted. Every S3 request (Velero writing backups, Loki flushing chunks, Terraform reading and writing state) goes through that database, and SQLite's WAL locking and shared-memory index were sitting on a network filesystem. I can't point to the single write that broke it; the errors themselves (`malformed`, then `locking protocol`) match the documented SQLite-over-NFS failure mode.

## The Recovery

SQLite has a `.recover` command that can extract data from a corrupted database:

```bash
# Dump recoverable data from corrupted SQLite
sqlite3 db.sqlite ".recover" > recovered.sql

# Recreate the database from the dump
sqlite3 db_clean.sqlite < recovered.sql

# Check the result
sqlite3 db_clean.sqlite "PRAGMA integrity_check;"
```

Before touching anything I copied the raw metadata directory off the cluster. `.recover` scans every page of the corrupted file and extracts whatever it can read; the rebuilt database passed `PRAGMA integrity_check`, and the bucket and object counts matched the state before the corruption.

That was not the end of it. On restart, Garage panicked in its Merkle tree updater (a known sharp edge after this kind of repair, upstream issue #1200). The Merkle, insert-queue and GC-todo tables are derived indexes that Garage rebuilds, not primary data, so I cleared them and let Garage's own background work settle the rest. Afterwards all three buckets (`loki-data`, `velero`, `terraform-state`) were present with the same sizes as before, and a live S3 `GetObject` against `terraform-state` returned the expected object.

It was the second SQLite corruption in a week. On 2026-06-16, while the volume was still on Longhorn, an OOM kill left `db.sqlite` with corrupted pages after an unclean shutdown. `.recover` saved most of it then too, but the `terraform-state` bucket and the access key Atlantis used had to be written back into SQLite by hand with a Python script, msgpack-encoding the entries the way Garage stores them.

The data was back, but nothing had changed about the conditions that corrupted it on NFS. It would happen again.

## The Fix

Move every embedded database to `local-path`. For Garage that was a one-line change on the PVC (2026-06-23):

```yaml
# kubernetes/apps/garage/garage.yml - garage-meta PVC
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: local-path   # was: nfs-client
```

As the update note at the top says, Garage's metadata has since moved again, to LMDB on a dedicated disk.

The apps that need `local-path`:

| App | Database | Why local-path |
|---|---|---|
| Garage S3 (June to August 2026) | SQLite (metadata) | File locks + WAL shared memory |
| Mealie | SQLite (recipes) | SQLite file locks |
| Home Assistant | SQLite (recorder) | SQLite file locks |
| Authelia | PostgreSQL (CNPG) | CNPG manages its own PV |

PostgreSQL (via CNPG) doesn't have the SQLite problem in the same form. One server process owns the data directory and clients connect over TCP, so no file lock ever has to cross hosts. CNPG replicates at the PostgreSQL level, so each instance only needs its own `ReadWriteOnce` volume, and the [CNPG storage docs](https://cloudnative-pg.io/docs/current/storage) recommend local storage for predictable performance.

## The Trade-off

`local-path` means the PVC is pinned to one node. If the pod reschedules, it loses access to the data. For Garage, I accepted this at the time: Garage runs as a single instance, and without its metadata it can't serve anything anyway. If that node goes down, the objects on NFS survive, but S3 is unavailable until Garage is back.

For databases that need HA (Postgres, Redis), neither `local-path` nor NFS is the answer. Use an operator (CNPG for Postgres) that handles replication and failover above the storage layer.

The principle: **if the application is an embedded database that relies on file locks or shared memory (SQLite, BoltDB, LMDB), it goes on local-path. If it's a client-server database (PostgreSQL, MySQL), the server gets its own block or local volume and replication comes from an operator.**

---

SQLite on an SMB share in a Windows domain is the same failure class: SQLite's warnings apply to network filesystems in general, not only NFS. In Azure, this maps to Azure Files (SMB or NFS file shares) vs. Azure Disk (block storage). An embedded database belongs on an Azure Disk, not an Azure Files share. Same principle: embedded databases need local block storage with kernel-enforced locking and real shared memory.
