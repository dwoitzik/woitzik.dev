[Garage S3](/blog/velero-garage-k3s-backup/), my self-hosted S3-compatible object store, uses SQLite for its metadata database. One morning, Terraform state operations started failing with `SQLITE_CORRUPT`. The bucket metadata was gone. The `terraform-state` bucket, the Atlantis lock table and the Velero backup index all lived in that one SQLite file.

The root cause: Garage's metadata volume was an NFS-backed PersistentVolume, and SQLite's WAL (write-ahead logging) mode does not work over a network filesystem. The SQLite docs say so explicitly. The corruption showed up while a Velero backup and a Terraform state write were hitting Garage at the same time. The fix was moving every embedded database to `local-path`.

## The Storage Classes

My k3s cluster has two StorageClasses:

```yaml
# NFS - for most workloads (rendered by the nfs-subdir-external-provisioner Helm chart)
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: nfs-client
provisioner: cluster.local/nfs-provisioner-nfs-subdir-external-provisioner
reclaimPolicy: Retain
volumeBindingMode: Immediate
parameters:
  archiveOnDelete: "true"
  pathPattern: "${.PVC.namespace}/${.PVC.name}"
  onDelete: "retain"
mountOptions:
  - nfsvers=4.1
  - hard
  - timeo=600
  - retrans=3
---
# Local-path - for embedded databases (k3s built-in)
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: local-path
provisioner: rancher.io/local-path
reclaimPolicy: Delete
volumeBindingMode: WaitForFirstConsumer
```

The NFS server address and export are not StorageClass parameters. nfs-subdir-external-provisioner takes them as Helm values (`nfs.server: 10.0.20.100`, `nfs.path: /nfs-data/k8s-general`), mounts that export into its own pod, and creates one subdirectory per PVC. The chart derives the provisioner name from the release (`cluster.local/<release>-nfs-subdir-external-provisioner`); the plain manifests from the project's `deploy/` directory use `k8s-sigs.io/nfs-subdir-external-provisioner` instead. Whatever `kubectl get storageclass` shows is the one that counts.

NFS (`nfs-client`) is the default. It's backed by a dedicated LXC running an NFS server on ZFS, so the storage survives pod rescheduling: a pod on k3s-12 can mount the same PVC as a pod on k3s-13 because the NFS server is independent of any cluster node.

Local-path (`local-path`) pins the PV to whichever node created it through node affinity. The pod can only be scheduled on that node; if the node is down, the pod stays `Pending` until it comes back. That's a real limitation, and for some workloads it's the right trade-off.

## Why SQLite and NFS Don't Work

SQLite coordinates concurrent access with POSIX advisory locks (`fcntl()` with `F_SETLK`/`F_SETLKW`). On a local filesystem the kernel enforces those locks. On NFS, the lock has to travel over the network, and how it does depends on the protocol version:

1. **NFSv3** has no locking in the protocol itself. Locks go through the separate Network Lock Manager (NLM) sideband protocol, served by `rpc.lockd` and `rpc.statd` on client and server. If those daemons aren't running or reachable, or a client mounts with `nolock`, `fcntl()` locks only apply on the local client. Two clients can then both hold an "exclusive" lock on the same file.

2. **NFSv4** builds locking into the protocol (`LOCK`/`LOCKU` operations with lease-based state), so there is no `lockd`. Locks are leases: if a client can't renew in time, the server can drop its state, and lock behavior depends on the server and client implementations getting lease expiry and recovery right.

3. **WAL mode adds a harder problem.** Even with correct locks, WAL keeps a wal-index in a `-shm` file that every connection memory-maps as shared memory. From [sqlite.org/wal.html](https://www.sqlite.org/wal.html): "All processes using a database must be on the same host computer; WAL does not work over a network filesystem." Memory-mapped pages of a file on NFS are not kept coherent between clients, and NFS client-side caching gives only close-to-open consistency.

SQLite's own [How To Corrupt An SQLite Database File](https://www.sqlite.org/howtocorrupt.html) lists broken or missing lock implementations on network filesystems, "and NFS in particular", as a known corruption cause. When the locking or the shared wal-index breaks down, two writers can believe they own the database at the same time, and pages get overwritten.

## The Garage Incident

Garage runs with two storage mounts:

```yaml
# kubernetes/apps/garage/garage.yml
volumes:
  - name: data
    persistentVolumeClaim:
      claimName: garage-data      # NFS - bucket objects
  - name: meta
    persistentVolumeClaim:
      claimName: garage-meta      # local-path - SQLite metadata
```

The `data` volume (bucket objects) is on NFS. That's fine: Garage writes objects as plain files and doesn't rely on file locks for them. The `meta` volume (the SQLite database) was *also* on NFS initially. That worked until a Velero backup and a Terraform state write happened at the same time.

Velero calls Garage's S3 API to enumerate backup objects. Terraform calls it to read and write the state file. Both requests end up in SQLite through Garage's metadata layer. Under that concurrent load on an NFS-backed WAL database, pages 169–184 of `db.sqlite` were corrupted.

## The Recovery

SQLite has a `.recover` command that can extract data from a corrupted database:

```bash
# Dump recoverable data from corrupted SQLite
sqlite3 db.sqlite ".recover" > recovered.sql

# Recreate the database from the dump
sqlite3 db_clean.sqlite < recovered.sql
```

The `.recover` command scanned every page of the corrupted file and extracted whatever data it could read. For pages 169–184 (the corrupted range), it found partial data: enough to reconstruct the bucket and key metadata, but not enough to guarantee referential integrity.

After recovery, the missing objects (the `terraform-state` bucket and the Atlantis lock key) had to be re-inserted manually with Python:

```python
import sqlite3
import msgpack

conn = sqlite3.connect("db_clean.sqlite")
# Garage uses msgpack-encoded metadata with 'G2key'/'G2bkt' prefixes
# Re-insert the terraform-state bucket
conn.execute("INSERT INTO buckets (name, ...) VALUES (...)")
conn.commit()
```

The data was back, but nothing had changed about the conditions that corrupted it. It would happen again.

## The Fix

Move every embedded database to `local-path`:

```yaml
# Garage - meta volume moved to local-path
volumes:
  - name: meta
    persistentVolumeClaim:
      claimName: garage-meta      # NOW: local-path (was: nfs-client)
```

The apps that need `local-path`:

| App | Database | Why local-path |
|---|---|---|
| Garage S3 | SQLite (metadata) | File locks + WAL shared memory |
| Mealie | SQLite (recipes) | SQLite file locks |
| Home Assistant | SQLite (recorder) | SQLite file locks |
| Authelia | PostgreSQL (CNPG) | CNPG manages its own PV |

PostgreSQL (via CNPG) doesn't have the SQLite problem in the same form. One server process owns the data directory and clients connect over TCP, so no file lock ever has to cross hosts. CNPG replicates at the PostgreSQL level, so each instance only needs its own `ReadWriteOnce` volume, and the [CNPG storage docs](https://cloudnative-pg.io/docs/current/storage) recommend local storage for predictable performance.

## The Trade-off

`local-path` means the PVC is pinned to one node. If the pod reschedules, it loses access to the data. For Garage, this is acceptable: Garage runs as a single instance, and without its metadata it can't serve anything anyway. If that node goes down, the objects on NFS survive, but S3 is unavailable until Garage is back.

For databases that need HA (Postgres, Redis), neither `local-path` nor NFS is the answer. Use an operator (CNPG for Postgres) that handles replication and failover above the storage layer.

The principle: **if the application is an embedded database that relies on file locks or shared memory (SQLite, BoltDB, LMDB), it goes on local-path. If it's a client-server database (PostgreSQL, MySQL), the server gets its own block or local volume and replication comes from an operator.**

---

SQLite on an SMB share in a Windows domain is the same failure class: SQLite's warnings apply to network filesystems in general, not only NFS. In Azure, this maps to Azure Files (SMB or NFS file shares) vs. Azure Disk (block storage). An embedded database belongs on an Azure Disk, not an Azure Files share. Same principle: embedded databases need local block storage with kernel-enforced locking and real shared memory.
