> **Update (November 2026):** The first version of this post described what two weekly Chaos Mesh experiments broke: a 90-second Authelia outage, slower Velero backups and ArgoCD syncs, flickering Uptime Kuma monitors. None of that is backed by the cluster's history, so I have removed it. The repo history shows what actually happened. The two `Schedule` objects were declared in git but not applied until a drift guard flagged them on 2026-08-23, three days after this post went up. Once applied, they selected opt-in labels that no workload in the cluster carried, so every run matched zero pods. They were deleted on 2026-10-16. This version tells that story instead, and describes the quarterly game day that replaced them.

I set up two weekly chaos experiments on my k3s cluster (three VMs on a single Proxmox host): a pod-kill every Sunday at 03:00 UTC and a 100ms network latency injection at 03:30 UTC, both scoped to the `apps` namespace and to opt-in labels. In four months they never touched a single pod. Nothing alerted on that, because from the outside an experiment that matches nothing looks the same as one that passes.

**[View the complete homelab infrastructure source on GitHub](https://github.com/dwoitzik/homelab-infrastructure)**

## The Setup

Chaos Mesh runs in the `chaos-mesh` namespace, deployed via Helm chart v2.8.3:

```yaml
# kubernetes/system/chaos-mesh/application.yml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: chaos-mesh
  namespace: argocd
spec:
  source:
    repoURL: https://charts.chaos-mesh.org
    chart: chaos-mesh
    targetRevision: 2.8.3
    helm:
      values: |
        controllerManager:
          replicaCount: 1
        chaosDaemon:
          runtime: containerd
          socketPath: /run/k3s/containerd/containerd.sock
        dashboard:
          create: true
          securityMode: false
        webhook:
          certManager:
            enabled: true
```

`webhook.certManager.enabled` came later. By default the chart generates a new self-signed webhook certificate on every render, so ArgoCD's self-heal saw those Secrets as permanently OutOfSync and kept re-applying them. Handing the certificates to cert-manager makes them stable across renders.

The `socketPath` matters: k3s runs its own containerd with its own socket, not the standard Docker or containerd path. Pod-kill doesn't care, because the controller deletes pods through the Kubernetes API. Everything that goes through `chaos-daemon` does: NetworkChaos, container-kill, IO and stress faults all need the daemon to reach the runtime, and with the wrong socket they fail instead of injecting anything.

The two Schedule resources, as they were in `kubernetes/system/chaos-mesh/schedules.yml`:

```yaml
# Weekly pod-kill - Sunday 03:00 UTC
apiVersion: chaos-mesh.org/v1alpha1
kind: Schedule
metadata:
  name: weekly-pod-kill
  namespace: chaos-mesh
spec:
  schedule: "0 3 * * 0"
  concurrencyPolicy: Forbid
  type: PodChaos
  podChaos:
    action: pod-kill
    mode: one
    selector:
      namespaces:
        - apps
      labelSelectors:
        "chaos-kill": "enabled"
    gracePeriod: 0
---
# Weekly network latency - Sunday 03:30 UTC
apiVersion: chaos-mesh.org/v1alpha1
kind: Schedule
metadata:
  name: weekly-network-latency
  namespace: chaos-mesh
spec:
  schedule: "30 3 * * 0"
  concurrencyPolicy: Forbid
  type: NetworkChaos
  networkChaos:
    action: delay
    mode: all
    selector:
      namespaces:
        - apps
      labelSelectors:
        "chaos-network": "enabled"
    delay:
      latency: "100ms"
      correlation: "25"
      jitter: "10ms"
    duration: "5m"
    direction: to
```

`mode: one` on the pod-kill means exactly one matching pod is killed per run. `mode: all` on the latency experiment applies to every pod with the label. `gracePeriod: 0` means immediate termination with no graceful shutdown, which is closer to a kernel panic or power loss than a clean drain. The opt-in labels were deliberate: not every app is safe to kill unattended, so each one would have to carry `chaos-kill: enabled` to be eligible.

## What Actually Happened

Nothing, for two separate reasons.

**The schedules were never applied.** `schedules.yml` sat in `kubernetes/system/chaos-mesh/`, but the ArgoCD Application for Chaos Mesh only deploys the Helm chart. The Schedules were meant to be applied by hand with `kubectl apply`, and that never happened. Git said the experiments existed; the cluster had none. A declared-vs-live drift checker I added on 2026-08-23 caught them on its first run, along with a `PodMonitor` that had the same problem.

**Once applied, they matched nothing.** No workload in the cluster had ever been given `chaos-kill: enabled` or `chaos-network: enabled`. The drift-guard run had already confirmed zero matching pods, which is why applying them looked safe. It was safe, and also useless. Every Sunday the pod-kill failed with "no pod is selected" and left `weekly-pod-kill` stuck with a `PodChaos` in a running state. With `concurrencyPolicy: Forbid`, that stuck object then blocked every later run. The latency schedule failed the same way.

None of this produced an alert. Chaos Mesh recorded the failures on its own objects, and nothing watched those objects. On 2026-10-16 I deleted `schedules.yml` instead of labeling workloads to make it run.

## What Replaced It

The scheduled test that actually runs is `dr-game-day` (`kubernetes/system/monitoring/dr-game-day.yml`), a plain CronJob, not Chaos Mesh. On the 1st of January, April, July and October at 10:00 it:

1. Checks that `homepage` answers HTTP 200, and aborts if it does not, so the test never runs against an already-broken service.
2. Deletes every pod matching `app=homepage` in `apps`.
3. Polls the Service every 3 seconds for up to 180 seconds and posts PASS with the recovery time, or FAIL with an `@here`, to Discord.

`homepage` is the target because it is stateless (its only volume is an `emptyDir` rebuilt by an init container) and runs with `replicas: 1`, so no second replica hides the downtime window and there is no data to lose. The RBAC Role can only delete pods in `apps`, and the script only selects `app=homepage`. The first triggered run on 2026-08-26 recovered in 18 seconds. Backup integrity has its own monthly job that restores [Velero backups](/blog/velero-garage-k3s-backup/) into a scratch namespace; the game day measures recovery speed, not restore correctness.

Chaos Mesh is still installed for ad-hoc experiments, applied on demand against whatever I have labeled for that run.

## What It Taught

### 1. An experiment that selects nothing looks like success

A label-selector experiment with no matching pods does not fail loudly. It does nothing, and "nothing happened" is also what a passing resilience test looks like from the outside. Any scheduled experiment needs a check that it hit a target: count the affected pods, or alert on the experiment object's own failure status. The game day does this implicitly, because it fails if the pre-check or the recovery poll fails.

### 2. Declared is not applied

The schedules lived in git for over two months before anything noticed they were not in the cluster. Anything under `kubernetes/system/` that ArgoCD does not own needs something comparing git to live state. That is what the drift checker does now.

### 3. PDBs cover evictions, not failures

This part of the original post holds regardless of the results. A PodDisruptionBudget makes drains and node maintenance wait. Chaos Mesh's pod-kill deletes pods directly through the API, and PDBs only gate evictions, so a pod-kill with `mode: all` would take out every replica regardless of the PDB, exactly like a real crash or OOM kill. `mode: one` is what limits the blast radius of the experiment. Replica count and spread protect against real failures.

### 4. Init containers decide recovery time

Authelia and Paperless both start with a `wait-for-vault-secret` init container that blocks until the Vault-backed secret files exist (it checks every 2 seconds). After a cold cluster restart, when Vault starts sealed, that wait is the whole recovery time. I have not measured it under a pod-kill. That is the next ad-hoc experiment worth running, now with a check that it actually killed something.

### 5. Chaos testing on a homelab is still worth it

The cluster has no SLA, but the lesson here (a resilience control that silently does nothing) is the same one production teams learn from backup jobs that never ran. Finding it in a homelab is cheap. It's the same reasoning behind [treating a cascading OOM-kill/DNS-storm failure](/blog/k3s-cascading-failure-oomkill-dns-storm/) as worth a full root-cause writeup even though nobody was paged.

At enterprise scale the tools change, the method doesn't: Azure Chaos Studio for VM and AKS fault injection (its AKS faults are Chaos Mesh under the hood), Azure Load Testing for a performance baseline and Azure Monitor for measuring blast radius. Inject realistic failures in a controlled environment, verify they hit their target, measure the impact, fix what breaks. Chaos Studio bills by target action-minutes, so it pays to have practiced the experiment in the homelab first.
