For public-facing services, Let's Encrypt's HTTP-01 challenge just works. In my homelab, services run on internal IPs behind a [MikroTik RB5009\*](/go/4w08b21) with default-deny rules, so Let's Encrypt can't reach the cluster to verify ownership and HTTP-01 is out.

DNS-01 solves this. Instead of serving a file over HTTP, you prove control of the domain by creating a DNS TXT record. The cluster only needs outbound access to the Cloudflare API; it never has to be reachable from the internet.

Below is the setup that issues and renews a wildcard certificate for the whole domain with cert-manager, Cloudflare DNS and [ArgoCD](/blog/argocd-gitops-k3s-homelab/).

**[View the complete homelab infrastructure source on GitHub](https://github.com/dwoitzik/homelab-infrastructure)**

## Why DNS-01 and Not HTTP-01

HTTP-01 requires Let's Encrypt to make an HTTP request to `http://yourdomain.com/.well-known/acme-challenge/...`. For publicly reachable services that's fine. A homelab cluster on `10.0.20.x` behind NAT and a firewall, or behind an ISP that puts you on CGNAT with no public IPv4 at all, is unreachable.

DNS-01 works differently:
1. cert-manager creates a `_acme-challenge.yourdomain.com` TXT record via the Cloudflare API
2. Let's Encrypt queries the zone's authoritative DNS to verify the record exists
3. Verification succeeds without any inbound connection to your cluster
4. cert-manager deletes the TXT record and stores the certificate as a Kubernetes Secret

Every connection is outbound from the cluster. No port forwarding, no public IP, no inbound firewall rules.

## Why Wildcard

A wildcard certificate (`*.yourdomain.com`) covers every subdomain with a single certificate. Without it, you need a separate certificate request for each service:

```
auth.yourdomain.com     → separate cert
vault.yourdomain.com    → separate cert
grafana.yourdomain.com  → separate cert
```

With a wildcard:

```
*.yourdomain.com        → one cert, covers everything
```

Let's Encrypt only issues wildcard certificates via DNS-01, which rules out HTTP-01 here a second time.

## Step 1: Deploy cert-manager via ArgoCD

cert-manager ships as a Helm chart. Two sets of values matter for DNS-01 with Cloudflare:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: cert-manager
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://charts.jetstack.io
    targetRevision: v1.14.4
    chart: cert-manager
    helm:
      values: |
        installCRDs: true
        extraArgs:
          - --dns01-recursive-nameservers=1.1.1.1:53,8.8.8.8:53
          - --dns01-recursive-nameservers-only
  destination:
    server: https://kubernetes.default.svc
    namespace: cert-manager
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true
```

`installCRDs: true`: cert-manager needs its CRDs (`Certificate`, `ClusterIssuer`, `CertificateRequest`, etc.). Without this value you have to install them separately before the chart works. From chart v1.15 the value is called `crds.enabled`; `installCRDs` is deprecated there.

`--dns01-recursive-nameservers`: this is the non-obvious one. Before telling Let's Encrypt to validate, cert-manager runs its own propagation check, using the resolvers from the pod's `/etc/resolv.conf` (the cluster DNS) to find the zone's nameservers. If the internal resolver answers for `yourdomain.com` itself (split-horizon DNS on the router, a local override) or caches the empty answer, the check never passes and the challenge hangs. Pointing cert-manager at `1.1.1.1` and `8.8.8.8` takes the internal resolver out of the loop.

`--dns01-recursive-nameservers-only`: by default cert-manager uses the recursive resolvers only to locate the authoritative nameservers and then queries those directly. This flag makes it run the whole check against the listed recursive resolvers instead, which helps when the authoritative servers aren't directly reachable from the cluster.

## Step 2: Create the Cloudflare API Token Secret

cert-manager needs API access to create and delete TXT records in Cloudflare. Create a scoped API token in the Cloudflare dashboard with only the permissions it needs:

- Zone → Zone → Read
- Zone → DNS → Edit

Store it as a Kubernetes Secret:

```bash
kubectl create secret generic cloudflare-api-token-secret \
  --from-literal=api-token=YOUR_CLOUDFLARE_API_TOKEN \
  -n cert-manager
```

Use a scoped token, not the Global API Key. Zone read and DNS edit on the one zone is all it needs.

In production this Secret should come from Vault rather than a one-off `kubectl create secret`. The [External Secrets Operator + Vault](/blog/external-secrets-operator-vault-kubernetes/) pattern keeps the token out of Git and out of shell history.

## Step 3: Create the ClusterIssuer

The `ClusterIssuer` is the cert-manager resource that defines how to obtain certificates. It's cluster-scoped (not namespace-scoped), so any `Certificate` resource in any namespace can reference it:

```yaml
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: letsencrypt-production
spec:
  acme:
    server: https://acme-v02.api.letsencrypt.org/directory
    email: your-email@yourdomain.com
    privateKeySecretRef:
      name: letsencrypt-production-account-key
    solvers:
    - dns01:
        cloudflare:
          apiTokenSecretRef:
            name: cloudflare-api-token-secret
            key: api-token
        selector:
          dnsZones:
            - "yourdomain.com"
```

The `selector` limits this solver to names in `yourdomain.com`. With one solver it is optional, but once you add a second zone or a second solver, it decides which solver (and which token) handles which domain.

The `privateKeySecretRef` holds the ACME account private key, which cert-manager creates on first use. Don't delete it: cert-manager would register a fresh ACME account, and the link to the old one is gone.

## Step 4: Request the Wildcard Certificate

With the ClusterIssuer in place, request the wildcard certificate:

```yaml
apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: wildcard-yourdomain-tls
  namespace: kube-system  # Same namespace as Traefik
spec:
  secretName: wildcard-yourdomain-tls
  issuerRef:
    name: letsencrypt-production
    kind: ClusterIssuer
  dnsNames:
  - "yourdomain.com"
  - "*.yourdomain.com"
```

Both `yourdomain.com` and `*.yourdomain.com` are listed because the wildcard covers one level of subdomains but not the apex domain.

The certificate is stored in `kube-system` because that's where [Traefik](/blog/metallb-traefik-k3s-argocd/) runs. Traefik's `tlsStore` references this Secret directly:

```yaml
tlsStore:
  default:
    defaultCertificate:
      secretName: wildcard-yourdomain-tls
```

With the default certificate set, an IngressRoute only needs a `tls` section. Traefik serves the default certificate for any host that has no more specific match. `tls.secretName` would resolve in the IngressRoute's own namespace (`monitoring` here), not in `kube-system`, so a cross-namespace reference to the wildcard Secret fails. Leave `secretName` out and use `tls: {}`, and Traefik picks the default certificate:

```yaml
apiVersion: traefik.io/v1alpha1
kind: IngressRoute
metadata:
  name: grafana
  namespace: monitoring
spec:
  entryPoints:
    - websecure
  routes:
    - match: Host(`grafana.yourdomain.com`)
      kind: Rule
      services:
        - name: grafana
          port: 3000
  tls: {}  # no secretName: Traefik serves the default certificate from the TLSStore
```

## Verifying the Certificate

Check the certificate status:

```bash
kubectl get certificate -n kube-system wildcard-yourdomain-tls
```

Expected output when ready:
```
NAME                       READY   SECRET                     AGE
wildcard-yourdomain-tls    True    wildcard-yourdomain-tls    5m
```

If `READY` stays `False`, look at the CertificateRequest, Order and Challenge resources for the error. All three live in the Certificate's namespace (`kube-system` here):

```bash
kubectl describe certificaterequest -n kube-system
kubectl describe order -n kube-system
kubectl describe challenge -n kube-system
```

The most common failure: the Cloudflare API token doesn't have DNS edit permissions on the correct zone.

## The Timing Problem

DNS-01 challenges take longer than HTTP-01. TXT record propagation alone can take 30–60 seconds, Let's Encrypt verification adds another lookup, and the whole challenge typically completes in 2–5 minutes. If you're used to HTTP-01 finishing in 30 seconds, this feels slow, but it's normal.

The cert-manager logs show the flow:

```
Waiting for DNS01 challenge propagation...
Successfully created record "_acme-challenge.yourdomain.com"
Verifying the DNS01 challenge...
Challenge verified - DNS01 record found
```

cert-manager renews the 90-day certificate 30 days before expiry, so the DNS-01 round trip happens about every 60 days. You won't notice it unless you watch the logs.

## Gotcha: Cloudflare Proxy Mode

The Cloudflare proxy (orange cloud) doesn't affect DNS-01. Proxying applies to A/AAAA/CNAME records serving HTTP traffic; TXT records are never proxied. What does break is an API token scoped to the wrong zone. The Cloudflare API rejects the record creation, and the error only shows up in the Challenge resource's status, not on the Certificate. Scope the token to the exact zone where the TXT records will be created, and check `kubectl describe challenge` first when issuance stalls.

## The Result

Once the certificate is issued and Traefik is configured with the `tlsStore` default:

- Every route behind Traefik gets valid TLS
- No per-service certificate configuration
- cert-manager renews the certificate 30 days before expiry without intervention
- A new service is reachable at `service.yourdomain.com` with valid HTTPS as soon as its route exists

Issuance, storage and renewal are automated. The only manual step was creating the Cloudflare API token Secret, once.
