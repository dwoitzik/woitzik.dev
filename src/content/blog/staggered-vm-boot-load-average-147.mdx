After a host reboot, every VM and LXC on the Proxmox host started at the same time. Twelve guests booted at once, all hitting the same NVMe for root filesystem reads, service starts and NFS mounts. The host load average hit 147.

On Linux, load average counts tasks that are runnable or stuck in uninterruptible I/O wait. On a 16-thread CPU, 147 means that on average about nine tasks were queued for every hardware thread. Every service was slow to start, k3s took minutes to become ready, and DNS didn't resolve for the first 90 seconds because the Raspberry Pi DNS nodes were waiting for services that hadn't booted yet.

The fix was boot order, not more hardware.

> **Update (November 2026):** staggered boot fixed the boot-time storm, but it was not the whole story behind the host freezes I was chasing that week. An undersized PSU (mitigated by dropping the BIOS TDP from 54W to 25W) and a known OpenZFS 2.4.1 deadlock under ARC pressure (addressed by upgrading to 2.4.2 and capping ARC) were the other contributors. The k3s cluster has also since moved from three-member embedded etcd to a single server with SQLite via kine.

## The Boot Storm

Without startup ordering, every guest with `onboot=1` starts as soon as the host is up. The host's NVMe serves root filesystem reads for every guest, plus the ZFS txg commits from the NFS server, plus etcd writes from the k3s nodes (the cluster ran three-member embedded etcd at the time).

That's a thundering herd: 12 guests requesting I/O at the same moment, the NVMe queue fills, I/O latency spikes, and services that depend on each other (k3s needs NFS, k3s apps need DNS, DNS needs k3s services) end up waiting on each other in a chain.

The load doesn't spike and recover; it compounds. Services that miss their start timeout retry and add more work to the queue. The k3s control-plane tries to mount NFS volumes, NFS is slow because it's competing with 11 other guests for I/O, k3s retries the mount, and the load climbs further.

## The Fix: Staggered Boot Order

Proxmox supports a `startup` order with delays. In Terraform with the `bpg/proxmox` provider, that's the `startup` block (`order`, `up_delay`, `down_delay`):

```hcl
# terraform/stacks/proxmox/lxc.tf
# NFS first - k3s depends on it
resource "proxmox_virtual_environment_container" "ct_srv_nfs_01" {
  # ...
  startup {
    order    = 1
    up_delay = 15 # seconds to wait before starting the next guest
  }
}

# terraform/stacks/proxmox/vm.tf
# k3s server - waits for NFS
resource "proxmox_virtual_environment_vm" "vm_srv_k3s_11_master" {
  # ...
  on_boot = true
  startup {
    order    = 2
    up_delay = 30
  }
}

# k3s agents - 30s apart from each other
resource "proxmox_virtual_environment_vm" "vm_srv_k3s_12_worker" {
  # ...
  startup {
    order    = 3
    up_delay = 30
  }
}

resource "proxmox_virtual_environment_vm" "vm_srv_k3s_13_worker" {
  # ...
  startup {
    order    = 4
    up_delay = 30
  }
}
```

The order:
1. **NFS** (order 1): boots first with a 15s head start. k3s PVCs mount from NFS, so NFS must be ready before k3s starts.
2. **k3s-11** (order 2): the k3s server (API server, SQLite datastore via kine). Starts after NFS and needs NFS for system PVCs.
3. **k3s-12** (order 3): agent. Starts 30s after the server.
4. **k3s-13** (order 4): agent. Starts 30s after k3s-12.
5. **LXCs** (order 5 and 6, 10s apart): everything else, including Docker workloads, the media stack and the DMZ.

The full sequence takes about 3 minutes until everything is online. Before, everything started at once, load hit 147, and it took 5+ minutes to settle.

## Why NFS First

NFS is the storage layer. Every k3s PVC (Authelia, Vaultwarden, Paperless, Nextcloud) mounts from the NFS server at `10.0.20.100`. If NFS isn't ready when k3s starts, the mounts fail, the kubelet retries with exponential backoff, and the pods sit in `ContainerCreating` for minutes.

NFS in turn depends on ZFS, because the export directory lives on the ZFS pool, and the pool needs a few seconds after boot to import and mount. The head start gives ZFS and NFS time to settle before k3s floods them with mount requests.

## The CPU Scheduling Priority

Beyond boot order, k3s VMs get CPU scheduling priority via `cpu.units`:

```hcl
# k3s VMs: explicit scheduling weight
cpu {
  cores = 4
  type  = "host"
  units = 2048
}

# most LXCs: units left unset
cpu {
  cores = 2
}
```

`cpu.units` maps to the guest's cgroup CPU weight, which the Linux scheduler uses to split CPU time when guests compete for the same cores. On Proxmox VE 7 and later (cgroup v2) an unset guest gets the default weight of 100, not the 1024 of the cgroup v1 days. So with the k3s VMs at 2048 and most LXCs left unset, the k3s VMs get roughly 20 times the share of an LXC under contention. When Ollama runs LLM inference on the AI LXC and the k3s server needs CPU, k3s gets it first. The one LXC I deliberately raised is the Minecraft server, which also runs at 2048 because tick latency matters to players.

The weighting matters during boot as well: even with staggered starts, late-booting LXCs overlap with k3s workloads that are already running, and the weight keeps k3s ahead.

## The `onboot` Gotcha

For the k3s VMs, `on_boot = true` on `proxmox_virtual_environment_vm` works as expected. For LXCs it doesn't: on `bpg/proxmox` 0.100.0 the container resource's `start_on_boot` isn't read back from the API into state, so `terraform plan` shows "No changes" regardless of the live `onboot` value, and a value set in Terraform never gets applied.

So `onboot` has to be set by hand after any LXC is recreated:

```bash
pct set <id> -onboot 1
```

I found this out the hard way. After recreating a container via Terraform, `onboot` was back at `0`, and the next host reboot skipped that container without a warning. The k3s control-plane came up without its NFS mount, and half the cluster sat in CrashLoopBackOff until I noticed.

The workaround is a manual `pct set` step in the operations runbook after every LXC creation. Not ideal, but documented and repeatable.

## Before vs. After

| Metric | Before (simultaneous) | After (staggered) |
|---|---|---|
| Peak load average | 147 | 12 |
| Time to k3s ready | 5+ minutes | 90 seconds |
| Time to DNS functional | 90 seconds | 30 seconds |
| I/O wait % | 85% | 15% |
| Failed mount attempts | 12-15 | 0 |

Staggering didn't make the boot slower overall. It spread the I/O over 3 minutes instead of packing it into the first 30 seconds. Individual services start later, but the cluster as a whole is stable sooner because nothing is fighting for I/O. The same host also runs [a memory overcommit guard](/blog/overcommit-guard-python-host-freeze/) for the RAM side: boot order handles the I/O storm, the guard handles memory.

---

The cloud has the same problem. Scale a VM scale set from 0 to 50 instances and all 50 hit the same database, registry and config service at once. The answer there is the same idea, spreading load over time with rolling batches and startup jitter. In a homelab you do it yourself with `startup.order` and `startup.up` delays.

[Designing Data-Intensive Applications\*](/go/4aUtkCs) has a useful framing for this kind of problem. It's written about databases rather than hypervisors, but its discussion of queueing delays applies to any resource that everything wants at the same moment.
