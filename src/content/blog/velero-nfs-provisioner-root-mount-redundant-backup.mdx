In one of Velero's nightly backups, a single volume took 33.4GB and 207 seconds, about 65% of all bytes in that run. Backup size alone is unremarkable for a cluster with many PVCs; one volume accounting for two thirds of the bytes is not. The nfs-provisioner's root-mount volume was backing up the entire shared NFS export as a single blob, even though every app's individual PVC (a subdirectory of the same tree) was already backed up separately.

The fix was a one-line annotation. The investigation almost went wrong, because my first hypothesis pointed at the wrong disk entirely.

## The Symptom

The PodVolumeBackup stats of a real nightly run showed one disproportionate entry: the volume `nfs-subdir-external-provisioner-root` in the nfs-provisioner's pod, 33.4GB uploaded in 207 seconds, about 65% of the total bytes of that backup.

## The Investigation

The nfs-provisioner pod mounts the entire shared NFS export at `/persistentvolumes`. Every app's PVC is a subdirectory of this tree. With `defaultVolumesToFsBackup: true`, Velero backs up every volume a pod mounts, including the root mount that contains all the subdirectories.

Each app's own pod also mounts its PVC subdirectory separately. Velero backs that up too. So the same data is backed up twice: once as part of the root mount, once as the individual PVC.

## The First Hypothesis (Wrong)

My first guess was to exclude `garage-data` and `immich-library`, Garage's object data and Immich's photo library, which live on separate USB-attached disks ([Seagate Portable 2TB External HDD&#42;](/go/4vxwLpY)). Excluding it would have reduced backup size, but the USB disks aren't on the contended rpool. The bottleneck was the SSD, not USB, so excluding the Immich volume would have been the wrong fix for the right symptom.

## The Right Fix

I verified the target before acting. Inside the provisioner pod, `/persistentvolumes` is just an NFS mount of the export (`10.0.20.100:/nfs-data/k8s-general`), so `findmnt` there only tells you which export it is, not which disk is underneath. The disk question has to be answered on the Proxmox host: `findmnt` and `zfs list` there showed that the directory behind the export, `/nfs-data`, lived on `rpool`, the contended SSD pool.

```bash
# In the provisioner pod: the root mount is the NFS export itself
kubectl -n nfs-provisioner exec deploy/nfs-provisioner-nfs-subdir-external-provisioner -- \
  ls /persistentvolumes/
# one <namespace>/ directory per namespace, one <pvc-name>/ directory per PVC below it

# On the Proxmox host: which pool holds the exported directory
findmnt -T /nfs-data
zfs list
```

The provisioner creates every PVC as `<namespace>/<pvc-name>` under that export (its `pathPattern`), so the root mount contains every individual PVC. Backing up the root mount backs up every PVC a second time.

### The Exclusion

```yaml
# kubernetes/system/nfs-provisioner/application.yml
podAnnotations:
  backup.velero.io/backup-volumes-excludes: nfs-subdir-external-provisioner-root
```

One annotation. Velero skips the root-mount volume entirely. Every app's individual PVC still gets backed up through its own pod's mount.

## Result

The 33.4GB and 207 seconds of the root-mount volume drop out of every nightly run, which on that run's numbers is roughly two thirds of the uploaded bytes. Nothing lost coverage: every PVC is still backed up individually.

## The Pattern

This trap applies to any NFS provisioner that mounts the export root in its own pod:

1. NFS provisioner pod mounts the entire export root
2. App pods mount individual PVC subdirectories
3. Velero backs up both, the root mount AND the individual PVCs
4. The root mount is redundant because it contains everything the individual PVCs contain

The fix is to exclude the root mount via `backup.velero.io/backup-volumes-excludes` on the provisioner pod.

## How to Find Redundant Backups

```bash
# List all PodVolumeBackups and their sizes
kubectl get podvolumebackups -A -o json | \
  jq -r '.items[] | "\(.spec.volume) \(.status.progress.totalBytes // 0) \(.metadata.namespace)"' | \
  sort -k2 -rn | head -10
```

If one volume is disproportionately large and its data is already covered by individual PVC backups, it's redundant.
