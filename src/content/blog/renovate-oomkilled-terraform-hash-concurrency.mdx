Renovate kept getting OOMKilled on the [BMAX Mini PC\*](/go/4bv3yF1) that runs my entire k3s cluster. The CronJob would start, run for a while and die with exit code 137. The obvious reading was not enough memory, so I raised the limit.

Three rounds later (2 GiB, then 3 GiB, then 4 GiB) it was still dying. The fix wasn't a bigger limit. It was changing what Renovate did with the memory it had.

**[View the complete homelab infrastructure source on GitHub 🐙](https://github.com/dwoitzik/homelab-infrastructure)**

## The Escalation

Round 1: the CronJob was OOMKilled at 2 GiB. Every job, three retries each, all dying. `kubectl describe pod` confirmed exit code 137, reason `OOMKilled`. I raised the container limit to 3 GiB and the V8 heap to 2304Mi, keeping the same ~25% non-heap headroom as before.

Round 2: OOMKilled again at 3 GiB, same pattern. I checked for regressions: no commit between the last clean run and the first failure had meaningfully grown the dependency count. The internal-docs relocation merged after the failures started, and Renovate doesn't scan `.md` files anyway. I read it as ordinary run-to-run variance tipping an already marginal limit over.

Round 3: the bump to 4 GiB. Except it landed as 3 GiB, because the edit was described in the PR but never made before merge. A separate PR made the intended change: 3 GiB → 4 GiB, 2304Mi → 3072Mi heap.

Still OOMKilled.

## The Diagnostic Run

Guessing at limits wasn't working, so I stopped trying to outrun the spike and measured it instead.

I ran Renovate off-cluster with 12 GiB of headroom, a real GitHub token, real branches and explicit authorization, to measure the actual peak.

The run finished cleanly with exit 0. Peak memory: **3.99 GiB**.

So this was never unbounded growth. The kernel's oom-kill records put the 2 GiB kills at an anon-rss of about 2054–2064Mi and the 4 GiB kills at about 4.12–4.15 GiB, both just over the cap. Those numbers only show where the limit was, not how high the process wanted to go. A 3.99 GiB peak leaves no margin under a 4 GiB cgroup limit, so normal run-to-run variance was enough to cross it mid-spike, before GC could reclaim anything.

## The Root Cause: Terraform Hash Concurrency

The spike wasn't random. Renovate's Terraform manager was downloading and SHA256-hashing all 14 platform builds of a major `hashicorp/aws` provider bump (5.x → 6.53.0) to keep `.terraform.lock.hcl` valid.

At Renovate's default `concurrentRequestLimit` of 16, up to 16 of those provider zips, each a large binary, can sit in memory at once while being hashed. Any major provider upgrade with many platform builds will trigger the same spike.

So the fix was to flatten the spike at the source, in a `hostRules` entry for `releases.hashicorp.com`:

```json
{
  "hostRules": [
    {
      "matchHost": "releases.hashicorp.com",
      "concurrentRequestLimit": 2
    }
  ]
}
```

This caps concurrent requests to `releases.hashicorp.com` at 2, so only two provider zips are buffered at a time and the spike shrinks. On top of that, the limit went to 6 GiB with a 4608Mi V8 heap as defense in depth, sized from the measured 3.99 GiB peak with real GC margin instead of a blind guess.

```yaml
env:
  - name: NODE_OPTIONS
    value: "--max-old-space-size=4608"
resources:
  requests:
    memory: 1Gi
  limits:
    memory: 6Gi
```

The CronJob had been suspended during the outage, and this fix doesn't re-enable it. That's a separate decision once the change is reviewed and validated in production.

## The Lesson

The memory bumps were the obvious response to OOMKilled, and they were wrong, because they treated the symptom (the process needs more memory) instead of the cause (the process buffers too many large objects at once).

The diagnostic run with 12 GiB of headroom was the turning point. Once I had the real peak, 3.99 GiB, the question changed: why is the peak that high, and can I flatten it instead of accommodating it?

`concurrentRequestLimit: 2` flattens it. The memory limit is the safety net, not the fix.

It's the same pattern as Kubernetes resource requests: you size requests for what the app needs to run normally and use limits as a ceiling for spikes. Here the normal usage was far below the spike, and the spike was inflated by a default nobody had touched.

---

The same trap exists outside Kubernetes. Azure VM sizing, AKS node pool autoscaling and Cosmos DB RU allocation all invite you to answer peak usage with more capacity instead of finding out what drives the peak.
