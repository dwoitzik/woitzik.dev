Most Kubernetes tutorials end with `kubectl apply -f`. You deploy something, it works, and you move on. Three weeks later you have no idea what's running in your cluster, why it's configured that way, or how to recreate it if something breaks. My cluster runs on a [BMAX Mini PC\*](/go/4bv3yF1): small enough to sit in a 10" rack, powerful enough for a full k3s stack.

GitOps fixes this. With ArgoCD, the Git repository is the single source of truth for everything in the cluster. No manual `kubectl apply`, no Helm commands in your shell history, no hand-edited resources. If it's not in Git, it doesn't exist.

Here is how my complete homelab stack (MetalLB, Traefik, Longhorn, cert-manager, Authelia, and Vaultwarden) is managed as a single Git repository with ArgoCD.

**[View the complete homelab infrastructure source on GitHub](https://github.com/dwoitzik/homelab-infrastructure)**

## The Repository Structure

Everything lives in one repository under a `kubernetes/` directory:

```
homelab-infrastructure/
└── kubernetes/
    ├── apps/                    # User-facing applications
    │   ├── authelia/
    │   │   ├── authelia.yml     # Deployment + Service
    │   │   ├── configmap.yml    # ConfigMap
    │   │   ├── ingress.yml
    │   │   └── users_database_secret.yml
    │   └── vaultwarden/
    │       ├── ingress.yml
    │       └── pvc.yml
    ├── system/                  # Cluster infrastructure
    │   ├── argocd/              # ApplicationSet + ArgoCD config
    │   ├── argocd-config/       # ArgoCD's own ingress
    │   ├── cert-manager/        # Helm chart Application
    │   ├── cert-manager-config/ # ClusterIssuer
    │   ├── longhorn/            # Helm chart Application
    │   ├── metallb/             # Helm chart Application
    │   ├── metallb-config/      # IPAddressPool + L2Advertisement
    │   └── traefik/             # Helm chart Application
    └── test-app/                # nginx for smoke testing
```

The separation between `apps/` and `system/` is intentional. System components are cluster infrastructure and need to exist before applications can run. Applications are workloads that depend on them. Keeping the two apart makes that dependency visible in the repo layout.

## Two Ways Applications Get Created

There is no single root Application in this repo. Applications come from two places.

**Everything under `kubernetes/apps/`** is picked up by one ApplicationSet,
`kubernetes/system/argocd/apps-applicationset.yaml`. Its git directory generator turns every
subdirectory into its own Application, named after the directory:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: homelab-apps
  namespace: argocd
spec:
  generators:
    - git:
        repoURL: 'https://github.com/dwoitzik/homelab-infrastructure.git'
        revision: main
        directories:
          - path: kubernetes/apps/*
  template:
    metadata:
      name: '{{path.basename}}'
    spec:
      project: default
      source:
        repoURL: 'https://github.com/dwoitzik/homelab-infrastructure.git'
        targetRevision: main
        path: '{{path}}'
      destination:
        server: 'https://kubernetes.default.svc'
        namespace: apps
      syncPolicy:
        automated:
          prune: true
          selfHeal: true
        syncOptions:
          - CreateNamespace=true
```

Adding a new app is a new directory and a push. No Application manifest to write.

**Everything under `kubernetes/system/`** has its own `application.yml` per component
(`cert-manager/application.yml`, `metallb/application.yml`, and so on). Nothing generated those
or tracked them: each one had to be created once with `kubectl apply`. That turned out to be the
weak spot of this setup, covered in the bootstrap section below.

## How Applications Are Structured

Each component follows one of two patterns depending on whether it's a Helm chart or raw manifests.

**Pattern 1: Helm Chart from External Registry**

For upstream charts (MetalLB, Traefik, Longhorn, cert-manager), the Application points directly at the Helm repository:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: cert-manager
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://charts.jetstack.io
    targetRevision: v1.14.4
    chart: cert-manager
    helm:
      values: |
        installCRDs: true
        extraArgs:
          - --dns01-recursive-nameservers=1.1.1.1:53,8.8.8.8:53
          - --dns01-recursive-nameservers-only
  destination:
    server: https://kubernetes.default.svc
    namespace: cert-manager
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true
```

The chart version is pinned (`v1.14.4`). Never use `latest` for system components. You want to control when upgrades happen, not have ArgoCD surprise you on a random sync.

**Pattern 2: Raw Manifests from Git**

For CRD configurations and custom resources that extend Helm charts, a separate Application points at a path in the Git repository:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: cert-manager-config
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/dwoitzik/homelab-infrastructure.git
    targetRevision: main
    path: kubernetes/system/cert-manager-config
  destination:
    server: https://kubernetes.default.svc
    namespace: cert-manager
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
```

This pattern (Helm chart Application plus a separate config Application) appears for MetalLB and cert-manager. The split exists because the CRDs installed by the Helm chart must exist before the configuration resources can be applied. This repo doesn't use sync waves for it. With the config in its own Application, a sync that hits missing CRDs fails on its own without blocking the chart, and the config converges once the CRDs are there. That's simpler than managing the ordering inside a single Application.

## The Deployment Workflow

Once the cluster is running, the entire deployment workflow is:

```
1. Edit a file in the repository
2. git commit -m "describe the change"
3. git push
```

ArgoCD polls the repository every 3 minutes by default. Within a few minutes of a push, it detects the difference between the desired state (Git) and the actual state (cluster) and reconciles automatically.

No `kubectl apply`. No `helm upgrade`. No SSH into nodes. The Git history is the deployment log.

## Handling the Bootstrap Problem

There is one chicken-and-egg problem: ArgoCD has to exist before it can manage anything. The bootstrap sequence is:

```bash
# 1. Install ArgoCD itself (one-time manual step)
kubectl create namespace argocd
kubectl apply -n argocd -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml

# 2. Create the ApplicationSet for kubernetes/apps/*
kubectl apply -f kubernetes/system/argocd/apps-applicationset.yaml

# 3. Create each system Application once
kubectl apply -f kubernetes/system/metallb/application.yml
kubectl apply -f kubernetes/system/cert-manager/application.yml
# ...one per component under kubernetes/system/
```

After step 2, the apps assemble themselves from Git. Step 3 is the catch: every system
Application is a one-off `kubectl apply`, and once it exists, nothing in ArgoCD watches the file
that defines it. Edit that `application.yml` in Git and the live Application stays as it was.
A sweep in July 2026 found 18 of 41 live Applications in exactly that state. The fix was one more
Application, `system-app-bootstrap`, that points at `kubernetes/system/` and includes every
`*/application.yml`, so the definitions themselves are now synced from Git too.

## Automated vs Manual Sync

All Applications in this setup use `automated` sync with `selfHeal: true`. This means:

- ArgoCD automatically applies changes when it detects drift from Git
- If someone changes something in the cluster by hand (`kubectl edit`, a click in a dashboard), ArgoCD reverts it within minutes
- `prune: true` means resources deleted from Git are deleted from the cluster

This is intentionally strict. The cluster enforces Git as the source of truth, and manual changes don't survive a sync cycle.

For production workloads where you want to review changes before they apply, switch to manual sync and use ArgoCD's UI or CLI to approve deployments.

## The Result

With ArgoCD managing the full stack:

- **Reproducibility:** the cluster's desired state is entirely in Git, and a rebuild is a short, known list of `kubectl apply` commands
- **Auditability:** every change is a Git commit with author, timestamp, and diff
- **Drift prevention:** `selfHeal: true` reverts manual changes automatically
- **Clear dependencies:** system components and their config live in separate Applications from the workloads that need them

The entire homelab, from bare metal to running Authelia and Vaultwarden, is a Git repository. If the cluster burns down, install ArgoCD, apply the ApplicationSet and the system Applications, and wait.

One caveat I learned later: a `Synced` badge is not proof that a merged change is live. I wrote up [three merged fixes that never took effect](/blog/gitops-merged-not-applied-argocd-drift/) and how to check for that.
