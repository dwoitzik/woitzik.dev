The 3-2-1 backup rule is simple: 3 copies of your data, on 2 different media types, with 1 copy offsite. My homelab has all three layers on paper. In practice, each layer had its own failure mode that I discovered only when I needed it, starting with [the Garage S3 target Velero backs into](/blog/velero-garage-k3s-backup/), where layer 1 lives.

> **Update (November 2026):** When this post went up, it said the Cloudflare R2 offsite layer was scaffolded but not active. That was already out of date: the R2 manifests were added to the ArgoCD sync with real credentials on 2026-08-22, almost four weeks before publication. The offsite layer has been running since then, with one bad gap: from about 2026-10-04 to 2026-10-18 a budget guard paused it, and the offsite backups expired while it was paused (details below). Checked live on 2026-11-04: `r2-offsite` is `Available` and the last three `daily-offsite` backups completed. I have also corrected the schedules and retention values, which did not match the repo, and replaced a restore error message and two verification steps I could not back up with what the repo actually shows.

## The Three Layers

```
Layer 1: Velero → Garage S3 (in-cluster, daily 05:00 UTC, 7 days)
    ↓
Layer 2: PBS → External HDD (local, every other day 03:00 Europe/Berlin)
    ↓
Layer 3: Velero → Cloudflare R2 (offsite, daily 04:00 UTC, 3 days)
         (rclone → Google Drive: disabled)
```

### Layer 1: Velero → Garage S3

Velero backs up every namespace except the `kube-*` system namespaces to Garage S3, a self-hosted S3-compatible object store running inside the same cluster.

```yaml
# kubernetes/system/velero/schedule.yml
spec:
  schedule: "0 5 * * *"
  template:
    ttl: 168h0m0s  # 7 days
    includedNamespaces:
      - "*"
    excludedNamespaces:
      - kube-system
      - kube-public
      - kube-node-lease
    storageLocation: default
    defaultVolumesToFsBackup: true
```

`defaultVolumesToFsBackup: true` was the fix that mattered. Without it, Velero only captured Kubernetes manifests, not the PVC data. The backups "completed" for weeks with zero data.

After the fix, Velero's node-agent DaemonSet uses Kopia to copy every pod volume's contents into Garage. The `nfs-client` storage class has no CSI snapshotter, so file-system backup is the only way PVC data gets captured at all. Daily backups, 7-day retention. Garage's own data and metadata volumes are excluded with the `backup.velero.io/backup-volumes-excludes` annotation; before that, Velero backed Garage up into Garage until the disk filled.

The weak spot: Garage runs inside the cluster. If the cluster dies, Velero and Garage go with it. Layer 1 is good for recovering individual PVCs or namespaces in a running cluster, not for full cluster recovery.

### Layer 2: PBS → External HDD

Proxmox Backup Server (PBS) backs up VM and LXC disk images to a [Seagate 2TB External HDD\*](/go/4vxwLpY) connected via USB.

```bash
# Proxmox VE backup job (/etc/pve/jobs.cfg), schedule "*-*-01/2 03:00":
# every other day at 03:00 host time (Europe/Berlin, 01:00 UTC in summer).
# Equivalent one-off run: every guest except the cloud-init template 9000,
# to the PBS storage "local-pbs" (datastore on the USB HDD, /mnt/pbs-storage)
vzdump --all 1 --exclude 9000 --storage local-pbs --mode snapshot \
  --compress zstd --prune-backups 'keep-daily=7,keep-weekly=4'
```

PBS handles deduplication, compression and incremental backups. The USB HDD is a second medium, independent of the NVMe the cluster runs on, so it survives cluster failures.

The weak spot: PBS and the k3s VMs share the same physical host, and the HDD hangs off it by USB. If the NVMe dies, the datastore on the HDD is intact, but I have to rebuild Proxmox VE and PBS before I can restore anything. A power surge, fire or theft takes the primary data and the backup together. Layer 2 protects against software failure (corruption, accidental deletion) and single-disk failure, not against losing the site.

### Layer 3: Offsite

The first offsite attempt was rclone syncing the PBS datastore to Google Drive. Google's API throttled it to about 1.6 KiB/s in a manual test, with an estimated 12 weeks for the initial full sync. That is not a config bug. A PBS datastore is tens of thousands of small chunk files, and Drive's API handles that shape badly. The Drive account also did not have enough free space for the datastore. The cron job is now deliberately absent in the Ansible role, and PBS has no offsite copy.

The offsite layer that works is a second Velero `BackupStorageLocation` on Cloudflare R2:

```yaml
# kubernetes/system/velero/offsite-schedule.yml
apiVersion: velero.io/v1
kind: Schedule
metadata:
  name: daily-offsite
  namespace: velero
spec:
  schedule: "0 4 * * *"
  template:
    ttl: 72h0m0s
    storageLocation: r2-offsite
    defaultVolumesToFsBackup: true
    includedNamespaces:
      - apps
      - vault
      - database
      - argocd
```

R2 has no egress fees, and Velero writes to it over the S3 API directly, with no consumer-sync throttling in the path. It also fixes the circular part of layer 1: Garage runs inside the cluster Velero is protecting, so an in-cluster-only target is lost with the cluster. The offsite set covers four namespaces, and the big volumes (media, Prometheus, Loki, Garage data) are excluded per pod with the same annotation. A full set is about 6.3 GB of raw volume data, which Kopia deduplicates and compresses to roughly 4 GiB in the bucket.

R2 has no native spending cap, and I do not want to pay past the 10 GiB free tier. A CronJob, `r2-usage-guard`, checks stored bytes once a day and pauses `daily-offsite` above 9 GiB. It deliberately never resumes on its own, and it sends a "still paused" ntfy reminder with the age of the last offsite backup.

That design deleted the offsite set once. With the original 7-day TTL, a full set plus a week of deltas reached the cap, and the guard paused the schedule around 2026-10-04. The reminders went unread. While the schedule was paused, the TTL kept running, and seven days after the last run every offsite backup had expired and been pruned. When I found it on 2026-10-18, R2 held about 0.23 GiB of leftover Kopia metadata and zero backups: the guard meant to avoid a small overage had removed the disaster-recovery copy. The fix was a shorter TTL (3 days instead of 7), which keeps steady state around one full set plus two days of deltas, well under the cap. The failure mode is still there: any pause that outlives the TTL wipes the offsite set, so the reminder has to be acted on.

## The Restore Gotcha

PBS restores a guest's configuration exactly as it was, including the MAC address, and the guest OS brings up the same static or cloud-init IP. A restored or cloned copy that runs next to the original is two machines with one identity on the same VLAN.

I have hit this from the clone side rather than in a restore drill. After a hard reboot of the Proxmox host, two orphaned clones (VMIDs 9211 and 9213) that still had `onboot: 1` started next to the real k3s-11 and k3s-13 nodes, with the same IPs, and caused IP/MAC conflicts on VLAN 20. A third leftover, LXC 9200, carries the same hostname and MAC as the real `ct-srv-docker-01` and is only harmless because it stays stopped.

For restores, the safer sequence is: restore to a temporary VMID with the Unique option (`qmrestore --unique`, or the "Unique" checkbox in the GUI), which assigns new random MAC addresses; keep it off the network or stop the original before booting it; verify; then swap. `--unique` avoids the MAC clash but not an IP clash from a static or cloud-init address. Either way it is a manual multi-step process, not something you want to work out under time pressure in a real disaster. Before any host reboot, I now check that no stale VMID has `onboot: 1`.

## What Actually Works

| Layer | Protects Against | Doesn't Protect Against |
|---|---|---|
| Velero → Garage | PVC corruption, namespace deletion, accidental kubectl delete | Cluster-wide failure (Garage is in-cluster) |
| PBS → USB HDD | Software corruption, accidental VM deletion, ZFS pool issues, NVMe failure | Site loss: surge, fire, theft (HDD is attached to the same host) |
| Velero → Cloudflare R2 | Host hardware failure, theft, fire (for the four critical namespaces) | VMs and LXCs (PBS has no offsite copy), excluded large volumes, anything older than 3 days, a guard pause that outlives the TTL |

Where that leaves me: three copies, two media, one offsite, so 3-2-1 holds for the cluster's critical data. It does not hold for the Proxmox guests themselves: PBS still lives on the same host as everything it protects, and losing the site means rebuilding the VMs and LXCs from Terraform and Ansible and restoring the cluster data from R2.

## The Verification Gap

The lesson I'd put first: **a backup you haven't restored is not a backup.**

Velero and PBS both ran on schedule, and until recently neither had been fully restored. The Velero `defaultVolumesToFsBackup` gap existed for weeks because nobody tested a restore.

What runs now:

1. **Monthly Velero restore test** (`kubernetes/system/velero/restore-test.yml`, 06:00 UTC on the 1st): restores the `vault` namespace from the latest completed backup into a scratch namespace, waits for the restored `vault-0` to become Ready, and checks that the restored storage reports itself initialized. Failures go to ntfy. It tests `vault` instead of `database` on purpose: a namespace-mapped restore of the CNPG Postgres cluster could start a second instance archiving WAL to the same S3 path as the live one. A CNPG-native restore test is still to do.
2. **Prometheus alerts on Velero itself:** failed, partially failed and stale backups, plus an alert when the Velero metrics disappear.
3. **The R2 guard's staleness reminder**, which only helps if someone reads it.

PBS restores are still manual. There is no scheduled PBS restore test yet, and that is the next gap to close.

---

In Azure, backup verification is a compliance requirement: ISO 27001 (control 8.13, information backup) expects backups to be tested, and NIS2 lists backup management among its required risk-management measures. Azure Backup reports "Completed" for a VM, but with selective disk backup configured wrong, a data disk can be missing from the recovery point. The only way to know is to restore a test VM and check its contents, the same drill I now run monthly against Velero, and still have to automate for PBS.
