Kubernetes has no opinion about what you run. You can deploy a container with no resource limits, no security context, root access to the host filesystem, and an image tagged `:latest` that changes every week, and the scheduler will place it without complaint. In a homelab on a [BMAX Mini PC\*](/go/4bv3yF1), that's annoying. In a production cluster, it's a compliance failure.

[Kyverno](https://kyverno.io/) is a Kubernetes-native policy engine. It runs as an admission webhook: every `kubectl apply`, every ArgoCD sync, every Helm install is evaluated against your policies before the object is stored. Violations are either blocked (Enforce) or logged (Audit).

Below are the three policies running on my k3s cluster and the Audit-first rollout that lets you enforce gradually without breaking existing workloads.

## Why Admission Control

The alternative to admission control is runtime enforcement: scan running containers, alert on violations, remediate manually. That works, but it's reactive: a misconfigured deployment gets scheduled, pulls an image, and starts running before anything flags it.

Admission control is preventive. The webhook intercepts the API request before the object is created. A rejected request never touches the scheduler.

For supply chain security, which is about controlling what can run and not only what is running, admission control is the right layer.

## Installing Kyverno via ArgoCD

Kyverno deploys via Helm:

```yaml
# kubernetes/system/kyverno/application.yml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: kyverno
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://kyverno.github.io/kyverno/
    targetRevision: 3.2.6
    chart: kyverno
    helm:
      values: |
        admissionController:
          replicas: 1
        backgroundController:
          replicas: 1
  destination:
    server: https://kubernetes.default.svc
    namespace: kyverno
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true
```

Since Kyverno 1.10 the chart runs separate controllers. The admission controller handles the webhook. The reports controller runs background scans of existing resources and writes the `PolicyReport` objects; it's enabled by default, so it doesn't appear in these values. The background controller handles generate and mutate-existing rules. Without background scanning (`background: true` on each policy plus the reports controller), you only see violations at admission time, and existing non-compliant resources stay invisible.

## Policy 1: Require Resource Limits (Audit)

Containers without resource limits are a noisy-neighbor problem. A single container with unbounded memory can push the whole node into memory pressure, and then the kubelet evicts, or the kernel OOM killer kills, other pods on that node.

```yaml
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: require-resource-limits
  annotations:
    policies.kyverno.io/title: Require Resource Limits
    policies.kyverno.io/description: >
      Pods without resource limits can starve other workloads on the same node.
      Run `kubectl get policyreport -A` to see violations before enforcing.
spec:
  validationFailureAction: Audit
  background: true
  rules:
    - name: check-container-limits
      match:
        any:
          - resources:
              kinds: [Pod]
              namespaces: [apps, monitoring, database]
      validate:
        message: "Container '{{ request.object.spec.containers[0].name }}' must define resources.limits (cpu and memory)."
        foreach:
          - list: "request.object.spec.containers"
            deny:
              conditions:
                any:
                  - key: "{{ element.resources.limits | length(@) }}"
                    operator: Equals
                    value: 0
```

This one runs in `Audit` mode: violations are logged to `PolicyReport` but not blocked. That's intentional. Before enforcing, you need to know what would break.

Check current violations:

```bash
kubectl get policyreport -A
kubectl describe policyreport -n apps
```

The report shows every pod in `apps`, `monitoring`, and `database` namespaces that's missing resource limits. Fix those, then flip `validationFailureAction` to `Enforce`.

## Policy 2: Disallow Privileged Containers (Enforce)

This one is in `Enforce` mode from day one. No homelab service of mine needs privileged mode. If something asks for `privileged: true`, that's a reason to investigate, not to accommodate.

```yaml
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: disallow-privileged-containers
spec:
  validationFailureAction: Enforce
  background: true
  rules:
    - name: check-privileged
      match:
        any:
          - resources:
              kinds: [Pod]
              namespaces: [apps, monitoring, database, external-secrets]
      validate:
        message: "Privileged containers are not allowed."
        foreach:
          - list: "request.object.spec.containers"
            deny:
              conditions:
                any:
                  - key: "{{ element.securityContext.privileged || false }}"
                    operator: Equals
                    value: true
```

`|| false` handles the case where `securityContext` is not set: the expression evaluates to false, which correctly passes validation (no security context means non-privileged).

This blocks containers with `securityContext.privileged: true`, and nothing else. `hostPID`, `hostNetwork`, and `hostPath` volumes are separate pod-spec fields that this rule never looks at, and it only iterates over `containers`, not `initContainers` or `ephemeralContainers`. Covering those needs additional rules; Kyverno's Pod Security Standards policy library has ready-made ones.

## Policy 3: Disallow `:latest` Image Tag (Audit)

Images tagged `:latest` are non-deterministic. What `nginx:latest` points to today is different from what it pointed to last week, so rolling back means guessing which image you were running before. Reproducible deployments need pinned tags, either semver (`4.39.20`) or a digest (`sha256:abc123`).

```yaml
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: disallow-latest-tag
spec:
  validationFailureAction: Audit
  background: true
  rules:
    - name: check-image-tag
      match:
        any:
          - resources:
              kinds: [Pod]
              namespaces: [apps, monitoring, database]
      validate:
        message: "Image '{{ element.image }}' must use a specific tag, not :latest or untagged."
        foreach:
          - list: "request.object.spec.containers"
            deny:
              conditions:
                any:
                  - key: "{{ element.image }}"
                    operator: Equals
                    value: "*:latest"
                  - key: "{{ element.image | contains(@, ':') }}"
                    operator: Equals
                    value: false
```

The second condition catches images with no tag at all: `nginx` without a tag still resolves to `latest`.

## Real-World Example: The Authelia `:latest` Violation

When I first enabled the `disallow-latest-tag` policy in Audit mode and ran `kubectl get policyreport -n apps`, Authelia showed up immediately:

```
PASS  disallow-privileged-containers  authelia-xxx    apps
FAIL  disallow-latest-tag             authelia-xxx    apps
  → ghcr.io/authelia/authelia:latest
```

The Authelia deployment had been running `latest` from day one. The fix:

```yaml
# Before
image: ghcr.io/authelia/authelia:latest

# After
image: ghcr.io/authelia/authelia:4.39.20
```

Once pinned, the PolicyReport cleared. That's the Audit → Enforce workflow in practice: enable, observe, fix violations, then enforce.

## The Audit → Enforce Rollout Strategy

The sequence that makes Kyverno safe to adopt on a running cluster:

```
1. Deploy all policies in validationFailureAction: Audit
2. Wait for background scans to populate PolicyReports (5-10 min)
3. kubectl get policyreport -A → review violations
4. Fix violations in affected deployments
5. Change policy to validationFailureAction: Enforce
6. Verify no new violations in PolicyReport
```

Going straight to Enforce on a running cluster breaks things. Enforce doesn't touch pods that are already running, but the next time a controller creates one (a rollout, an eviction, an ArgoCD sync, a Helm hook Job), the new pod gets rejected. Audit first gives you visibility without the blast radius.

### How the Rollout Actually Went

The first pass followed that sequence cluster-wide: once a PolicyReport sweep showed zero violations, `require-resource-limits` and `disallow-latest-tag` went to Enforce. After a cluster rebuild wiped the `kyverno` namespace, I re-staged everything back to Audit and flipped it again more carefully, namespace by namespace instead of all at once. The default stays `Audit`, and `validationFailureActionOverrides` switches individual namespaces to `Enforce` once each one is verified clean:

```yaml
spec:
  validationFailureAction: Audit
  validationFailureActionOverrides:
    - action: Enforce
      namespaces: [database, apps, security]
```

`monitoring` taught the real lesson. A PolicyReport only reflects pods that exist at the moment of the sweep. Right after enforcing there, the next Grafana restart from the kube-prometheus-stack chart was blocked: the chart's sidecars (`grafana-sc-dashboard`, `grafana-sc-datasources`) and other chart-templated containers in Loki and Promtail ship without resource limits by upstream default. A clean report had not meant a safe Enforce.

So the limits and image-tag policies are now enforced only in namespaces whose manifests I write myself (`apps`, `database`, `security`). Patching every third-party sidecar's resources, and keeping that patched across chart upgrades, is a separate and larger job. The privileged-container policy has no such problem and is enforced in `monitoring` and `external-secrets` as well.

One version note: the chart pinned above ships Kyverno 1.12, where `spec.validationFailureAction` is the switch. From Kyverno 1.13 on, that field is deprecated in favor of a per-rule `validate.failureAction`.

## Scoping Policies to Specific Namespaces

All three policies match only workload namespaces. The snippets above show the first version; today `require-resource-limits` and `disallow-latest-tag` cover `apps`, `database` and `security`; `disallow-privileged-containers` also covers `monitoring` and `external-secrets`. System namespaces (`kube-system`, `kube-public`, `argocd`, `kyverno`) are excluded deliberately.

System components often need exceptions: hostPath volumes, privileged containers for CNI plugins, no resource limits on critical infrastructure. Scoping the policies to workload namespaces avoids blocking cluster internals while still enforcing where it counts.

## PolicyReport: The Visibility Layer

```bash
# All reports across all namespaces
kubectl get policyreport -A

# Kyverno 1.12 keeps one report per resource, named by UID;
# -o wide shows which resource each report belongs to
kubectl get policyreport -n apps -o wide
kubectl describe policyreport <resource-uid> -n apps

# All violations
kubectl get policyreport -A -o json | \
  jq '.items[].results[] | select(.result == "fail")'
```

PolicyReports are ordinary Kubernetes custom resources, and Kyverno also exports policy results as Prometheus metrics. That's enough to build Grafana dashboards, alert on violations, and track compliance over time.

The `require-resource-limits` violation count is a useful metric: as you fix deployments, it should trend toward zero. When it hits zero and stays there, flip to Enforce.

## Enterprise Bridge

These policies map to controls auditors ask about: ISO/IEC 27001:2022 Annex A 8.8 (management of technical vulnerabilities; A.12.6.1 in the 2013 edition) and NIS2 Article 21(2)(d) (supply chain security) and (e) (security in acquisition, development and maintenance, including vulnerability handling).

On AKS, the equivalent layer is Azure Policy plus Defender for Containers: same concept, different implementation. For teams running Kubernetes in regulated environments, Kyverno policies committed to Git give you the audit trail compliance frameworks ask for. Every policy change is a pull request, and every violation is logged.
