## The Architecture

Cloudflare Tunnel works by running a `cloudflared` daemon inside the cluster that maintains an outbound-only connection to Cloudflare's edge. External requests hit Cloudflare and travel through that tunnel to the origin service and back. For the tunneled hostnames there are no inbound ports, no port forwarding, and nothing listening on the WAN side.

The Terraform configuration (Cloudflare provider v5, where `config` and `ingress` are attributes, not blocks) defines the tunnel ingress rules:

```hcl
# terraform/stacks/cloudflare/main.tf (abridged)
resource "cloudflare_zero_trust_tunnel_cloudflared_config" "homelab" {
  account_id = var.account_id
  tunnel_id  = var.tunnel_id

  config = {
    ingress = [
      {
        hostname = "photos.woitzik.dev"
        service  = "http://immich-server.apps.svc.cluster.local:2283"
        origin_request = {
          no_tls_verify            = false
          connect_timeout          = 10
          tcp_keep_alive           = 30
          keep_alive_connections   = 10
          http_host_header         = "photos.woitzik.dev"
          disable_chunked_encoding = false
        }
      },
      {
        hostname = "analytics.woitzik.dev"
        service  = "http://10.0.20.205:80"
        origin_request = {
          no_tls_verify    = false
          http_host_header = "analytics.woitzik.dev"
        }
      },
      {
        hostname = "media.woitzik.dev"
        service  = "http://10.0.20.254:8096"
        origin_request = {
          no_tls_verify    = false
          http_host_header = "media.woitzik.dev"
        }
      },
      { service = "http_status:404" }
    ]
  }
}
```

The catch-all `http_status:404` is mandatory: `cloudflared` refuses an ingress config whose last rule doesn't match every request. It is also the access policy. Any hostname without its own rule gets a 404 at the tunnel and never reaches the cluster, which is how the other 40-odd internal hostnames stay LAN/VPN-only.

## Split-DNS on AdGuard

The tunnel creates a split-brain DNS problem. Public DNS points the tunneled hostnames at Cloudflare's anycast IPs, while LAN clients should reach internal services directly via the Traefik VIP without touching Cloudflare. The same `woitzik.dev` names have to resolve differently depending on which resolver the client asks.

AdGuard Home handles this with a wildcard rewrite:

```yaml
# ansible/roles/adguard/templates/AdGuardHome.yaml.j2 (excerpt)
rewrites:
  - domain: "*.woitzik.dev"
    answer: "10.0.20.200"   # Traefik LoadBalancer IP
    enabled: true
  - domain: headscale.woitzik.dev
    answer: "10.0.20.200"
    enabled: true
```

The `*.woitzik.dev` wildcard covers every internal service, including the tunneled ones. A phone on Wi-Fi at home resolves `photos.woitzik.dev` to Traefik and uploads straight to the cluster; the same phone on cellular never asks AdGuard and goes through public DNS and the tunnel. I briefly had a more specific rewrite that pinned `photos` to Cloudflare's anycast IPs so LAN clients would take the tunnel too, and removed it: going through Cloudflare from inside the LAN only adds the 100 MB request-body limit described below, for no benefit. Hostnames that need a different internal answer (the raw-TCP Minecraft servers, for example) get their own more specific rewrite, which AdGuard prefers over the wildcard.

The gotcha: the wildcard applies to the search domain too. If the Proxmox host's search domain is `woitzik.dev`, every short internal hostname gets expanded into the wildcard, including `pve.woitzik.dev`, `pbs.woitzik.dev`, and other names that should never resolve to Traefik. A related leak showed up during setup, with a different cause: PTR queries for k3s pod IPs (10.42.0.0/16) were being forwarded to the <AffiliateLink href="/go/4f5WDEI">FritzBox</AffiliateLink>. With `private_networks` left empty, AdGuard treats every RFC 1918 range as private and sends those reverse lookups to its private PTR resolver, which was the Fritz!Box. It could not answer them, and each query burned a 2-second timeout. Scoping `private_networks` to the Fritz!Box LAN (192.168.178.0/24) fixed it.

## The Chunked Encoding Fix

Large photo and video uploads to Immich through Cloudflare Tunnel were failing with `ECONNRESET`. The uploads would reach 60–80% and then drop the connection.

My first fix, recorded in CHANGELOG v0.8.0, set `chunked_encoding = true`, `write_timeout = 600` and `read_timeout = 120` on the tunnel's origin request. None of those are real `cloudflared` origin settings. The actual knob is `disableChunkedEncoding` (`disable_chunked_encoding` in the Terraform provider), and chunked transfer to the origin is already on by default. The current config states that default explicitly:

```hcl
origin_request = {
  no_tls_verify            = false
  connect_timeout          = 10
  tcp_keep_alive           = 30
  keep_alive_connections   = 10
  http_host_header         = "photos.woitzik.dev"
  disable_chunked_encoding = false
}
```

`disable_chunked_encoding = false` keeps `cloudflared` streaming the request body to the origin in chunks instead of buffering the whole payload. There is no per-origin write timeout to raise.

The other limit to know: Cloudflare's proxy caps the request body size per plan (100 MB on Free and Pro). Any single upload request above that is rejected at the edge, whatever the tunnel config says. That affects every service behind Cloudflare Tunnel that accepts large files in one request, Nextcloud and Paperless included, so check how the client splits uploads before blaming the tunnel. In my setup the limit only applies away from home: on the LAN the wildcard rewrite sends `photos.woitzik.dev` to Traefik, so large uploads never touch Cloudflare.

## Atlantis Through Traefik (Historical)

This section describes how Atlantis was exposed until August 2026. It has no tunnel entry or public DNS record anymore; a self-hosted GitHub Actions runner polls GitHub outbound, so nothing has to reach Atlantis from the internet. The pattern still applies to any service that has to be public and has no login of its own.

Atlantis needs to receive GitHub webhooks for Terraform PR events. The naive approach is to expose Atlantis directly via Cloudflare Tunnel. The problem: Atlantis's web UI has no authentication unless you opt into basic auth, so anyone who finds the URL can read plan output and release locks.

The fix is to route Atlantis through Traefik first, which applies the [Authelia](/blog/k3s-authelia-proxmox-homelab/) ForwardAuth middleware before the request reaches Atlantis:

```hcl
{
  hostname = "atlantis.woitzik.dev"
  service  = "https://traefik.kube-system.svc.cluster.local:443"
  origin_request = {
    no_tls_verify      = false
    http_host_header   = "atlantis.woitzik.dev"
    origin_server_name = "atlantis.woitzik.dev"
  }
}
```

The Cloudflare Tunnel points at Traefik's HTTPS entrypoint, not at Atlantis. `origin_server_name` is needed because `cloudflared` otherwise checks Traefik's certificate against the service hostname (`traefik.kube-system.svc.cluster.local`) and fails with a 502. Pointing at Traefik's plain-HTTP port instead does not work either: Traefik redirects it to HTTPS, and the tunnel relays the redirect back to the client in a loop.

Atlantis runs on its own LXC (10.0.20.250), so Traefik reaches it through a selector-less Service with a manual Endpoints object. The IngressRoute has two routes:

```yaml
apiVersion: traefik.io/v1alpha1
kind: IngressRoute
metadata:
  name: atlantis-final
  namespace: apps
spec:
  entryPoints: [websecure]
  routes:
  # GitHub webhook path: no Authelia, the webhook's HMAC secret is the auth
  - match: Host(`atlantis.woitzik.dev`) && PathPrefix(`/events`)
    kind: Rule
    priority: 10
    services: [{name: external-atlantis, port: 4141}]
  - match: Host(`atlantis.woitzik.dev`)
    kind: Rule
    priority: 1
    middlewares:
      - name: crowdsec-bouncer
      - name: authelia
      - name: websockets
    services: [{name: external-atlantis, port: 4141}]
```

GitHub webhooks go to `/events` and skip Authelia, because a forward-auth redirect would break delivery. Atlantis checks the webhook's HMAC signature against its shared secret, so that path is not unauthenticated. Everything else, including the web UI with its plan output and lock controls, requires Authelia.

This pattern (Cloudflare Tunnel → Traefik → Authelia → service) works for any external service without auth of its own. The tunnel handles ingress, Traefik handles routing and TLS, Authelia handles authentication.

## DNS Record Management

Cloudflare DNS records for the tunnel CNAMEs are Terraform-managed:

```hcl
resource "cloudflare_dns_record" "tunnel_photos" {
  zone_id = var.zone_id
  name    = "photos"
  type    = "CNAME"
  content = "abc123.cfargotunnel.com"
  proxied = true
  ttl     = 1
}
```

`proxied = true` sends traffic through Cloudflare's proxy, which provides DDoS protection, rate limiting, and WAF rules. `ttl = 1` means "automatic", which proxied records require. In the real file `content` is `"${var.tunnel_id}.cfargotunnel.com"`; `media` and `analytics` have the same shape.

Two records are `proxied = false`. `headscale.woitzik.dev` is a DNS-only record that resolves to the WAN IP, kept current by a DDNS CronJob in the cluster (Terraform ignores changes to its `content`), because Headscale's protocol cannot pass Cloudflare's proxy. The Minecraft record is a CNAME to a `playit.gg` hostname, since raw TCP game traffic cannot go through Cloudflare's HTTP proxy either. The old `atlantis`, `auth`, and `home` records and the `*.woitzik.dev` public wildcard were deleted in August 2026; those names only resolve inside the LAN and over the tailnet now.

---

Cloudflare Tunnel's no-inbound-port model is the same pattern as Azure Front Door with Private Link origins: external traffic enters through a managed proxy, never touches your firewall directly, and the origin needs no public endpoint. The split-DNS problem maps to Azure Private DNS Zones, where internal clients resolve to private endpoints and external clients to public DNS. Different tools, same architecture.
